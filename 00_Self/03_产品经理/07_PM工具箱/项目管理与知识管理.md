# 项目管理与知识管理：PM 的操作系统

> 项目管理决定你能不能把事做成，知识管理决定你能不能越做越好。两者共同构成 PM 的"操作系统" — 一个管执行，一个管成长。

## 二、Linear 深度使用

### 核心概念

| 概念 | 说明 | PM 角色 |
|------|------|--------|
| **Issue** | 最小工作单元 | 创建需求、定义优先级、分配负责人 |
| **Project** | 相关 Issue 的集合 | 管理一个功能/项目的全生命周期 |
| **Cycle** | 固定时长的迭代（1-4 周） | 规划迭代范围、跟踪进度 |
| **Initiative** | 跨项目的战略目标 | 对齐 OKR、管理产品路线图 |
| **View** | 自定义筛选视图 | 按团队/优先级/状态等维度查看 |
| **Triage** | 需求收集箱 | 统一入口，避免需求散落 |

### 自动化配置

**PM 必配的自动化规则**：

| 触发条件 | 动作 | 价值 |
|---------|------|------|
| Issue 创建时 | 自动分配到 Triage | 需求不遗漏 |
| Issue 状态变为 "In Review" | 自动通知 PM | 及时参与评审 |
| Cycle 开始前 1 天 | 发送 Slack/飞书通知 | 提醒规划 |
| Issue 超过 7 天未更新 | 自动标记 Stale | 避免僵尸需求 |
| Project 完成时 | 自动归档 | 保持工作区整洁 |
| Priority 设为 Urgent | 自动 @PM | 紧急需求即时响应 |

**自动化最佳实践**：

- 规则不超过 10 条 — 太多会产生噪音
- 每条规则有明确目的 — 不要为了自动化而自动化
- 定期审查 — 删除不再适用的规则

### Cycles 管理

**Cycle 规划流程**：

| 步骤 | 时间 | PM 动作 | 产出 |
|------|------|--------|------|
| 需求收集 | Cycle 前 3 天 | 整理 Triage、收集 stakeholder 输入 | 候选需求池 |
| 优先级排序 | Cycle 前 2 天 | RICE 评分、与 Tech Lead 对齐 | 排序后的需求列表 |
| 容量规划 | Cycle 前 1 天 | 评估 story points、确认交付范围 | Cycle Commitment |
| Kickoff | Cycle 第 1 天 | 团队对齐目标和分工 | 共识 |
| Mid-cycle Check | Cycle 中间 | 检查进度、处理 blocker | 风险预警 |
| Retro | Cycle 最后 1 天 | 回顾产出、记录改进点 | Retro 笔记 |

**RICE 评分框架**：

| 维度 | 说明 | 评分范围 |
|------|------|---------|
| **R**each | 影响多少用户 | 1-10（千人=1，百万人=10） |
| **I**mpact | 对用户的影响程度 | 0.25/0.5/1/2/3 |
| **C**onfidence | 对判断的信心度 | 50%/80%/100% |
| **E**ffort | 所需工作量 | 1-10（人周） |

**RICE Score = (Reach x Impact x Confidence) / Effort**

### Projects 管理

**Project 文档模板**：

```markdown
## 背景与目标
- 为什么做？（业务背景）
- 做成什么样？（成功标准）

## 范围
- In Scope：包含什么
- Out of Scope：不包含什么

## 关键里程碑
- M1: 设计评审（Week X）
- M2: 技术方案评审（Week X）
- M3: 开发完成（Week X）
- M4: 上线（Week X）

## 风险与依赖
- 风险 1：xxx → 应对：xxx
- 依赖 1：xxx → Owner：xxx

## 链接
- PRD: [链接]
- 设计稿: [链接]
- 技术方案: [链接]
```

### Initiatives 管理

**Initiative 层级结构**：

```
Company OKR
└── Initiative（战略目标）
    └── Project（具体项目）
        └── Issue（工作单元）
```

**PM 操作要点**：

- Initiative 是 PM 的"产品路线图" — 每个 Initiative 对应一个产品目标
- 定期更新 Initiative 进展 — 至少每月一次
- Initiative 下的 Project 要有清晰的依赖关系 — 用 Project Graph 可视化

## 三、知识管理哲学

### 三大知识管理体系

| 体系 | 核心理念 | 代表人物 | 适合人群 |
|------|---------|---------|---------|
| **Zettelkasten** | 原子化笔记 + 双向链接 | Niklas Luhmann | 研究型、学术型 |
| **MOC** | 地图式导航 + 层级组织 | Nick Milo | 结构化思维者 |
| **Second Brain** | CODE 框架 + 渐进式总结 | Tiago Forte | 实践型、行动导向 |

### Zettelkasten（卡片盒笔记法）

**核心原则**：

| 原则 | 说明 | PM 实操 |
|------|------|--------|
| **原子化** | 每条笔记只表达一个想法 | "用户在结账时放弃购物车的 3 个原因" 而不是 "电商用户行为分析" |
| **自己的话** | 用自己的理解重新表述 | 不要复制粘贴，用自己的话总结 |
| **链接** | 建立笔记间的连接 | 发现新旧笔记的关联时立即链接 |
| **引用** | 标注信息来源 | 会议记录、文章、数据都要注明来源 |

**PM 的 Zettelkasten 实践**：

| 笔记类型 | 示例 | 链接方向 |
|---------|------|---------|
| **文献笔记** | 会议记录、竞品分析、行业报告 | → 永久笔记 |
| **永久笔记** | 一个独立的洞察或结论 | ↔ 其他永久笔记 |
| **索引笔记** | 某个主题的导航页 | → 永久笔记 |
| **项目笔记** | 特定项目的需求和决策 | → 永久笔记 |

### MOC（Map of Content）

**MOC 结构**：

```
00_产品经理.md（域级 MOC）
├── 链接到 → 需求分析相关笔记
├── 链接到 → 数据分析相关笔记
├── 链接到 → 项目管理相关笔记
└── 链接到 → 各子文件夹的 MOC
```

**MOC vs 文件夹**：

| 维度 | MOC | 文件夹 |
|------|-----|-------|
| 组织方式 | 非线性，网状 | 线性，树状 |
| 灵活性 | 一个笔记可出现在多个 MOC | 一个笔记只在一个文件夹 |
| 维护成本 | 需要主动更新链接 | 自动按规则排列 |
| 适合场景 | 知识关联复杂、跨领域 | 知识边界清晰、独立 |

### Second Brain（第二大脑）

**CODE 框架**：

| 步骤 | 说明 | PM 工具 |
|------|------|--------|
| **C**apture | 捕获有价值的信息 | Web Clipper、截图、语音备忘 |
| **O**rganize | 按行动性组织 | PARA（Projects/Areas/Resources/Archives） |
| **D**istill | 渐进式总结 | 标注→摘要→精华，逐层提炼 |
| **E**xpress | 输出和分享 | 文档、方案、分享会 |

**PARA 组织法**：

| 分类 | 定义 | PM 示例 |
|------|------|--------|
| **Projects** | 有明确目标和截止日期 | Q3 产品上线、竞品分析报告 |
| **Areas** | 需要持续关注的领域 | 用户增长、技术趋势、团队管理 |
| **Resources** | 感兴趣的主题 | 设计系统、AI 工具、行业报告 |
| **Archives** | 已完成/不再活跃 | 旧项目、过期报告 |

## 五、AI 时代知识管理

### RAG（Retrieval-Augmented Generation）

| 概念 | 说明 | PM 视角 |
|------|------|--------|
| **检索增强生成** | AI 先检索知识库，再生成回答 | 让 AI 基于你的文档回答问题 |
| **向量搜索** | 用语义相似度而非关键词匹配 | "用户留存" 也能找到 "用户粘性" 的文档 |
| **Embedding** | 把文本转为向量 | 知识库的"索引"方式 |
| **Chunk** | 文档切片 | 影响检索精度的关键参数 |

**PM 应用场景**：

| 场景 | 实现方式 | 价值 |
|------|---------|------|
| PRD 问答 | 把历史 PRD 喂给 RAG 系统 | 新 PM 快速了解产品历史 |
| 会议记录搜索 | 向量化会议纪要 | "上次讨论定价策略是什么结论？" |
| 竞品知识库 | 竞品分析文档 + RAG | 随时查询竞品信息 |
| 内部知识助手 | 公司文档 + AI Chat | 减少重复提问 |

### AI 知识管理工具

| 工具 | 类型 | 核心能力 | PM 使用场景 |
|------|------|---------|------------|
| **Notion AI** | 内置 AI | 文档问答、摘要、写作 | 在 Notion 内直接提问 |
| **Mem.ai** | AI 笔记 | 自动组织、智能搜索 | 快速记录和检索 |
| **Khoj** | 开源 AI 助手 | 本地 RAG、多数据源 | 隐私敏感的个人知识库 |
| **Obsidian + Copilot** | 插件 AI | 本地 AI 问答 | Obsidian 用户的 AI 增强 |
| **Dify** | AI 应用平台 | 自建 RAG 应用 | 团队级知识助手 |

### AI 时代的知识管理策略

| 传统做法 | AI 时代做法 | 价值 |
|---------|-----------|------|
| 手动分类和打标签 | AI 自动分类和推荐标签 | 减少组织成本 |
| 关键词搜索 | 语义搜索 + AI 问答 | 找到更相关的结果 |
| 手动写摘要 | AI 自动生成摘要 | 信息消化速度提升 5x |
| 人工整理知识图谱 | AI 自动发现知识关联 | 发现隐藏的连接 |
| 定期回顾笔记 | AI 主动推送相关笔记 | 知识被激活而非沉睡 |

**注意事项**：

- AI 不能替代思考 — 它帮你检索和整理，但洞察来自你的大脑
- 数据安全 — 敏感文档不要上传到公共 AI 服务
- 质量把关 — AI 生成的摘要可能遗漏关键信息，重要决策必须回溯原文

## 七、工具整合与自动化

### PM 工具栈全景

```
沟通层：飞书 / Slack / 钉钉
  ↕
项目层：Linear / Jira / 飞书项目
  ↕
知识层：Notion / Obsidian / Confluence
  ↕
设计层：Figma / 即时设计 / v0.dev
  ↕
数据层：Metabase / Tableau / 飞书多维表格
```

### 自动化场景

| 场景 | 触发 | 动作 | 工具 |
|------|------|------|------|
| 需求状态变更 | Linear Issue 状态更新 | 飞书通知相关人 | Linear + 飞书 Webhook |
| 设计稿更新 | Figma 文件有新版本 | Linear 评论通知 | Figma + Linear 集成 |
| 周报自动生成 | 每周五 17:00 | 汇总本周 Linear 完成项 | Linear API + Notion |
| 会议纪要归档 | 飞书妙记生成完毕 | 自动同步到 Notion | 飞书 + Notion API |
| 竞品动态追踪 | 每周一 9:00 | 爬取竞品更新 | Perplexity + Notion |

### Zapier / Make 自动化示例

**Linear → Notion 周报自动化**：

```
Trigger: Linear - Cycle completed
Action 1: Linear - Get all issues in cycle
Action 2: Notion - Create database entry
  - Title: "Week {date} 周报"
  - Content: Issue list with status
```

**飞书妙记 → Notion 会议纪要**：

```
Trigger: 飞书 - 新的会议纪要
Action 1: 提取会议摘要和 Action Items
Action 2: Notion - Create page in 会议纪要 database
Action 3: Linear - Create issues for Action Items
```

> 💡 **核心观点**：项目管理和知识管理不是两件独立的事 — 项目管理产生的经验沉淀为知识，知识管理的成果指导项目决策。PM 的"操作系统"应该是：用 Linear/Jira 管执行，用 Obsidian/Notion 管思考，用自动化把两者串联起来。工具是手段，建立"输入→处理→输出→沉淀"的闭环才是目的。
