# 原型与设计协作：从想法到落地的桥梁

> 原型是 PM 最有力的沟通武器。一份好原型胜过十页 PRD — 它让抽象需求变成可触摸的体验，让团队对齐从"理解"升级为"共识"。

---

## 一、原型层级体系

### 三级原型模型

| 层级 | 名称 | 保真度 | 制作时间 | 核心目的 | 适用阶段 |
|------|------|-------|---------|---------|---------|
| L1 | **Lo-fi 原型** | 低保真 | 30 分钟 - 2 小时 | 验证概念、对齐方向 | 需求探索期 |
| L2 | **Hi-fi 原型** | 高保真 | 2 - 8 小时 | 验证交互、收集反馈 | 需求细化期 |
| L3 | **Interactive 原型** | 可交互 | 1 - 3 天 | 用户测试、开发交付 | 设计定稿期 |

### 各层级详解

**L1 Lo-fi 原型**：

- **工具**：纸笔、Excalidraw、Whimsical、FigJam
- **产出**：线框图、流程图、信息架构图
- **受众**：产品团队内部、早期 stakeholder 对齐
- **关键原则**：足够粗糙以鼓励反馈，不要让人纠结视觉细节

**L2 Hi-fi 原型**：

- **工具**：Figma、即时设计、Sketch
- **产出**：带视觉设计的页面稿、关键交互流程
- **受众**：设计评审、用户访谈、管理层汇报
- **关键原则**：聚焦核心流程，不要追求 100% 覆盖

**L3 Interactive 原型**：

- **工具**：Figma Prototype、v0.dev、Bolt.new、Axure
- **产出**：可点击、可跳转的交互原型
- **受众**：可用性测试、开发 handoff、客户演示
- **关键原则**：只做核心路径的交互，边缘场景用标注说明

### 选型决策树

```
需要原型来做什么？
├── 内部讨论、方向对齐 → L1 Lo-fi（Excalidraw / 纸笔）
├── 设计评审、用户访谈 → L2 Hi-fi（Figma / 即时设计）
├── 可用性测试、客户演示 → L3 Interactive（Figma Prototype / v0.dev）
└── 开发交付 → L2 + 标注 + Design Spec（Figma Dev Mode）
```

## 二、Figma 核心功能：PM 视角

### 为什么 PM 需要懂 Figma？

| 角色 | Figma 用途 | 价值 |
|------|-----------|------|
| 需求评审 | 直接在设计稿上标注评论 | 减少文字歧义，沟通效率提升 3x |
| 原型验证 | 自己搭建简单原型 | 不依赖设计师，快速验证想法 |
| 开发对齐 | 用 Dev Mode 查看设计参数 | 减少"这个间距是多少"的反复确认 |
| 版本管理 | 查看设计历史、对比版本 | 追溯设计变更，理解决策过程 |

### PM 必会的 Figma 功能

#### 1. 组件（Components）

| 概念 | 说明 | PM 需要知道的 |
|------|------|-------------|
| **Component** | 可复用的设计元素 | 修改母版，所有实例同步更新 |
| **Instance** | 组件的使用实例 | 可以覆盖部分属性（文字、颜色） |
| **Variant** | 组件的不同状态 | 如按钮的 default / hover / disabled |
| **Auto Layout** | 自适应布局 | 内容增减时自动排列，类似前端 Flexbox |

**PM 实操**：
- 用组件理解设计系统 — 看到一个按钮组件，就知道所有按钮都从这里派生
- 提需求时引用组件名 — "把 Primary Button 的文案改成..." 比 "那个蓝色的按钮" 精确 10 倍
- 检查一致性 — 如果发现某处按钮不是组件实例，可能是设计遗漏

#### 2. Auto Layout

| 属性 | 作用 | 类比 |
|------|------|------|
| **Direction** | 水平 / 垂直排列 | CSS `flex-direction` |
| **Padding** | 内边距 | CSS `padding` |
| **Gap** | 元素间距 | CSS `gap` |
| **Fill Container** | 拉伸填充 | CSS `flex-grow` |
| **Hug Contents** | 适应内容 | CSS `width: fit-content` |

**PM 实操**：
- 理解 Auto Layout = 理解前端实现约束 — 提需求时知道什么容易做、什么难
- 列表类需求天然对应 Auto Layout — 新增/删除元素时布局自动调整

#### 3. 原型模式（Prototype）

| 交互类型 | 说明 | PM 使用场景 |
|---------|------|------------|
| **Navigate To** | 页面跳转 | 模拟核心用户流程 |
| **Overlay** | 弹层覆盖 | 模拟 Modal、Toast、Dropdown |
| **Swap** | 局部替换 | 模拟 Tab 切换、状态变更 |
| **Scroll To** | 滚动定位 | 模拟长页面内的锚点跳转 |
| **Smart Animate** | 智能动画 | 模拟页面过渡、元素变化 |

**PM 实操**：
- 只做 Happy Path 的交互 — 边缘场景用文字标注
- 用 Smart Animate 做状态过渡 — 让原型看起来更真实
- 分享 Prototype 链接给 stakeholder — 比静态截图有说服力 10 倍

#### 4. Dev Mode

| 功能 | 说明 | PM 价值 |
|------|------|--------|
| **Inspect Panel** | 查看元素属性 | 理解设计参数，减少沟通 |
| **Code Snippet** | 自动生成 CSS/iOS/Android 代码 | 与开发对齐实现方案 |
| **Compare Changes** | 对比设计版本差异 | 追溯需求变更 |
| **Ready for Dev** | 标记可开发状态 | 管理设计交付进度 |

**PM 实操**：
- 用 Dev Mode 自查设计稿 — 在交给开发前先检查间距、颜色是否一致
- 用 Compare Changes 做设计评审 — 快速定位变更点
- 管理 Ready for Dev 状态 — 确保开发拿到的是最新且确认的版本

## 三、AI 原型生成工具

### 工具对比

| 工具 | 生成速度 | 视觉质量 | 交互能力 | 代码质量 | 适合阶段 |
|------|---------|---------|---------|---------|---------|
| **v0.dev** | ★★★★★ | ★★★★★ | ★★★★☆ | ★★★★★ | 概念验证、Landing Page |
| **Bolt.new** | ★★★★☆ | ★★★★☆ | ★★★★★ | ★★★★☆ | MVP、内部工具 |
| **Lovable** | ★★★★☆ | ★★★★☆ | ★★★★☆ | ★★★★☆ | 非技术 PM 独立搭建 |
| **Figma AI** | ★★★★☆ | ★★★★★ | ★★★☆☆ | N/A | 设计稿优化、组件生成 |

### v0.dev 深度使用

**最佳 Prompt 结构**：

```
[组件类型] + [视觉风格] + [功能描述] + [技术约束]

示例：
"A SaaS pricing page with 3 tiers (Basic/Pro/Enterprise),
minimal design, dark mode support, built with shadcn/ui components,
responsive layout"
```

**PM 使用场景**：

| 场景 | Prompt 示例 | 输出 |
|------|-----------|------|
| Landing Page | 产品描述 + 风格 + 核心功能 | 完整页面，可直接部署 |
| 表单设计 | 字段列表 + 验证规则 + 布局 | 带校验的交互表单 |
| 数据看板 | 指标列表 + 图表类型 + 布局 | Dashboard 组件 |
| 邮件模板 | 内容结构 + 品牌风格 | HTML 邮件模板 |

### Bolt.new 深度使用

**核心优势**：全栈能力 — 前端 + 后端 + 数据库一体化

**PM 使用场景**：

| 场景 | 描述 | 复杂度 |
|------|------|-------|
| 内部工具 | 审批流、数据录入、报表查看 | 中 |
| MVP 产品 | 核心功能验证、用户测试 | 高 |
| 活动页面 | 报名页、抽奖页、投票页 | 低 |
| API 演示 | 接口文档、交互式 API 测试 | 中 |

### AI 原型 vs 传统原型

| 维度 | AI 原型（v0/Bolt） | 传统原型（Figma/Axure） |
|------|-------------------|----------------------|
| 速度 | 分钟级 | 小时/天级 |
| 精细度 | 中等，风格统一 | 高，可逐像素调整 |
| 交互深度 | 可运行，有真实交互 | 模拟交互，有条件逻辑 |
| 代码可用性 | 直接可用 | 需要重新开发 |
| 迭代成本 | 重新生成，几乎为零 | 手动修改，成本高 |
| 适用场景 | 早期验证、MVP | 最终交付、精细设计 |

**最佳实践**：

1. **先 AI 后 Figma** — 用 AI 快速生成方向，确认后用 Figma 精细打磨
2. **AI 做探索，Figma 做收敛** — 探索阶段多用 AI 生成方案，收敛阶段用 Figma 定稿
3. **不要用 AI 原型直接交付开发** — 除非是内部工具或 MVP

## 四、设计系统（Design System）

### 核心概念

| 概念 | 定义 | PM 需要了解的程度 |
|------|------|-----------------|
| **Design Token** | 设计变量（颜色、间距、字号） | 了解 — 影响需求表达方式 |
| **组件库** | 可复用的 UI 组件集合 | 深入 — 需求复用组件库中的组件 |
| **模式库** | 常见交互模式的标准化方案 | 深入 — 避免重复造轮子 |
| **品牌指南** | Logo、色彩、字体的使用规范 | 了解 — 确保产品符合品牌调性 |

### Design Token 体系

| Token 类型 | 示例 | 说明 |
|-----------|------|------|
| **Color** | `color-primary-500` | 品牌色、功能色、中性色 |
| **Typography** | `font-size-heading-1` | 字号、字重、行高 |
| **Spacing** | `space-4` | 间距、内边距 |
| **Border** | `radius-md` | 圆角、边框 |
| **Shadow** | `shadow-card` | 阴影层级 |
| **Motion** | `duration-fast` | 动画时长、缓动函数 |

**PM 实操**：
- 提需求时用 Token 名 — "这个卡片用 `shadow-card`" 比 "加个阴影" 精确
- 理解 Token 层级 — Global → Alias → Component，改 Global 影响全局
- 新增需求先查组件库 — 80% 的 UI 需求可以用现有组件组合实现

### PM 与设计系统的协作

| 场景 | PM 角色 | 设计师角色 |
|------|--------|-----------|
| 新功能需求 | 描述用户需求和业务逻辑 | 从组件库中组合方案 |
| 设计系统扩展 | 提出新的通用场景 | 设计新组件/Token |
| 一致性检查 | 检查 PRD 中的 UI 描述是否符合设计系统 | 检查设计稿是否使用标准组件 |
| 版本升级 | 评估升级对现有功能的影响 | 执行设计系统升级 |

## 五、PM 与设计师协作模式

### Design Sprint（设计冲刺）

| 阶段 | 时间 | PM 参与 | 产出 |
|------|------|--------|------|
| **Understand** | Day 1 | 主导 | 问题定义、用户地图、长期目标 |
| **Diverge** | Day 2 | 参与 | 多种方案草图 |
| **Decide** | Day 3 | 主导 | 选定方案、Storyboard |
| **Prototype** | Day 4 | 支持 | 高保真原型 |
| **Test** | Day 5 | 主导 | 用户测试结果、下一步计划 |

**PM 关键职责**：
- Day 1：确保问题定义准确 — "我们要解决什么问题？"
- Day 3：做出决策 — 在多个方案中选一个，拍板
- Day 5：解读结果 — 把用户反馈转化为产品决策

### Design Critique（设计评审）

**PM 参与设计评审的框架**：

| 维度 | 检查点 | 问题示例 |
|------|-------|---------|
| **用户目标** | 是否解决了用户问题？ | "用户在这个场景下的核心诉求是什么？" |
| **业务目标** | 是否达成了业务指标？ | "这个设计如何帮助提升转化率？" |
| **信息层级** | 重要内容是否突出？ | "用户第一眼会看到什么？" |
| **操作效率** | 完成任务需要几步？ | "能不能减少一次点击？" |
| **一致性** | 是否符合设计系统？ | "这个组件和系统里的有出入吗？" |
| **边界情况** | 异常状态是否考虑？ | "空状态、错误状态、极端数据怎么处理？" |

**评审原则**：

- ✅ 对事不对人 — "这个方案的问题是..." 而不是 "你这个设计有问题"
- ✅ 提问题而非答案 — "如果用户不登录会怎样？" 而不是 "加个登录按钮"
- ✅ 先理解意图 — "你为什么选择这种布局？" 先听设计师的思路
- ❌ 不要在评审中提新需求 — 评审是检查已有设计，不是塞新功能

### Design Handoff（设计交付）

**PM 需要确认的交付清单**：

| 检查项 | 说明 | 负责人 |
|-------|------|-------|
| 核心流程覆盖 | 所有 PRD 中的场景都有对应设计 | PM + 设计师 |
| 交互标注 | 复杂交互有动效说明或 Prototype | 设计师 |
| 边界状态 | 空状态、加载状态、错误状态 | 设计师 |
| 响应式适配 | 移动端/平板/桌面端适配方案 | 设计师 |
| 设计系统一致性 | 所有元素使用标准组件和 Token | 设计师 |
| 切图和标注 | Dev Mode 中的 Ready for Dev 状态 | 设计师 |
| PRD 对照 | 设计稿与 PRD 的映射关系 | PM |

## 七、PM 原型实操指南

### 快速原型 Checklist

**开始前**：

- [ ] 明确原型目的（验证什么假设？给谁看？）
- [ ] 确定保真度层级（L1/L2/L3）
- [ ] 梳理核心用户流程（不超过 3 条）
- [ ] 准备参考案例（竞品截图、灵感收集）

**制作中**：

- [ ] 先画信息架构，再画界面
- [ ] 只做核心路径，边缘场景用标注
- [ ] 使用设计系统中的标准组件
- [ ] 保持一致性（间距、颜色、字号）

**完成后**：

- [ ] 自己走一遍核心流程
- [ ] 检查边界状态（空/加载/错误）
- [ ] 准备解说词（关键设计决策的理由）
- [ ] 收集反馈并记录

### 常见错误

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 过早精细化 | 陷入细节，忽略方向 | 先 Lo-fi 对齐方向，再 Hi-fi 细化 |
| 追求 100% 覆盖 | 时间成本爆炸 | 只做核心路径 80%，边缘用标注 |
| 跳过信息架构 | 界面逻辑混乱 | 先画 Site Map / User Flow |
| 不用设计系统 | 视觉不一致，开发成本高 | 先查组件库，再提新组件需求 |
| 忽略边界状态 | 上线后才发现问题 | 空状态、错误状态、极端数据必须设计 |

---

> 💡 **核心观点**：原型不是设计师的专属工具，而是 PM 的核心表达方式。一个能自己做原型的 PM，沟通效率和需求质量都会显著提升。不需要成为设计专家，但需要理解设计语言、会用基础工具、知道什么时候该用什么层级的原型。
