## 一、指标体系设计

### 1.1 指标分类：三层金字塔

| 层级 | 类型 | 定义 | 示例 |
|------|------|------|------|
| L1 | **原子指标** | 最小可度量单元，不含业务限定和统计口径 | 支付金额、下单量、访问次数 |
| L2 | **派生指标** | 原子指标 + 统计周期 + 统计粒度 + 业务限定 | 近7天各城市外卖GMV、当日新用户下单数 |
| L3 | **复合指标** | 多个派生指标通过四则运算组合 | 客单价 = GMV / 下单量、转化率 = 下单人数 / 访问人数 |

**关系图**：

```
原子指标（度量）
  ├── + 统计周期 + 统计粒度 + 业务限定 → 派生指标
  │       └── 派生指标 A ÷ 派生指标 B → 复合指标
  └── 直接参与复合指标计算
```

**为什么分三层**：
- 原子指标保证**口径一致性**——全公司用同一个"支付金额"定义
- 派生指标保证**可复用性**——同一个原子指标可组合出无数业务场景
- 复合指标保证**分析深度**——比率、趋势、归因都建立在此基础上

### 1.2 指标命名规范

**标准公式**：

```
{业务过程}_{统计周期}_{统计粒度}_{业务限定}_{聚合方式}
```

| 字段 | 说明 | 示例 |
|------|------|------|
| 业务过程 | 度量的业务动作 | 支付、下单、访问、退货 |
| 统计周期 | 时间范围 | 近7日、当日、当月、滚动30天 |
| 统计粒度 | 聚合维度 | 全国、各城市、各品类、各渠道 |
| 业务限定 | 筛选条件 | 新用户、VIP、跨境、首单 |
| 聚合方式 | 计算方法 | 总量、均值、去重数、比率 |

**命名示例**：

| 推荐命名 | 反例 | 问题 |
|----------|------|------|
| `支付金额_近7日_各城市_新用户_求和` | `新用户GMV` | 缺统计周期，"GMV"口径模糊 |
| `下单量_当日_全国_全部_计数` | `今日订单数` | "订单"和"下单"不明确，粒度缺失 |
| `退货率_当月_各品类_全部_比率` | `月退货率` | 缺粒度和限定，品类还是渠道？ |

**命名原则**：
1. **动词优先**：用业务动作（支付、下单）而非名词（GMV、订单量）
2. **全拼不用缩写**：首次定义时标注英文，如 `GMV(Gross Merchandise Volume)`
3. **限定语放后面**：先核心度量，后修饰条件

### 1.3 好指标 vs 虚荣指标

| 维度 | ✅ 好指标 | ❌ 虚荣指标 |
|------|----------|------------|
| **可行动** | 能直接驱动决策和行动 | 看完不知道该做什么 |
| **可比较** | 支持趋势、对标、A/B 对比 | 孤立数字，无法对比 |
| **可归因** | 变化可追溯到具体原因 | 涨了不知道为什么涨 |
| **比率优于绝对数** | 转化率、留存率、ARPU | 总注册用户数、累计GMV |
| **趋势优于快照** | 环比/同比变化率 | 当前在线人数（瞬间值） |
| **细分优于汇总** | 分渠道/分城市/分人群 | 全公司总营收 |

**典型转换**：

| 虚荣指标 | 转化为好指标 |
|----------|-------------|
| 总注册用户数 | 月活跃用户占比（MAU/注册数） |
| 日GMV | GMV 环比增长率 |
| 页面浏览量 PV | 页面转化率（目标完成数/PV） |
| 累计订单量 | 复购率（二次购买用户/首次购买用户） |

### 1.4 北极星指标选择方法论

**North Star Metric** 是一个最能反映产品核心价值的单一指标。

**四条检验标准**：

| 标准 | 说明 | 检验问题 |
|------|------|----------|
| **可执行** | 团队行动能直接影响它 | "如果这个指标下降，我们能做什么？" |
| **可衡量** | 有清晰的计算口径和数据源 | "不同人算出来结果一样吗？" |
| **领先指标** | 它变化后其他指标会跟随变化 | "它涨了，营收会跟着涨吗？" |
| **业务反映** | 体现用户获得的真实价值 | "用户真的因为这个获得了价值吗？" |

**不同业务类型的北极星指标参考**：

| 业务类型 | 北极星指标 | 辅助指标 |
|----------|-----------|---------|
| 电商 | 周购买用户数 | 转化率、客单价、复购率 |
| SaaS | 周活跃账户数 | 功能使用深度、NPS、续费率 |
| 社交 | 日均发布内容用户数 | 互动率、关注链深度、留存 |
| 外卖 | 日完成订单量 | 取消率、配送时长、好评率 |
| 内容 | 日均阅读时长 | 完播率、分享率、关注转化 |

**选择流程**：

```
1. 梳理用户核心价值主张
     ↓
2. 列出候选指标（3-5个）
     ↓
3. 用四条标准逐一评分（1-5分）
     ↓
4. 选择总分最高者
     ↓
5. 验证：回看历史数据，该指标变化是否领先于营收变化
     ↓
6. 确定并公示，配套拆解子指标树
```

### 1.5 指标字典模板

| 字段 | 说明 | 示例 |
|------|------|------|
| **指标名称** | 命名规范后的全名 | 支付金额_近7日_各城市_新用户_求和 |
| **业务口径** | 精确的计算定义 | 用户完成支付的订单实付金额之和，不含退款 |
| **计算公式** | 数学表达式 | SUM(orders.pay_amount) WHERE pay_time >= T-7 |
| **数据源** | 表/字段/数据库 | dw.order_fact.pay_amount |
| **统计周期** | 默认时间范围 | 滚动7天（T-7 到 T-1） |
| **统计粒度** | 默认聚合维度 | 城市 |
| **业务限定** | 默认筛选条件 | 新用户（注册时间 <= 下单时间 + 7天） |
| **负责人** | 口径 Owner | 张三（数据产品） |
| **更新频率** | 数据刷新周期 | 每日 08:00 |
| **下游报表** | 使用该指标的 Dashboard | 用户增长看板、城市经营日报 |
| **数据质量规则** | 异常告警条件 | 日波动 > 30% 触发告警 |
| **备注** | 特殊说明 | 2025年Q3起不含测试订单 |

**指标字典管理原则**：
1. **一指标一 Owner**：口径争议时 Owner 有最终解释权
2. **变更需审批**：口径变更走评审流程，通知下游使用者
3. **版本化管理**：记录每次口径变更的时间、原因、影响范围
4. **定期清理**：每季度 review 一次，下线无人使用的指标

## 二、Dashboard 设计原则

### 2.1 四层信息架构

| 层级 | 名称 | 目的 | 内容 | 交互方式 |
|------|------|------|------|----------|
| L1 | **概览** | 一眼看全局 | 北极星指标 + 3-5个核心 KPI + 趋势 | 只看不操作 |
| L2 | **维度下钻** | 定位问题区域 | 按城市/品类/渠道拆解指标 | 点击下钻 |
| L3 | **明细分析** | 找到根因 | 趋势对比、分布、相关性分析 | 筛选、联动 |
| L4 | **行动建议** | 驱动决策 | 异常标注、预警提示、操作入口 | 导出、跳转 |

**设计逻辑**：从"发生了什么"到"为什么发生"到"该做什么"，逐层深入。

### 2.2 Dashboard 设计 Checklist

| # | 原则 | 检查问题 |
|---|------|----------|
| 1 | **一屏一主题** | 每个 Dashboard 是否聚焦一个业务问题？ |
| 2 | **F型阅读动线** | 核心指标是否在左上角（视觉起点）？ |
| 3 | **对比才有意义** | 每个数字旁边是否有环比/同比/目标值？ |
| 4 | **图表类型匹配** | 趋势用折线、占比用饼图/堆叠、分布用直方图？ |
| 5 | **色彩有语义** | 红色=异常、绿色=正常、灰色=基准？还是彩虹色无意义？ |
| 6 | **筛选器克制** | 筛选器是否不超过3个？是否设置了合理默认值？ |
| 7 | **加载性能** | 首屏加载是否 < 3秒？大数据量是否做了预聚合？ |
| 8 | **有使用说明** | 口径说明、数据时效、负责人是否标注？ |

### 2.3 常见反模式

| 反模式 | 表现 | 根因 | 修正方案 |
|--------|------|------|----------|
| **数据垃圾场** | 一个 Dashboard 塞 30+ 图表，什么都有等于什么都没有 | 需求堆叠，没有取舍 | 拆分为多个专题 Dashboard，每个聚焦一个问题 |
| **KPI 罗列墙** | 20个数字卡片平铺，看不出重点和关系 | 把指标字典直接搬上屏幕 | 分层展示：L1 核心 3-5个，L2 可下钻展开 |
| **无下钻路径** | 只有汇总数字，点进去什么都看不到 | 设计时只考虑了"看"没考虑"分析" | 每个汇总图表都要有维度下钻出口 |
| **彩虹配色** | 饼图用了10种颜色，折线图7条线叠在一起 | 默认主题未调整 | 限制调色板至 5-7 色，重要线用粗线+高饱和 |
| **静态快照** | 只展示当天数据，无法看趋势和对比 | 开发省事，只查单日数据 | 默认展示近 7/30 天，支持时间范围切换 |
| **移动端照搬** | PC 端 Dashboard 直接缩小到手机 | 没有做移动端适配 | 见下方移动端适配要点 |

### 2.4 移动端适配要点

| 维度 | 要求 |
|------|------|
| **布局** | 单列纵向排列，不用横向滚动；卡片全宽 |
| **图表简化** | 移除次要坐标轴、隐藏图例（用标签替代）、减少数据点 |
| **交互** | 支持手势缩放，筛选器用底部抽屉，不用侧边栏 |
| **字体** | 最小 12px，关键数字 20px+，确保户外可读 |
| **加载** | 优先渲染首屏核心卡片，下拉加载更多 |
| **离线** | 缓存最近一次数据，断网时展示缓存 + 时效提示 |

## 三、BI 开发工作流

### 3.1 六步标准流程

| 阶段 | 产出物 | 关键角色 | 质量门 |
|------|--------|----------|--------|
| **1. 需求** | 需求文档（业务问题、看板目标、核心指标） | 业务方 + 数据产品 | 需求评审通过 |
| **2. 设计** | 指标字典 + 原型图 + 数据模型设计 | 数据产品 + 数据开发 | 设计评审通过 |
| **3. 开发** | ETL 任务 + 报表/看板 + 权限配置 | 数据开发 + 前端 | 代码 Review |
| **4. 测试** | 口径验证报告 + 性能测试 + 权限测试 | QA + 数据产品 | 数据准确性 100% |
| **5. 发布** | 上线 + 使用文档 + 培训 | 数据产品 + 业务方 | 用户验收通过 |
| **6. 迭代** | 需求收集 + 优化 backlog | 数据产品 | 定期 review |

**流程图**：

```
需求收集 → 需求评审 → 指标定义 → 口径对齐
                                        ↓
发布上线 ← UAT验收 ← 集成测试 ← 开发实现
    ↓
使用培训 → 效果跟踪 → 迭代优化（回到需求收集）
```

### 3.2 自助分析 vs 固定报表

| 维度 | 固定报表 | 自助分析 |
|------|----------|----------|
| **用户** | 业务管理层、运营 | 数据分析师、BI 工程师 |
| **使用频率** | 每日/每周固定查看 | 临时探索、专题分析 |
| **交互方式** | 筛选器 + 下钻（有限） | 拖拽维度、自由组合、SQL |
| **数据范围** | 预定义数据集 | 全量明细数据 |
| **开发成本** | 一次开发长期使用 | 搭建平台，用户自助产出 |
| **治理难度** | 低（统一口径） | 高（口径可能不一致） |
| **适用场景** | 日报、周报、经营看板 | 异常排查、专题研究、探索性分析 |

**选型建议**：

| 场景 | 推荐 |
|------|------|
| 高频、口径稳定、面向管理层 | 固定报表 |
| 低频、需求多变、面向分析师 | 自助分析 |
| 两者混合 | 固定报表做 L1/L2，自助分析做 L3/L4 |

### 3.3 权限设计

| 权限层级 | 说明 | 实现方式 | 示例 |
|----------|------|----------|------|
| **行级权限 (RLS)** | 同一报表，不同用户看到不同行 | 数据表加权限字段，查询时自动过滤 | 大区经理只看本大区数据 |
| **列级权限 (CLS)** | 隐藏敏感列 | 字段级权限配置 | 一线员工看不到成本列 |
| **功能级权限** | 控制可执行的操作 | 角色 + 功能权限矩阵 | 业务方只能看不能导出 |

**权限矩阵模板**：

| 角色 | 查看 | 下钻 | 导出 | 分享 | 管理 |
|------|------|------|------|------|------|
| 高管 | 全部 | 全部 | 全部 | 是 | 否 |
| 业务负责人 | 本部门 | 本部门 | 本部门 | 本部门 | 否 |
| 数据分析师 | 全部 | 全部 | 全部 | 否 | 否 |
| 数据产品经理 | 全部 | 全部 | 全部 | 是 | 是 |
| 外部合作方 | 指定看板 | 否 | 否 | 否 | 否 |

**权限设计原则**：
1. **最小权限原则**：默认无权限，按需申请
2. **角色优于个人**：绑定角色不绑个人，人员变动时只需调整角色
3. **定期审计**：每季度 review 一次权限分配，清理离职/转岗人员

## 四、常见 BI 产品形态

### 4.1 形态对比总览

| 形态 | 核心价值 | 典型用户 | 技术要求 | 代表产品 |
|------|----------|----------|----------|----------|
| **固定报表** | 标准化信息传递 | 业务管理层 | 低 | Excel 报表、邮件日报 |
| **Dashboard** | 实时监控 + 交互下钻 | 全员 | 中 | Grafana、Tableau、Quick BI |
| **自助分析** | 灵活探索数据 | 数据分析师 | 高 | Superset、Metabase、Power BI |
| **数据大屏** | 全局态势感知 | 管理层/展厅 | 中 | DataV、FineReport |
| **嵌入式分析** | 业务系统内嵌 BI | 业务操作人员 | 中 | iframe 嵌入、SDK 集成 |
| **数据门户** | 统一数据入口 | 全员 | 高 | 自建数据门户 |

### 4.2 各形态详解

#### 固定报表 / Dashboard

**适用场景**：
- 日报、周报、月报等周期性经营分析
- 核心 KPI 实时监控
- 管理层驾驶舱

**设计要点**：
- 遵循四层信息架构（概览 → 下钻 → 明细 → 行动）
- 指标口径在报表内标注
- 支持导出 PDF/Excel

#### 自助分析（拖拽式 OLAP）

**适用场景**：
- 临时数据需求、探索性分析
- 业务方自助取数，减少对数据团队的依赖
- A/B 测试分析、专题研究

**设计要点**：
- 预建好宽表或语义层（Semantic Layer），降低使用门槛
- 提供常用分析模板（趋势、对比、分布、漏斗）
- 需配套治理机制，防止口径泛滥

**语义层核心组件**：

| 组件 | 说明 |
|------|------|
| 维度（Dimension） | 分析角度：时间、地区、品类、渠道 |
| 度量（Measure） | 可聚合的数值：金额、数量、人数 |
| 指标（Metric） | 度量 + 口径 + 限定 = 业务含义明确的数字 |
| 关联关系 | 表之间的 Join 关系，预定义避免用户自行关联出错 |

#### 数据大屏

**适用场景**：
- 指挥中心、运营监控室
- 展厅展示、会议演示
- 重大活动实时监控（大促、发布会）

**设计要点**：

| 维度 | 要求 |
|------|------|
| **布局** | 16:9 或超宽屏，核心信息居中，辅助信息两侧 |
| **数据量** | 一屏不超过 8 个信息模块，每模块 1-2 个核心指标 |
| **刷新频率** | 根据场景选择：秒级（监控）、分钟级（经营）、小时级（战略） |
| **视觉** | 深色背景、高对比度、大字号，3米外可读 |
| **动效** | 适度使用，数字翻牌、地图热力、趋势流动，不要喧宾夺主 |

#### 嵌入式分析

**适用场景**：
- CRM 内嵌客户分析
- ERP 内嵌库存分析
- 电商后台内嵌商品分析

**集成方式**：

| 方式 | 优点 | 缺点 |
|------|------|------|
| iframe 嵌入 | 最快、最简单 | 样式不统一、跨域问题 |
| SDK 集成 | 体验最好、可深度定制 | 开发成本高 |
| API + 自建 | 完全可控 | 最高开发成本 |

#### 数据门户

**适用场景**：
- 企业级数据资产管理
- 统一数据入口和导航
- 数据治理体系落地

**核心模块**：

| 模块 | 功能 |
|------|------|
| 指标中心 | 指标字典、口径管理、血缘追踪 |
| 报表中心 | 报表目录、收藏、订阅 |
| 数据目录 | 数据资产浏览、分类、搜索 |
| 数据质量 | 质量看板、异常告警 |
| 权限中心 | 申请、审批、审计 |

## 五、BI 建设常见坑与应对

| # | 坑 | 表现 | 应对 |
|---|-----|------|------|
| 1 | **需求没有收敛** | 做了 100 张报表，实际在用的不到 20 张 | 先梳理核心业务场景，优先级排序，迭代交付 |
| 2 | **口径不统一** | 同一个指标，财务和业务算出来不一样 | 建立指标字典，一指标一 Owner，口径评审机制 |
| 3 | **数据质量失控** | 报表数字对不上，业务不信任数据 | 建立数据质量监控，异常自动告警，定期对账 |
| 4 | **只建不用** | Dashboard 上线后无人访问 | 配套培训 + 使用数据追踪 + 定期优化 |
| 5 | **技术驱动而非业务驱动** | 用了最先进的 BI 工具但没人用 | 回到业务问题，用最合适的工具解决最痛的问题 |
| 6 | **权限管理失控** | 数据泄露或权限申请流程过长 | 角色化管理 + 定期审计 + 自助申请审批流 |

---

## 六、总结

| 维度 | 核心要点 |
|------|----------|
| **指标体系** | 三层分类（原子/派生/复合）、命名规范化、好指标可行动可比较 |
| **北极星指标** | 一到两个、领先于营收、可驱动团队行动 |
| **Dashboard** | 四层架构、一屏一主题、对比才有意义 |
| **BI 工作流** | 六步标准流程、固定报表与自助分析互补 |
| **权限** | 行级/列级/功能级三层，最小权限 + 角色化 |
| **产品形态** | 根据用户和场景选型，不要一刀切 |
