## 一、需求阶段

### 1.1 业务需求 vs 数据需求

| 维度 | 业务需求 | 数据需求 |
|------|----------|----------|
| **提出方** | 业务方/产品 | 数据团队 |
| **核心问题** | 要解决什么业务问题 | 需要哪些数据、什么粒度、什么频率 |
| **输出物** | 业务场景描述、用户故事 | 数据表/报表/API/指标定义 |
| **典型表述** | "我要看每个区域的销售趋势" | "按区域+月度聚合销售额，T+1 更新" |
| **验收标准** | 业务目标达成 | 数据准确、及时、可查 |

**关键动作**：业务需求必须翻译为明确的数据需求，才能进入开发。

### 1.2 需求评审 Checklist

```
□ 数据源确认
  - 源系统名称 & 负责人
  - 数据接入方式（CDC / 全量 / API）
  - 源表结构 & 字段说明
  - 数据量级（日增量 / 全量）

□ 粒度确认
  - 最细粒度是什么（用户级 / 订单级 / 天级）
  - 是否需要多粒度输出

□ 时效性
  - T+0（实时）/ T+1（隔日）/ T+N
  - 可接受的最大延迟

□ 口径确认
  - 指标计算公式（分子/分母/过滤条件）
  - 与现有指标是否重复
  - 业务侧签字确认

□ 输出形式
  - 表 / 报表 / API / 文件
  - 消费方 & 使用场景

□ 历史数据
  - 是否需要回刷历史
  - 回刷范围（1年/3年/全量）
```

## 二、建模设计

### 2.1 数仓分层架构

```
┌─────────────────────────────────────────────────┐
│                   ADS 应用层                      │
│         面向业务场景，直接消费                      │
├─────────────────────────────────────────────────┤
│                   DWS 汇总层                      │
│         轻度聚合，公共指标                         │
├─────────────────────────────────────────────────┤
│                   DWD 明细层                      │
│         清洗、标准化、关联                         │
├─────────────────────────────────────────────────┤
│                   ODS 原始层                      │
│         原样入仓，保留历史                         │
├─────────────────────────────────────────────────┤
│               数据源（业务系统）                    │
└─────────────────────────────────────────────────┘
```

#### 各层详解

| 层级 | 英文全称 | 职责 | 数据处理 | 典型表 |
|------|----------|------|----------|--------|
| **ODS** | Operational Data Store | 原始数据落地，保留源系统结构 | 去重、编码统一，不做业务逻辑 | `ods_{来源}_{表名}` |
| **DWD** | Data Warehouse Detail | 清洗、标准化、维度关联 | 数据质量清洗、字段标准化、主外键关联 | `dwd_{业务域}_{主题}_{粒度}` |
| **DWS** | Data Warehouse Summary | 轻度聚合，构建公共指标 | 按维度聚合（日/周/月），构建宽表 | `dws_{业务域}_{主题}_{粒度}_{周期}` |
| **ADS** | Application Data Store | 面向具体应用场景 | 高度聚合，直接对接报表/API | `ads_{应用场景}_{描述}` |

#### 各层数据流转示例

```
ods_order_raw          →  dwd_trade_order_df     →  dws_trade_order_1d     →  ads_trade_region_report
(原始订单表)              (清洗后订单明细)           (日粒度聚合)              (区域销售报表)
```

### 2.2 维度建模选型

#### 三种模型对比

| 维度 | 星型模型 Star | 雪花模型 Snowflake | 宽表 Flat |
|------|---------------|---------------------|-----------|
| **结构** | 事实表 + 一层维度表 | 事实表 + 多层规范化维度表 | 所有字段平铺一张表 |
| **Join 次数** | 少（1次/维度） | 多（多层展开） | 无（0次） |
| **查询性能** | 好 | 中等 | 最好 |
| **存储冗余** | 中等（维度表重复） | 最少（规范化） | 最大（大量冗余） |
| **维护成本** | 低 | 高（多层依赖） | 中（字段爆炸） |
| **适用场景** | OLAP 标准分析 | 维度层次复杂、需规范化 | 高并发查询、BI 报表 |

#### 选型决策树

```
需要建模？
├── 查询性能优先？
│   ├── 是 → 宽表
│   └── 否 → 维度模型
│       ├── 维度层次简单（<3层）？
│       │   ├── 是 → 星型模型
│       │   └── 否 → 雪花模型
│       └── 维度表是否频繁变化？
│           ├── 是 → 星型 + SCD
│           └── 否 → 星型
└── 存储成本敏感？
    ├── 是 → 雪花模型
    └── 否 → 星型模型
```

**产品经验法则**：90% 的场景用星型模型起步，性能不够再做宽表。

### 2.3 缓慢变化维度（SCD）

| SCD 类型 | 策略 | 实现方式 | 保留历史 | 适用场景 |
|----------|------|----------|----------|----------|
| **Type 1** | 直接覆盖 | UPDATE 字段值 | 不保留 | 错误修正、无需历史 |
| **Type 2** | 新增行 | 加 `start_date` / `end_date` / `is_current` 字段 | 保留完整历史 | 客户等级、产品分类变化 |
| **Type 3** | 新增列 | 加 `previous_xxx` 字段 | 保留上一版本 | 只关心前后两次变化 |

#### SCD Type 2 实现示例

```
┌──────────┬──────────┬────────────┬────────────┬────────────┐
│ user_id  │ level    │ start_date │ end_date   │ is_current │
├──────────┼──────────┼────────────┼────────────┼────────────┤
│ U001     │ 普通会员  │ 2024-01-01 │ 2024-06-30 │ N          │
│ U001     │ 黄金会员  │ 2024-07-01 │ 9999-12-31 │ Y          │
└──────────┴──────────┴────────────┴────────────┴────────────┘
```

### 2.4 事实表设计

| 事实表类型 | 定义 | 粒度 | 典型场景 | 更新策略 |
|-----------|------|------|----------|----------|
| **事务事实表** Transaction | 记录业务事件 | 每笔交易一行 | 订单、支付、点击 | 只 INSERT |
| **周期快照事实表** Periodic Snapshot | 固定周期的状态快照 | 每周期一行 | 日库存余额、月度 KPI | 每周期 INSERT |
| **累积快照事实表** Accumulating Snapshot | 记录有生命周期的事件 | 实体一行，里程碑多列 | 订单全流程（下单→发货→签收） | UPDATE 里程碑字段 |

#### 事务事实表设计模板

```sql
-- dwd_trade_order_df（日分区事实表）
CREATE TABLE dwd_trade_order_df (
    order_id        BIGINT      COMMENT '订单ID',
    user_id         BIGINT      COMMENT '用户ID',
    product_id      BIGINT      COMMENT '商品ID',
    region_code     STRING      COMMENT '区域编码',
    order_amount    DECIMAL(18,2) COMMENT '订单金额',
    pay_amount      DECIMAL(18,2) COMMENT '实付金额',
    order_status    STRING      COMMENT '订单状态',
    order_time      TIMESTAMP   COMMENT '下单时间',
    pay_time        TIMESTAMP   COMMENT '支付时间',
    dt              STRING      COMMENT '分区字段-日期'
)
COMMENT '交易订单明细-日分区'
PARTITIONED BY (dt STRING);
```

### 2.5 命名规范

#### 表名命名

```
{层级}_{业务域}_{主题}_{粒度}[_{周期}]

示例：
dwd_trade_order_df          -- DWD层-交易域-订单-明细-日全量
```

| 层级 | 前缀 | 说明 |
|------|------|------|
| ODS | `ods_` | 原始层 |
| DWD | `dwd_` | 明细层 |
| DWS | `dws_` | 汇总层 |
| ADS | `ads_` | 应用层 |
| DIM | `dim_` | 维度表 |

#### 粒度后缀

| 后缀 | 含义 | 示例 |
|------|------|------|
| `_df` | Daily Full（日全量） | `dwd_order_df` |

| `_1m` | 1 月聚合 | `dws_user_1m` |

#### 字段命名

| 类型 | 前缀 | 示例 |
|------|------|------|

## 三、ETL/ELT 开发

### 3.1 ETL vs ELT 选型

| 维度 | ETL（传统） | ELT（云数仓时代） |
|------|------------|-------------------|
| **处理位置** | ETL 服务器 | 数仓内（计算下推） |
| **数据流向** | 抽取 → 转换 → 加载 | 抽取 → 加载 → 转换 |
| **适用架构** | 传统数仓（Teradata/Oracle） | 云数仓（Snowflake/MaxCompute/BigQuery） |
| **计算资源** | ETL 工具资源 | 数仓计算资源 |
| **扩展性** | 受 ETL 服务器限制 | 弹性扩展 |
| **开发工具** | Informatica/DataStage/Kettle | SQL/Spark/Flink/dbt |
| **推荐场景** | 遗留系统、复杂转换逻辑 | 新建数仓、云原生 |

**决策建议**：新项目优先 ELT，SQL 是最通用的语言。

### 3.2 数据质量检查维度

| 维度 | 定义 | 检查方法 | 告警阈值示例 |
|------|------|----------|-------------|
| **完整性** Completeness | 数据是否齐全 | NULL 值比例、必填字段缺失率 | NULL 率 > 5% 告警 |
| **准确性** Accuracy | 数据是否正确 | 与源系统对账、业务规则校验 | 差异 > 0.1% 告警 |
| **一致性** Consistency | 多处数据是否一致 | 跨表/跨层对比 | 不一致记录 > 0 告警 |
| **时效性** Timeliness | 数据是否按时到达 | SLA 时间检查 | 超时 > 30min 告警 |
| **唯一性** Uniqueness | 主键是否重复 | 主键去重计数 | 重复 > 0 告警 |
| **有效性** Validity | 值是否在合理范围 | 枚举值、区间检查 | 无效记录 > 1% 告警 |

#### 数据质量检查 SQL 模板

```sql
-- 1. 完整性检查
SELECT
    COUNT(*) AS total_cnt,
    SUM(CASE WHEN user_id IS NULL THEN 1 ELSE 0 END) AS null_user_cnt,
    ROUND(SUM(CASE WHEN user_id IS NULL THEN 1 ELSE 0 END) / COUNT(*) * 100, 2) AS null_rate
FROM dwd_trade_order_df
WHERE dt = '${bizdate}';

-- 2. 主键唯一性检查
SELECT
    order_id,
    COUNT(*) AS dup_cnt
FROM dwd_trade_order_df
WHERE dt = '${bizdate}'
GROUP BY order_id
HAVING COUNT(*) > 1;

-- 3. 行数波动检查（与前一天对比）
SELECT
    today.cnt AS today_cnt,
    yesterday.cnt AS yesterday_cnt,
    ROUND(ABS(today.cnt - yesterday.cnt) / yesterday.cnt * 100, 2) AS change_rate
FROM (
    SELECT COUNT(*) AS cnt FROM dwd_trade_order_df WHERE dt = '${bizdate}'
) today
CROSS JOIN (
    SELECT COUNT(*) AS cnt FROM dwd_trade_order_df WHERE dt = DATE_SUB('${bizdate}', 1)
) yesterday;

-- 4. 枚举值检查
SELECT DISTINCT order_status
FROM dwd_trade_order_df
WHERE dt = '${bizdate}'
  AND order_status NOT IN ('待付款', '已付款', '已发货', '已完成', '已取消');
```

### 3.3 增量 vs 全量策略

| 策略 | 实现方式 | 优点 | 缺点 | 适用场景 |
|------|----------|------|------|----------|
| **全量** | 每次覆盖整表 | 逻辑简单、无遗漏 | 资源消耗大 | 小表（<100万）、维表 |
| **增量** | `WHERE update_time > 上次同步时间` | 资源消耗小 | 可能遗漏删除数据 | 大表、高频更新 |
| **CDC** | 捕获数据库 binlog | 实时、完整 | 依赖源系统配置 | 实时数仓、大表 |
| **分区交换** | 按分区整体替换 | 高效、可回滚 | 要求数据可按分区完整切分 | 日分区表 |

#### 增量策略选择决策树

```
源表数据量？
├── < 100 万行 → 全量同步
├── 100万 ~ 1000万
│   ├── 变更比例 > 30%？ → 全量
│   └── 变更比例 < 30%？ → 增量（update_time）
└── > 1000 万行
    ├── 有 update_time 字段？ → 增量
    ├── 有 binlog 权限？ → CDC
    └── 都没有 → 全量（按天分区）
```

### 3.4 调度依赖设计

#### 依赖关系图示例

```
[数据源] → [ODS 同步] → [DWD 清洗] → [DWS 聚合] → [ADS 报表]
                              ↓
                         [DIM 维表] ─────→ [DWS 聚合]
```

#### 调度配置模板

| 任务名 | 上游依赖 | 调度频率 | 超时时间 | 重试次数 | 告警 |
|--------|----------|----------|----------|----------|------|
| `ods_order_sync` | 源系统就绪 | 每日 02:00 | 1h | 3 | 失败告警 |
| `dwd_trade_order_df` | `ods_order_sync` | 每日 03:00 | 2h | 2 | 失败告警 |
| `dim_user_df` | `ods_user_sync` | 每日 03:00 | 1h | 2 | 失败告警 |
| `dws_trade_order_1d` | `dwd_trade_order_df`, `dim_user_df` | 每日 04:00 | 1h | 2 | 失败告警 |
| `ads_trade_report` | `dws_trade_order_1d` | 每日 05:00 | 30min | 2 | 失败+SLA告警 |

#### 调度设计原则

1. **DAG 层次清晰**：ODS → DWD → DWS → ADS，不跨层依赖
2. **并行优先**：无依赖的任务并行执行
3. **超时兜底**：每个任务设置合理超时，避免级联阻塞
4. **告警分级**：ODS 失败 → 紧急；ADS 失败 → 一般

## 四、测试与上线

### 4.1 数据测试方法

| 测试类型 | 方法 | SQL 示例 | 通过标准 |
|----------|------|----------|----------|
| **行数校验** | 源表与目标表行数对比 | `SELECT COUNT(*) FROM src = COUNT(*) FROM tgt` | 差异 = 0 |
| **主键唯一** | 主键去重计数 | `GROUP BY pk HAVING COUNT(*) > 1` | 结果为空 |
| **阈值告警** | 关键指标波动检查 | 与前一天/上月对比 | 波动 < 阈值 |
| **对账** | 金额/数量汇总对比 | `SUM(amount)` 源 vs 目标 | 差异 < 0.01% |
| **抽样比对** | 随机抽样逐字段对比 | 随机 1000 条逐字段比对 | 100% 一致 |
| **业务规则** | 业务逻辑验证 | 状态枚举、金额>0、时间合理性 | 违规 = 0 |
| **空值检查** | 必填字段非空 | `WHERE required_field IS NULL` | 结果为空 |

```
□ 先跑 shadow 任务（不影响生产）
□ 观察 1~3 天无异常
□ 切换生产调度

权限与安全
□ 表权限已配置
□ 敏感字段已脱敏/加密
□ 数据分级标签已打
```

### 4.4 回滚方案

| 场景 | 回滚策略 | 操作步骤 | 预计耗时 |
|------|----------|----------|----------|
| **表结构变更** | DDL 回滚 | 执行反向 DDL，恢复原结构 | < 5min |
| **数据错误** | 分区恢复 | 恢复前一日分区快照 | < 30min |
| **逻辑错误** | 代码回滚 + 重跑 | Git revert + 重跑任务 | 视数据量 |
| **全量数据异常** | 快照恢复 | 从快照恢复整表 | 视数据量 |
| **调度异常** | 任务回滚 | 暂停调度 → 修复 → 重跑 | < 15min |

## 五、运维与监控

### 5.1 SLA 定义

| 指标 | 定义 | 目标值 | 度量方式 |
|------|------|--------|----------|
| **数据就绪时间** | 核心表每日就绪时间 | 08:00 前 | 调度系统监控 |
| **任务成功率** | 调度任务成功执行比例 | > 99.5% | 成功次数 / 总执行次数 |
| **数据质量分** | DQ 检查通过率 | > 98% | 通过检查数 / 总检查数 |
| **数据延迟** | 数据到达延迟时间 | < 30min | 实际就绪 - 预期就绪 |
| **故障恢复时间** MTTR | 从告警到恢复的时间 | < 1h | 恢复时间 - 告警时间 |
| **数据可用率** | 数据可正常查询的时间比 | > 99.9% | 可用时长 / 总时长 |

#### SLA 分级

| 级别 | 适用对象 | 就绪时间 | 延迟容忍 | 告警升级 |
|------|----------|----------|----------|----------|
| **P0** | 核心经营报表 | 08:00 | 15min | 立即电话 |
| **P1** | 日常分析报表 | 10:00 | 30min | IM 告警 |
| **P2** | 探索性分析 | 12:00 | 2h | 邮件通知 |
| **P3** | 非核心数据 | 无硬性要求 | 无 | 工单记录 |

### 5.2 告警策略

#### 告警分级

| 级别 | 触发条件 | 通知方式 | 响应时间 | 处理人 |
|------|----------|----------|----------|--------|
| **Critical** | P0 表未按时就绪、数据大面积异常 | 电话 + IM + 邮件 | 15min | 值班 DE + TL |
| **Warning** | P1 表延迟、质量分下降 | IM + 邮件 | 30min | 值班 DE |
| **Info** | P2/P3 表延迟、非关键告警 | 邮件 | 2h | 对应负责人 |

#### 告警规则模板

| 告警名称 | 触发条件 | 级别 | 持续时间 | 通知对象 |
|----------|----------|------|----------|----------|
| 任务超时 | 执行时间 > SLA 阈值 | Warning | 即时 | 值班 DE |
| 任务失败 | 重试后仍失败 | Critical | 即时 | 值班 DE + TL |
| 数据量异常 | 行数波动 > 50% | Warning | 即时 | 数据 Owner |
| 质量分下降 | DQ 分 < 95% | Warning | 即时 | 数据 Owner |
| SLA 违规 | 就绪时间超 SLA | Critical | 即时 | 值班 DE + TL |
| 存储超限 | 单表 > 阈值 | Info | 每日 | 数据 Owner |

### 5.3 成本优化

#### 存储优化

| 策略 | 方法 | 节省比例 | 适用场景 |
|------|------|----------|----------|
| **分区** | 按日期/业务维度分区 | 30~70% 查询扫描量 | 所有大表必做 |
| **存储格式** | Parquet/ORC 替代 Text | 50~80% 存储空间 | 列式存储优先 |
| **压缩** | Snappy/Zstd 压缩 | 60~80% 存储空间 | 所有表默认开启 |
| **生命周期** | 过期数据归档/删除 | 视数据量 | ODS 保留 90 天，DWD 保留 2 年 |
| **去重** | 定期清理重复数据 | 视重复率 | 增量同步易产生重复 |

#### 计算优化

| 策略 | 方法 | 效果 | 适用场景 |
|------|------|------|----------|
| **分区裁剪** | WHERE 条件带分区字段 | 减少 90%+ 扫描 | 所有查询 |
| **列裁剪** | SELECT 只取需要的列 | 减少 IO 50%+ | 所有查询 |
| **小文件合并** | 定期合并小文件 | 提升读取性能 | 增量写入场景 |
| **资源隔离** | 核心任务独占队列 | 保障 SLA | P0 任务 |
| **预计算** | 高频查询结果物化 | 查询提速 10x+ | ADS 层 |

### 6.2 常见问题速查

| 问题 | 可能原因 | 排查方向 |
|------|----------|----------|
| 数据对不上 | 口径不一致 / 增量遗漏 / 时区问题 | 逐层比对，缩小范围 |
| 任务超时 | 数据量激增 / 资源不足 / 小文件过多 | 查看执行计划，检查资源 |
| 查询慢 | 未命中分区 / 数据倾斜 / Join 大表 | EXPLAIN 分析，加分区条件 |
| 数据重复 | 增量逻辑错误 / 幂等未保证 | 检查主键去重逻辑 |
| 上游变更 | 源系统字段变更 / 架构调整 | 加 Schema 变更监控 |
