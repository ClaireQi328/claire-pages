# AI 应用的工程层反幻觉

> 工程层的反幻觉不是"让 LLM 回答得更准"，而是"让 Agent 在自动执行时不跑偏"。以样件订单自动化为蓝本，讲清楚在事件驱动架构下，该怎么分层卡控。

---

## 一、核心区别：事件驱动 vs 自然语言驱动

| 维度 | 自然语言驱动 | 事件驱动（Agent 自动执行） |
|------|------------|------------------------|
| **触发方式** | 用户打字："帮我下一单" | 业务事件：需求到达、价格匹配完成、状态变更 |
| **AI 的角色** | 理解意图 + 提取参数 + 调工具 | 监听事件 + 判断分流 + 自动执行 |
| **幻觉风险** | 理解错意图、提取错参数 | 判断错分流、执行错动作、跳过闸门 |
| **卡控重点** | Schema 校验 + 人工确认 | 规则引擎 + 状态机 + 人工闸门 + 反向校验 |

样件订单自动化属于**事件驱动**：不是用户打字让 AI 下单，而是需求到达后 Agent 自动判断该走哪条路、该执行什么动作。

## 二、四层架构与各层的反幻觉职责

```
┌─ L4 业务闭环层 ──────────────────────────────┐
│  页面控制室 · 异常队列 · 准确率评估 · 降级机制  │  ← 兜底
└───────────────────────────────────────────────┘
  ↑
┌─ L3 能力层 ──────────────────────────────────┐
│  规则引擎（确定性）· Skill（可复用能力）· CLI   │  ← 执行
└───────────────────────────────────────────────┘
  ↑
┌─ L2 AI 识别层 ───────────────────────────────┐
│  7 个业务事件触发点 · 三态分流 · 字段补全       │  ← 判断
└───────────────────────────────────────────────┘
  ↑
┌─ L1 数据源层 ────────────────────────────────┐
│  EP · SAP · SZ · 试制系统 · 米Tab · 台账 · 预算  │  ← 数据
└───────────────────────────────────────────────┘
```

| 层 | 防什么 | 核心手段 | 失败后果 |
|----|--------|---------|---------|
| L1 数据源 | 数据不准 | 台账清洗 + 字段映射校验 | 上游数据错，下游全错 |
| L2 AI 识别 | 判断错分流 | 规则引擎 + 边界检测 + 反向校验 | 走错执行路径 |
| L3 能力层 | 执行错动作 | CLI/Skill 确定性执行 + Agent Role 约束 | 订单数据错误 |
| L4 业务闭环 | 异常漏网 | 异常队列 + 降级机制 + 人工兜底 | 错误订单流入下游 |

## 三、L2 识别层：7 个触发点与三态分流

### 3.1 七个触发点

| 触发点 | 事件 | Agent 判断什么 | 卡控方式 |
|--------|------|--------------|---------|
| 01 需求接入 | 多源需求到达 | 归集到哪个项目/车型 | 米Tab 编码映射校验 |
| 02 字段补全 | 缺字段 | 该补什么值 | 映射表查表补全（确定性） |
| 03 价格匹配 | 字段完整 | 有价/无价/一品多点？ | **规则引擎三态分流** |
| 04 供应商推荐 | 一品多点 | 推荐哪个供应商 | Agent 推荐 + 采购员强制确认 |
| 05 下单触发 | 规则命中 | 该推哪个系统 | 三策略分流 + 人工闸门 |
| 06 升版检测 | V2 启动 | 何时撤 V1 | V2 确认后才撤 V1 |
| 07 进度查询 | 查询请求 | 查询意图解析 | 路由表 + Schema |

### 3.2 三态分流

```
价格匹配
  ├─ 有价格 ──→ 直接进入下单流程
  ├─ 无价格 ──→ 触发定价任务，阻塞流程
  └─ 一品多点 ──→ Agent 推荐 → 采购员强制确认
```

三态分流由**规则引擎**执行，不是 LLM 判断。规则引擎看的是台账中的确定性字段（有无价格、供应商数量），不存在"理解错"的可能。

### 3.3 怎么保证匹配都对？

规则引擎本身不会"幻觉"，但**规则可以写错、数据可以喂错、边界可以漏掉**。这是另一层意义上的"幻觉"——不是 LLM 编造，而是系统性错误。

#### 问题一：规则本身对不对？

| 风险 | 举例 | 保障手段 |
|------|------|---------|
| 规则写反 | "有价格"和"无价格"的判断条件搞反了 | **Golden Set 测试**：用 100 条已知结果的历史数据回归测试规则 |
| 边界漏掉 | 价格为 0 但有软模费，该算"有价"还是"无价"？ | **边界用例库**：专门维护一批边界 case，每次规则变更必须全过 |
| 规则冲突 | 两条规则同时命中，结果不确定 | **优先级 + 互斥设计**：规则引擎必须有明确的优先级和冲突处理机制 |

```
Golden Set 示例：
  物料A：台账有价格 ¥12.5    → 预期"有价"   → 实际"有价"   ✅
  物料B：台账无价格记录       → 预期"无价"   → 实际"无价"   ✅
  物料C：台账有价格 ¥0（软模）→ 预期"无价"   → 实际"有价"   ❌ 规则有 bug
  物料D：2 家供应商都有价格   → 预期"一品多点"→ 实际"有价"   ❌ 规则漏了多供应商场景
```

#### 问题二：数据喂进来之前对不对？

规则引擎再准，数据脏了一样错。所以**数据质量是匹配准确率的天花板**：

| 数据问题 | 对匹配的影响 | 保障手段 |
|---------|------------|---------|
| 台账价格为 0 | 把"有价"误判为"无价" | 数据清洗：价格 ≤ 0 标记为无效，不参与匹配 |
| 供应商编码重复 | 把"一品多点"误判为"单点" | 去重合并：同一供应商多条记录合并 |
| 字段缺失 | 规则引擎无法判断 | 字段完整性校验：缺失字段阻塞匹配，不猜测 |
| 编码映射错 | 物料对应到错误的台账记录 | 映射校验：新映射关系必须人工确认后才生效 |

**关键洞察**：匹配准确率 = 规则准确率 × 数据准确率。规则 100% 准确但数据只有 90% 准确，最终匹配也只有 90%。**数据清洗的 ROI 往往高于规则优化**。

#### 问题三：边界 case 怎么处理？

规则引擎处理不了的 case 不应该硬判，而应该**显式标记为"不确定"**，转人工：

```
三态分流增加第四态：

  ├─ 有价格 ──→ 自动进入下单
  ├─ 无价格 ──→ 触发定价任务
  ├─ 一品多点 ──→ Agent 推荐 + 强制确认
  └─ 不确定 ──→ 转人工判断（新增）
       触发条件：规则置信度低 / 数据异常 / 边界 case
```

**不要让规则引擎在不确定时硬选一条路**。"不确定"本身就是一种有价值的判断——它告诉系统"这里需要人来看"。

#### 问题四：规则怎么迭代不出错？

| 手段 | 做法 | 目的 |
|------|------|------|
| **Shadow Mode** | 新规则上线时不实际生效，只记录判断结果，和旧规则对比 | 无风险验证新规则 |
| **A/B 分流** | 10% 流量走新规则，90% 走旧规则，对比准确率 | 渐进式上线 |
| **规则版本化** | 每次规则变更有版本号，可回滚 | 出问题秒级回滚 |
| **变更审批** | 规则变更需双人审批（写规则的人不能自己审批） | 防止个人错误 |

## 四、Agent Role 设计：给 Agent 划底线

Agent 不是"什么都能干的万能助手"，而是**有明确角色、底线和边界的执行者**。设计 Agent 时必须定义清楚三件事：它是什么角色、它的底线在哪、它什么时候必须停下来。

### 4.1 Agent Role 定义模板

```yaml
agent:
  name: 样件订单 Agent
  role: 订单流程自动化执行者（不是决策者）

  # 底线：这些规则不可被任何 prompt 覆盖
  red_lines:
    - "不得在未收到人工确认的情况下推送 SAP/SZ"
    - "不得在一品多点场景中自主选择供应商"
    - "不得在 V2 未确认时撤销 V1"
    - "不得修改已发货状态的订单"
    - "不得将不确定的匹配结果硬判为确定"

  # 能力边界：Agent 只能做这些事
  allowed_actions:
    - 归集需求到项目/车型
    - 调用 Skill 执行字段补全
    - 调用规则引擎执行三态分流
    - 推荐供应商（附数据来源）
    - 组装订单信息（供人工确认）
    - 推送订单到 SAP/SZ（仅在人工确认后）
    - 查询订单状态和进度

  # 禁止动作：Agent 绝对不能做这些事
  prohibited_actions:
    - 自主决定供应商选择
    - 静默执行任何写操作
    - 修改价格（价格来自框架协议）
    - 判断需求是否该取消（只能建议）
    - 覆盖规则引擎的判断结果

  # 升级条件：遇到这些情况必须停下来
  escalation_triggers:
    - "规则引擎返回'不确定'"
    - "数据校验不通过"
    - "同一需求连续 3 次匹配失败"
    - "金额超过阈值"
    - "涉及已发货/已收货状态的变更"
```

### 4.2 Red Line 的工程实现

Red Line 不能只写在 prompt 里（prompt 可以被越狱），必须在**多个层面同时约束**：

| 层面 | 实现方式 | 效果 |
|------|---------|------|
| **Prompt 层** | system prompt 声明 red line | 最弱——LLM 可能忽略 |
| **Skill 层** | Skill 代码中硬编码前置检查 | 中等——Skill 内部可控 |
| **MCP/工具层** | 工具侧做权限校验（如 SAP 推送接口要求 confirm_token） | 最强——工具不接受未确认的调用 |
| **状态机层** | 状态机不允许非法状态转换 | 最强——物理上不可能 |

**最佳实践**：Red Line 至少在两个层面同时约束。比如"不可静默下单"，既要 prompt 声明，也要 SAP 接口要求 confirm_token——即使 LLM 忽略了 prompt，SAP 接口也会拒绝。

### 4.3 Agent 的"自知之明"

好的 Agent 应该知道自己的能力边界，而不是什么都尝试：

```
Agent 的自我认知：
  "我是订单流程的自动化执行者，不是决策者。
   我可以推荐、可以组装、可以查询、可以执行已确认的操作。
   但我不能替人做选择，不能在不确定时硬选一条路。
   遇到我的能力边界，我会停下来告诉人，而不是自己瞎猜。"
```

这不只是 prompt 工程，更是一种**产品设计哲学**：Agent 的价值不在于"什么都能干"，而在于"该干的干得好，不该干的知道停"。

## 五、反向校验：输出不只看"生成了什么"

正向校验是"输入合法→执行→输出"，反向校验是**"拿输出反推回去，看和输入是否对得上"**。这是工程上最容易忽略、但最有价值的反幻觉手段。

### 5.1 什么是反向校验

```
正向流程：
  需求（物料A × 500）→ Agent 组装 → 订单信息 → 推送 SAP

反向校验：
  SAP 返回的订单 → 读出来 → 和原始需求比对
    物料对不对？→ 物料A ✅
    数量对不对？→ 500 ✅
    供应商对不对？→ 确认的供应商 ✅
  全部一致 → 确认成功
  有不一致 → 报警 + 回滚
```

**本质**：不信任 Agent 的中间过程，只信任系统侧的最终结果。

### 5.2 订单场景的反向校验点

| 执行动作 | 正向（Agent 做的） | 反向（系统验证的） | 不一致怎么办 |
|---------|------------------|------------------|------------|
| 字段补全 | Agent 调映射表补了"项目编码" | 回读映射表，确认补全值正确 | 退回人工补全 |
| 价格匹配 | 规则引擎判断"有价" | 回读台账，确认价格字段非空 | 重新匹配 |
| 供应商推荐 | Agent 推荐供应商 X | 回查供应商 X 的资质状态 | 撤回推荐 |
| 创建订单 | 推送 SAP 创建 PO-xxx | 回读 PO-xxx，比对所有字段 | 报警 + 回滚 |
| 升版执行 | V2 生效 + V1 撤销 | 回查 V1 状态确认已撤、V2 状态确认生效 | 回滚升版 |

### 5.3 反向校验的三种模式

| 模式 | 做法 | 适用场景 | 代价 |
|------|------|---------|------|
| **即时回读** | 执行后立即回读结果比对 | 每个写操作（创建、修改、升版） | 增加一次查询 |
| **批量对账** | 定期批量比对 Agent 输出和系统实际状态 | 发现延迟性错误 | 需要对账引擎 |
| **下游验证** | 从下游系统（SAP/SZ）反查，而不是看 Agent 的输出 | 发现 Agent 记录和实际执行不一致 | 最可靠但最慢 |

**推荐组合**：即时回读（保每笔正确）+ 批量对账（发现系统性问题）。

### 5.4 反向校验的工程实现

```yaml
# 反向校验配置
reverse_validation:
  create_order:
    trigger: "SAP 返回订单号后"
    action: "回读订单，逐字段比对"
    fields_to_check: [supplier, sku, quantity, price, delivery_date]
    on_mismatch: "报警 + 自动回滚 + 进异常队列"

  field_completion:
    trigger: "字段补全完成后"
    action: "回读映射表，确认补全值"
    on_mismatch: "标记为'补全不确定'，转人工"

  supplier_recommendation:
    trigger: "推荐生成后"
    action: "回查供应商资质、历史交期数据"
    on_mismatch: "降级推荐置信度，附加风险提示"
```

## 六、两道人工闸门

### 闸门一：需求锁定

```
需求创建（草稿）
  ↓
  ┌─ 闸门 ────────────────────────────────┐
  │  需求必须处于"锁定"状态才能进入下游     │
  │  未锁定 → 阻塞                         │
  │  修改 → 解锁→改→重新锁定（留版本备注）  │
  └─────────────────────────────────────────┘
  ↓
价格匹配 / 订单生成
```

防止 Agent 在需求还在变动时就触发下游流程。需求是源头，源头不稳，下游全乱。

### 闸门二：下单前人工确认

```
价格匹配完成 + 供应商确认
  ↓
  ┌─ 闸门 ────────────────────────────────┐
  │  推送 SAP/SZ 前必须人工确认             │
  │  A策略也不可静默执行                    │
  │  确认留痕：谁、什么时候、什么内容        │
  └─────────────────────────────────────────┘
  ↓
推送 SAP/SZ
```

即使 A 策略全自动，推送动作本身必须由人触发。这是最后一道防线。

## 七、订单状态机：越往后越紧

### 8 个主状态

```
需求创建(草稿) → 需求锁定 → 价格匹配 → 下单确认 → 已下单 → 已发货 → 已收货 → 完成关闭
```

### 状态约束矩阵

| 状态 | Agent 能干什么 | Agent 不能干什么 | 变更方式 |
|------|--------------|----------------|---------|
| ① 草稿 | 自由修改所有字段 | — | 直接改 |
| ② 锁定 | 读取需求，触发匹配 | 修改字段 | 解锁→改→重新锁定 |
| ③ 价格匹配 | 三态分流、推荐供应商 | 自主选择供应商 | 推荐 + 强制确认 |
| ④ 下单确认 | 组装订单信息 | 静默推送 SAP/SZ | 人工确认后推送 |
| ⑤ 已下单 | 追踪状态 | 直接修改订单 | 走升版 V2 |
| ⑥ 已发货 | 查询物流 | 取消订单 | 仅换货/补发 |
| ⑦ 已收货 | 查询收货状态 | 修改任何内容 | 走退货退款流程 |
| ⑧ 完成关闭 | 只读 | 任何写操作 | 终态，不可变 |

### 升版时序约束

```
V1 保持生效 → V2 确认后 → V2 生效 + V1 撤销
```

Agent 不能在 V2 未确认时就撤 V1，否则下游订单失效。

## 八、三种实现形态的反幻觉设计

| 形态 | 适用场景 | 确定性 | 反幻觉手段 |
|------|---------|--------|----------|
| **CLI** | 数据清洗、字段映射 | ⭐⭐⭐⭐⭐ | 输入输出完全确定，无 LLM |
| **Skill** | 规则引擎、价格匹配 | ⭐⭐⭐⭐⭐ | 规则确定性执行，无 LLM |
| **Agent** | 多源对接、供应商推荐、异常处理 | ⭐⭐⭐ | 靠 Role 约束 + 闸门 + 反向校验 |

**一句话**：能用 CLI/Skill 的不用 Agent。Agent 只做需要判断的事，但判断的结果必须有闸门兜底。

## 九、L4 闭环层：兜底机制

### 异常队列

| 异常类型 | 举例 | 处理方式 |
|---------|------|---------|
| 数据异常 | 台账价格为 0、重复记录 | 退回数据清洗 |
| 匹配异常 | 三态分流返回"不确定" | 转人工判断 |
| 执行异常 | SAP 推送失败 | 重试或人工介入 |
| 校验异常 | 反向校验不一致 | 报警 + 回滚 + 人工核查 |

### 准确率评估与降级

```
准确率 ≥ 95% → 继续自动执行
准确率 80%~95% → 提升人工复核比例
准确率 < 80% → 该环节退回人工处理
```

## 十一、通用原则总结

| # | 原则 | 含义 |
|---|------|------|
| 1 | **确定性优先** | 能用规则引擎不用 LLM，能用 CLI/Skill 不用 Agent |
| 2 | **闸门不可绕过** | 关键节点必须人工确认，Red Line 至少两层约束 |
| 3 | **越晚越严格** | 状态机后期约束更强，Agent 自由度递减 |
| 4 | **推荐不决策** | Agent 只能推荐，不能替人做最终决定 |
| 5 | **不确定就说不确定** | 边界 case 不硬判，显式转人工 |
| 6 | **反向校验** | 不信任中间过程，拿最终结果反推比对 |
| 7 | **数据质量是天花板** | 匹配准确率 = 规则准确率 × 数据准确率 |
| 8 | **异常不吞掉** | 所有异常进队列，不被 Agent 自行处理 |
| 9 | **可观测可降级** | 准确率可评估，表现差时可降级 |
| 10 | **规则变更要 Shadow** | 新规则先影子运行，验证后才生效 |
