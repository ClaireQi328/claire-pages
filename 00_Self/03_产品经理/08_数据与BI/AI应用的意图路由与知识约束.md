# AI 应用的意图路由与知识约束

> 不管是数据助手还是知识助手，核心问题都是"怎么让 LLM 不自由发挥"。路由表、语义层、Ontology、分析框架是四种不同层级的约束机制，理解它们的本质区别才能选对方案。

---

## 一、核心概念辨析

### 1.1 四种约束机制

| 维度 | 路由表（Routing Table） | 本体（Ontology） | 语义层（Semantic Layer） | 分析框架（Analysis Framework） |
|------|----------------------|-----------------|------------------------|----------------------------|
| **本质** | 分发机制 — 输入→走哪条路 | 世界模型 — 领域里有什么、关系是什么 | 业务语言→数据查询的翻译层 | 方法论 — 这类问题怎么分析 |
| **结构** | 扁平的 if-then 映射表 | 图：实体-关系-约束 | 指标+维度+度量定义 | 多步推理模板 |
| **回答的问题** | "用户问了 X，该调哪个查询？" | "采购单是什么？和供应商什么关系？" | "库存周转率怎么算？" | "交期恶化该怎么分析？" |
| **类比** | 交通指示牌 | 城市地图 | 翻译官 | 导航策略 |

**一句话区分**：

> 路由表告诉你"碰到什么走什么"，Ontology 告诉你"这个世界长什么样"，语义层告诉你"业务语言怎么变成查询"，分析框架告诉你"这类问题怎么拆解"。

### 1.2 四者的关系

```
Ontology（知识层）
│  实体、属性、关系、约束
│
├──→ 路由表（行为层）     ← 可从 Ontology 推导，意图可穷举时用
│
├──→ 语义层（翻译层）     ← Ontology 的工程化形态，指标查询用
│
└──→ 分析框架（方法层）   ← 复杂问题的推理路径，替代路由表处理开放意图
```

四者不是互斥关系，而是不同抽象层。路由表和分析框架是**行为层**（怎么做），Ontology 和语义层是**知识层**（是什么）。

## 二、路由表：确定性分发

### 2.1 典型结构

路由表的核心是**意图→执行路径**的确定性映射。两个领域的对比：

#### 数据助手（供应链）

| 意图 ID | 触发模式 | 查询模板 | 必要槽位 | 输出格式 |
|---------|---------|---------|---------|---------|
| `INV_QUERY` | 库存、在库、呆滞 | `SELECT * FROM inventory WHERE sku={sku}` | `sku` | 表格 |
| `PO_STATUS` | 采购单、PO、到货 | `SELECT status FROM po WHERE po_no={po_no}` | `po_no` | 卡片 |
| `DEMAND_FC` | 预测、需求、销量 | `SELECT * FROM forecast WHERE sku={sku}` | `sku` | 图表 |
| `SUPPLIER_PERF` | 供应商、准时率 | `SELECT * FROM supplier_score WHERE supplier={s}` | `supplier` | 仪表盘 |

#### 知识助手（企业知识库）

| 意图 ID | 触发模式 | 知识域 | 必要槽位 | 输出格式 |
|---------|---------|--------|---------|---------|
| `POLICY_QUERY` | 制度、规定、流程、审批 | HR/行政知识库 | `topic` | 引用原文 |
| `TECH_SUPPORT` | 怎么操作、如何配置、报错 | IT 支持知识库 | `system`, `error` | 步骤指引 |
| `ONBOARDING` | 入职、新人、培训 | 新人引导知识库 | `role`, `dept` | 清单 |
| `PRODUCT_SPEC` | 参数、规格、兼容性 | 产品知识库 | `product_model` | 对比表 |
| `COMPLIANCE` | 合规、法规、标准 | 法务知识库 | `region`, `business` | 条款引用 |

**共同点**：不管是查数据还是查知识，路由表的本质都是**把开放的自然语言映射到确定的执行路径**。

**区别**：

| 维度 | 数据助手路由 | 知识助手路由 |
|------|------------|------------|
| 执行目标 | 模板化 SQL 查询 | RAG 检索 + 片段拼装 |
| 返回内容 | 结构化数据 | 非结构化文本片段 |
| 准确性保障 | SQL 模板确定 | 检索质量 + 引用溯源 |
| 槽位用途 | WHERE 条件 | 检索范围过滤 |

### 2.2 槽位约束

| 槽位名 | 数据助手示例 | 知识助手示例 |
|--------|------------|------------|
| `sku` | `SKU-XXXXXX`，必须存在于主数据 | — |
| `po_no` | `PO-XXXXXXXX`，必须存在 | — |
| `topic` | — | 员工手册/财务制度/安全规范，模糊匹配 |
| `product_model` | — | `Model-XXXX`，精确匹配或模糊确认 |
| `role` | — | 工程师/产品经理/销售，枚举值 |
| `region` | 仓库编码 `SH/BJ/GZ` | 法规辖区 `CN/EU/US` |

### 2.3 异常处理路由

| 条件 | 动作 | 数据助手示例 | 知识助手示例 |
|------|------|------------|------------|
| 意图置信度 < 0.7 | 反问确认 | "查库存还是采购单？" | "问的是报销制度还是采购流程？" |
| 槽位缺失 | 追问（最多 2 轮） | "查哪个 SKU？" | "哪个产品的规格？" |
| 查询无结果 | 未找到 + 修正建议 | "该 SKU 不存在" | "未找到相关制度，试试关键词 XX" |
| 结果过多 | 分页 + 摘要 | "共 128 条，先看汇总" | "找到 15 篇相关文档，最匹配的是…" |
| 意图不在表内 | 兜底 | "暂时处理不了" | "建议联系 HR/IT/法务" |

### 2.4 数据流向

```
用户输入
  ↓
AI 识别意图 + 提取槽位
  ↓
路由表匹配
  ↓
┌──────────────────────────────────┐
│  数据助手：模板化 SQL → 数据库    │
│  知识助手：RAG 检索 → 知识库      │
└──────────────────────────────────┘
  ↓
AI 转述结果（附引用/数据来源）
```

**核心原则**：AI 只做 3 件事 ——

| 步骤 | AI 干的活 | 不让 AI 干的活 |
|------|----------|--------------|
| ① 意图识别 | 自然语言→意图 ID | ❌ 自己决定查什么 |
| ② 槽位提取 | 对话中抽取结构化参数 | ❌ 推断/编造参数值 |
| ③ 结果转述 | 自然语言解读结果 | ❌ 自己"编"数据或知识 |

## 三、语义层：声明式翻译

### 3.1 工作原理

```
用户："上个月华东区的库存周转率是多少？"
         ↓
语义层定义：
  指标: inventory_turnover = COGS / AVG(inventory_value)
  维度: region, time_period, product_category
         ↓
LLM 基于元数据生成 SQL
```

这里**没有路由表**，LLM 基于语义层的元数据直接生成查询。

### 3.2 语义层的核心组件

| 组件 | 作用 | 供应链示例 | 知识助手类比 |
|------|------|-----------|------------|
| **指标（Metrics）** | 业务度量的标准化定义 | 库存周转率、OTD | 知识库中的"实体属性" |
| **维度（Dimensions）** | 分析切面 | 时间、区域、品类 | 知识分类标签 |
| **度量（Measures）** | 原子计算 | `SUM(cogs)` | — |
| **实体关系** | 关联 | 采购单→供应商 | 概念→定义→案例 |
| **约束** | 校验 | 日期范围、枚举值 | 文档版本、生效范围 |

> 注：语义层主要服务于数据查询场景。知识助手更多依赖 Ontology + RAG，而非语义层。

### 3.3 语义层 vs 路由表

| 对比 | 路由表 | 语义层 |
|------|--------|--------|
| **定义方式** | 人工写意图→SQL 映射 | 声明指标+维度，引擎编译 |
| **覆盖范围** | 预定义的 N 种意图 | 组合爆炸：指标×维度×筛选 |
| **维护成本** | 每加一个意图改一次表 | 加一个指标/维度，自动扩展 |
| **灵活性** | 低：问法变了要改表 | 高：任意组合查询 |
| **准确性** | 高：确定性模板 | 中：依赖 LLM 生成质量 |

## 四、什么时候用什么

### 4.1 选型决策树

```
用户意图可穷举？（< 20 种固定问题）
  ├─ 是 → 路由表（确定性高，维护成本高）
  └─ 否 → 场景类型？
            ├─ 数据查询 → 语义层 + Text-to-SQL
            ├─ 知识检索 → Ontology + RAG
            └─ 复杂分析 → 分析框架 + Agent
```

### 4.2 场景对照

| 场景 | 用路由表？ | 更合适的方案 |
|------|-----------|------------|
| 事务型查询（查单据、查状态） | ✅ 适合 | 路由表 + 模板化 SQL |
| 固定知识查询（制度、FAQ） | ✅ 适合 | 路由表 + RAG 检索 |
| 指标查询（周转率、OTD） | ❌ 不适合 | 语义层 + Text-to-SQL |
| 知识检索（跨文档关联） | ❌ 不适合 | Ontology + RAG |
| 探索性分析（根因、趋势） | ❌ 不适合 | 分析框架 |
| 开放探索（风险全景） | ❌ 不适合 | Agent 自主规划 |

### 4.3 演化路径

```
阶段 1：路由表
  - 意图 < 20 种，人工维护
  - 确定性高，但扩展性差

      ↓ 语义层 / Ontology 建设

阶段 2：混合模式
  - 简单查询走路由表（40%）
  - 指标/知识检索走语义层/RAG（40%）
  - 复杂分析走分析框架（15%）
  - 兜底（5%）

      ↓ 语义层 / Ontology 成熟

阶段 3：知识驱动
  - 路由表被吸收为高频查询缓存
  - Ontology 驱动自动路由
  - 分析框架处理复杂意图
```

## 五、有 Ontology 还需要路由表吗？

### 5.1 Ontology 的盲区

Ontology 知道"世界长什么样"，但不知道"这道题怎么解"：

| 维度 | Ontology 能覆盖？ | 复杂分析还需要什么 |
|------|------------------|-----------------|
| 实体定义 | ✅ 采购单、供应商、物料 | — |
| 关系定义 | ✅ 采购单→属于→供应商 | — |
| 知识分类 | ✅ 制度→财务制度→报销制度 | — |
| 分析路径 | ❌ | 跨 3 张表怎么 JOIN？先算什么后算什么？ |
| 业务规则 | ❌ | 呆滞库存判定标准？安全库存公式？ |
| 推理编排 | ❌ | 多步推理的顺序和分支逻辑 |

### 5.2 分析框架：路由表的替代品

Ontology 存在时，复杂问题的约束机制不应该是路由表（穷举意图），而是**分析框架（方法论）**：

```
Ontology（知识层）
│  实体、关系、指标、维度
│
├──→ 分析框架（方法层）        ← 路由表的替代品
│    ├── 根因分析：趋势→维度拆解→关联因素→排除法
│    ├── 对比分析：对标→差异→归因→建议
│    ├── 预警分析：阈值→异常→影响范围→处置建议
│    ├── 知识综合：多源检索→交叉验证→归纳→引用
│    └── 决策支持：方案枚举→优劣对比→推荐
│
└──→ 工具链（执行层）
     ├── SQL 生成器（数据助手）
     ├── RAG 检索器（知识助手）
     ├── 图表生成器
     └── 报告生成器
```

**路由表 vs 分析框架**：

| 维度 | 路由表 | 分析框架 |
|------|--------|---------|
| **粒度** | 一个意图一个模板 | 一种方法适配多个场景 |
| **维护** | 意图×场景 = 指数增长 | N 种方法覆盖 M 个场景（N ≪ M） |
| **扩展** | 新场景要加新映射 | 新场景复用已有方法组合 |
| **类比** | 每条路一个指示牌 | 一套导航策略到任意目的地 |

### 5.3 有 Ontology 时仍需路由表的场景

| 场景 | 为什么分析框架不够 | 路由表的作用 |
|------|-------------------|------------|
| **合规/审计查询** | 结果必须 100% 准确 | 确定性模板，零幻觉 |
| **高频固定查询** | LLM 每次重新推理浪费 token | 缓存高频路径 |
| **跨系统编排** | 涉及多个 API 调用顺序 | 预定义编排流程 |
| **权限控制** | 不同角色看到不同数据 | 路由时注入权限过滤 |

## 六、适配场景详解

### 6.1 数据助手：从简单到复杂

#### 场景 A1：单域查询（路由表 ✅）

> "PO-2026070012 的到货状态？"

```
意图匹配 → PO_STATUS
槽位提取 → po_no = "PO-2026070012"
模板执行 → SELECT status, eta FROM po WHERE po_no = ?
结果转述 → "该采购单已发货，预计 7/18 到达上海仓"
```

- 特点：意图明确、槽位少、查询确定
- 方案：路由表最稳

#### 场景 A2：指标查询（语义层 ✅）

> "华东区上个月的库存周转率是多少？"

```
语义层解析：
  指标 = inventory_turnover = COGS / AVG(inventory_value)
  维度 = region('华东'), time('2026-06')
SQL 生成 → 语义层引擎编译
结果转述 → "华东区 6 月库存周转率 4.2 次，环比下降 0.3 次"
```

- 特点：指标有标准定义，维度可任意组合
- 方案：语义层覆盖，路由表反而限制灵活性

#### 场景 A3：根因分析（分析框架 ✅）

> "A 供应商近半年交期为什么恶化？"

```
分析框架：根因分析模板
  Step 1 - 趋势确认 → 取 A 供应商 OTD 月度趋势
  Step 2 - 维度拆解 → 按品类、工厂、物料类型拆解
  Step 3 - 关联因素 → 关联产能、来料质量、物流
  Step 4 - 对比排除 → 同品类其他供应商表现
  Step 5 - 建议生成 → 基于业务规则输出改善建议
```

- 特点：多步推理、跨域关联
- 方案：Ontology 提供知识，分析框架提供方法

#### 场景 A4：跨系统编排（路由表 ✅）

> "帮我给 A 供应商发一封交期催办邮件，并更新 ERP 预计到货日"

```
意图匹配 → SUPPLIER_FOLLOWUP
编排流程：
  Step 1 → 调用邮件 API 发送催办
  Step 2 → 调用 ERP API 更新预计到货日
  Step 3 → 写入跟进记录
权限校验 → 当前用户是否有供应商跟进权限
```

- 特点：涉及写操作、多系统、需要权限控制
- 方案：路由表定义编排流程

#### 场景 A5：开放探索（Agent）

> "帮我看看供应链整体有什么风险点"

```
Agent 自主规划：
  Step 1 → 查看库存异常（呆滞、超储、缺货）
  Step 2 → 查看供应商风险（交期恶化、质量下降）
  Step 3 → 查看需求波动（预测偏差、紧急订单比例）
  Step 4 → 汇总 Top 5 风险点 + 建议
```

- 特点：开放性问题，没有标准答案
- 方案：Agent 自主规划，Ontology 提供知识约束

### 6.2 知识助手：从简单到复杂

#### 场景 B1：FAQ 查询（路由表 ✅）

> "年假有多少天？"

```
意图匹配 → POLICY_QUERY
槽位提取 → topic = "年假"
RAG 检索 → 员工手册 §4.3 带薪年假
结果转述 → "入职满 1 年享有 5 天年假，满 10 年 10 天，满 20 年 15 天"
引用来源 → 员工手册 v3.2 §4.3
```

- 特点：问题标准、答案明确、需要引用原文
- 方案：路由表定位知识域 + RAG 精确检索

#### 场景 B2：操作指引（路由表 + RAG）

> "怎么配置 VPN？"

```
意图匹配 → TECH_SUPPORT
槽位提取 → system = "VPN", action = "配置"
RAG 检索 → IT 支持知识库 → VPN 配置指南
结果转述 → 分步骤指引（附截图引用）
兜底 → "如果仍有问题，提交 IT 工单 [[xxx]]"
```

- 特点：需要步骤化输出、可能附带截图
- 方案：路由表定位 + RAG 检索 + 结构化输出模板

#### 场景 B3：跨文档综合（Ontology + RAG）

> "我们公司在数据安全方面有哪些合规要求？分别适用于什么场景？"

```
Ontology 知道：
  数据安全 → 包含 → 数据分类、访问控制、加密、审计
  合规要求 → 来源 → 国家法规、行业标准、内部制度
  适用场景 → 按 → 数据类型、业务线、地区 区分

RAG 检索：
  → 信息安全管理制度（内部）
  → 个人信息保护法相关条款（外部）
  → ISO 27001 相关要求（外部）

综合输出：
  → 按数据分类分级整理要求
  → 标注每条要求的来源和适用范围
  → 标注内部制度与外部法规的对应关系
```

- 特点：需要跨多篇文档综合、需要结构化组织
- 方案：Ontology 提供知识结构，RAG 检索内容，分析框架组织输出

#### 场景 B4：决策支持（分析框架 ✅）

> "我们团队应该用 A 工具还是 B 工具？帮我做个对比分析"

```
分析框架：对比分析模板
  Step 1 - 需求澄清 → 追问使用场景、团队规模、预算
  Step 2 - 维度枚举 → 功能、成本、学习曲线、生态、安全
  Step 3 - 信息检索 → RAG 检索两个工具的产品文档 + 内部使用反馈
  Step 4 - 对比矩阵 → 逐维度打分
  Step 5 - 推荐 → 基于场景给出推荐 + 理由
```

- 特点：需要结构化对比、需要结合内部实际情况
- 方案：分析框架驱动，Ontology + RAG 提供信息

#### 场景 B5：知识探索（Agent）

> "帮我梳理一下公司现有的所有数据分析相关工具和它们的使用场景"

```
Agent 自主规划：
  Step 1 → 检索工具清单（IT 资产库、采购记录）
  Step 2 → 检索每个工具的使用文档和场景说明
  Step 3 → 按场景分类（BI、ETL、数据治理、AI/ML）
  Step 4 → 生成工具全景图 + 使用建议
```

- 特点：开放性问题，需要跨域检索和自主组织
- 方案：Agent 自主规划，Ontology 提供知识结构

### 6.3 跨域场景：数据 + 知识联动

实际业务中，数据查询和知识检索经常交织：

| 场景 | 数据部分 | 知识部分 | 联动方式 |
|------|---------|---------|---------|
| "这个物料的质检不合格率是多少？质检标准是什么？" | 查质检数据 | 查质检标准文档 | 先查数据，再用物料类型检索标准 |
| "供应商 A 的绩效评分是多少？我们的供应商管理办法怎么规定的？" | 查评分 | 查管理办法 | 数据+知识并行，结果对照 |
| "上季度采购成本超预算了，预算管理办法里怎么处理？" | 查预算执行 | 查预算管理办法 | 数据触发问题，知识给出处理流程 |
| "这个产品的退货率异常高，质量追溯流程是什么？" | 查退货数据 | 查追溯 SOP | 数据定位问题，知识给出行动方案 |

这类场景的处理模式：

```
用户输入
  ↓
意图分类器
  ├─ 纯数据 → 数据路由
  ├─ 纯知识 → 知识路由
  └─ 混合 → 拆分子意图
              ├─ 子意图 1 → 数据路由 → 结构化结果
              └─ 子意图 2 → 知识路由 → 文档片段
              ↓
           结果合并 → 综合回答
```

### 6.4 场景方案速查

| 场景 | 意图确定性 | 推理复杂度 | 推荐方案 | 路由表？ |
|------|----------|----------|---------|---------|
| A1. 查单据状态 | 高 | 低 | 路由表 + 模板 SQL | ✅ |
| A2. 查指标数据 | 中 | 低 | 语义层 + Text-to-SQL | ❌ |
| A3. 根因/对比分析 | 低 | 高 | Ontology + 分析框架 | ❌ |
| A4. 跨系统操作 | 高 | 中 | 路由表 + 编排 | ✅ |
| A5. 开放探索 | 低 | 高 | Agent + Ontology | ❌ |
| B1. FAQ/制度查询 | 高 | 低 | 路由表 + RAG | ✅ |
| B2. 操作指引 | 高 | 低 | 路由表 + RAG + 模板 | ✅ |
| B3. 跨文档综合 | 中 | 高 | Ontology + RAG | ❌ |
| B4. 决策支持 | 低 | 高 | 分析框架 + RAG | ❌ |
| B5. 知识探索 | 低 | 高 | Agent + Ontology | ❌ |
| 联动. 数据+知识 | 中 | 高 | 意图拆解 + 混合路由 | 部分 |

### 6.5 混合架构：实际产品怎么组合

成熟产品通常是**多种方案并存**：

```
用户输入
  ↓
┌─────────────────────────────────────────┐
│         意图分类器（轻量 LLM）            │
└──┬──────┬──────┬──────┬──────┬──────────┘
   ↓      ↓      ↓      ↓      ↓
事务查询 指标查询 知识检索 分析类  开放类
   ↓      ↓      ↓      ↓      ↓
路由表   语义层   RAG   分析框架  Agent
   ↓      ↓      ↓      ↓      ↓
模板SQL  编译SQL  检索   多步推理 自主规划
   ↓      ↓      ↓      ↓      ↓
└─────────────────────────────────────────┐
│         结果转述（统一 LLM）              │
└─────────────────────────────────────────┘
```

典型配比：

| 查询类型 | 数据产品占比 | 知识助手占比 | 方案 | 准确性要求 |
|---------|------------|------------|------|----------|
| 事务/FAQ 查询 | ~40% | ~35% | 路由表 | 100% |
| 指标/文档检索 | ~30% | ~30% | 语义层 / RAG | 95%+ |
| 综合分析 | ~20% | ~25% | 分析框架 | 85%+ |
| 开放探索 | ~10% | ~10% | Agent | 70%+ |

## 七、Text-to-SQL 与 RAG：没有路由表的方案

### 7.1 Text-to-SQL（数据助手）

| 组件 | 作用 | 类比 |
|------|------|------|
| 数据库 Schema | 表结构、字段注释 | 轻量 Ontology |
| 示例 SQL（few-shot） | 教 LLM 怎么写 | 隐式路由 |
| 查询校验层 | 拦截危险/错误 SQL | 安全兜底 |
| 语义层 | 指标+维度定义 | 业务翻译 |

### 7.2 Ontology + RAG（知识助手）

| 组件 | 作用 | 类比 |
|------|------|------|
| 知识图谱 / Ontology | 概念关系、分类体系 | 轻量 Ontology |
| 向量数据库 | 文档片段语义检索 | 隐式路由 |
| 重排序器 | 精排检索结果 | 质量保障 |
| 引用溯源 | 标注答案来源 | 可信度保障 |

### 7.3 元数据即路由

没有显式路由表时，**元数据本身就是路由信息**：

**数据助手**：
- 表注释 → "这张表是干什么的"
- 字段注释 → "这个字段代表什么业务含义"
- 示例 SQL → "这类问题怎么查"

**知识助手**：
- 文档标题/摘要 → "这篇文档讲什么"
- 文档分类标签 → "属于哪个知识域"
- 目录结构 → "知识的层级关系"

本质上是把路由表的信息**分散到了元数据中**，由 LLM 自行推理组合。

## 八、总结

| 问题 | 答案 |
|------|------|
| 一定有路由表吗？ | 不一定。语义层/元数据足够好时不需要 |
| 路由表和 Ontology 的区别？ | 路由表是行为（怎么做），Ontology 是知识（是什么） |
| 数据助手和知识助手的路由区别？ | 本质相同，执行目标不同（SQL vs RAG） |
| 有 Ontology 还要路由表吗？ | 大多数不需要，但需要分析框架替代 |
| 路由表的真正替代品是什么？ | 不是 Ontology，而是分析框架（方法层） |
| 什么时候用路由表？ | 意图可穷举、确定性要求高、语义层未建成时 |
| 路由表什么时候死不了？ | 合规审计、高频查询、跨系统编排、权限控制 |
| 数据+知识混合场景怎么处理？ | 意图拆解→分域路由→结果合并 |
| 实际产品怎么组合？ | 意图分类器→分发到路由表/语义层/RAG/分析框架/Agent |
