> 路线图不是承诺，是对当前认知的最佳表达。—— Melissa Perri

---

## 一、路线图的演变：从 Timeline 到 Outcome-based

### 传统 Timeline 路线图的问题

| 问题 | 表现 | 后果 |
|------|------|------|
| 承诺错觉 | 日期写死了就变成承诺 | 团队被迫赶工，质量下降 |
| 输出导向 | "Q3 做完搜索功能" | 做完了但没解决问题 |
| 灵活性差 | 市场变了但路线图没变 | 执行过时的计划 |
| 信任崩塌 | 频繁延期 | 利益相关者不再信任路线图 |

### Now-Next-Later 路线图

替代 Timeline 的轻量方案，核心思想是**用确定性程度而非时间来分层**：

```
┌─────────────────┬──────────────────┬──────────────────┐
│      NOW         │      NEXT         │      LATER        │
│   正在做          │   接下来做         │   未来可能做       │
│   确定性 >90%     │   确定性 60-90%    │   确定性 <60%      │
├─────────────────┼──────────────────┼──────────────────┤
│ 细化到 User      │ 细化到 Epic       │ 细化到 Theme       │
│ Story 级别       │ 级别              │ 级别              │
│                  │                   │                   │
│ • 团队正在开发    │ • 已排期但未开始    │ • 战略方向但未定义  │
│ • 范围基本锁定    │ • 范围可能调整      │ • 范围高度灵活     │
│ • 影响当前 OKR    │ • 影响下一周期 OKR  │ • 影响长期愿景     │
└─────────────────┴──────────────────┴──────────────────┘
```

#### 实践要点

| 原则 | 说明 |
|------|------|
| **Now 不超过 4-6 周** | 超过就变成了伪确定性 |
| **Next 是 1-3 个月** | 有清晰的 Why，How 还在探索 |
| **Later 是方向性** | 只有 Theme 和假设，没有具体方案 |
| **定期重新分类** | 每 2-4 周 review，Later 的可能升到 Next，Next 的可能降级 |
| **不是堆积** | Now 最多 3-5 项，Next 最多 5-8 项 |

### Outcome-based Roadmap（基于结果的路线图）

最高级的路线图形态：每个条目都是一个**期望结果**，而非功能输出。

| 维度 | Output-based | Outcome-based |
|------|-------------|---------------|
| 条目示例 | "增加导出功能" | "将用户月活从 40% 提升到 60%" |
| 成功标准 | 功能上线 | 指标改善 |
| 团队自主性 | 低（照做就行） | 高（自己想方案） |
| 变更成本 | 高（功能做了一半不能砍） | 低（换个方案还能达成目标） |
| 适合阶段 | 需求明确、执行阶段 | 探索阶段、PMF 前后 |

#### Outcome-based Roadmap 模板

```
主题 1：提升新用户激活率
  当前状态：注册到激活 25%
  目标状态：注册到激活 45%
  成功指标：7 日激活率
  信心水平：Medium（60%）
  选项池：
    - [ ] 引导流程优化
    - [ ] 模板预填充
    - [ ] 邀请同事激励
  当前选择：引导流程优化（已验证假设）

主题 2：企业客户续费率
  当前状态：年续费率 72%
  目标状态：年续费率 85%
  成功指标：12 月续费率
  信心水平：Low（40%）
  选项池：
    - [ ] 客户成功团队建设
    - [ ] 用量预警系统
    - [ ] 季度业务 Review
```

## 二、Theme-based Roadmap

在 Now-Next-Later 基础上，用 Theme（主题）组织路线图条目，确保与战略对齐。

### Theme 的来源

| 来源 | 示例 |
|------|------|
| **战略目标** | "进入企业市场" → Enterprise Theme |
| **用户痛点** | "协作效率低" → Collaboration Theme |
| **业务指标** | "留存率不足" → Retention Theme |
| **技术约束** | "系统不稳定" → Reliability Theme |

### Theme 分配原则

| 原则 | 说明 |
|------|------|
| **不超过 3-4 个 Theme** | 超过就失去聚焦 |
| **分配资源比例** | 如 60% 核心主题 + 20% 增长 + 20% 基础设施 |
| **每个 Theme 有 Owner** | 明确负责人和度量指标 |
| **Theme 之间有优先级** | 不是平等的 |

## 三、优先级框架深度对比

### RICE 框架

| 维度 | 说明 | 评分方式 |
|------|------|---------|
| **Reach（覆盖面）** | 多少用户/客户会受到影响 | 绝对数字，如"每季度 1000 个用户" |
| **Impact（影响力）** | 对每个用户的影响程度 | 3=巨大 2=高 1=中 0.5=低 0.25=极低 |
| **Confidence（信心）** | 对估算的把握程度 | 100%/80%/50%（低于 50% 需要先验证） |
| **Effort（工作量）** | 需要多少人月 | 以人月为单位，如 0.5 人月 |

**计算公式**：RICE Score = (Reach x Impact x Confidence) / Effort

**适用场景**：功能级优先级排序，有数据支撑的成熟产品

### ICE 框架

| 维度 | 说明 | 评分方式 |
|------|------|---------|
| **Impact（影响力）** | 对核心指标的影响 | 1-10 分 |
| **Confidence（信心）** | 对成功的把握 | 1-10 分 |
| **Ease（容易度）** | 实施难度（越容易分越高） | 1-10 分 |

**计算公式**：ICE Score = Impact x Confidence x Ease

**适用场景**：增长实验、A/B 测试优先级，数据不足时的快速评估

### WSJF 框架（SAFe）

| 维度 | 说明 | 评分方式 |
|------|------|---------|
| **User/Business Value** | 对用户/业务的价值 | Fibonacci: 1/2/3/5/8/13/21 |
| **Time Criticality** | 时间紧迫度 | Fibonacci |
| **Risk Reduction** | 降低的风险 | Fibonacci |
| **Job Size** | 工作量 | Fibonacci |

**计算公式**：WSJF = (User Value + Time Criticality + Risk Reduction) / Job Size

**适用场景**：SAFe 框架下的 PI Planning，大型组织的 Epic 优先级

### MoSCoW 框架

| 分类 | 含义 | 比例建议 |
|------|------|---------|
| **Must Have** | 没有就不发布 | ~60% 的资源 |
| **Should Have** | 重要但可以有 workaround | ~20% |
| **Could Have** | 锦上添花 | ~20% |
| **Won't Have (this time)** | 明确不做 | - |

**适用场景**：版本发布范围界定、利益相关者沟通

### Kano 模型

| 类型 | 定义 | 识别方式 | 产品策略 |
|------|------|---------|---------|
| **Must-be（必备）** | 没有会不满，有了不加分 | 用户认为理所当然 | 必须做到位 |
| **One-dimensional（线性）** | 越好越满意 | 线性关系 | 持续优化 |
| **Attractive（魅力）** | 没有不不满，有了会惊喜 | 用户没想到 | 差异化来源 |
| **Indifferent（无差异）** | 有没有都行 | 无相关性 | 不投入 |
| **Reverse（反向）** | 有了反而不满 | 负相关 | 避免做 |

**适用场景**：新功能决策、差异化策略、理解用户真实需求

## 四、框架选择决策矩阵

| 场景 | 推荐框架 | 原因 |
|------|---------|------|
| 成熟产品，有数据 | RICE | 数据驱动，减少主观判断 |
| 增长实验，快速迭代 | ICE | 简单快速，适合高频决策 |
| 大型组织，SAFe 体系 | WSJF | 与 SAFe 方法论对齐 |
| 版本范围界定 | MoSCoW | 利益相关者沟通友好 |
| 新功能决策 | Kano | 理解需求本质 |
| 战略级议题 | Weighted Scoring | 自定义维度，灵活度高 |

### 组合使用建议

```
第 1 层：战略对齐（Theme-based）
  └── 每个 Theme 是否与战略目标一致？不一致直接淘汰

第 2 层：需求类型判断（Kano）
  └── 这个功能属于 Must-be / Attractive / Indifferent？
  └── Indifferent → 不做

第 3 层：量化排序（RICE 或 ICE）
  └── 同一 Theme 内的功能用 RICE/ICE 量化排序

第 4 层：范围界定（MoSCoW）
  └── 这个版本 Must/Should/Could 各放多少？
```

## 五、反模式（Anti-Patterns）

### 反模式 1：功能投票（Feature Voting）

| 表面逻辑 | 实际问题 |
|---------|---------|
| "让用户投票决定做什么" | 最大声的用户不一定代表大多数 |
| "民主决策最公平" | 用户不知道什么对他们最好 |
| "票数多的优先做" | 淹没战略性但不受欢迎的决策 |

**替代方案**：用户反馈作为输入之一（不是唯一输入），结合数据分析和战略判断

### 反模式 2：HIPPO（Highest Paid Person's Opinion）

| 表面逻辑 | 实际问题 |
|---------|---------|
| "老板说的最重要" | 一个人的认知偏差决定产品方向 |
| "执行力强效率高" | 团队失去主动性，变成执行机器 |
| "老板见多识广" | 离用户最远的人做最多的决策 |

**替代方案**：数据驱动的决策流程，老板参与战略选择而非功能选择

### 反模式 3：资源驱动优先级

| 表面逻辑 | 实际问题 |
|---------|---------|
| "这个团队闲着，先做这个" | 资源错配，重要事项被搁置 |
| "这个容易做，先做" | 低价值的容易事排在高价值的难事前面 |
| "答应客户了，必须做" | 客户需求绑架产品战略 |

**替代方案**：先定优先级，再分配资源；不是资源决定做什么，而是做什么决定要什么资源

### 反模式 4：功能工厂（Feature Factory）

| 表面逻辑 | 实际问题 |
|---------|---------|
| "发版越多越好" | 输出导向，不关心结果 |
| "需求永远做不完" | 没有战略聚焦，什么都要做 |
| "做了就是进步" | 没有衡量功能是否真的有用 |

**替代方案**：Outcome-based roadmap，每个功能都有假设和成功标准

## 六、决策模板

### 优先级决策矩阵模板

**Step 1：评分**

| 功能/主题 | 用户价值 | 业务价值 | 技术风险 | 工作量(人周) | RICE 分数 |
|----------|:-------:|:-------:|:-------:|:----------:|:--------:|
| 示例功能 A | 8 | 7 | 3 | 4 | 140 |
| 示例功能 B | 6 | 5 | 5 | 2 | 75 |
| 示例功能 C | 4 | 3 | 2 | 1 | 30 |

**Step 2：决策**

| 功能/主题 | 战略对齐 | MoSCoW | 决策 |
|----------|:-------:|:------:|:----:|
| 示例功能 A | 高 | Must | 做 |
| 示例功能 B | 中 | Should | 做 |
| 示例功能 C | 低 | Won't | 不做 |

### 路线图 Review 检查清单

- [ ] 每个条目都有明确的 Why（为什么做）
- [ ] 每个条目都有成功标准（怎么算做完）
- [ ] Now/Next/Later 分类是否合理（Now 有没有超载）
- [ ] Theme 与战略目标对齐
- [ ] 资源分配与优先级一致
- [ ] 关键假设已识别并有验证计划
- [ ] 利益相关者已对齐（不是通知，是对齐）
- [ ] 有明确的"不做"清单

### 利益相关者沟通模板

```
本季度路线图重点

Theme 1: [名称]（占比 50%）
  目标：[指标从 X 到 Y]
  Now: [具体条目]
  Next: [具体条目]

Theme 2: [名称]（占比 30%）
  目标：[指标从 X 到 Y]
  Now: [具体条目]

明确不做：
  • [条目 + 原因]
  • [条目 + 原因]

风险与依赖：
  • [风险 + 缓解方案]
```

## 七、工具对比

| 工具 | 适合团队 | 核心优势 | 局限 | 价格 |
|------|---------|---------|------|------|
| **Linear** | 工程驱动团队 (10-100 人) | 极致速度、键盘操作、自动化 | 路线图功能弱 | $8/人/月 |
| **Shortcut** | 中型技术团队 | Epic/Story 层级清晰 | UI 不够现代 | $8.5/人/月 |
| **Productboard** | PM 团队 | 用户反馈→功能映射、路线图 | 贵、学习曲线高 | $25/人/月 |
| **Jira** | 大型企业 | 高度可定制、生态丰富 | 笨重、配置复杂 | $8.15/人/月 |
| **Notion** | 小团队/初创 | 灵活、多合一 | 缺乏专业 PM 功能 | $10/人/月 |
| **Miro** | 远程协作 | 可视化、白板路线图 | 不适合日常管理 | $10/人/月 |

### 工具选择建议

| 你的情况 | 推荐 |
|---------|------|
| 工程团队为主，追求效率 | Linear |
| PM 需要管理用户反馈 | Productboard |
| 大公司，已有 Atlassian 生态 | Jira + Productboard |
| 初创团队，预算有限 | Notion 或 Linear |
| 需要战略可视化 | Miro + 任何工单工具 |

## 八、优先级决策的组织保障
