# LLM 产品设计方法论

> 从模型选型到成本优化，AI 原生产品的核心设计决策框架。

---

## 一、模型选型决策树

### 1.1 选型三维度

| 维度 | 核心指标 | 低要求场景 | 高要求场景 |
|------|---------|-----------|-----------|
| **成本** | $/1M tokens | 内部工具、批量处理 | 面向用户的实时交互 |
| **延迟** | TTFT / TPS | 后台任务、异步生成 | 搜索、对话、代码补全 |
| **能力** | 推理/编码/多模态 | 简单分类、提取 | 复杂推理、长文档分析 |

### 1.2 决策树

```
用户是否实时等待？
├── 是 → 延迟优先
│   ├── 任务简单（分类/提取）→ Haiku / GPT-4o-mini / Gemini Flash
│   ├── 任务中等（摘要/问答）→ Sonnet / GPT-4o
│   └── 任务复杂（推理/编码）→ Opus / o3 / Claude Sonnet (extended thinking)
│
└── 否 → 成本优先
    ├── 批量处理 → 使用 Batch API（50% 折扣）
    ├── 非实时摘要 → 小模型 + 后处理
    └── 高质量输出 → 大模型，但 prompt caching 降本
```

### 1.3 实战案例

| 产品 | 选型策略 | 原因 |
|------|---------|------|
| **Perplexity** | Sonnet 级别 + 自研 ranking | 搜索场景延迟敏感，需要快速 first token |
| **Cursor** | 多模型路由：Tab 补全用小模型，Chat 用大模型 | 代码补全每秒触发，成本/延迟必须极致 |
| **Harvey AI** | Claude Opus + 定制 fine-tune | 法律场景零容错，质量优先于成本 |

### 1.4 模型路由（Model Routing）设计

高级产品不会只用一个模型，而是根据任务动态路由：

```python
# 伪代码：模型路由逻辑
def select_model(task):
    if task.complexity == "low" and task.latency_sensitive:
        return "claude-haiku"          # 最快最便宜
    elif task.complexity == "medium":
        return "claude-sonnet"         # 平衡之选
    elif task.requires_extended_thinking:
        return "claude-sonnet-ext"     # 深度推理
    elif task.quality_critical:
        return "claude-opus"           # 最高质量
    else:
        return "claude-sonnet"         # 默认
```

**产品设计要点**：
- 用户无感知：路由逻辑对用户透明，体验一致
- 降级策略：大模型不可用时自动 fallback 到小模型
- A/B 测试：持续验证路由策略的 ROI

## 二、幻觉治理策略

LLM 幻觉是 AI 产品的头号风险。治理需要多层防御。

### 2.1 三层防御体系

| 层级 | 策略 | 实现方式 | 适用场景 |
|------|------|---------|---------|
| **L1 预防** | Grounding | RAG 检索 + 上下文注入 | 知识问答、企业助手 |
| **L2 检测** | Citation / Attribution | 要求模型标注来源，后处理验证 | 搜索、研究报告 |
| **L3 兜底** | Human-in-the-Loop | 高风险输出需人工确认 | 医疗、法律、金融 |

### 2.2 Grounding 实践

Grounding 的核心是让模型"有据可依"：

```
# Prompt 中强制 grounding 的模板
你是一个企业知识助手。回答规则：
1. 只使用 <context> 标签中的信息回答
2. 如果上下文中没有相关信息，明确说"根据现有资料无法回答"
3. 引用时标注来源：[来源: 文档名称, 第X节]
4. 不要编造任何不在上下文中的信息

<context>
{retrieved_documents}
</context>

用户问题：{query}
```

### 2.3 Citation 设计

Perplexity 的 citation 模式值得学习：

| 设计要素 | Perplexity 做法 | 产品价值 |
|---------|----------------|---------|
| 内联引用 | 每个事实后标注 [1][2] | 用户可即时验证 |
| 来源列表 | 底部展示完整来源链接 | 建立信任 |
| 置信度 | 不显示数字，但选择性引用 | 避免过度承诺 |

**产品设计 Checklist**：
- [ ] 关键事实是否都有来源？
- [ ] 来源链接是否可点击？
- [ ] 无来源时是否有明确提示？
- [ ] 用户能否一键查看原始出处？

### 2.4 Human-in-the-Loop 分级

| 风险等级 | 输出类型 | 处理方式 | 示例 |
|---------|---------|---------|------|
| 低 | 通用问答 | 直接输出 | "帮我总结这篇文章" |
| 中 | 业务建议 | 输出 + 置信度标签 | "建议采购量为 X" |
| 高 | 关键决策 | 人工审核后才发布 | "合同条款修改建议" |
| 极高 | 合规/法务 | 多人审核 + 审计日志 | "法律意见书" |

## 三、评估体系

AI 产品的评估不能只靠"感觉"，需要系统化的评估体系。

### 3.1 评估三角

```
           自动评估
          /        \
         /    AI    \
        /   as Judge \
       /              \
  人工评估 ——————————— 用户指标
```

### 3.2 自动评估（Automated Evaluation）

| 评估方法 | 原理 | 适用 | 局限 |
|---------|------|------|------|
| **精确匹配** | 输出与标准答案完全匹配 | 分类、提取 | 过于刚性 |
| **BLEU/ROUGE** | n-gram 重叠度 | 翻译、摘要 | 不理解语义 |
| **BERTScore** | 语义相似度 | 通用文本生成 | 需要标注数据 |
| **LLM-as-Judge** | 用大模型评判 | 开放式回答 | 评判模型自身有偏见 |
| **代码执行** | 跑测试用例 | 代码生成 | 需要完善的测试集 |

### 3.3 LLM-as-Judge 详解

用 AI 评判 AI 是当前最实用的规模化评估方法：

```
# LLM-as-Judge Prompt 模板
你是一个严格的评审专家。请评估以下 AI 回答的质量。

## 评估标准
- 准确性 (1-5)：事实是否正确
- 完整性 (1-5)：是否覆盖了所有要点
- 清晰度 (1-5)：表达是否清晰易懂
- 有用性 (1-5)：是否真正帮到了用户

## 用户问题
{question}

## 参考答案
{reference_answer}

## AI 回答
{ai_answer}

## 输出格式（JSON）
{
  "accuracy": {"score": X, "reason": "..."},
  "completeness": {"score": X, "reason": "..."},
  "clarity": {"score": X, "reason": "..."},
  "helpfulness": {"score": X, "reason": "..."},
  "overall": {"score": X, "verdict": "pass/fail"}
}
```

**关键技巧**：
- 提供参考答案减少评判偏差
- 要求 JSON 结构化输出便于自动化
- 多维度评分而非单一分数
- 定期用人工评估校准 AI Judge

### 3.4 人工评估框架

| 评估维度 | 问题 | 评分标准 |
|---------|------|---------|
| **事实准确** | 回答中有多少事实错误？ | 0 错误 = 5 分 |
| **回答完整** | 是否遗漏了关键信息？ | 完整覆盖 = 5 分 |
| **表达清晰** | 用户能否一次看懂？ | 无需二次提问 = 5 分 |
| **语气恰当** | 是否符合品牌调性？ | 完全匹配 = 5 分 |
| **安全合规** | 是否包含有害/偏见内容？ | 无问题 = 5 分 |

### 3.5 评估驱动迭代

```
评估流程闭环：
  生产数据采样 → 自动评估初筛 → 人工评估精标 → 发现 failure pattern
       ↑                                                    ↓
  发版上线 ← 回归测试 ← 修复 prompt/模型 ← 制定改进方案
```

## 四、RAG vs Fine-tuning 选型

### 4.1 核心对比

| 维度 | RAG | Fine-tuning |
|------|-----|-------------|
| **知识更新** | 实时（换文档即可） | 需要重新训练 |
| **成本** | 低（无需训练） | 高（GPU + 数据标注） |
| **幻觉控制** | 好（有明确来源） | 一般（记忆可能模糊） |
| **个性化** | 弱（通用检索） | 强（可学习风格/格式） |
| **复杂推理** | 一般 | 好（可内化知识） |
| **延迟** | 较高（检索 + 生成） | 较低（直接生成） |
| **适用场景** | 知识问答、搜索 | 特定领域、特定风格 |

### 4.2 决策框架

```
你的核心需求是什么？
│
├── 需要最新信息 → RAG
│   └── 例：企业知识库、客服助手
│
├── 需要特定格式/风格 → Fine-tuning
│   └── 例：法律文书、代码风格
│
├── 需要减少幻觉 → RAG（有来源可追溯）
│   └── 例：医疗问答、金融分析
│
├── 需要降低推理成本 → Fine-tuning（小模型学大模型）
│   └── 例：Distillation，用 GPT-4 数据训练小模型
│
└── 以上都需要 → RAG + Fine-tuning 组合
    └── 例：Harvey AI（fine-tuned 模型 + RAG 检索案例法）
```

### 4.3 实战组合策略

| 产品 | 策略 | 效果 |
|------|------|------|
| **Perplexity** | 纯 RAG | 搜索场景知识实时更新是刚需 |
| **Harvey AI** | Fine-tune + RAG | 法律推理需要内化 + 案例检索 |
| **GitHub Copilot** | Fine-tune（Codex） | 代码生成需要学习编程模式 |
| **企业客服** | RAG 为主 | 知识库频繁更新，不需要风格迁移 |

## 五、成本优化策略

### 5.1 成本构成分析

| 成本项 | 占比 | 优化方向 |
|--------|------|---------|
| **Input tokens** | 40-60% | Prompt 压缩、缓存 |
| **Output tokens** | 30-50% | 限制输出长度、结构化 |
| **API 调用次数** | 10-20% | 批处理、合并请求 |
| **重试/纠错** | 5-15% | 提升首次成功率 |

### 5.2 Prompt Caching

Anthropic 和 OpenAI 都支持 prompt caching，对长 system prompt 效果显著：

| 策略 | 节省 | 原理 |
|------|------|------|
| **System prompt 缓存** | 最高 90% 输入成本 | 相同前缀只计费一次 |
| **长文档缓存** | 50-80% | 文档部分命中缓存 |
| **对话历史缓存** | 30-50% | 历史消息不重复计费 |

**Prompt 结构优化**（把不变的内容放前面）：

```
# ✅ 正确：system prompt 在前，可缓存
[System Prompt - 固定部分，可缓存]
[知识库文档 - 半固定部分，可缓存]
[用户对话历史 - 变化部分]
[当前用户问题 - 每次变化]

# ❌ 错误：每次变化的内容在前面，破坏缓存
[当前时间戳]
[用户问题]
[System Prompt - 本可缓存但被破坏]
```

### 5.3 Batching（批处理）

| 场景 | 实现方式 | 节省 |
|------|---------|------|
| 批量文档处理 | Batch API（Anthropic/OpenAI） | 50% |
| 分类任务 | 多条合并到一个 prompt | 70%+ |
| 数据提取 | 并行 + 结果合并 | 延迟降低 |

```
# 批处理示例：一次处理多条数据
请对以下 10 条用户反馈进行情感分类，输出 JSON 数格：

1. "这个产品太好用了！"
2. "客服态度很差"
...

输出格式：
[{"id": 1, "sentiment": "positive"}, ...]
```

### 5.4 Distillation（蒸馏）

用大模型生成高质量训练数据，训练小模型替代：

| 步骤 | 操作 | 工具 |
|------|------|------|
| 1. 数据生成 | 用 GPT-4 / Opus 生成标注数据 | OpenAI Batch API |
| 2. 质量过滤 | 人工抽检 + 自动评估 | LLM-as-Judge |
| 3. 模型训练 | Fine-tune 小模型 | OpenAI FT / 自训练 |
| 4. 部署替换 | 小模型替代大模型 | 推理服务 |
| 5. 持续监控 | 对比效果，发现退化 | 评估 pipeline |

**案例**：企业客服场景，用 Opus 生成 10k 条高质量回答 → 训练 Haiku 级别模型 → 成本降低 95%，质量损失 < 5%。

### 5.5 成本监控 Dashboard

每个 AI 产品都应建立成本监控：

| 指标 | 计算方式 | 告警阈值 |
|------|---------|---------|
| 单次调用成本 | tokens × 单价 | > $0.05 |
| 日均成本 | 每日 API 支出 | > 预算 120% |
| 每用户成本 | 日成本 / DAU | > $0.50 |
| 缓存命中率 | 缓存 token / 总 token | < 30% |
| 首次成功率 | 无需重试的比例 | < 85% |

## 六、设计 Checklist

每个 LLM 产品上线前过一遍：

| # | 检查项 | 状态 |
|---|--------|------|
| 1 | 模型选型是否匹配延迟/成本/能力需求？ | |
| 2 | 是否有幻觉防护（grounding/citation/HITL）？ | |
| 3 | 评估体系是否覆盖自动+人工+用户指标？ | |
| 4 | RAG vs Fine-tuning 决策是否有依据？ | |
| 5 | 成本优化措施是否到位（caching/batching）？ | |
| 6 | 是否有降级策略（模型不可用时的 fallback）？ | |
| 7 | 是否有用户反馈机制（thumbs up/down）？ | |
| 8 | 是否有 A/B 测试框架？ | |
| 9 | 是否有安全审核（有害内容/偏见检测）？ | |
| 10 | 成本监控 Dashboard 是否就绪？ | |
