## 一、PM 日常 AI 工作流

### 1.1 全流程 AI 渗透

| 工作环节 | AI 能做什么 | 工具 | 效率提升 |
|---------|-----------|------|---------|
| **需求分析** | 用户反馈聚类、痛点提取 | Claude / GPT | 3-5x |

## 二、Prompt 设计原则

### 2.1 基础框架：CLEAR

| 原则 | 英文 | 说明 | 示例 |
|------|------|------|------|
| **C**ontext | 上下文 | 提供背景信息 | "你是一个 B2B SaaS 产品经理..." |
| **L**anguage | 语言 | 明确输出语言 | "用中文回答，专业术语保留英文" |
| **E**xpectation | 期望 | 明确输出格式 | "输出 Markdown 表格" |
| **A**ction | 行动 | 明确任务 | "分析以下用户反馈，提取痛点" |
| **R**eference | 参考 | 提供参考示例 | "参考以下格式..." |

### 2.2 Few-shot Prompting

通过示例让模型理解你要的输出格式：

```
# Zero-shot（效果一般）
请将用户反馈分类为：功能需求、Bug 报告、体验问题

用户反馈："搜索功能太慢了，每次要等 5 秒以上"
分类：

# Few-shot（效果更好）
请将用户反馈分类为：功能需求、Bug 报告、体验问题

示例 1：
反馈："希望能支持导出 PDF"
分类：功能需求

示例 2：
反馈："点击登录按钮后页面白屏"
分类：Bug 报告

示例 3：
反馈："设置页面层级太深，找了半天找不到"
分类：体验问题

现在请分类：
反馈："搜索功能太慢了，每次要等 5 秒以上"
分类：
```

**Few-shot 设计要点**：
| 要点 | 说明 |
|------|------|
| 示例数量 | 3-5 个最佳，覆盖边界情况 |
| 示例多样性 | 覆盖不同分类，避免 bias |
| 边界案例 | 至少 1 个容易混淆的示例 |
| 排列顺序 | 最相似的示例放最后（recency bias） |

### 2.3 Chain-of-Thought (CoT)

让模型"展示思考过程"，提升复杂任务准确率：

```
# 不用 CoT
请分析这个功能的 ROI。
功能：AI 客服助手
成本：开发 50 万，年运营 20 万
预期：减少 30% 人工客服

# 用 CoT
请分析这个功能的 ROI，展示你的推理过程。

功能：AI 客服助手
成本：开发 50 万，年运营 20 万
预期：减少 30% 人工客服

请按以下步骤推理：
1. 计算当前人工客服年成本
2. 计算 AI 客服节省的成本
3. 计算总投入（开发 + 运营）
4. 计算 ROI = (节省 - 投入) / 投入
5. 考虑隐性收益（用户满意度、24/7 服务等）
6. 给出综合评估
```

### 2.4 Structured Output

强制模型输出结构化数据，便于后续处理：

```
请分析以下竞品信息，输出 JSON 格式：

竞品名称：{name}
官网：{url}

输出格式（严格 JSON，不要额外文字）：
{
  "name": "竞品名称",
  "positioning": "一句话定位",
  "target_users": ["用户群体1", "用户群体2"],
  "core_features": [
    {"name": "功能名", "description": "描述", "our_coverage": "有/无/部分"}
  ],
  "pricing": {
    "model": "免费/订阅/按量",
    "range": "价格区间"
  },
  "strengths": ["优势1", "优势2"],
  "weaknesses": ["劣势1", "劣势2"],
  "opportunity": "我们可以差异化的机会点"
}
```

### 2.5 System Prompt 设计模板

```
# 角色定义
你是一个资深 B2B SaaS 产品经理助手。

# 能力边界
- 擅长：需求分析、竞品研究、PRD 撰写、数据分析
- 不擅长：法律建议、医疗诊断、财务审计（遇到时建议咨询专业人士）

# 输出规范
- 语言：中文为主，专业术语保留英文
- 格式：优先使用表格，复杂分析用结构化列表
- 风格：直接给结论，再展开说明；不废话

# 工作方式
- 收到模糊需求时，先提问澄清，不猜
- 分析问题时，用"结论 → 依据 → 建议"结构
- 给建议时，区分"推荐"和"备选"

# 知识截止
- 知识截止日期：2025年12月
- 不确定的信息：明确标注"需要验证"
```

## 三、AI 辅助产品决策

### 3.1 用 AI 做用户访谈分析

**场景**：50 条用户访谈记录，需要提取关键洞察。

```
Prompt：
以下是 50 条用户访谈记录。请完成以下分析：

## 任务
1. **痛点聚类**：将用户提到的痛点归类（最多 8 个类别）
2. **频次统计**：每个痛点被多少用户提到
3. **严重度评估**：根据用户描述的情感强度，评估每个痛点的严重度（高/中/低）
4. **代表性原话**：每个痛点选 1-2 条最有代表性的用户原话
5. **产品建议**：针对 Top 3 痛点，给出初步产品方向

## 输出格式
### 痛点分布
| 排名 | 痛点类别 | 提及人数 | 严重度 | 代表性原话 |
|------|---------|---------|--------|-----------|

### Top 3 痛点产品建议
[每个痛点给出 2-3 个可行的产品方向]

---

{粘贴访谈记录}
```

### 3.2 用 AI 做数据洞察

**场景**：拿到一份业务数据，需要快速找洞察。

```
Prompt：
以下是我们的产品数据（最近 30 天）。请分析：

## 数据
{数据表格或 CSV}

## 分析要求
1. **关键指标趋势**：DAU、留存、转化率的变化趋势
2. **异常检测**：有没有异常波动？可能的原因是什么？
3. **用户分群**：基于行为数据，识别不同用户群体
4. **机会点**：数据中有什么可以利用的增长机会？
5. **风险预警**：有什么需要关注的下降趋势？

## 输出要求
- 每个发现用"数据 + 洞察 + 建议"结构
- 关键数字加粗
- 优先级排序：最重要的发现排最前
```

### 3.3 用 AI 做 PRD 生成

```
Prompt：
请帮我撰写以下功能的 PRD。

## 功能概述
功能名称：{功能名}
一句话描述：{描述}
目标用户：{用户画像}

## 背景
- 业务目标：{目标}
- 用户痛点：{痛点}
- 数据支撑：{数据}

## PRD 结构要求
1. **需求背景**（为什么做）
2. **目标与指标**（做成什么样，怎么衡量）
3. **用户故事**（As a... I want... So that...）
4. **功能详述**
   - 核心流程（主路径 + 分支）
   - 界面描述（每个页面的关键元素和交互）
   - 异常处理（网络错误、权限不足、数据为空等）
5. **数据需求**（需要埋哪些点）
6. **上线计划**（分期策略）
7. **开放问题**（需要讨论的决策点）

## 注意
- 每个功能点要写验收标准
- 界面描述要具体到字段级别
- 异常处理要覆盖所有边界情况
```

### 3.4 用 AI 做竞品分析

```
Prompt：
请帮我做以下竞品的深度分析。

## 竞品列表
{竞品名称和官网}

## 分析维度
1. **产品定位**：目标市场、目标用户、核心价值主张
2. **功能矩阵**：核心功能对比表
3. **商业模式**：定价策略、盈利模式
4. **技术架构**：技术栈、AI 能力（如适用）
5. **用户体验**：上手难度、交互设计亮点
6. **市场表现**：融资、用户规模、增长趋势
7. **SWOT 分析**：每个竞品的优劣势
8. **差异化机会**：我们能在哪里胜出

## 输出格式
- 竞品概览用表格
- 每个维度用"发现 → 意义 → 我们的策略"结构
- 最后给出 3-5 条可执行的竞争策略建议
```

| 工具 | 最佳用途 | PM 使用场景 | 定价 |
|------|---------|-----------|------|
| **Claude** | 长文档分析、复杂推理、写作 | PRD 撰写、数据分析、研究 | $20/月 Pro |
| **GPT-4o** | 通用任务、多模态 | 快速问答、图片分析 | $20/月 Plus |
| **Cursor** | 代码编写、技术方案 | 原型开发、SQL、技术沟通 | $20/月 Pro |
| **Perplexity** | 实时搜索、来源追溯 | 竞品研究、市场调研 | $20/月 Pro |
| **v0** | UI 原型生成 | 快速原型、设计稿 | $20/月 Pro |

| **NotebookLM** | 文档深度分析 | 论文研读、长文档理解 | 免费 |

### 4.2 各工具深度使用指南

#### Claude（首选写作和分析）

**最佳场景**：
- 长 PRD 撰写（支持超长上下文）
- 复杂数据分析（Artifacts 可视化）
- 多轮深度讨论（推理能力强）

**PM 技巧**：
| 技巧 | 说明 |
|------|------|
| 用 Projects | 把产品背景、用户画像、竞品资料上传到 Project |
| 长文档分析 | 直接上传 PDF/文档，Claude 原生支持 |
| Artifacts | 让 Claude 生成可交互的 HTML 原型 |
| Extended Thinking | 复杂分析任务开启深度思考模式 |

```
# Claude Project System Prompt 示例
你是一个 B2B SaaS 产品的 AI 产品助手。

## 产品背景
{产品介绍}

## 目标用户
{用户画像}

## 当前阶段
{产品阶段}

## 竞品
{竞品列表}

## 工作方式
- 所有分析基于我们上传的产品数据和文档
- 不确定的信息标注 [待验证]
- 输出格式：结论先行，表格优先
```

#### Cursor（首选技术相关）

**最佳场景**：
- 写 SQL 查询数据
- 快速搭建前端原型
- 理解技术方案

**PM 技巧**：
| 技巧 | 说明 |
|------|------|
| Cmd+K | 选中代码后自然语言描述修改意图 |
| Chat 模式 | 讨论技术方案，不直接改代码 |
| Composer | 多文件同时修改，适合搭建原型 |
| @docs | 引用官方文档，确保用法正确 |

```
# PM 用 Cursor 的典型场景

场景 1：数据分析
  "帮我写一个 SQL 查询：从 orders 表中，
   按月统计最近 6 个月的 GMV 和订单量，
   并计算环比增长率"

场景 2：快速原型
  "用 Next.js + Tailwind 创建一个简单的
   产品需求列表页面，支持搜索和状态筛选"

场景 3：理解代码
  "解释这段代码的业务逻辑，用产品经理
   能理解的语言"
```

#### Perplexity（首选研究调研）

**最佳场景**：
- 竞品实时信息（融资、产品更新）
- 行业趋势研究
- 技术方案调研

**PM 技巧**：
| 技巧 | 说明 |
|------|------|
| Focus 模式 | 选择 Academic/Reddit/YouTube 等来源 |
| Pro Search | 深度搜索，会追问澄清需求 |
| Collections | 按主题组织研究结果 |
| 搭配 Claude | Perplexity 找信息，Claude 做分析 |

```

竞品调研：
"{竞品名} latest product updates 2026 funding"

行业趋势：
"AI agent market size growth 2025 2026 enterprise adoption"

技术调研：

```

#### v0（首选原型设计）

**最佳场景**：
- 快速出可交互原型
- 验证交互想法
- 给开发看预期效果

**PM 技巧**：
| 技巧 | 说明 |
|------|------|

| 迭代修改 | 在生成结果基础上继续对话修改 |
| 导出代码 | 生成的代码可以直接给开发参考 |

## 五、Prompt 模板库（PM 专用）

### 5.1 需求优先级排序

```
请用 RICE 框架评估以下需求的优先级。

## 需求列表
{需求列表}

## 评估维度
- Reach：影响多少用户（具体数字或估计）
- Impact：对用户的影响程度（0.25/0.5/1/2/3）
- Confidence：对评估的确信度（100%/80%/50%）
- Effort：开发工作量（人天）

## 输出
| 需求 | Reach | Impact | Confidence | Effort | RICE 分数 | 优先级 |
|------|-------|--------|------------|--------|-----------|--------|

RICE = (Reach × Impact × Confidence) / Effort

请按 RICE 分数从高到低排序，并给出 Top 3 的执行建议。
```

### 5.2 用户故事生成

```
根据以下需求描述，生成用户故事和验收标准。

## 需求描述
{需求描述}

## 输出格式
### Epic
{Epic 名称}

### User Stories
#### US-1: {标题}
**As a** {用户角色}
**I want to** {行为}
**So that** {价值}

**验收标准 (AC):**
- [ ] AC1: {具体可测的条件}
- [ ] AC2: {具体可测的条件}
- [ ] AC3: {异常场景处理}

**优先级:** P0/P1/P2
**估算:** S/M/L/XL
```

### 5.3 技术方案评审准备

```
我即将参加以下功能的技术方案评审。请帮我准备。

## 功能描述
{功能描述}

## 请帮我准备
1. **应该问的问题**（技术可行性、性能、安全）
2. **可能的风险点**（技术债、依赖、时间线）
3. **需要确认的决策点**（方案取舍、优先级）
4. **验收标准**（怎么算做完了）
5. **时间线建议**（里程碑拆分）

## 注意
- 问题要具体，不要泛泛而谈
- 风险要给出缓解建议
- 决策点要给出选项和 trade-off
```

## 六、AI 使用效率 Tips

### 6.1 日常习惯

| 习惯 | 说明 | 节省时间 |
|------|------|---------|
| **模板化** | 把常用 Prompt 存为模板 | 每次省 5 分钟 |
| **分步提问** | 复杂任务分步骤，不要一次问完 | 减少返工 |
| **给示例** | 始终给 1-2 个示例 | 减少理解偏差 |
| **要求结构化** | 明确输出格式（表格/JSON/列表） | 减少格式调整 |
| **善用快捷键** | 学会工具的快捷操作 | 操作效率 2x |

### 6.2 常见错误

| 错误 | 正确做法 |
|------|---------|
| Prompt 太短太模糊 | 提供上下文 + 明确要求 + 示例 |
| 一次问太多 | 分步骤，每步聚焦一个问题 |
| 不验证输出 | 关键内容必须人工核实 |
| 只用一个工具 | 根据任务选择最合适的工具 |
| 不迭代 | 第一版不满意就继续优化 Prompt |
| 把 AI 当搜索引擎 | AI 擅长生成和分析，不擅长查实时数据 |

### 6.3 效率度量

建议追踪自己的 AI 使用效率：

| 指标 | 计算方式 | 目标 |
|------|---------|------|
| AI 使用频率 | 每天使用 AI 的次数 | > 10 次 |
| 任务覆盖率 | 用 AI 辅助的任务比例 | > 60% |
| 时间节省 | 传统方式时间 - AI 辅助时间 | > 50% |
| 首次满意率 | AI 输出直接可用的比例 | > 70% |
