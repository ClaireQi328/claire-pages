# AI Agent 产品架构

> Agent 不是"更聪明的 Chatbot"，而是"能自主完成任务的数字员工"。理解架构才能做好产品。

---

## 一、Agent 核心概念

### 1.1 Agent vs Chatbot

| 维度 | Chatbot | Agent |
|------|---------|-------|
| **交互模式** | 一问一答 | 自主规划 + 执行 |
| **工具使用** | 无或有限 | 动态调用外部工具 |
| **任务复杂度** | 单轮对话 | 多步骤、跨系统任务 |
| **状态管理** | 无状态/短期记忆 | 长期记忆 + 任务上下文 |
| **错误处理** | 返回错误信息 | 自主重试、换策略 |
| **典型产品** | ChatGPT 基础对话 | Cursor Agent、Claude Code |

### 1.2 Agent 核心循环

```
感知 (Perceive)
  ↓
规划 (Plan)
  ↓
执行 (Act) ←→ 工具调用 (Tool Use)
  ↓
观察 (Observe)
  ↓
反思 (Reflect)
  ↓
→ 回到"规划"，直到任务完成
```

## 二、Agent 设计模式

### 2.1 三大主流模式

| 模式 | 原理 | 适用场景 | 代表产品 |
|------|------|---------|---------|
| **ReAct** | Reasoning + Acting 交替 | 通用问答、简单工具调用 | Perplexity、多数 Chatbot |
| **Plan-and-Execute** | 先制定计划，再逐步执行 | 复杂多步骤任务 | Claude Code、Devin |
| **Multi-Agent** | 多个专业 Agent 协作 | 复杂工作流、团队模拟 | CrewAI 应用、AutoGen |

### 2.2 ReAct 模式详解

ReAct 是最基础也最常用的模式：

```
Thought: 用户问的是公司营收，我需要查数据库
Action: query_database("SELECT revenue FROM financials WHERE year=2025")
Observation: revenue = 1.2B
Thought: 我拿到了数据，现在可以回答了
Action: respond("2025年营收为 12 亿美元")
```

**产品设计要点**：
- Thought 对用户可选展示（提升信任）
- Action 需要有权限控制
- Observation 需要有错误处理

### 2.3 Plan-and-Execute 模式详解

适合复杂任务，先规划再执行：

```
# Plan 阶段
用户目标：帮我写一份竞品分析报告
计划：
1. 确认竞品列表（与用户确认）
2. 收集各竞品产品信息（搜索）
3. 整理功能对比表（结构化）
4. 撰写分析报告（生成）
5. 生成可视化图表（工具）

# Execute 阶段（逐步执行，每步可调整计划）
执行步骤 1 → 完成
执行步骤 2 → 发现某竞品信息不足 → 调整计划，增加补充调研步骤
...
```

**与 ReAct 的关键区别**：
| 维度 | ReAct | Plan-and-Execute |
|------|-------|-------------------|
| 规划时机 | 每一步临时决定 | 一开始就制定全局计划 |
| 适合任务 | 3 步以内的简单任务 | 5 步以上的复杂任务 |
| 可预测性 | 低（每步都可能变） | 高（计划可预览） |
| 用户信任 | 中 | 高（先看到计划） |

### 2.4 Multi-Agent 模式详解

多个 Agent 各司其职，协作完成任务：

```
┌─────────────┐
│  Orchestrator│  ← 总协调者
│    Agent     │
└──┬───┬───┬──┘
   │   │   │
   ▼   ▼   ▼
┌───┐┌───┐┌───┐
│研究││分析││写作│  ← 专业 Agent
│Agent││Agent││Agent│
└───┘└───┘└───┘
```

| 角色 | 职责 | 工具 |
|------|------|------|
| **Orchestrator** | 任务分配、进度管理、结果汇总 | 无（纯协调） |
| **Research Agent** | 信息收集、数据检索 | 搜索、数据库、API |
| **Analysis Agent** | 数据分析、推理判断 | 计算、图表、统计 |
| **Writer Agent** | 内容生成、格式化 | 文本生成、模板 |

**适用场景**：
- 企业级工作流（审批 → 执行 → 报告）
- 复杂研究任务（多来源 → 分析 → 撰写）
- 软件开发（需求 → 设计 → 编码 → 测试）

## 三、工具链设计

### 3.1 Function Calling 基础

Function Calling 是 Agent 使用工具的核心机制：

```json
{
  "name": "search_database",
  "description": "搜索产品数据库，返回匹配的产品信息",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {
        "type": "string",
        "description": "搜索关键词"
      },
      "filters": {
        "type": "object",
        "properties": {
          "category": {"type": "string"},
          "price_range": {"type": "array", "items": {"type": "number"}}
        }
      },
      "limit": {
        "type": "integer",
        "default": 10
      }
    },
    "required": ["query"]
  }
}
```

**设计原则**：
| 原则 | 说明 | 反例 |
|------|------|------|
| **命名清晰** | 动词_名词，一看就懂 | `do_stuff` → `search_products` |
| **描述准确** | description 告诉模型何时用 | 无描述 → 模型不知道何时调用 |
| **参数精简** | 必要参数 required，可选给 default | 所有参数都 required |
| **错误友好** | 返回可理解的错误信息 | 返回 stack trace |

### 3.2 MCP（Model Context Protocol）

Anthropic 推出的 MCP 是工具标准化的重要进展：

```
传统方式：每个工具单独适配每个模型
  Tool A ←→ Claude
  Tool A ←→ GPT
  Tool B ←→ Claude     → N×M 适配
  Tool B ←→ GPT

MCP 方式：统一协议，一次适配
  Tool A ──→ MCP Server ──→ Any LLM
  Tool B ──→ MCP Server ──→ Any LLM    → N+M 适配
```

**MCP 产品意义**：
| 维度 | 价值 |
|------|------|
| **开发者** | 工具只需写一次 MCP Server，所有 LLM 都能用 |
| **产品经理** | 工具生态可复用，不用为每个模型重新对接 |
| **用户** | 一个 Agent 可以无缝使用多个工具生态 |

### 3.3 工具链设计模式

| 模式 | 说明 | 适用 |
|------|------|------|
| **串行链** | A → B → C，前一步输出是后一步输入 | 数据处理流水线 |
| **并行扇出** | A → [B, C, D] 同时执行 | 多源信息收集 |
| **条件分支** | 根据结果选择不同工具 | 审批流、路由 |
| **循环重试** | 失败后换参数重试 | 搜索、API 调用 |

## 四、编排 vs 自主（Orchestration vs Autonomy）

### 4.1 自主度光谱

```
低自主 ◄────────────────────────────────────► 高自主

规则引擎 → 工作流编排 → 半自主 Agent → 全自主 Agent
  │           │              │              │
  └ 固定流程   └ 预定义路径    └ 有限自主决策   └ 完全自主
  └ 无 AI      └ AI 辅助决策   └ AI 主导执行    └ AI 独立完成
  └ 100%可控   └ 90%可控      └ 70%可控        └ 50%可控
```

### 4.2 两种架构对比

| 维度 | Orchestrated（编排式） | Autonomous（自主式） |
|------|----------------------|---------------------|
| **控制方式** | 预定义工作流 | Agent 自主决策 |
| **确定性** | 高（可预测） | 低（灵活但不确定） |
| **适用场景** | 企业审批、标准流程 | 创意任务、探索性工作 |
| **产品形态** | 低代码工作流 | Agent Chat |
| **代表产品** | n8n、Zapier AI | Claude Code、Devin |
| **风险管理** | 简单（流程可控） | 复杂（需要 guardrails） |

### 4.3 混合架构（推荐）

大多数产品应该采用混合架构：

```
高确定性部分 → 编排式（workflow）
  例：数据提取、格式转换、审批流

低确定性部分 → 自主式（agent）
  例：内容生成、分析推理、创意任务

边界 → Human-in-the-Loop
  例：关键决策点、高风险操作
```

## 五、Memory 系统

### 5.1 三种记忆类型

| 类型 | 作用 | 生命周期 | 实现方式 |
|------|------|---------|---------|
| **Short-term** | 当前对话上下文 | 单次会话 | 对话历史窗口 |
| **Long-term** | 用户偏好、历史知识 | 跨会话持久化 | 向量数据库 / KV 存储 |
| **Episodic** | 具体事件记忆 | 长期 | 结构化日志 + 检索 |

### 5.2 Short-term Memory

```
# 实现方式：对话窗口管理
策略一：固定窗口（最近 N 轮）
  优点：简单可控
  缺点：可能丢失重要上下文

策略二：Token 预算（总 token 上限）
  优点：充分利用上下文
  缺点：需要计算 token

策略三：摘要压缩（旧对话压缩为摘要）
  优点：保留关键信息
  缺点：压缩可能丢失细节

推荐：Token 预算 + 摘要压缩组合
```

### 5.3 Long-term Memory

| 存储方式 | 适用 | 查询方式 | 代表方案 |
|---------|------|---------|---------|
| **向量数据库** | 语义记忆 | 相似度搜索 | Pinecone、Weaviate |
| **KV 存储** | 结构化偏好 | 精确 key 查询 | Redis、SQLite |
| **知识图谱** | 关系型知识 | 图查询 | Neo4j |
| **文件系统** | 文档型记忆 | 全文搜索 | Obsidian vault |

### 5.4 Memory 产品设计要点

| 要点 | 说明 |
|------|------|
| **可控性** | 用户能查看、编辑、删除 Agent 的记忆 |
| **透明性** | 明确告知 Agent 记住了什么 |
| **隔离性** | 不同用户/项目的记忆严格隔离 |
| **遗忘机制** | 过时信息自动衰减或标记过期 |
| **隐私合规** | 符合 GDPR/个人信息保护法 |

## 六、人机协作模式

### 6.1 三种协作模式

| 模式 | 英文 | 人的角色 | Agent 角色 | 适用 |
|------|------|---------|-----------|------|
| **人在环中** | Human-in-the-Loop | 每步审批 | 执行者 | 高风险操作 |
| **人在环上** | Human-on-the-Loop | 监督+可干预 | 主执行者 | 中风险任务 |
| **人在环外** | Human-out-of-the-Loop | 设定规则 | 完全自主 | 低风险批量任务 |

### 6.2 Human-in-the-Loop 设计

```
Agent 提出方案
    ↓
展示给用户，等待确认
    ↓
┌── 用户同意 → 继续执行
├── 用户修改 → Agent 根据修改调整
└── 用户拒绝 → Agent 重新规划
```

**产品设计要点**：
- 方案展示要结构化、可对比
- 修改要方便（编辑框 vs 重新描述）
- 拒绝后 Agent 要能理解原因

### 6.3 Human-on-the-Loop 设计

```
Agent 自主执行
    ↓
关键节点推送通知给用户
    ↓
┌── 用户无操作 → 继续执行（默认同意）
├── 用户暂停 → 等待指示
└── 用户干预 → 接管控制权
```

**关键设计**：
- 通知频率要适度（太频繁 = 噪音，太少 = 失控）
- 用户随时可以接管
- 操作日志完整可审计

### 6.4 协作模式选择

```
任务风险评估：
├── 数据不可恢复（删除、发送）→ Human-in-the-Loop
├── 影响范围大（批量操作）→ Human-on-the-Loop
├── 可逆操作（草稿、分析）→ Human-out-of-the-Loop
└── 不确定 → 默认更保守的模式
```

## 七、安全与对齐

### 7.1 Agent 安全风险矩阵

| 风险 | 说明 | 等级 | 缓解措施 |
|------|------|------|---------|
| **Prompt Injection** | 恶意输入劫持 Agent | 高 | 输入过滤 + 权限隔离 |
| **过度授权** | Agent 权限超出必要 | 高 | 最小权限原则 |
| **数据泄露** | Agent 访问不该访问的数据 | 高 | 数据分级 + 访问控制 |
| **无限循环** | Agent 陷入死循环 | 中 | 步数限制 + 超时 |
| **错误累积** | 错误逐步放大 | 中 | 检查点 + 回滚 |
| **社会工程** | 诱导 Agent 执行危险操作 | 中 | 确认机制 + 敏感操作拦截 |

### 7.2 安全设计原则

| 原则 | 实现 |
|------|------|
| **最小权限** | Agent 只获得完成任务所需的最少权限 |
| **沙箱执行** | 代码在隔离环境运行，不能访问宿主系统 |
| **操作审计** | 每一步操作都记录日志，可追溯 |
| **速率限制** | 限制工具调用频率，防止滥用 |
| **人工确认** | 高风险操作（发邮件、修改数据）需确认 |
| **优雅降级** | 工具不可用时有 fallback，不崩溃 |

### 7.3 对齐设计

| 层级 | 目标 | 手段 |
|------|------|------|
| **系统级** | Agent 行为符合产品目标 | System prompt + guardrails |
| **用户级** | Agent 理解用户真实意图 | 澄清问题 + 确认机制 |
| **社会级** | Agent 行为符合社会规范 | Constitutional AI + 安全过滤 |

## 八、主流 Agent 框架对比

| 框架 | 出品方 | 定位 | 优势 | 劣势 |
|------|--------|------|------|------|
| **OpenAI Agent SDK** | OpenAI | 官方 SDK | 与 GPT 生态深度集成 | 相对封闭 |
| **Claude Agent SDK** | Anthropic | 官方 SDK | MCP 协议、安全设计好 | 生态较新 |
| **LangGraph** | LangChain | 图编排 | 灵活、可定制 | 学习曲线陡 |
| **CrewAI** | CrewAI | 多 Agent | 角色模拟直观 | 复杂场景受限 |
| **AutoGen** | Microsoft | 多 Agent | 对话式协作 | 调试困难 |

### 框架选型建议

| 场景 | 推荐 | 原因 |
|------|------|------|
| 快速原型 | Claude Agent SDK / OpenAI SDK | 开箱即用 |
| 复杂工作流 | LangGraph | 图编排灵活 |
| 多角色协作 | CrewAI | 角色定义直观 |
| 企业级 | LangGraph + 自研 | 可控性强 |
