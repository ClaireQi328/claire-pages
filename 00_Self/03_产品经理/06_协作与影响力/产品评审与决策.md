## 一、Design Review 流程

### 1.1 评审的三种类型

| 类型 | 目的 | 时机 | 参与人 | 输出 |
|------|------|------|--------|------|
| **Concept Review** | 验证方向对不对 | 想法阶段 | PM + Design + Eng Lead | Go/No-Go 决策 |
| **Design Review** | 验证方案好不好 | 原型阶段 | PM + Design + Eng + QA | 设计修改意见 |
| **Spec Review** | 验证细节全不全 | PRD 完成后 | 全团队 | PRD 签字确认 |

### 1.2 评审前（Before）

**准备清单：**

| 准备项 | 具体要求 | 完成标记 |
|--------|---------|---------|
| 文档/设计稿 | 提前 24h 发给参与者 | [ ] |
| 背景材料 | 附上用户研究数据、竞品分析 | [ ] |
| 明确目标 | 本次评审要解决什么问题？ | [ ] |
| 议程 | 每个议题的时间分配 | [ ] |
| 参与者确认 | 确认关键决策者能参加 | [ ] |
| 预沟通 | 重大分歧提前 1:1 对齐 | [ ] |

**评审议程模板：**

```markdown
# [功能名称] Design Review

> 时间：2026-07-10 14:00-15:00 | 地点：会议室 A / 飞书会议
> 参与人：PM、设计师、Tech Lead、QA Lead

## 议程
| 时间 | 内容 | 负责人 |
|------|------|--------|
| 14:00-14:10 | 背景与目标 | PM |
| 14:10-14:30 | 设计方案展示 | 设计师 |
| 14:30-14:50 | 讨论与反馈 | 全员 |
| 14:50-15:00 | 总结与 Action Items | PM |

## 需要决策的问题
1. 方案 A vs 方案 B？
2. 是否需要 Phase 2？
3. 技术可行性确认？
```

### 1.3 评审中（During）

**PM 的角色：**

| 角色 | 行为 |
|------|------|
| **主持人** | 控制时间、引导讨论方向、确保每个人发言 |
| **翻译者** | 将设计师的视觉语言翻译为工程师的技术语言 |
| **记录者** | 记录所有反馈、决策和 Action Items |
| **裁判** | 当讨论偏离主题时拉回来 |

**评审中避免的模式：**

| 错误模式 | 表现 | 正确做法 |
|---------|------|---------|
| 设计评审变成需求评审 | 讨论"要不要做"而不是"怎么做" | 明确评审范围，需求问题会后单独讨论 |
| 一个人讲全场 | PM 或设计师独占时间 | 主动邀请沉默的人发言 |
| 发散讨论 | 从导航栏聊到支付系统 | 记录 off-topic 问题，会后单独讨论 |
| 只给负面反馈 | "这个不好""那个不行" | 每条反馈都要有建设性建议 |
| 当场做所有决策 | 仓促决定复杂问题 | 记录下来，需要的决策会后再确认 |

**有效的反馈格式：**

```
❌ "这个按钮不好看"
✅ "这个按钮的颜色对比度不够，建议用品牌主色，
    因为我们需要确保 [用户群体] 能清楚识别主要操作"

❌ "用户不会这么用"
✅ "根据用户测试数据，70% 的用户会在 xxx 场景下
    先尝试 xxx 操作，建议把 xxx 放在更显眼的位置"
```

### 1.4 评审后（After）

**24 小时内完成：**

| 行动 | 内容 | Owner |
|------|------|-------|
| 发送会议纪要 | 决策 + Action Items + 截止日期 | PM |
| 更新设计稿 | 根据反馈修改 | 设计师 |
| 更新 PRD | 同步评审中的决策 | PM |
| 跟踪 Action Items | 确保每个事项有人负责 | PM |

## 二、Decision Log（决策记录）

### 2.1 为什么需要 Decision Log

| 不用 Decision Log 的后果 | 用 Decision Log 的收益 |
|------------------------|----------------------|
| 同样的争论反复出现 | "我们 3 月讨论过，结论是 xxx" |
| 新人不知道历史决策的原因 | 快速了解"为什么是这样" |
| 决策者离开后上下文丢失 | 决策知识留在团队 |
| 无法复盘决策质量 | 追踪决策结果，持续改进 |

### 2.2 Decision Log 模板

```markdown
# Decision Log — [项目名称]

| ID | 日期 | 决策 | 结论 | 决策者 | 状态 |
|----|------|------|------|--------|------|
| D001 | 07-10 | 搜索技术选型 | A: Elasticsearch | Tech Lead + PM | ✅ 已确认 |
| D002 | 07-10 | MVP 不含语音搜索 | C: Phase 2 | PM + VP | ✅ 已确认 |
| D003 | 07-12 | 灰度策略 | A: 1% 小流量 | PM | ⏳ 待确认 |

**决策详情：**

| ID | 背景 | 选项 | 依据 |
|----|------|------|------|
| D001 | 用户搜索延迟 > 3s | A: Elasticsearch / B: Algolia / C: 自研 | 成本低、团队熟悉、可满足需求 |
| D002 | 资源有限，优先核心搜索 | A: 包含 / B: 不包含 / C: Phase 2 | 用户调研显示优先级低于文字搜索 |
| D003 | 需要验证新搜索转化率 | A: 1% / B: 5% / C: 10% | 风险控制，先小流量验证 |
```

### 2.3 决策记录的 ADR 格式（Architecture Decision Record）

适用于重大技术或产品决策：

```markdown
# ADR-001: 搜索引擎选型

## 状态
已确认（2026-07-10）

## 背景
用户搜索延迟超过 3 秒，搜索转化率比行业均值低 40%。
需要选择新的搜索技术方案。

## 决策
选择 Elasticsearch 作为搜索后端。

## 选项
### 选项 A: Elasticsearch
- 优势：开源、团队有经验、社区活跃
- 劣势：运维复杂度较高
- 成本：服务器 ¥X/月 + 0.5 人维护

### 选项 B: Algolia
- 优势：开箱即用、运维零成本
- 劣议：成本随数据量线性增长、数据在美国
- 成本：¥Y/月（按搜索量计费）

### 选项 C: 自研
- 优势：完全可控
- 劣势：开发周期 3 个月、维护成本高
- 成本：3 人月 + 持续维护

## 依据
- 团队有 Elasticsearch 经验，上手成本低
- 预估搜索量在可控范围内，自运维成本合理
- 数据合规要求数据在国内

## 影响
- 需要 1 名工程师学习 ES 集群管理
- Q3 排期需预留 2 周迁移时间

## 复盘
- [ ] 2026-10-10 复盘搜索延迟是否降到 < 1s
- [ ] 2026-10-10 复盘搜索转化率是否提升
```

### 2.4 决策质量评估

定期复盘过去的决策，提升决策能力：

| 评估维度 | 问题 | 评分标准 |
|---------|------|---------|
| **决策速度** | 从发现问题到做出决策花了多久？ | < 1 周 = 好，> 1 月 = 需改进 |
| **信息充分度** | 决策时掌握了足够的信息吗？ | 有数据支撑 = 好，凭直觉 = 风险 |
| **方案多样性** | 考虑了足够的选项吗？ | ≥ 3 个选项 = 好，只有 1 个 = 风险 |
| **结果验证** | 决策结果符合预期吗？ | 用数据验证，不要只看感觉 |
| **复盘频率** | 是否定期回顾决策质量？ | 每月回顾关键决策 |

## 三、技术方案评审

### 3.1 PM 在技术评审中关注什么

| 关注维度 | 具体问题 | 为什么重要 |
|---------|---------|-----------|
| **用户体验影响** | 这个技术方案对用户体验有什么影响？ | 性能、延迟、可靠性直接影响用户 |
| **可扩展性** | 能否支持未来 10 倍用户量？ | 避免短期方案变成长期技术债 |
| **时间线合理性** | 这个方案真的能在 x 周内完成吗？ | 过于乐观的估算是项目延期的主因 |
| **风险点** | 哪些环节可能出问题？ | 提前准备 Plan B |
| **依赖关系** | 需要其他团队配合吗？ | 跨团队依赖是最大风险 |
| **数据与隐私** | 用户数据如何处理？合规吗？ | 数据泄露的后果比功能 bug 严重得多 |
| **可测试性** | 如何验证方案是否按预期工作？ | 无法测试 = 无法确认质量 |
| **回滚能力** | 出问题能快速回滚吗？ | 上线后发现问题的兜底方案 |

### 3.2 PM 应该问的技术问题清单

**架构层面：**

| 问题 | 目的 |
|------|------|
| "这个方案的主要技术风险是什么？" | 提前识别风险 |
| "有没有更简单的方案能达到同样效果？" | 避免过度工程化 |
| "如果用户量增长 10 倍，这个架构需要改吗？" | 评估可扩展性 |
| "这个方案对现有系统有什么影响？" | 评估改动范围 |

**时间与资源：**

| 问题 | 目的 |
|------|------|
| "估算的依据是什么？有哪些不确定性？" | 理解估算的可信度 |
| "哪些部分可以并行开发？哪些必须串行？" | 优化项目排期 |
| "如果时间减半，MVP 的最小范围是什么？" | 找到真正的 MVP |
| "有哪些外部依赖？它们的时间线确认了吗？" | 识别瓶颈 |

**质量与安全：**

| 问题 | 目的 |
|------|------|
| "如何做负载测试？目标 QPS 是多少？" | 确保性能达标 |
| "用户数据存储在哪里？加密了吗？" | 合规检查 |
| "上线后的监控和告警方案是什么？" | 可观测性 |
| "最坏情况下会发生什么？如何恢复？" | 灾难预案 |

### 3.3 技术评审的参与策略

| PM 技术水平 | 参与策略 | 重点 |
|------------|---------|------|
| 初级 | 多听多问，不装懂 | 理解技术决策对用户体验的影响 |
| 中级 | 提出业务约束，参与讨论 | 确保技术方案满足业务需求 |
| 高级 | 参与技术选型，挑战方案 | 从产品和技术双重角度评估 |

**通用原则：**
- PM 不需要评判代码质量，但需要评判用户体验影响
- PM 不需要选择技术栈，但需要确认技术约束下的产品方案
- PM 不需要写技术文档，但需要审阅技术文档中的用户体验风险

## 四、Go/No-Go 决策框架

### 4.1 决策时机

| 决策点 | 时间 | 核心问题 | 参与者 |
|--------|------|---------|--------|
| **立项决策** | Discovery 后 | 这个问题值得解决吗？ | PM + VP + Eng Lead |
| **方案决策** | Design 后 | 这个方案可行吗？ | PM + Design + Eng |
| **上线决策** | QA 后 | 质量达标了吗？能上线吗？ | PM + Eng + QA |
| **全量决策** | 灰度后 | 数据符合预期吗？ | PM + VP + Data |

### 4.2 Go/No-Go Checklist

**上线 Go/No-Go 检查表：**

```markdown
# [功能名称] Go/No-Go Checklist

> 决策日期：2026-07-10
> 计划上线日期：2026-07-15
> 决策人：PM + Tech Lead + QA Lead

## 功能完整性
- [ ] 所有 Must-have 功能已完成
- [ ] 所有验收标准通过
- [ ] 设计稿已实现且像素级对齐

## 质量
- [ ] 单元测试覆盖率 > 80%
- [ ] 集成测试通过
- [ ] 性能测试达标（P99 < 500ms）
- [ ] 安全扫描无高危漏洞
- [ ] 无障碍测试通过

## 运维
- [ ] 监控和告警已配置
- [ ] 日志已接入
- [ ] 回滚方案已测试
- [ ] 灰度策略已确认（1% → 5% → 20% → 100%）

## 团队
- [ ] On-call 工程师已确认
- [ ] 客服话术已准备
- [ ] 帮助文档已更新

## 决策
- [ ] Go — 按计划上线
- [ ] Conditional Go — 需要解决 xxx 后上线
- [ ] No-Go — 延期，原因：xxx
```

### 4.3 决策矩阵

当需要在多个方案中选择时：

| 评估维度 | 权重 | 方案 A | 方案 B | 方案 C |
|---------|------|--------|--------|--------|
| 用户价值 | 30% | 9 | 7 | 8 |
| 技术可行性 | 25% | 7 | 9 | 6 |
| 时间成本 | 20% | 6 | 8 | 9 |
| 资源投入 | 15% | 7 | 6 | 8 |
| 风险程度 | 10% | 8 | 7 | 5 |
| **加权总分** | 100% | **7.55** | **7.45** | **7.30** |

评分说明：
- 9-10：优秀，明显优势
- 7-8：良好，满足要求
- 5-6：一般，有改进空间
- 3-4：较差，需要权衡
- 1-2：不可接受

### 4.4 灰度发布决策

| 灰度阶段 | 流量 | 监控指标 | 升级条件 | 回滚条件 |
|---------|------|---------|---------|---------|
| 1% | 内部 + 小流量 | 错误率、延迟、转化率 | 错误率 < 0.1% | 错误率 > 1% |
| 5% | 小范围用户 | 同上 + 业务指标 | 核心指标无恶化 | 任何指标显著下降 |
| 20% | 大范围用户 | 同上 + 长期行为 | 所有指标达标 | 用户投诉增加 |
| 100% | 全量 | 持续监控 | — | — |

**灰度决策模板：**

```markdown
# [功能名称] 灰度升级决策

## 当前状态
- 灰度阶段：5% 流量
- 已运行时间：3 天
- 累计用户：xxx

## 核心指标
| 指标 | 目标 | 当前值 | 状态 |
|------|------|--------|------|
| 错误率 | < 0.1% | 0.05% | ✅ |
| P99 延迟 | < 500ms | 380ms | ✅ |
| 搜索转化率 | 不下降 | +2.3% | ✅ |
| 用户投诉 | 无新增 | 0 | ✅ |

## 决策
- [x] 升级到 20%
- [ ] 维持 5%（原因：xxx）
- [ ] 回滚（原因：xxx）

## 下一步
- 升级时间：2026-07-12 10:00
- 监控重点：xxx
- 下次决策时间：2026-07-15
```

## 五、产品复盘（Postmortem / Retrospective）

### 5.1 Postmortem vs Retrospective

| 维度 | Postmortem | Retrospective |
|------|-----------|---------------|
| **触发条件** | 事故/失败后 | 每个 Sprint/版本结束后 |
| **目的** | 找根因，防止再发生 | 改进流程，提升效率 |
| **文化** | 无指责（Blameless） | 持续改进 |
| **频率** | 按需（出问题时） | 固定节奏 |
| **输出** | 根因分析 + 行动计划 | 改进项 + 实验 |

### 5.2 Postmortem 模板

```markdown
# [事故名称] Postmortem

> 日期：2026-07-10
> 严重程度：P1 / P2 / P3
> 影响范围：xxx 用户 / xxx 小时
> 参与人：PM、Eng Lead、QA、On-call

## 事故时间线
| 时间 | 事件 |
|------|------|
| 07-10 10:00 | 用户报告搜索结果异常 |
| 07-10 10:15 | 工程师确认问题 |
| 07-10 10:30 | 定位到根因：索引更新脚本 bug |
| 07-10 11:00 | 回滚到上一版本 |
| 07-10 11:30 | 确认恢复正常 |

## 根因分析（5 Whys）
1. Why: 搜索结果异常 → 索引数据不一致
2. Why: 索引数据不一致 → 更新脚本有 bug
3. Why: 更新脚本有 bug → 代码变更未充分测试
4. Why: 未充分测试 → 测试环境数据与生产不同
5. Why: 测试环境数据不同 → 没有使用生产数据的测试流程

## 根本原因
测试环境缺少生产数据的子集，导致边界情况未被发现。

## 影响
- 用户影响：xxx 用户搜索体验异常 1 小时
- 业务影响：搜索转化率下降 xx%
- 品牌影响：收到 x 条用户投诉

## 改进行动
| 行动 | Owner | 截止日期 | 状态 |
|------|--------|---------|------|
| 建立生产数据脱敏同步到测试环境的流程 | Eng Lead | 07-20 | 待完成 |
| 索引更新脚本增加数据一致性校验 | 工程师 | 07-15 | 待完成 |
| 建立索引更新的监控告警 | SRE | 07-17 | 待完成 |

## 经验教训
1. 测试环境的数据质量直接影响测试的有效性
2. 数据变更类操作需要额外的一致性校验
3. 监控覆盖需要包含数据质量维度
```

### 5.3 Sprint Retrospective 模板

**Start-Stop-Continue 框架：**

```markdown
# Sprint XX Retrospective

> 日期：2026-07-10
> Sprint 周期：06-26 ~ 07-10

## 数据
| 指标 | 计划 | 实际 | 差异 |
|------|------|------|------|
| Story Points | 34 | 28 | -18% |
| 完成 Story 数 | 8 | 7 | -1 |
| Bug 数 | 5 | 8 | +3 |
| 代码评审时间 | < 4h | 6h | +50% |

## Start（开始做）
| 改进项 | Owner | 下个 Sprint 验证 |
|--------|--------|-----------------|
| PR 大小限制 400 行 | Tech Lead | 评审时间 < 4h |
| 每日站会后 5 分钟 Q&A | PM | 减少 Slack 上的重复问题 |

## Stop（停止做）
| 改进项 | 原因 |
|--------|------|
| 周五下午部署 | 3 次周五部署导致周末加班 |
| 需求变更不通知 QA | 导致测试遗漏 |

## Continue（继续做）
| 做法 | 价值 |
|------|------|
| 技术方案评审 | 提前发现设计问题 |
| 每周用户反馈 review | 及时发现体验问题 |

## 实验
本 Sprint 我们尝试：[xxx]
验证指标：[xxx]
回顾结论：[xxx]
```

### 5.4 无指责复盘文化（Blameless Postmortem）

**核心原则：**

| 原则 | 说明 | 错误做法 | 正确做法 |
|------|------|---------|---------|
| 对事不对人 | 关注系统问题，不追究个人 | "小王写了个 bug" | "代码审查流程没有覆盖这个场景" |
| 假设善意 | 每个人都在当时信息下做了最好的判断 | "为什么你不先测试？" | "是什么原因导致没有在测试环境发现？" |
| 系统思维 | 用系统视角看问题，不归因于个人能力 | "他技术不行" | "缺少自动化测试覆盖" |
| 行动导向 | 重点是改进，不是追责 | 争论谁的责任 | 聚焦改进行动 |

**引导话术：**

```
❌ "谁负责这个功能？为什么没有测试？"
✅ "当时的测试流程是什么？哪个环节可以加强？"

❌ "这个 bug 太低级了"
✅ "我们的代码审查流程如何能捕获这类问题？"

❌ "下次注意点就行了"
✅ "我们能加什么自动化检查来防止类似问题？"
```

## 六、避免委员会设计（Design by Committee）

### 6.1 什么是委员会设计

```
委员会设计的特征：
- 每个人都要发表意见
- 所有意见都被采纳（或至少被考虑）
- 最终方案是所有意见的折中
- 结果：没有明确的用户体验愿景，四不像
```

### 6.2 委员会设计的症状

| 症状 | 表现 | 根因 |
|------|------|------|
| 功能臃肿 | 一个页面塞了 20 个功能 | 每个利益方都加了自己的需求 |
| 设计摇摆 | 评审后方案大改 | 不同评委意见矛盾，PM 不敢取舍 |
| 没有取舍 | "这个也要，那个也要" | 没有明确的优先级标准 |
| 特色丧失 | 产品没有差异化 | 追求面面俱到，失去焦点 |
| 决策瘫痪 | 讨论了 3 轮还没定方案 | 决策权不明确，谁都能否决 |

### 6.3 如何避免

**策略 1：明确决策者**

| 角色 | 权限 | 说明 |
|------|------|------|
| **DRI（Directly Responsible Individual）** | 最终决策权 | 通常是 PM，对结果负责 |
| **Advisor** | 建议权 | 提供输入，但不做最终决策 |
| **Informed** | 知情权 | 被告知决策，不需要参与讨论 |

**策略 2：建立评审规则**

```
Design Review 规则：
1. DRI 做最终决策，其他人提供建议
2. 每位参与者最多提 3 条核心反馈
3. DRI 必须回应每条反馈（采纳/不采纳 + 原因）
4. 分歧无法解决时，升级到 DRI 的上级
5. 不在评审会上做所有决策，复杂问题单独讨论
```

**策略 3：用原则做决策**

当面临分歧时，回到产品原则：

```
示例：产品原则
1. 简单优先于全面
2. 核心场景完美 > 所有场景及格
3. 移动端体验优先于桌面端
4. 用户效率优先于功能数量

当设计师说"加个高级筛选"，工程师说"保持简洁"时：
→ 回到原则 2：核心搜索场景完美 > 高级筛选
→ 决策：Phase 1 不做高级筛选
```

**策略 4：限制评审参与者**

| 参与者数量 | 评审效果 |
|-----------|---------|
| 3-5 人 | 高效，能深入讨论 |
| 6-8 人 | 效率下降，但覆盖面足够 |
| 9+ 人 | 效率急剧下降，容易变成委员会设计 |

**策略 5：分层评审**

```
Layer 1: PM + Design + Eng Lead（3 人）→ 核心方案
Layer 2: + QA + Data（5 人）→ 方案细化
Layer 3: + 相关团队（按需）→ 信息同步（非决策）
```

### 6.4 处理"所有人都想参与决策"的情况

| 场景 | 应对策略 |
|------|---------|
| 高管突然加入评审 | 提前沟通"这次评审的目标是 xxx，最终决策权在 xxx" |
| 工程师挑战产品方向 | "你的技术视角很有价值，我们来讨论'在确定方向下怎么做最优'" |
| 设计师坚持方案 A，PM 要方案 B | "我们用用户测试数据来决定，下周出结果" |
| 销售要求加功能 | "我记录下来，一起评估优先级，有数据支撑的话我支持" |
| 每个人都要给反馈 | "请聚焦在你的专业领域，其他方面我们另外讨论" |

## 七、决策的高阶技巧

### 7.1 决策日记（Decision Journal）

每次重大决策时记录：

```markdown
# Decision Journal — 2026-07-10

## 决策
选择 Elasticsearch 作为搜索后端

## 当时的背景
- 用户搜索延迟 > 3s
- 竞品搜索体验明显优于我们
- Q3 有 2 名后端工程师可用

## 我的推理过程
- 用户核心需求是速度 → 需要高性能方案
- 团队有 ES 经验 → 学习成本低
- 数据合规 → 必须国内部署
- 排除 Algolia（数据在美国）、自研（周期太长）

## 我的假设
1. ES 能将延迟降到 < 500ms
2. 团队能在 2 周内完成迁移
3. 运维成本在可控范围内

## 预期结果
- 搜索延迟 < 500ms
- 搜索转化率提升 20%+

## 实际结果（3 个月后填写）
- 搜索延迟：xxx ms
- 搜索转化率：xxx%
- 其他影响：xxx

## 复盘
- 哪些假设被验证了？
- 哪些假设被推翻了？
- 下次同类决策我会怎么做？
```

### 7.2 决策质量评估矩阵

| 决策特征 | 好决策 | 坏决策 |
|---------|--------|--------|
| 信息基础 | 基于数据和用户洞察 | 基于直觉或最高薪者意见 |
| 选项数量 | 考虑了 3+ 个选项 | 只有 1 个方案 |
| 风险评估 | 明确列出风险和缓解 | 忽视风险 |
| 可逆性 | 区分单向门和双向门 | 对所有决策同等对待 |
| 时间投入 | 匹配决策的重要性 | 小决策花太多时间，大决策太仓促 |
| 利益相关者 | 正确的人参与 | 太多人或太少人 |

### 7.3 单向门 vs 双向门决策

Jeff Bezos 的决策分类法：

| 类型 | 特征 | 决策方式 | 示例 |
|------|------|---------|------|
| **单向门（One-way Door）** | 不可逆或逆转成本极高 | 慢决策、多数据、深思熟虑 | 选择技术架构、定价策略 |
| **双向门（Two-way Door）** | 可逆、试错成本低 | 快决策、先做再调 | UI 细节、文案、灰度比例 |

**PM 的决策节奏：**

```
双向门决策 → 快速决策，用数据验证，不行就改
单向门决策 → 充分讨论，收集数据，谨慎决定

原则：大多数决策是双向门，不要把双向门当单向门来决策
```

## 八、常见错误与避坑

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 评审前不发材料 | 评审时大家在读材料，效率低 | 提前 24h 发文档，会上直接讨论 |
| 评审会上做所有决策 | 复杂决策被仓促决定 | 复杂问题记录下来，会后单独讨论 |
| 不记录决策 | 同样的争论反复出现 | 用 Decision Log 记录每个决策 |
| 只做 Postmortem 不做 Retrospective | 只处理事故，不改进流程 | 固定节奏做 Sprint Retro |
| 所有人都能参与决策 | 委员会设计，四不像 | 明确 DRI，限制参与者 |
| 对所有决策同等对待 | 大决策太仓促，小决策花太多时间 | 区分单向门和双向门 |
| 决策后不复盘 | 无法提升决策质量 | 用 Decision Journal 追踪 |
| 评审变成批评会 | 团队害怕评审，消极应对 | 无指责文化，聚焦改进 |
