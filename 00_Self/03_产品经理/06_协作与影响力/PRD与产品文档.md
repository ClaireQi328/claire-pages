## 一、现代 PRD 的本质：决策记录而非模板堆砌

### 1.1 传统 PRD 的问题

| 问题 | 表现 | 后果 |
|------|------|------|
| 模板驱动 | 填满每个 section 但没有灵魂 | 团队不读，沦为形式 |
| 面面俱到 | 50 页文档覆盖所有边界情况 | 关键信息被淹没 |
| 一次性产物 | 写完即弃，不再更新 | 与实现脱节 |
| 描述而非论证 | "要做什么"但不说"为什么" | 团队无法自主决策 |

### 1.2 现代 PRD 的核心理念

```
传统 PRD：需求描述文档（What）
现代 PRD：决策记录文档（Why + What + How to decide）
```

**现代 PRD 的三个支柱：**

| 支柱 | 内容 | 价值 |
|------|------|------|
| **决策上下文** | 我们面临什么问题？有哪些约束？ | 团队理解背景，减少反复沟通 |
| **决策记录** | 我们选了什么方案？为什么放弃其他方案？ | 避免重复讨论，新人快速上手 |
| **决策验证** | 怎么判断决策是否正确？ | 对齐成功标准，支持复盘 |

### 1.3 PRD 的阅读者分析

| 读者 | 关注什么 | 你该怎么写 |
|------|---------|-----------|
| 工程师 | 技术约束、边界条件、验收标准 | 精确、无歧义、可测试 |
| 设计师 | 用户场景、体验目标、品牌调性 | 以用户故事为核心 |
| 老板 | 业务价值、资源投入、风险 | 开头一页说清楚 Why 和 ROI |
| QA | 验收标准、测试场景 | Given-When-Then 格式 |
| 运营 | 上线时间、灰度策略、回滚方案 | 单独的上线计划 section |

## 二、One-pager vs PRD vs Spec

### 2.1 三种文档的定位

| 维度 | One-pager | PRD | Technical Spec |
|------|-----------|-----|----------------|
| **目的** | 快速对齐方向 | 详细定义需求 | 技术实现方案 |
| **时机** | 想法阶段（Pre-discovery） | 立项后（Post-discovery） | 设计确认后（Pre-dev） |
| **作者** | PM | PM | 工程师（PM 审阅） |
| **篇幅** | 1 页 | 3-8 页 | 5-15 页 |
| **读者** | 决策层 + 全团队 | 全团队 | 工程团队 |
| **核心问题** | 为什么做？值不值得？ | 做什么？怎么做？ | 怎么实现？ |

### 2.2 One-pager 模板

```markdown
# [项目名称] One-pager

## 问题（1-2 句话）
用户在什么场景下遇到什么问题？数据支撑？

## 方案概述（2-3 句话）
我们打算怎么解决？核心假设是什么？

## 成功指标（3-5 个）
- 北极星指标：xxx
- 护栏指标：xxx（不能恶化的）

## 资源与时间
- 团队：x PM + x 工程 + x 设计
- 周期：x 周
- 依赖：xxx

## 风险与开放问题
1. xxx
2. xxx
```

### 2.3 选择决策树

```
你有新想法？
├── 不确定值不值得做 → One-pager → 评审 → 决定是否立项
├── 已决定要做，需要定义需求 → PRD
└── 需求已明确，需要技术方案 → Technical Spec
    └── 大型项目 → 三者都需要，按阶段产出
```

## 三、用户故事的正确用法

### 3.1 常见误区

| 误区 | 为什么错 | 正确做法 |
|------|---------|---------|
| 把用户故事当需求容器 | 一个 Story 塞进 20 个功能点 | 一个 Story = 一次可交付的用户价值 |
| 格式至上 | 所有需求都套 "As a...I want...So that" | 格式服务于理解，不是为了填空 |
| 忽视 So that | 不写用户动机 | 动机是最重要的一部分 |
| Epic = 大 Story | Epic 只是更大的 Story | Epic 是主题/目标，Story 是具体行为 |
| 忽略非功能需求 | 只写功能，不写性能/安全/可访问性 | 用 Spike 或补充 Story 覆盖 |

### 3.2 用户故事的正确结构

```
用户故事 ≠ 需求规格
用户故事 = 团队对话的触发器
```

**INVEST 原则：**

| 原则 | 含义 | 检查方法 |
|------|------|---------|
| **I**ndependent | 不依赖其他 Story | 能独立开发和上线吗？ |
| **N**egotiable | 可协商的，不是合同 | 团队能讨论不同的实现方式吗？ |
| **V**aluable | 对用户有明确价值 | So that 说得清楚吗？ |
| **E**stimable | 可估算 | 工程师能给 story point 吗？ |
| **S**mall | 足够小，一个 Sprint 能完成 | 能拆得更小吗？ |
| **T**estable | 可测试 | 验收标准明确吗？ |

### 3.3 用户故事拆分技巧

| 拆分方法 | 示例 | 适用场景 |
|---------|------|---------|
| 按操作步骤 | 搜索 → 筛选 → 查看详情 | 流程型功能 |
| 按数据类型 | 支持图片 → 支持视频 → 支持文档 | 多类型输入 |
| 按用户角色 | 管理员能... → 普通用户能... | 权限差异 |
| 按平台 | Web 端 → 移动端 → API | 多端适配 |
| 按 Happy/Sad path | 正常流程 → 异常处理 → 边界条件 | 质量保障 |
| 按 CRUD | 创建 → 查看 → 编辑 → 删除 | 基础功能 |

### 3.4 用户故事地图（User Story Mapping）

```
用户活动（骨架）
├── 注册 → 浏览商品 → 下单 → 支付 → 收货 → 评价

Release 1（Walking Skeleton — MVP）
├── 邮箱注册     │ 商品列表   │ 单品下单 │ 支付宝  │ 查看物流  │ 文字评价
│
Release 2（增强）
├── 手机注册     │ 搜索筛选   │ 购物车   │ 微信支付 │ 签收确认  │ 图片评价
│
Release 3（完善）
├── 第三方登录   │ 推荐       │ 凑单满减 │ 花呗    │ 退换货   │ 视频评价
```

## 四、验收标准：Given-When-Then

### 4.1 格式说明

```
Given（前置条件）：系统处于什么状态？
When（触发行为）：用户执行什么操作？
Then（预期结果）：系统应该有什么响应？
```

### 4.2 实战示例

**场景：用户登录**

```gherkin
Scenario: 正常登录
  Given 用户已注册，账号为 test@example.com
  When  输入正确密码并点击"登录"
  Then  跳转到首页，显示用户名

Scenario: 密码错误
  Given 用户已注册，账号为 test@example.com
  When  输入错误密码并点击"登录"
  Then  提示"密码错误"，剩余尝试次数 -1

Scenario: 账号不存在
  Given 系统中不存在 notexist@example.com
  When  输入任意密码并点击"登录"
  Then  提示"账号或密码错误"（不泄露账号是否存在）

Scenario: 连续 5 次密码错误
  Given 用户已连续输入错误密码 4 次
  When  第 5 次输入错误密码
  Then  账号锁定 30 分钟，发送安全提醒邮件
```

### 4.3 验收标准检查清单

| 检查项 | 标准 |
|--------|------|
| Happy path | 主流程覆盖了吗？ |
| Edge cases | 边界条件（空值、极值、特殊字符）覆盖了吗？ |
| Error handling | 异常情况有明确的预期行为吗？ |
| 性能 | 有响应时间要求吗？（如 < 2s） |
| 权限 | 不同角色的行为差异明确吗？ |
| 兼容性 | 多端/多浏览器/多版本覆盖了吗？ |
| 可访问性 | 屏幕阅读器、键盘导航支持吗？ |

### 4.4 从用户故事到验收标准的流程

```
用户故事
  "作为买家，我想收藏商品，以便下次快速找到"

拆解思考：
├── 买家在什么场景下收藏？ → 商品详情页
├── 收藏后在哪能看到？ → 收藏夹列表
├── 有数量限制吗？ → 上限 500
├── 能批量操作吗？ → v1 不支持
└── 已下架商品怎么办？ → 显示"已下架"标签，不自动删除

→ 产出 5-8 条 Given-When-Then
```

## 五、文档即代码（Docs as Code）

### 5.1 为什么选择 Docs as Code

| 传统方式 | Docs as Code | 收益 |
|---------|-------------|------|
| Word/Confluence | Markdown + Git | 版本可追溯，diff 可见 |
| 邮件发文档 | Pull Request 评审 | 结构化反馈，异步协作 |
| 手动排版 | 自动生成 | 专注内容，不折腾格式 |
| 文档和代码分离 | 文档在代码仓库旁 | 同步更新，不会脱节 |

### 5.2 工具选择矩阵

| 工具 | 适合团队 | 优势 | 劣势 |
|------|---------|------|------|
| **Markdown + Git** | 技术型团队 | 版本控制、diff、PR 评审 | 非技术人员门槛高 |
| **Notion** | 中小团队 | 低门槛、数据库视图、模板 | 大团队权限管理弱 |
| **Obsidian** | 个人/小团队 | 本地优先、双链、插件生态 | 协作能力有限 |
| **Confluence** | 大企业 | 权限管理、集成 Jira | 臃肿、搜索差、格式混乱 |
| **飞书文档** | 国内团队 | 实时协作、权限管理、AI 助手 | 外部分享受限 |

### 5.3 Git 管理文档的最佳实践

```
repo/
├── docs/
│   ├── prd/
│   │   ├── 2026-Q3-feature-xyz/
│   │   │   ├── one-pager.md
│   │   │   ├── prd.md
│   │   │   ├── decision-log.md
│   │   │   └── assets/
│   │   │       └── wireframe.png
│   │   └── README.md          ← PRD 索引
│   ├── specs/
│   └── templates/
├── .github/
│   └── CODEOWNERS             ← 指定文档 reviewer
└── README.md
```

**Git 工作流：**

| 操作 | 命令/流程 |
|------|----------|
| 新建 PRD | 从 main 创建分支 `docs/feature-xyz` |
| 评审 | 提 PR，@相关人 review |
| 合并 | 至少 1 人 approve 后 merge |
| 更新 | 直接在 main 上小改，大改走 PR |

## 六、AI 辅助文档写作

### 6.1 AI 在 PRD 写作中的最佳使用场景

| 场景 | AI 擅长 | AI 不擅长 | PM 的角色 |
|------|---------|----------|----------|
| 初稿生成 | 快速生成结构框架 | 理解业务上下文 | 提供上下文，AI 出框架，PM 填充 |
| 验收标准 | 根据用户故事生成 GWT | 覆盖边界情况 | 补充 edge cases |
| 竞品分析 | 收集和整理公开信息 | 判断战略含义 | 做判断和决策 |
| 文档润色 | 改善表达、统一术语 | 理解隐含假设 | 审阅准确性 |
| 翻译 | 多语言翻译 | 文化适配 | 本地化审阅 |

### 6.2 AI Prompt 模板

**生成用户故事：**
```
你是一个资深产品经理。基于以下需求描述，生成用户故事（含验收标准）。

功能描述：[xxx]
目标用户：[xxx]
业务目标：[xxx]

要求：
1. 每个故事符合 INVEST 原则
2. 验收标准用 Given-When-Then 格式
3. 覆盖 Happy path + 至少 2 个 Edge case
4. 用中文输出
```

**评审 PRD：**
```
你是一个严格的技术 lead。请从以下角度评审这份 PRD：
1. 需求是否有歧义？（可能导致不同理解的地方）
2. 边界条件是否覆盖？
3. 验收标准是否可测试？
4. 是否遗漏了非功能需求？
5. 有没有隐含假设需要澄清？

PRD 内容如下：
[paste]
```

### 6.3 AI 辅助文档的注意事项

| 风险 | 防范措施 |
|------|---------|
| AI 生成的内容看起来很专业但有错误 | 必须人工审阅，特别是数据和业务逻辑 |
| 团队过度依赖 AI，丧失独立思考能力 | AI 是辅助工具，决策权在人 |
| 机密信息泄露给 AI 平台 | 敏感数据脱敏后再输入 |
| 生成内容的版权风险 | 确认公司对 AI 生成内容的政策 |

## 八、文档生命周期管理

### 8.1 文档状态流转

```
Draft → In Review → Approved → In Development → Shipped → Archived
  ↑         |                                     |
  └─────────┘（需要修改）                          |
                    ←─────────────────────────────┘（复盘后更新）
```

### 8.2 文档维护责任

| 阶段 | 维护人 | 频率 |
|------|--------|------|
| Draft → Approved | PM | 持续更新直到评审通过 |
| In Development | PM + Tech Lead | 每周检查是否需要更新 |
| Shipped | PM | 上线后 1 周内更新最终版 |
| Archived | PM | 标记归档，保留供复盘 |

### 8.3 文档健康度检查

每月检查一次：

| 检查项 | 标准 | 动作 |
|--------|------|------|
| 有无 PRD 与实现不一致？ | 代码 vs 文档 diff | 更新文档或标记已知差异 |
| 有无过期的开放问题？ | 超过 30 天未关闭 | 关闭或升级 |
| 有无缺失的验收标准？ | Story 无 GWT | 补充 |
| Decision Log 是否完整？ | 决策无记录 | 补充背景和结论 |

---

## 九、常见错误与避坑

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| PRD 写完不评审 | 团队不认可，执行时扯皮 | 正式评审，获取 sign-off |
| 需求描述含糊 | 工程师自行理解，结果偏差 | 用验收标准消除歧义 |
| 写了 PRD 不更新 | 文档与实现脱节 | 文档随代码一起更新 |
| 所有需求同等重要 | 什么都做 = 什么都做不好 | MoSCoW 排序，明确 Won't |
| 只写功能不写非功能 | 上线后性能/安全问题 | 非功能需求单独 section |
| 文档太长没人看 | 关键信息被淹没 | 分层：One-pager → PRD → Spec |
| 忽视文档的"观众" | 工程师看不懂、老板没耐心 | 针对不同读者准备不同版本 |
