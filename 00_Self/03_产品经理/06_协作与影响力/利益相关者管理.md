# 利益相关者管理

> 产品经理最重要的能力不是写 PRD，而是让正确的人在正确的时间做出正确的决策。

## 一、利益相关者地图（Stakeholder Map）

### 1.1 Power/Interest 矩阵

```
        高 Interest
            │
   Keep     │     Manage
   Satisfied│     Closely
            │
 ───────────┼──────────── Power
            │
   Monitor  │     Keep
   (Minimum)│     Informed
            │
        低 Interest
```

| 象限 | 策略 | 典型角色 | 沟通频率 | 方式 |
|------|------|---------|---------|------|
| **Manage Closely** | 主动管理，深度参与 | CEO/VP、直属上级、Tech Lead | 每周 1-2 次 | 1:1、决策会议 |
| **Keep Satisfied** | 定期汇报，满足需求 | 其他部门 VP、关键投资人 | 每 1-2 周 | 月报、里程碑汇报 |
| **Keep Informed** | 保持透明，提供信息 | 跨团队 PM、运营负责人 | 每周 | 周报、Slack/飞书群 |
| **Monitor** | 最低限度关注 | 外围团队、行政支持 | 按需 | 邮件、文档 |

### 1.2 利益相关者识别清单

| 维度 | 问自己 | 来源 |
|------|--------|------|
| 决策权 | 谁能拍板这个功能做不做？ | 组织架构 |
| 资源控制 | 谁分配工程师/设计师的时间？ | 资源经理 |
| 信息依赖 | 谁掌握我不了解的关键信息？ | 需求分析 |
| 执行依赖 | 谁需要配合才能上线？ | 项目计划 |
| 影响范围 | 这个功能会影响谁的 KPI？ | OKR 对齐 |
| 否决权 | 谁可以一票否决？ | 治理结构 |

```markdown
### 影响策略
```

## 二、向上管理（Managing Up）

### 2.1 理解高管的决策模式

| 高管类型 | 决策风格 | 你需要准备什么 | 避免什么 |
|---------|---------|--------------|---------|
| **数据驱动型**（多数技术公司 CEO） | 要数据、要模型、要 A/B test 结果 | 完整的数据分析、ROI 计算、竞品数据 | 模糊的描述、没有数据支撑的判断 |
| **直觉型**（乔布斯式） | 快速判断、重视品味和愿景 | 用户故事、设计原型、情感共鸣 | 太多技术细节、冗长的数据报告 |
| **政治型**（大企业 VP） | 关注组织影响、平衡各方利益 | 利益相关者分析、风险评估、分阶段方案 | 只谈产品不谈组织 |
| **执行型**（COO 式） | 关注可行性和时间线 | 详细的执行计划、里程碑、资源需求 | 只有愿景没有路径 |

### 2.2 如何用数据说服高管

**数据说服的 SPQA 框架：**

| 步骤 | 内容 | 示例 |
|------|------|------|
| **S**ituation | 背景数据 | "我们的 NPS 从 45 降到 32" |
| **P**roblem | 问题聚焦 | "主要原因是搜索功能满意度从 4.2 降到 2.8" |
| **Q**uestion | 关键问题 | "是否投入资源重建搜索？" |
| **A**nswer | 你的建议 | "建议 Q3 重建搜索，预期 NPS 回升至 40+" |

**数据呈现技巧：**

| 技巧 | 说明 | 示例 |
|------|------|------|
| 对比基准 | 单独的数字没有意义 | "我们 2.8 vs 行业均值 4.1" |
| 换算成钱 | 业务语言比产品语言更有力 | "搜索体验差导致月流失 2000 用户 = ¥60 万/月" |
| 时间趋势 | 展示问题的紧迫性 | "过去 3 个月持续下降，如果不干预..." |
| 竞品对标 | 外部压力 | "竞品 A 的搜索转化率是我们的 2 倍" |
| 分母思维 | 避免被质疑样本量 | "基于过去 30 天 50 万次搜索会话" |

### 2.3 向上汇报的金字塔结构

```
           ┌─────────────┐
           │   结论/建议   │  ← 一开始就说
           └──────┬──────┘
      ┌───────────┼───────────┐
   ┌──┴──┐    ┌──┴──┐    ┌──┴──┐
   │论据1 │    │论据2 │    │论据3 │  ← 3 个支撑论据
   └──┬──┘    └──┬──┘    └──┬──┘
   ┌──┴──┐    ┌──┴──┐    ┌──┴──┐
   │数据  │    │数据  │    │数据  │  ← 每个论据有数据支撑
   └─────┘    └─────┘    └─────┘
```

**邮件/文档模板：**

```markdown
Subject: [决策请求] 搜索功能重建 — Q3 立项

## 结论
建议 Q3 投入 2 名工程师 + 1 名设计师重建搜索功能，
预计投入 6 周，预期月收入增加 ¥XX 万。

## 为什么现在做
1. 用户满意度连续 3 个月下降（数据）
2. 搜索转化率低于行业均值 40%（对标）
3. 竞品 A 刚上线新搜索，用户增长加速（竞争）

## 资源需求
- 2 后端 + 1 前端 + 1 设计师，共 6 周
- 不影响 Q3 其他 P0 项目

## 风险
- 如果搜索重建失败，回滚方案是保持现状（零风险）
- 需要数据团队支持 1 周（已确认可用）

## 需要您的决策
- [ ] 批准立项
- [ ] 调整优先级
- [ ] 需要更多信息
```

### 2.4 向 CEO 汇报的特别注意事项

| CEO 类型 | 关注点 | 你的准备 |
|---------|--------|---------|
| 产品型 CEO | 用户体验、产品品味 | 带原型和用户故事，少用 PPT |
| 技术型 CEO | 架构合理性、技术债务 | 准备技术方案概要，能回答"为什么不直接..." |
| 商业型 CEO | 收入、增长、市场份额 | 用商业指标说话，ROI 计算清晰 |
| 运营型 CEO | 效率、成本、可规模化 | 强调流程改进和可复制性 |

**万能原则：**
- 先说结论，再展开
- 准备好被挑战，预期 2-3 个追问
- 承认不确定性，给出你如何验证的计划
- 不要抱怨资源不够，提出你用有限资源能做什么

## 三、横向影响（Cross-functional Influence）

### 3.1 与工程师协作

| 场景 | 常见冲突 | 解决方案 |
|------|---------|---------|
| 需求变更 | "你又改需求！" | 用数据证明变更价值，接受进度影响 |
| 技术债务 | "先还债再做新功能" | 将技术债纳入 backlog，和业务需求一起排优先级 |
| 估算分歧 | "这个做不了 / 要 3 个月" | 问清楚为什么，一起拆分找到 MVP |
| 工期压力 | "时间不够就砍测试" | 用质量数据说话，不接受"先上线再说" |

**与工程师建立信任的方法：**

| 方法 | 具体做法 |
|------|---------|
| 尊重技术判断 | 不要 micromanage 实现细节 |
| 坦诚面对不确定性 | "我不确定这个方案是否可行，我们一起验证" |
| 保护工程师时间 | 减少不必要的会议，异步沟通 |
| 分享业务上下文 | 让工程师理解 Why，而不只是 What |
| 给予技术决策权 | 让工程师选择实现方式，PM 只定义验收标准 |

### 3.2 与设计师协作

| 场景 | PM 的角色 | 设计师的角色 |
|------|----------|-------------|
| 需求定义 | 提供用户问题和业务约束 | 提供设计方向和交互方案 |
| 原型评审 | 从用户流程和业务逻辑角度评审 | 从视觉和交互角度评审 |
| 可行性讨论 | 协调工程师评估 | 根据技术约束调整方案 |
| 用户测试 | 制定测试计划 | 执行测试，分析设计问题 |

**避免的模式：**
- "把这个按钮改成蓝色" — 你在做设计师的工作
- "设计看起来不错" — 你需要给具体反馈（哪个部分满足了什么需求）
- "用户不会喜欢这个" — 用数据说话，不要替用户做判断

**有效的设计反馈模板：**

```
反馈：[具体元素]
作用：这个设计解决了什么用户问题？
建议：我认为 [xxx] 可能更好，因为 [xxx]
开放：你怎么看？
```

### 3.3 与市场/销售协作

| 角色 | 关注点 | 你需要提供什么 |
|------|--------|--------------|
| 市场 | 产品故事、差异化、上市时间 | 产品定位、核心卖点、发布计划 |
| 销售 | 功能承诺、客户痛点、竞品对比 | 功能路线图、竞品分析、FAQ |
| 客服 | 已知问题、解决时间、话术 | 已知问题列表、修复时间表、临时方案 |

**处理销售"承诺客户一个功能"的问题：**

| 阶段 | 行动 |
|------|------|
| 预防 | 定期同步路线图给销售，明确"在做什么 / 不做什么" |
| 发生时 | 不直接拒绝，了解客户的真实需求和优先级 |
| 决策 | 如果客户足够重要，评估是否调整优先级 |
| 沟通 | 给销售明确的时间线，不要模糊承诺 |

### 3.4 跨团队影响的 LARA 模型

当面临跨团队分歧时：

| 步骤 | 含义 | 示例 |
|------|------|------|
| **L**isten | 倾听对方的观点和需求 | "你认为搜索不重要，为什么？" |
| **A**cknowledge | 承认对方的关切是合理的 | "你说的对，技术债确实影响开发效率" |
| **R**espond | 用数据和逻辑回应 | "但数据显示搜索转化率下降 40%，直接影响收入" |
| **A**dd | 提出建设性的解决方案 | "我们可以分阶段：先修复 P0 bug，Q4 再重建" |

## 四、冲突处理

### 4.1 冲突类型与应对策略

| 冲突类型 | 表现 | 根因 | 策略 |
|---------|------|------|------|
| **利益冲突** | 两个团队争抢同一资源 | 资源分配机制不清晰 | 用 ROI 数据排序，升级到共同上级 |
| **优先级冲突** | A 团队觉得功能 X 重要，B 团队觉得 Y 重要 | OKR 未对齐 | 回到公司目标，用影响矩阵排序 |
| **资源冲突** | 工程师时间不够分配 | 需求 > 供给 | 砍需求或加人，不能"都要" |
| **方法冲突** | PM 要方案 A，工程师要方案 B | 评估标准不同 | 定义共同的评估维度，一起评估 |
| **信息冲突** | 双方掌握的信息不同 | 沟通不充分 | 先同步信息，再做决策 |

### 4.2 冲突解决框架

**Thomas-Kilmann 冲突模式：**

```
          高
    竞争    │    协作
  （我赢你输）│  （双赢）
          │
 ─────────┼────────── 坚持自己立场
          │
    回避    │    妥协
  （都不赢）│  （各让一步）
          │
          低
        迁就（你赢我输）
        高
      关注他人
```

| 模式 | 适用场景 | 不适用场景 |
|------|---------|-----------|
| **协作** | 双方利益都重要，需要最佳方案 | 时间紧急、信任缺失 |
| **竞争** | 紧急决策、原则性问题 | 需要长期合作的关系 |
| **妥协** | 时间紧迫、双方势均力敌 | 有明显最优解时 |
| **回避** | 问题不重要、需要冷静期 | 问题会恶化的情况 |
| **迁就** | 关系比结果重要、对方确实更对 | 你的立场是正确的时候 |

### 4.3 实战冲突场景

**场景 1：销售 VP 要求立即做一个大客户定制功能**

```
你的回应模板：

1. 理解："我理解这个客户对我们很重要。"
2. 数据："目前有 3 个 P0 功能在排期，影响 10 万用户。"
3. 方案：
   方案 A：推后客户定制，按原计划做 P0（推荐）
   方案 B：抽 1 人做最小化定制，P0 延期 1 周
   方案 C：完全切换到定制功能，P0 延期 3 周
4. 建议："建议方案 A，因为 [ROI 计算]。"
5. 决策："需要您来决定。"
```

**场景 2：工程师认为 PM 的方案技术上不合理**

```
1. 不要说："我不管技术怎么实现，就要这个效果。"
2. 要说："你能帮我理解技术上的约束是什么？"
3. 然后："那在这些约束下，我们能实现的最接近目标用户的方案是什么？"
4. 一起找到满足用户需求且技术可行的方案
```

**场景 3：两个 PM 争夺同一资源**

```
1. 先私下沟通，了解对方的优先级和背景
2. 一起用框架评估（如 RICE、ICE）
3. 如果无法达成一致，带数据去找共同上级
4. 不在公开场合争论，保持专业
```

## 五、沟通策略

### 5.1 同步 vs 异步沟通

| 维度 | 同步沟通 | 异步沟通 |
|------|---------|---------|
| **适用场景** | 复杂讨论、决策会议、冲突处理 | 状态更新、文档评审、信息共享 |
| **工具** | 会议、电话、视频 | 文档、邮件、飞书消息、PR |
| **优点** | 实时反馈、减少误解 | 深度思考、可追溯、不打断 |
| **缺点** | 打断工作、效率低 | 反馈慢、可能理解偏差 |
| **PM 的使用原则** | 能异步就异步，必须同步时控制时长 | 文档先行，会议只讨论文档无法解决的 |

### 5.2 沟通方式选择决策树

```
需要沟通？
├── 信息传递（状态更新、周知）
│   └── 异步：飞书群消息 / 文档 / 周报
│
├── 需要讨论（方案选择、设计评审）
│   ├── 问题清晰、可书面表达 → 异步：文档 + 评论
│   └── 问题复杂、需要实时对齐 → 同步：会议（提前发文档）
│
├── 需要决策（Go/No-Go、优先级）
│   ├── 决策者明确、信息充分 → 异步：文档 + 签字
│   └── 需要多方讨论 → 同步：决策会议
│
└── 冲突处理
    └── 先异步收集各方观点 → 再同步讨论解决
```

### 5.3 会议效率优化

| 原则 | 具体做法 |
|------|---------|
| 会前有准备 | 提前 24h 发 agenda + 相关文档 |
| 会中有记录 | 指定记录人，实时记录 decisions + action items |
| 会后有跟进 | 24h 内发会议纪要，明确 owner 和 deadline |
| 能不开就不开 | 先问"这个能不能用文档解决？" |
| 控制人数 | 决策会议 ≤ 7 人，信息同步用文档代替 |
| 控制时间 | 默认 30 分钟，需要更长才加时间 |

**会议纪要模板：**

```markdown
# [会议主题] 会议纪要

> 日期：2026-07-10 | 参与人：xxx | 时长：30 min

## 讨论要点
1. xxx
2. xxx

## 决策
| 决策内容 | 负责人 | 依据 |
|---------|--------|------|
| xxx | xxx | xxx |

## Action Items
| 事项 | 负责人 | 截止日期 | 状态 |
|------|--------|---------|------|
| xxx | xxx | 2026-07-15 | 待完成 |

## 下次会议
- 时间：xxx
- 议题：xxx
```

### 5.4 书面沟通的最佳实践

| 场景 | 格式 | 要点 |
|------|------|------|
| 邮件汇报 | 金字塔结构 | 结论先行，附件详细 |
| 飞书消息 | 简短 + 行动项 | "请确认 xxx，截止日期 xxx" |
| 文档评审 | 评论 + 建议 | 指出具体位置，给出替代方案 |
| 周报 | 表格 + 趋势 | 进度、风险、下周计划 |

```
    背景：xxx
    建议：xxx
    需要你确认：xxx
    请今天 5 点前回复，谢谢！"
```

## 六、Shreyas Doshi 的 LNO 框架

### 6.1 框架定义

Shreyas Doshi（前 Stripe/Twitter/GPM）提出的任务分类框架：

| 类型 | 定义 | 标准 | 投入程度 |
|------|------|------|---------|
| **L — Leverage** | 杠杆任务：投入产出比极高的任务 | 做得好 vs 做得一般，结果差距巨大 | 全力投入，追求卓越 |
| **N — Neutral** | 中性任务：做了有收益，不做有损失 | 做得好 vs 做得一般，结果差距不大 | 做到 80 分即可，快速完成 |
| **O — Overhead** | 开销任务：必须做但不直接创造价值 | 不做会出问题，但做了也不会更好 | 最小化投入，能委托就委托 |

### 6.2 PM 的任务分类示例

| 任务 | 分类 | 理由 | 策略 |
|------|------|------|------|
| 定义产品战略 | L | 方向错了，执行再好也白费 | 花足够时间，深度思考 |
| 用户研究 | L | 洞察质量直接影响产品成败 | 亲自参与，深度访谈 |
| 写 PRD | N | 质量达标即可，不必追求完美 | 用模板加速，AI 辅助 |
| 参加周会 | N | 需要了解进展，但不必每个都精彩 | 准备好数据，30 分钟内结束 |
| 填报工时 | O | 必须做但无价值 | 每周五花 5 分钟批量填 |
| 回复例行邮件 | O | 必须回复但不需深度思考 | 批量处理，模板化回复 |
| 产品评审（关键项目） | L | 评审质量决定产品方向 | 充分准备，邀请正确的人 |
| 产品评审（例行项目） | N | 需要参与但不必每个都主导 | 快速过，聚焦关键问题 |

### 6.3 LNO 框架的使用方法

**Step 1：任务清单分类**

```
每天早上花 5 分钟：
1. 列出今天所有任务
2. 每个任务标记 L / N / O
3. L 任务安排在精力最好的时段
4. O 任务安排在精力低谷或批量处理
```

**Step 2：优化 L 任务的投入**

| L 任务 | 投入优化 |
|--------|---------|
| 产品战略 | 安排 2 小时深度思考，关闭所有通知 |
| 用户研究 | 亲自访谈 5 个用户，而不是看 50 份问卷 |
| 关键决策 | 用 Decision Journal 记录推理过程 |

**Step 3：压缩 N 和 O 任务的时间**

| N/O 任务 | 时间压缩方法 |
|---------|------------|
| 写 PRD | 用模板 + AI 辅助，从 4 小时压缩到 1.5 小时 |
| 周会 | 提前发周报，会议只讨论问题和决策 |
| 邮件 | 每天 2 个固定时段处理，其他时间不看 |
| 工时填报 | 每周五下午批量完成 |

### 6.4 LNO 与精力管理

```
精力曲线 vs 任务安排：

精力
高 │  ██ L 任务（深度思考、创意、决策）
   │  ██
   │  ██ L 任务
   │    ██ N 任务（文档、评审、讨论）
   │      ██
中 │        ██ N 任务
   │          ██
   │            ██ O 任务（邮件、审批、杂事）
低 │              ██ O 任务
   └───────────────────────────────── 时间
   9am              12pm             6pm
```

### 6.5 团队层面的 LNO 应用

作为 PM Lead，帮助团队成员识别 L 任务：

| 做法 | 效果 |
|------|------|
| 每周 1:1 讨论任务分类 | 帮助团队成员优先处理 L 任务 |
| 减少团队的 O 任务 | 自动化或取消不必要的流程 |
| 保护团队的 L 任务时间 | 减少打断、限制会议 |
| 公开自己的 LNO 分类 | 示范和推广这个思维方式 |

## 七、利益相关者管理的高阶技巧

### 7.1 建立信任账户

```
信任 = 可靠性 × 专业性 × 亲密度
       ─────────────────────────
            自我导向

可靠性：说到做到，按时交付
专业性：做决策有依据，能预判风险
亲密度：了解对方的诉求和压力
自我导向：减少，即少为自己争取，多为团队创造价值
```

**信任存款 vs 取款：**

| 存款（加分） | 取款（减分） |
|-------------|-------------|
| 主动分享信息 | 信息不透明 |
| 承认错误 | 推卸责任 |
| 帮助他人完成目标 | 只关心自己的 KPI |
| 提前预警风险 | 事后才说"我早就知道" |
| 兑现承诺 | 食言 |

### 7.2 影响力的来源

| 来源 | 说明 | 如何建立 |
|------|------|---------|
| **专业权威** | 你比别人更懂用户和市场 | 持续研究、分享洞察 |
| **信息优势** | 你掌握别人不知道的信息 | 建立信息网络、主动同步 |
| **关系网络** | 你认识关键决策者 | 投资关系、主动帮助 |
| **过往记录** | 你的判断经常被验证是对的 | 记录预测、复盘对错 |
| **人格魅力** | 别人愿意跟你合作 | 真诚、靠谱、有趣 |

### 7.3 利益相关者管理的日历

| 频率 | 活动 | 对象 |
|------|------|------|
| 每周 | 1:1 对齐 | 直属上级、核心协作方 |
| 每两周 | 路线图同步 | 跨团队 PM、市场、销售 |
| 每月 | 业务 Review | VP/Director 级别 |
| 每季度 | 战略对齐 | CEO/高管团队 |
| 按需 | 危机处理 | 相关利益方 |

### 7.4 常见错误与避坑

| 错误 | 后果 | 正确做法 |
|------|------|---------|
| 只向上管理，忽视横向 | 跨团队协作困难 | 同样投入精力经营横向关系 |
| 对所有人都用同一套话术 | 信息传递失效 | 根据对方风格定制沟通方式 |
| 冲突时选择回避 | 问题恶化，信任下降 | 及时、建设性地面对冲突 |
| 会议太多 | 团队效率下降 | 严格评估每个会议的必要性 |
| 只在需要帮忙时才联系 | 被认为是功利的 | 平时就投资关系，不只在有求时 |
| 不记录决策 | 同样的争论反复出现 | 用 Decision Log 记录每个重要决策 |
