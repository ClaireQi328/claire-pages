> 没有度量就没有管理，没有实验就没有优化。

## 一、North Star Metric（北极星指标）

### 1.1 定义

北极星指标是**最能反映产品为用户创造核心价值的单一指标**。它不是 KPI 的汇总，而是整个团队对"什么代表用户成功"的共识。

```
北极星指标 = 用户获得核心价值的量化表达
```

### 1.2 选择标准

| 标准 | 说明 | 反面例子 |
|------|------|---------|
| **反映用户价值** | 用户真的因为这个指标获益 | 注册用户数（不代表价值） |
| **领先指标** | 指标增长能预测未来收入 | 收入（是滞后指标） |
| **可行动** | 团队的行为能影响它 | 市场份额（受竞品影响） |
| **可度量** | 能准确、持续地测量 | 用户满意度（主观） |
| **易理解** | 全公司都能理解 | 复杂的加权公式 |
| **无虚荣成分** | 不会被刷量误导 | PV/UV |

### 1.3 经典北极星指标

| 产品类型 | 北极星指标 | 为什么 |
|---------|-----------|--------|
| 协作工具 | 每周活跃团队数 | 团队使用代表核心价值 |
| 电商 | 每周购买用户数 | 直接关联收入 |
| 内容平台 | 每日内容消费时长 | 用户获得内容价值 |
| SaaS 工具 | 每周完成关键任务数 | 反映产品使用深度 |
| 社交产品 | 每日发送消息用户数 | 连接价值的体现 |
| 支付产品 | 每月交易用户数 | 交易频次反映依赖度 |

### 1.4 北极星指标反模式

```
❌ 常见错误                    ✅ 正确做法

注册用户数                     激活用户数
月活跃用户 (MAU)               每周活跃团队数
页面浏览量 (PV)                内容消费时长
总收入                         付费用户数 × 人均使用频次
App 下载量                     每日打开 App 用户数
```

**反模式解析**：

| 反模式 | 问题 | 修正 |
|--------|------|------|
| **虚荣指标** | 数字好看但不反映价值 | 选领先指标，不选滞后指标 |
| **复合指标** | 太复杂，无法归因 | 保持单一、清晰 |
| **平台指标** | 只反映供给侧 | 兼顾供需两端 |
| **全局指标** | 掩盖局部问题 | 允许子指标拆解 |

## 二、指标层级体系

### 2.1 三层指标架构

```
┌─────────────────────────────────────────────────┐
│            North Star Metric                     │
│         （北极星指标：1 个）                       │
│     例：每周活跃付费团队数                         │
└──────────────────────┬──────────────────────────┘
                       │
        ┌──────────────┼──────────────┐
        │              │              │
┌───────▼──────┐ ┌─────▼──────┐ ┌────▼───────┐
│  Input       │ │  Input     │ │  Input     │
│  Metrics     │ │  Metrics   │ │  Metrics   │
│  (3~5 个)    │ │  (3~5 个)  │ │  (3~5 个)  │
│              │ │            │ │            │
│  注册转化率   │ │  激活率    │ │  付费转化率 │
│  邀请率      │ │  留存率    │ │  扩展收入   │
└──────────────┘ └────────────┘ └────────────┘
        │              │              │
┌───────▼──────────────▼──────────────▼───────┐
│              Guardrail Metrics               │
│              (护栏指标：5~10 个)              │
│                                             │
│  App 崩溃率 < 0.1%  | 页面加载 < 2s         │
│  客户满意度 > 4.0   | 退款率 < 2%           │
│  数据准确性 > 99.9% | 系统可用性 > 99.95%   │
└─────────────────────────────────────────────┘
```

### 2.2 指标层级详解

| 层级 | 数量 | 特征 | 作用 | 更新频率 |
|------|------|------|------|---------|
| **North Star** | 1 | 公司级、长期稳定 | 对齐方向 | 周/月 |
| **Input** | 3~5 | 可直接影响、领先指标 | 指导决策 | 日/周 |
| **Guardrail** | 5~10 | 底线、不可突破 | 防止副作用 | 实时/日 |

### 2.3 指标拆解示例

以"每周活跃付费团队数"为例：

```
每周活跃付费团队数
├── 新增付费团队数
│   ├── 注册 → 激活转化率
│   ├── 激活 → 付费转化率
│   └── 新注册团队数（渠道）
├── 存量付费团队留存率
│   ├── 周留存率
│   ├── 功能使用深度
│   └── 客户支持满意度
└── 流失团队复活率
    ├── 复活触达率
    └── 复活转化率
```

### 2.4 指标命名规范

```
命名公式：[动作] + [对象] + [时间窗口] + [计算方式]

✅ 每周活跃付费团队数
✅ 新用户 7 日激活率
✅ 月度净收入留存率 (NRR)
❌ 用户数（模糊）
❌ 转化率（哪个转化？）
❌ 活跃度（怎么算？）
```

## 三、因果推断 vs 相关性

### 3.1 核心区别

```
相关性：A 和 B 同时变化
因果性：A 导致 B 变化

经典例子：
冰淇淋销量 ↑  ←相关→  溺水人数 ↑
冰淇淋销量 ↑  ←因果→  温度 ↑
溺水人数 ↑    ←因果→  温度 ↑（更多人游泳）
```

### 3.2 相关性的陷阱

| 陷阱 | 例子 | 后果 |
|------|------|------|
| **伪相关** | 冰淇淋销量与溺水相关 | 做出错误决策 |
| **反向因果** | 活跃用户更多 → 功能使用更多（而非反过来） | 错误归因 |
| **遗漏变量** | 用户留存高是因为产品好，不是因为推送多 | 资源错配 |
| **幸存者偏差** | 只看活跃用户，忽略流失用户 | 高估效果 |

### 3.3 建立因果关系的方法

| 方法 | 适用场景 | 可信度 | 成本 |
|------|---------|--------|------|
| **A/B 测试** | 在线实验 | 最高 | 中 |
| **RCT（随机对照实验）** | 线下实验 | 最高 | 高 |
| **工具变量（IV）** | 无法随机化 | 高 | 中 |
| **断点回归（RDD）** | 有明确阈值 | 高 | 低 |
| **双重差分（DID）** | 政策变化 | 中高 | 低 |
| **倾向得分匹配（PSM）** | 观察性数据 | 中 | 低 |
| **Granger 因果检验** | 时间序列 | 低 | 低 |

### 3.4 产品经理的因果检查清单

在做决策前，问自己：

1. 这个相关性有没有可能被第三个变量解释？
2. 因果方向是否正确？（A→B 还是 B→A）
3. 能不能设计一个 A/B 测试来验证？
4. 如果不能做 A/B 测试，有没有自然实验的机会？
5. 这个结论在不同用户群体中是否一致？

## 四、A/B 测试全流程

### 4.1 流程总览

```
1. 假设     2. 设计     3. 执行     4. 分析     5. 决策
   │           │           │           │           │
   ▼           ▼           ▼           ▼           ▼
提出假设    计算样本量   随机分组    统计检验    上线/迭代
明确指标    设定显著性   监控护栏    计算效应    文档归档
            设定效应量   等待足够    多重检验
                        样本量
```

### 4.2 假设设计

**假设模板**：

```
如果我们 [做某个改变]，
那么 [核心指标] 会 [变化方向和幅度]，
因为 [用户行为逻辑]。

示例：
如果我们把注册按钮从灰色改为蓝色，
那么注册转化率会提升 5%~10%，
因为蓝色更醒目，且符合用户对"可点击"的预期。
```

**假设评估矩阵**：

| 维度 | 评估标准 | 评分 |
|------|---------|------|
| 影响力 | 如果成功，影响多大？ | 高/中/低 |
| 信心度 | 成功的概率有多大？ | 高/中/低 |
| 实现难度 | 需要多少开发资源？ | 高/中/低 |
| 优先级 | 影响力 × 信心度 / 实现难度 | 计算值 |

### 4.3 样本量计算

**核心概念**：

| 参数 | 含义 | 典型取值 |
|------|------|---------|
| **α（显著性水平）** | 第一类错误概率（假阳性） | 0.05（5%） |
| **β（第二类错误）** | 假阴性概率 | 0.2（20%） |
| **Power（统计功效）** | 1-β，检测出真实效应的概率 | 0.8（80%） |
| **MDE（最小可检测效应）** | 你希望检测到的最小变化 | 1%~10% |
| **Baseline Rate** | 当前基准转化率 | 已知 |

**样本量公式（近似）**：

```
n = 16 × σ² / δ²

n = 每组样本量
σ² = 方差（对于比率：p × (1-p)）
δ = MDE（最小可检测效应的绝对值）

简化版本（转化率场景）：
n ≈ 16 × p × (1-p) / (MDE)²
```

**快速参考表（α=0.05, Power=0.8）**：

| 基准转化率 | MDE=1% | MDE=2% | MDE=5% | MDE=10% |
|-----------|--------|--------|--------|---------|
| 5% | 1,522,000 | 380,500 | 60,880 | 15,220 |
| 10% | 2,896,000 | 724,000 | 115,840 | 28,960 |
| 20% | 5,120,000 | 1,280,000 | 204,800 | 51,200 |
| 30% | 6,724,000 | 1,681,000 | 268,960 | 67,240 |
| 50% | 7,840,000 | 1,960,000 | 313,600 | 78,400 |

**解读**：基准转化率越低、MDE 越小，需要的样本量越大。

### 4.4 显著性与效应量

#### 4.4.1 P 值

```
P 值 = 在零假设（H₀）为真的情况下，观察到当前或更极端结果的概率

P < 0.05 → 拒绝 H₀ → 差异"统计显著"
P ≥ 0.05 → 不能拒绝 H₀ → 差异不显著
```

**P 值不是什么**：

| 常见误解 | 正确理解 |
|---------|---------|
| P < 0.05 意味着效果是真的 | 只是说偶然概率低 |
| P = 0.03 意味着 3% 的概率是假的 | P 值不是假阳性概率 |
| P > 0.05 意味着没有效果 | 可能是样本量不够 |
| 小 P 值意味着大效果 | P 值与效应大小无关 |

#### 4.4.2 效应量（Effect Size）

```
Cohen's d = (Mean_A - Mean_B) / Pooled_StdDev

对于转化率：
绝对差异 = p_B - p_A
相对差异 = (p_B - p_A) / p_A × 100%
```

| 效应量 | Cohen's d | 实际意义 |
|--------|-----------|---------|
| 小 | 0.2 | 可检测但业务意义有限 |
| 中 | 0.5 | 有实际业务价值 |
| 大 | 0.8 | 显著的业务影响 |

**业务意义 vs 统计显著**：

```
              统计显著        统计不显著
业务意义大    ✅ 上线         ⚠️ 延长测试
业务意义小    ⚠️ 谨慎评估     ❌ 放弃
```

### 4.5 多重检验问题

当你同时测试多个变体或多个指标时，假阳性率会膨胀。

```
单次测试假阳性率：α = 5%
测试 1 次：至少一个假阳性的概率 = 5%
测试 5 次：至少一个假阳性的概率 = 1 - (1-0.05)^5 = 22.6%
测试 10 次：至少一个假阳性的概率 = 1 - (1-0.05)^10 = 40.1%
测试 20 次：至少一个假阳性的概率 = 1 - (1-0.05)^20 = 64.2%
```

**修正方法**：

| 方法 | 做法 | 适用场景 |
|------|------|---------|
| **Bonferroni** | α' = α / n（最保守） | 多指标检验 |
| **Benjamini-Hochberg (FDR)** | 控制错误发现率 | 探索性分析 |
| **Holm-Bonferroni** | 逐步修正（比 Bonferroni 灵活） | 通用 |
| **预注册主指标** | 只对主指标做显著性判断 | 最佳实践 |

## 五、A/B 测试反模式

### 5.1 P-hacking

**定义**：不断调整分析方法直到得到 P < 0.05。

```
❌ P-hacking 行为：
- 测试多个细分群体，只报告显著的那个
- 调整时间窗口直到结果显著
- 去掉"异常值"后重新分析
- 测试多个指标，只报告显著的
- 中途停止实验（刚好显著时）
```

**预防措施**：
1. 预注册假设、指标、分析计划
2. 指定单一主指标（Primary Metric）
3. 指定分析时间窗口，不提前查看
4. 所有分析（包括不显著的）都要报告

### 5.2 Peeking（偷看）

**定义**：在实验未达到预定样本量时反复查看结果并做出决策。

```
❌ Peeking 的危害：

样本量累积 →
时间 1: P=0.08 → 继续等
时间 2: P=0.03 → 停！上线！  ← 这就是偷看
时间 3: P=0.12 → （如果继续等）

偷看 + 提前停止 = 严重的假阳性膨胀
```

**正确做法**：

| 方法 | 说明 |
|------|------|
| **固定样本量** | 预计算样本量，到期再看 |
| **Sequential Testing** | 使用专用方法（如 mSPRT）允许中期查看 |
| **Alpha Spending** | 分配中期检验的显著性预算 |

### 5.3 Cherry-picking

**定义**：选择性报告有利结果，隐藏不利结果。

```
❌ Cherry-picking 场景：
- 测试了 5 个指标，只报告 2 个显著的
- 测试了 3 个用户群体，只报告效果最好的
- 测试了 2 周，只报告最好的那周
- 多个实验，只报告成功的
```

### 5.4 反模式速查表

| 反模式 | 表现 | 后果 | 预防 |
|--------|------|------|------|
| P-hacking | 调整分析直到显著 | 假阳性 | 预注册 |
| Peeking | 提前偷看结果 | 假阳性 | 固定样本量 |
| Cherry-picking | 选择性报告 | 误导决策 | 全量报告 |
| 样本污染 | 用户分到多组 | 效应稀释 | 用户级分组 |
| 新奇效应 | 新版本刚上线效果好 | 高估效果 | 等待稳定 |
| 幸存者偏差 | 只看留存用户 | 高估效果 | ITT 分析 |
| Simpson 悖论 | 整体与细分矛盾 | 错误结论 | 分层分析 |

## 七、A/B 测试实战 Checklist

### 7.1 实验前

- [ ] 假设已明确（改变什么 → 预期效果 → 为什么）
- [ ] 主指标已确定（只有 1 个 Primary Metric）
- [ ] 护栏指标已确定（防止副作用）
- [ ] 样本量已计算（基于 MDE 和基准值）
- [ ] 分流方案已确定（用户级 vs 会话级）
- [ ] 分流比例已确定（50/50 vs 90/10）
- [ ] 实验时长已确定（至少覆盖完整周期）
- [ ] 实验文档已创建（含假设、设计、指标）

### 7.2 实验中

- [ ] 分流均匀性已验证（AA 测试）
- [ ] 护栏指标无异常
- [ ] 新奇效应已消退（通常 1~2 周）
- [ ] 未提前偷看结果
- [ ] 样本污染已排查

### 7.3 实验后

- [ ] 主指标结果已分析
- [ ] 效应量已计算（不只是 P 值）
- [ ] 置信区间已报告
- [ ] 细分分析已完成（新/老用户、设备类型等）
- [ ] 多重检验已修正（如果测试了多个变体/指标）
- [ ] 实验结论已文档化
- [ ] 上线/迭代决策已做出
- [ ] 学习点已归档

## 八、从指标到决策的框架

### 8.1 数据驱动决策流程

```
1. 定义问题
   └── 业务问题是什么？想要改变什么？

2. 提出假设
   └── 什么原因导致这个问题？

3. 选择指标
   └── 什么指标能验证假设？

4. 设计实验
   └── 怎么隔离因果？

5. 收集数据
   └── 需要多少数据？多久？

6. 分析结果
   └── 效果是否显著？是否有业务意义？

7. 做出决策
   └── 上线？迭代？放弃？

8. 归档学习
   └── 学到了什么？下次怎么改进？
```

### 8.2 指标异常排查流程

```
指标异常
├── 确认数据准确性
│   ├── 埋点是否正常？
│   ├── 数据管道是否有延迟？
│   └── 是否有数据源变化？
│
├── 定位变化范围
│   ├── 哪个用户群体？
│   ├── 哪个渠道？
│   ├── 哪个功能？
│   └── 什么时间段开始？
│
├── 排查外部因素
│   ├── 是否有产品发布？
│   ├── 是否有营销活动？
│   ├── 是否有竞品动作？
│   └── 是否有季节性因素？
│
└── 制定行动
    ├── 如果是正向变化 → 复制到其他群体
    ├── 如果是负向变化 → 回滚或修复
    └── 如果原因不明 → 深入调研
```
