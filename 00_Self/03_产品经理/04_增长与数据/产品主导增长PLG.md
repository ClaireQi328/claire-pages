# 产品主导增长（PLG）

> Product-Led Growth：让产品本身成为最强大的获客、激活和留存引擎。

---

## 一、PLG 核心理念

### 1.1 什么是 PLG

PLG 是一种**以产品为核心驱动力的增长策略**。用户通过直接使用产品来完成获客、转化和扩展，而非依赖销售团队的推动。

| 维度 | 传统 Sales-Led | Product-Led Growth |
|------|---------------|-------------------|
| 获客方式 | SDR 外呼、市场活动 | 产品自传播、口碑 |
| 决策者 | 管理层/采购 | 终端用户 |
| 销售周期 | 数周到数月 | 数分钟到数天 |
| 收入驱动 | 销售团队规模 | 产品使用深度 |
| 客户获取成本 | 高 | 低（边际趋近于零） |
| 扩展模式 | 加人 | 加功能/加席位 |

**核心公式**：

```
PLG 增长 = 产品体验 × 自然传播 × 付费转化效率
```

### 1.2 PLG 的底层逻辑

```
用户发现产品 → 免费试用 → 体验核心价值 → 成为活跃用户 → 推荐他人
     ↑                                                    |
     └────────────────────────────────────────────────────┘
                        （正向循环）
```

关键转变：
- **从"卖产品"到"用产品"**：先让用户感受到价值，再谈付费
- **从"说服"到"证明"**：不靠 PPT，靠实际体验
- **从"一次性交易"到"持续关系"**：用户持续使用、持续付费、持续推荐

## 二、三种 PLG 模式

### 2.1 Freemium（免费增值）

**定义**：核心功能永久免费，高级功能付费。

| 要素 | 说明 |
|------|------|
| 免费范围 | 核心功能可用，有容量/功能上限 |
| 转化时机 | 用户遇到免费版天花板时 |
| 典型转化率 | 2%~5%（免费→付费） |
| 适合场景 | 工具类产品、协作类产品 |

**设计要点**：
- 免费版必须能独立传递核心价值（不能是残废版）
- 付费墙设置在"用户已经上瘾"之后
- 限制维度选择：功能 > 容量 > 时间

**经典 Freemium 限制设计**：

| 产品 | 免费限制 | 付费触发点 |
|------|---------|-----------|
| Slack | 消息历史 90 天 | 团队需要回溯历史 |
| Notion | 个人无限，团队 1000 块 | 团队协作需求增长 |
| Zoom | 40 分钟时长 | 会议需要更长时间 |
| Canva | 部分模板/素材 | 需要专业设计资源 |

### 2.2 Free Trial（免费试用）

**定义**：全功能开放，限定时间（通常 7~30 天）。

| 要素 | 说明 |
|------|------|
| 试用范围 | 全部功能 |
| 转化时机 | 试用到期前 |
| 典型转化率 | 10%~25% |
| 适合场景 | 复杂产品、需要数据积累的产品 |

**关键决策：是否需要信用卡？**

| 方案 | 优点 | 缺点 | 转化率影响 |
|------|------|------|-----------|
| 不要信用卡 | 注册门槛低，试用量大 | 质量参差不齐 | 注册量高，付费率低 |
| 要信用卡 | 用户意图强，转化率高 | 注册量大幅下降 | 注册量低，付费率高 |
| 延迟要信用卡 | 平衡两者 | 实现复杂 | 中等 |

### 2.3 Open Source（开源）

**定义**：核心产品开源，商业化通过托管服务、企业版、支持等。

| 要素 | 说明 |
|------|------|
| 获客方式 | 开源社区、GitHub star |
| 商业化路径 | SaaS 托管 > 企业版 > 专业服务 |
| 适合场景 | 开发者工具、基础设施产品 |

**经典案例**：

| 产品 | 开源策略 | 商业化 |
|------|---------|--------|
| GitLab | 核心开源 | SaaS + 企业版 |
| Plausible | 完全开源 | 托管服务收费 |
| Cal.com | 核心开源 | SaaS + 企业功能 |
| PostHog | 产品分析开源 | 云托管 + 企业版 |

## 三、关键指标体系

### 3.1 PLG 核心指标

```
                    ┌─────────────────┐
                    │  北极星指标       │
                    │ (Weekly Active   │
                    │  Teams/Paying)   │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
     ┌────────▼──────┐ ┌────▼─────┐ ┌──────▼───────┐
     │   激活率       │ │ TTV      │ │ 自然传播系数  │
     │ Activation    │ │ Time-to- │ │ Viral        │
     │ Rate         │ │ Value    │ │ Coefficient  │
     └───────────────┘ └──────────┘ └──────────────┘
```

#### 3.1.1 激活率（Activation Rate）

**定义**：新注册用户在指定时间内完成关键动作的比例。

```
激活率 = 完成 Aha Moment 的用户数 / 总注册用户数 × 100%
```

**各产品 Aha Moment 对照**：

| 产品 | Aha Moment | 时间窗口 |
|------|-----------|---------|
| Slack | 团队发送 2000 条消息 | 7 天 |
| Dropbox | 存入第一个文件 | 第一天 |
| Facebook | 10 天内加 7 个好友 | 10 天 |
| Twitter | 关注 30 个账号 | 7 天 |
| Notion | 创建第一个数据库 | 第一天 |
| Zoom | 完成第一次会议 | 第一天 |

**提升激活率的方法**：
1. 减少注册步骤（Social Login、延迟注册）
2. 引导式 Onboarding（Checklist、Tooltip Tour）
3. 预填模板/示例数据（降低空白恐惧）
4. 渐进式披露（Progressive Disclosure）

#### 3.1.2 Time-to-Value（TTV）

**定义**：从注册到感受到产品核心价值的时间。

```
TTV = 用户首次体验 Aha Moment 的时间 - 注册时间
```

| TTV 范围 | 产品类型 | 策略 |
|---------|---------|------|
| < 5 分钟 | 工具类 | 即开即用，预设模板 |
| 5~30 分钟 | 协作类 | 快速邀请队友，Demo 数据 |
| 30 分钟~2 小时 | 分析类 | 数据导入向导，自动报告 |
| 数天 | 平台类 | 渐进式搭建，分步引导 |

**缩短 TTV 的设计手段**：

```
传统流程：注册 → 完善资料 → 学习教程 → 配置 → 使用
    TTV: ████████████████████████████████████ 长

PLG 流程：注册 → 预设模板 → 立即体验核心功能 → 自然探索
    TTV: ████████ 短
```

#### 3.1.3 自然传播系数（Viral Coefficient / K-factor）

**定义**：每个现有用户平均带来的新用户数。

```
K = i × c

i = 每个用户发出的邀请数
c = 邀请转化率

K > 1 → 指数增长
K = 1 → 线性增长
K < 1 → 增长衰减（需要其他渠道补充）
```

**各产品传播系数参考**：

| 产品 | 传播机制 | K 估算 |
|------|---------|--------|
| Zoom | 会议链接传播 | 1.2~1.5 |
| Slack | 团队邀请 | 0.8~1.2 |
| Calendly | 日程链接分享 | 1.0~1.5 |
| Notion | 模板分享 | 0.3~0.6 |
| Dropbox | 存储空间邀请 | 0.8~1.0 |

### 3.2 PLG 指标看板

| 指标 | 计算方式 | 健康基线 | 预警线 |
|------|---------|---------|--------|
| 注册→激活率 | 激活用户/注册用户 | > 30% | < 15% |
| TTV 中位数 | 中位数(首次价值体验-注册) | < 10 分钟 | > 30 分钟 |
| 免费→付费转化率 | 付费用户/免费用户 | > 3% | < 1% |
| 自然传播系数 K | i × c | > 0.5 | < 0.2 |
| 月活跃率 MAU/注册 | MAU/累计注册 | > 25% | < 10% |
| 净收入留存 NRR | (期初 MRR + 扩展 - 流失)/期初 MRR | > 110% | < 90% |

## 四、经典案例深度拆解

### 4.1 Slack — 团队协作的 PLG 标杆

**增长路径**：

```
个人试用 → 邀请同事 → 团队依赖 → 公司采购
     │            │           │          │
   Freemium    病毒传播     转换成本高   Sales 接手
```

**关键策略**：
1. **内建传播**：必须邀请他人才能体验核心价值（协作）
2. **渐进式限制**：免费版 90 天消息历史，团队越大越不够用
3. **Bottom-up 渗透**：从一个团队扩展到整个公司
4. **Magic Number**：团队发送 2000 条消息 → 留存率飙升

**数据**：
- 2014 年上线，8000 家公司申请试用
- 免费→付费转化率：30%（远超行业平均）
- 日活用户发送消息量：人均 40+ 条/天

### 4.2 Notion — 模板驱动的增长引擎

**增长飞轮**：

```
用户创建页面 → 分享给他人 → 新用户体验 → 创建自己的页面
      │                                      |
      └── 制作模板 → 发布到社区 → 更多人使用 ──┘
```

**关键策略**：
1. **模板市场**：降低上手门槛，同时产生 UGC 内容
2. **All-in-One 定位**：文档 + 数据库 + Wiki + 项目管理
3. **社区驱动**：用户自发制作教程、模板，形成内容生态
4. **教育市场**：学生免费，培养下一代用户

**增长数据**：
- 2020→2021：用户从 400 万增长到 2000 万
- 模板市场贡献超过 30% 的新用户来源
- NRR 超过 130%（席位扩展 + 功能升级）

### 4.3 Figma — 协作设计的颠覆者

**PLG 创新点**：

| 传统设计工具 | Figma |
|------------|-------|
| 本地安装，文件传来传去 | 浏览器打开，实时协作 |
| 设计师封闭工作 | 所有人都可以查看、评论 |
| 版本管理混乱 | 自动版本，链接分享 |
| 价格高，按 license 收费 | 免费版可用，按编辑者收费 |

**关键策略**：
1. **浏览器优先**：零安装，分享链接即可查看
2. **协作即传播**：每个查看者都是潜在用户
3. **组件库复用**：设计系统成为团队基础设施
4. **社区资源**：UI kit、图标库、模板降低使用门槛

### 4.4 Cal.com — 开源 PLG 的典范

**开源 + SaaS 双轨模式**：

```
GitHub 开源 → 开发者自部署 → 贡献代码 → 生态扩展
                    │
                    ├── 个人用户 → SaaS 免费版
                    │
                    └── 团队/企业 → SaaS 付费版/企业版
```

**关键策略**：
1. **完全开源核心**：建立信任，社区贡献
2. **一键部署**：降低自部署门槛
3. **SaaS 版本差异化**：托管、支持、企业功能
4. **API 优先**：嵌入式调度，扩展使用场景

## 五、PLG vs SLG 对比与混合模式

### 5.1 纯 PLG vs 纯 SLG

| 维度 | PLG | SLG |
|------|-----|-----|
| CAC（获客成本） | 低 | 高 |
| 销售周期 | 短（自助） | 长（人工跟进） |
| 客单价 | 低→中 | 中→高 |
| 可扩展性 | 高（边际成本低） | 低（依赖人员） |
| 适合客群 | SMB、个人用户 | Enterprise |
| 典型代表 | Zoom、Slack | Salesforce、Workday |
| 增长瓶颈 | 免费转付费率 | 销售产能 |

### 5.2 混合模式（PLG + SLG）

最成功的 SaaS 公司往往是混合模式：

```
                 PLG 漏斗                    SLG 漏斗
            ┌───────────────┐           ┌───────────────┐
            │  免费注册       │           │  Outbound     │
            │  (大量用户)     │           │  (精准客户)    │
            ├───────────────┤           ├───────────────┤
            │  自助激活       │           │  Demo + POC   │
            ├───────────────┤           ├───────────────┤
            │  自助付费       │           │  方案定制      │
            │  (信用卡)       │           ├───────────────┤
            ├───────────────┤           │  合同签约      │
            │  PQL 识别 ─────┼───合并───→│               │
            │  (高使用量用户)  │           │  大客户 Account│
            └───────────────┘           └───────────────┘
```

**PQL（Product Qualified Lead）定义**：

| 信号 | 说明 | 权重 |
|------|------|------|
| 使用频率 | 连续 7 天活跃 | 高 |
| 功能深度 | 使用高级功能 | 高 |
| 团队规模 | 邀请 > 5 人 | 中 |
| 数据量 | 创建内容超过阈值 | 中 |
| 触碰天花板 | 接近免费限制 | 高 |

**混合模式演进路径**：

```
阶段 1：纯 PLG → 积累用户基数
阶段 2：PLG + PQL → 识别高价值用户
阶段 3：PLG + PQL + Inside Sales → 主动触达
阶段 4：PLG + PQL + Field Sales → 覆盖企业客户
```

### 5.3 选择框架

```
你的产品适合什么模式？

Q1: 客户能否自助理解产品价值？
├── 是 → 倾向 PLG
└── 否 → 倾向 SLG

Q2: 平均客单价（ACV）？
├── < $1K → 纯 PLG
├── $1K~$25K → PLG + Inside Sales
├── $25K~$100K → PLG + Field Sales
└── > $100K → 纯 SLG + PLG 辅助

Q3: 决策流程？
├── 个人/小团队决定 → PLG
└── 需要多层审批 → SLG + PLG 培育
```

## 六、自助 Onboarding 设计原则

### 6.1 核心原则

| 原则 | 说明 | 实践 |
|------|------|------|
| **零摩擦启动** | 注册到首次价值体验，步骤最少 | Social Login、延迟注册、预填数据 |
| **渐进式披露** | 不一次性展示所有功能 | 按用户进度解锁功能提示 |
| **主动引导** | 不让用户迷失在空白页面 | Checklist、Tooltip Tour、空状态设计 |
| **即时反馈** | 每个动作都有响应 | 成就动效、进度条、确认提示 |
| **可逆操作** | 用户不怕试错 | Undo、版本历史、确认弹窗 |

### 6.2 Onboarding 模式对比

| 模式 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **Checklist** | 功能多的产品 | 完成感驱动、可追踪 | 可能变成任务负担 |
| **Tooltip Tour** | 界面复杂的产品 | 按需展示、不打断流程 | 容易被跳过 |
| **模板驱动** | 创作类产品 | 降低空白恐惧、快速上手 | 模板选择困难 |
| **Interactive Tutorial** | 概念新的产品 | 学习效果好 | 开发成本高 |
| **Empty State 引导** | 所有产品 | 自然融入界面 | 引导强度弱 |

### 6.3 Onboarding 流程设计模板

```
注册 (30 秒)
  │
  ├── 选择角色/场景 (10 秒)
  │     └── 个性化后续体验
  │
  ├── 关键动作引导 (2 分钟)
  │     └── 完成一个最小有价值任务
  │
  ├── 即时价值反馈 (即时)
  │     └── 展示成果、鼓励分享
  │
  └── 进阶功能提示 (持续)
        └── 按使用深度逐步解锁
```

### 6.4 Onboarding 优化 Checklist

- [ ] 注册步骤 ≤ 3 步
- [ ] Social Login 可用（Google/微信/GitHub）
- [ ] TTV < 5 分钟（工具类）或 < 30 分钟（平台类）
- [ ] 有明确的 Aha Moment 定义
- [ ] 空状态有引导设计
- [ ] 首次使用有模板或示例数据
- [ ] 关键动作有即时反馈
- [ ] 有 Onboarding 邮件/消息序列
- [ ] 激活率指标已埋点
- [ ] 有 A/B 测试计划

## 七、PLG 实施路线图

### 7.1 从零开始的 PLG 建设

```
Phase 1: 基础建设 (1-2 个月)
├── 定义 Aha Moment
├── 设计免费版边界
├── 搭建自助注册流程
└── 埋点关键行为

Phase 2: 体验优化 (2-3 个月)
├── 优化 Onboarding 流程
├── 设计引导体系
├── 缩短 TTV
└── 建立反馈循环

Phase 3: 传播引擎 (2-3 个月)
├── 内建分享机制
├── 模板/内容市场
├── 推荐奖励计划
└── 社区建设

Phase 4: 商业化优化 (持续)
├── PQL 模型搭建
├── 付费墙 A/B 测试
├── 扩展收入策略
└── Sales-Assist 流程
```

### 7.2 常见陷阱

| 陷阱 | 表现 | 解法 |
|------|------|------|
| **免费版太好** | 没有付费动力 | 设计合理的天花板 |
| **免费版太差** | 用户体验不到价值 | 确保核心功能可用 |
| **TTV 太长** | 注册后流失严重 | 精简引导、预填数据 |
| **忽视留存** | 只关注获客 | 留存优先于获客 |
| **过早加 Sales** | PLG 还没跑通就招销售 | 先验证 PMF 和转化率 |
| **指标虚荣** | 只看注册数 | 关注激活率和留存率 |

## 八、AI 时代的 Agent 产品指标体系

> 传统 PLG 指标关注"用户行为"，AI Agent 产品需要额外关注**模型能力、Token 效率和任务完成质量**。以下框架将传统增长指标与 AI 原生指标融合。

### 8.1 AI Agent 评估维度总览

```
                    ┌───────────────────────┐
                    │  Agent 产品北极星指标   │
                    │  任务完成率 × ROI      │
                    └──────────┬────────────┘
                               │
         ┌─────────────┬───────┴───────┬─────────────┐
         │             │               │             │
    ┌────▼────┐  ┌─────▼─────┐  ┌─────▼─────┐  ┌────▼────┐
    │ 效果指标 │  │ 效率指标   │  │ 成本指标   │  │ 安全指标 │
    │ Quality │  │ Efficiency│  │  Cost     │  │ Safety  │
    └─────────┘  └───────────┘  └───────────┘  └─────────┘
```

### 8.2 效果指标（Quality）—— Agent "能不能用"

| 指标 | 定义 | 计算方式 | 健康基线 | 数据来源 |
|------|------|---------|---------|---------|
| **任务完成率 (Task Completion Rate)** | Agent 成功完成目标任务的比率 | 成功任务数 / 总任务数 | > 80% | GAIA / SWE-bench |
| **准确率 (Accuracy)** | 输出结果的正确性 | 正确输出 / 总输出 | > 85% | 人工标注 + LLM-as-Judge |
| **幻觉率 (Hallucination Rate)** | 输出中包含虚构/错误信息的比率 | 含幻觉输出 / 总输出 | < 5% | 事实核查 pipeline |
| **工具调用成功率** | Agent 正确选择和使用工具的比率 | 成功调用 / 总调用 | > 90% | ToolBench / API-Bank |
| **多轮对话一致性** | 长对话中保持上下文连贯的能力 | 上下文一致轮次 / 总轮次 | > 85% | AgentBoard |
| **指令遵循率** | 按照用户指令执行的精确度 | 遵循指令 / 总指令 | > 90% | IFEval |

**核心 Benchmark 速查**：

| Benchmark | 评估维度 | 难度 | 说明 |
|-----------|---------|------|------|
| **SWE-bench / SWE-bench Verified** | 代码 Agent 解决 GitHub Issue | ★★★★ | 业界最权威的编码 Agent 评测 |
| **GAIA** | 通用 AI 助手多步推理 | ★★★★ | 需要工具使用 + 网页浏览 + 文档处理 |
| **AgentBench** | 多环境 Agent 交互 | ★★★ | OS / 数据库 / 知识图谱 / 网页 / 购物 |
| **WebArena / VisualWebArena** | 网页自动化 Agent | ★★★★ | 真实网站环境下的任务完成 |
| **τ-bench (Tau-bench)** | 客服场景 Agent | ★★★ | 航班预订、客户服务对话 |
| **MLE-bench** | 机器学习工程 Agent | ★★★★ | Kaggle 竞赛级别的 ML 工程任务 |
| **BrowserGym** | 浏览器自动化 | ★★★ | 跨网站交互能力评测 |
| **ToolBench / API-Bank** | 工具调用能力 | ★★ | 函数调用、API 使用准确性 |
| **HumanEval / MBPP** | 代码生成 | ★★ | 基础代码生成能力 |
| **LM Arena (Chatbot Arena)** | 人类偏好排名 | ★★★ | ELO 评分，用户盲测投票 |

### 8.3 效率指标（Efficiency）—— Agent "快不快、省不省"

| 指标 | 定义 | 计算方式 | 优化方向 |
|------|------|---------|---------|
| **Token 效率比** | 有效产出 / Token 消耗总量 | 成功任务的 Token / 总 Token | 提高每次推理的有效信息密度 |
| **单任务 Token 消耗** | 完成一个任务平均消耗的 Token 数 | 总 Token / 完成任务数 | 压缩 Prompt、减少无效推理 |
| **推理轮次 (Agent Steps)** | 完成任务所需的平均推理步数 | 总步数 / 任务数 | 更好的规划、减少试错 |
| **首次正确率 (First-Try Rate)** | 第一次就成功完成任务的比率 | 首次成功 / 总任务 | 减少 Retry 循环 |
| **端到端延迟 (E2E Latency)** | 从用户发出请求到最终结果的时间 | P50 / P95 / P99 延迟 | 流式输出、并行工具调用 |
| **上下文利用率** | 有效使用的上下文窗口占比 | 有效 Token / 上下文长度 | 避免冗余上下文填充 |

**Token 消耗结构拆解**：

```
单次 Agent 任务的 Token 成本构成
┌─────────────────────────────────────────────┐
│ System Prompt (固定开销)          ~15-25%    │
├─────────────────────────────────────────────┤
│ 用户输入 + 上下文                 ~10-15%    │
├─────────────────────────────────────────────┤
│ Agent 推理链 (Chain-of-Thought)   ~30-40%    │  ← 最大的优化空间
├─────────────────────────────────────────────┤
│ 工具调用 (输入/输出)              ~15-25%    │
├─────────────────────────────────────────────┤
│ 错误重试 (Retry/Loop)            ~5-20%     │  ← 衡量 Agent 成熟度
└─────────────────────────────────────────────┘
```

### 8.4 成本指标（Cost）—— Agent "划不划算"

| 指标 | 定义 | 计算方式 | 说明 |
|------|------|---------|------|
| **单任务成本 (Cost per Task, CPT)** | 完成一个任务的总成本 | (输入 Token × 单价 + 输出 Token × 单价 + 工具调用费) / 成功任务数 | 最核心的成本效率指标 |
| **有效成本率 (Effective Cost)** | 单位正确产出的成本 | 总成本 / 正确完成的任务数 | 排除失败重试的浪费 |
| **人工兜底率 (Human Escalation Rate)** | 需要人工介入的比率 | 人工介入次数 / 总任务数 | 越低越好，直接影响人力成本 |
| **Token 浪费率** | 无效 Token 消耗占比 | 重试 + 冗余 Token / 总 Token | 衡量 Agent 成熟度 |
| **ROI 倍数** | Agent 替代人力的价值比 | 人力成本节省 / Agent 运行成本 | > 3x 为健康 |

| GPT-4o-mini | ~0.15 | ~0.60 | 轻量高效 |
| Claude 3.5 Sonnet | ~3.00 | ~15.00 | 代码/推理强 |
| Claude 3.5 Haiku | ~0.80 | ~4.00 | 快速低成本 |
| Gemini 1.5 Pro | ~1.25 / ~2.50* | ~5.00 / ~10.00* | 长上下文 |
| DeepSeek-V3 | ~0.27 | ~1.10 | 国产性价比 |
| Qwen-Max | ~1.60 | ~6.40 | 国产旗舰 |

> *Gemini 1.5 Pro 价格区分 ≤128k / >128k 上下文

### 8.5 安全与可靠性指标（Safety & Reliability）

| 指标 | 定义 | 计算方式 | 预警线 |
|------|------|---------|--------|
| **安全拒绝率** | 正确拒绝有害请求的比率 | 正确拒绝 / 有害请求总数 | > 95% |

| **Guardrail 触发率** | 安全护栏被触发的频率 | 触发次数 / 总请求 | 监控趋势 |

### 8.7 成本优化策略

| 策略 | 原理 | 节省幅度 | 实施难度 |
|------|------|---------|---------|
| **模型路由 (Model Routing)** | 简单任务用小模型，复杂任务用大模型 | 40%~70% | ★★ |
| **语义缓存 (Semantic Cache)** | 相似问题命中缓存，不重复推理 | 20%~50% | ★★★ |
| **Prompt 压缩** | 精简 System Prompt 和上下文 | 10%~30% | ★★ |
| **上下文裁剪 (Context Pruning)** | 只保留相关历史，丢弃冗余 | 15%~30% | ★★★ |
| **级联架构 (Cascade)** | 先用廉价模型尝试，失败再升级 | 30%~60% | ★★★ |
| **批量推理 (Batch API)** | 非实时任务走批量通道 | 20%~50% | ★ |
| **结构化输出 (Structured Output)** | 强制 JSON Schema，减少解析失败 | 5%~15% | ★ |
| **Speculative Decoding** | 小模型草稿 + 大模型验证 | 20%~40% | ★★★★ |

**模型路由决策树**：

```
用户请求
    │
    ├── 意图明确 + 简单任务 → Haiku / Mini (低成本)
    │     例：FAQ 回答、格式转换、简单分类
    │
    ├── 中等复杂度 → Sonnet / GPT-4o (平衡)
    │     例：数据分析、文档总结、代码 Review
    │
    └── 高复杂度 / 需要深度推理 → Opus / GPT-4o + CoT (高成本)
          例：架构设计、多步推理、创意写作
```

### 8.8 Agent 评估方法论

| 方法 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **LLM-as-Judge** | 自动化批量评估 | 可扩展、成本可控 | 评判模型本身有偏见 |
| **人工标注 (Human Eval)** | 高质量基准集 | 最准确 | 成本高、不可扩展 |
| **A/B 测试** | 在线对比实验 | 反映真实用户偏好 | 需要流量、周期长 |
| **Pairwise 对比** | 模型间横向比较 | 比绝对评分更稳定 | 只有相对排名 |
| **代码评估器 (Code Evaluator)** | 确定性检查 | 无偏见、可重复 | 只能检查格式/结构 |
| **端到端 Benchmark** | 标准化评测 | 可横向对比 | 可能与真实场景脱节 |

**评估 Pipeline 建议**：

```
开发阶段 → 离线 Benchmark (SWE-bench / GAIA / 自建测试集)
    │
    ├── 不达标 → 迭代 Prompt / 模型 / 架构
    │
    └── 达标 → 灰度上线
              │
              ├── 在线 LLM-as-Judge 持续监控
              ├── 用户反馈采集 (👍👎 + 文字)
              └── 异常自动告警 (幻觉率飙升 / 延迟异常)
```

### 8.10 DAA：AI 时代的新度量衡

> 2026 年 5 月 13 日，百度 Create2026 大会上，李彦宏提出全新指标——**DAA（Daily Active Agents，日活智能体数）**，试图重新定义 AI 时代的价值度量标准。

#### 8.10.1 从 Token 到 DAA 的范式转变

| 维度 | Token 消耗量 | DAA（日活智能体数） |
|------|------------|-------------------|
| **衡量本质** | 投入（成本） | 产出（价值） |
| **代表含义** | 用户为 AI 消耗了多少算力 | 有多少智能体在给用户干活、交付结果 |
| **商业模式** | 卖算力（按量计费） | 卖结果（按价值计费） |
| **用户视角** | "我花了多少钱" | "它帮我干了多少事" |
| **类比** | DAU（日活跃用户数） | 日活"数字员工"数 |

**核心观点**：

```
传统 AI 度量：Token 消耗量 = 用户花了多少钱（成本视角）
    ↓
DAA 度量：日活智能体数 = 有多少 Agent 在替用户交付结果（价值视角）

关键转变：从"烧算力"到"干实事"
```

#### 8.10.2 DAA 指标定义与计算

**DAA（Daily Active Agents）**= 每日活跃智能体数

```
DAA = Σ（每个独立智能体实例 × 当日活跃条件）

活跃条件：
├── 完成至少 1 个任务
├── 产生至少 1 次工具调用
├── 生成至少 1 条有效输出
└── 接受至少 1 条用户指令
```

**DAA 的细分维度**：

| 维度 | 分类 | 说明 |
|------|------|------|
| **按类型** | 通用 Agent / 垂直 Agent | DuMate 等通用型 vs 秒哒、伐谋等垂直型 |
| **按形态** | C 端 Agent / B 端 Agent | 个人用户使用 vs 企业构建 |
| **按活跃度** | 高活跃 / 中活跃 / 低活跃 | 日任务数 >10 / 1-10 / <1 |
| **按价值交付** | 结果交付型 / 辅助增强型 | 独立完成任务 vs 辅助人类决策 |

#### 8.10.3 DAA vs 传统互联网指标

| 传统指标 | AI Agent 时代对应指标 | 说明 |
|---------|---------------------|------|
| DAU（日活跃用户数） | **DAA（日活智能体数）** | 从"多少人在用"到"多少 Agent 在干活" |
| MAU（月活跃用户数） | MAA（月活智能体数） | Agent 的长期活跃度 |
| 用户时长 | Agent 任务时长 | 从"用户停留多久"到"Agent 执行多久" |
| ARPU（用户平均收入） | ARPA（Agent 平均收入） | 单个 Agent 创造的收入 |
| 留存率 | Agent 存活率 | Agent 是否持续被使用和迭代 |
| 获客成本 CAC | Agent 部署成本 | 创建/配置一个 Agent 的成本 |

#### 8.10.4 DAA 与 Token 的关系

```
                    DAA 与 Token 不是对立，而是互补
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   Token 消耗量（投入端）         DAA（产出端）               │
│   ├── 输入 Token                ├── 日活通用 Agent 数       │
│   ├── 输出 Token                ├── 日活垂直 Agent 数       │
│   ├── 工具调用 Token            ├── Agent 任务完成数        │
│   └── 重试/冗余 Token           └── Agent 交付结果数        │
│                                                             │
│   关键公式：                                                │
│   Agent 效率 = DAA × 任务完成率 / Token 消耗总量            │
│                                                             │
│   → 同样的 Token 投入，DAA 越高 = Agent 越高效              │
└─────────────────────────────────────────────────────────────┘
```

#### 8.10.5 DAA 生态数据（百度案例）

| 指标 | 数据 | 说明 |
|------|------|------|
| 百度千帆平台 Agent 数 | >130 万个 | 截至 2026 年 2 月，企业构建的智能体 |
| DuMate 评测水平 | 多个国际 Agent Benchmark SOTA | 通用智能体能力验证 |
| 未来全球 DAA 预测 | >100 亿 | 李彦宏预测的全球日活智能体数 |

**百度 Agent 矩阵**：

```
DuMate（通用智能体入口）
    │
    ├── AI 搜索（信息获取）
    ├── 秒哒（快速执行）
    ├── 伐谋（复杂推理 + 自我演化）
    ├── 数字人（形象交互）
    ├── 文库（文档处理）
    └── 百科（知识查询）

核心特点：从"分散的垂直智能体" → "统一的通用智能体入口"
```

#### 8.10.6 DAA 视角下的 AI 产品评价框架

| 评价维度 | 关键问题 | 对应指标 |
|---------|---------|---------|
| **Agent 活跃度** | 有多少 Agent 在每天干活？ | DAA、DAA 增长率 |
| **任务交付能力** | Agent 交付了多少结果？ | 任务完成率、结果准确率 |
| **用户依赖度** | 用户离不开 Agent 吗？ | Agent 留存率、任务频次 |
| **效率提升** | Agent 比人工快多少？ | 单任务耗时对比、ROI 倍数 |
| **生态丰富度** | Agent 能调用多少能力？ | 工具调用种类、Skill 数量 |
| **自我进化能力** | Agent 越用越强吗？ | 任务完成率趋势、错误率下降 |

#### 8.10.7 DAA 对 PLG 的启示

> DAA 本质上是 PLG 思想在 AI Agent 时代的延伸：**让 Agent 本身成为增长引擎**。

```
传统 PLG 飞轮：
用户使用产品 → 体验价值 → 推荐他人 → 更多用户

AI Agent 时代飞轮（DAA 驱动）：
Agent 干活 → 交付结果 → 用户信任 → 更多任务委托
    ↑                                      │
    └── 更多使用数据 → Agent 自我进化 ←────┘
           │
           └── DAA 增长 → 单任务成本下降 → 免费额度提升 → 更多用户
```

**DAA 时代的产品策略**：

| 策略 | 说明 | 案例 |
|------|------|------|
| **Agent-first 设计** | 产品以 Agent 为核心，而非传统 UI | DuMate 一句话完成任务 |
| **结果导向定价** | 按交付结果收费，而非 Token 消耗 | "帮你写完报告" vs "消耗 10 万 Token" |
| **Skill 生态** | 能力模块化，Agent 可编排调用 | 百度秒哒、伐谋、数字人集成 |
| **自我进化闭环** | Agent 能评估自己的输出并改进 | 伐谋的"能验证、能闭环"机制 |
