## 一、RESTful API 设计原则

### 1.1 什么是 REST

REST（Representational State Transfer）是一种架构风格，不是协议。核心思想：**资源（Resource）+ 动词（HTTP Method）+ 表述（Representation）**。

### 1.2 六大约束

| 约束 | 含义 | PM 关注点 |
|------|------|-----------|
| 客户端-服务器分离 | 前后端独立演进 | 前端可以独立迭代，不影响后端 |
| 无状态 | 每个请求包含全部信息 | 影响性能和扩展性设计 |
| 可缓存 | 响应可标记为可缓存 | 影响数据实时性 vs 性能权衡 |
| 统一接口 | 标准化的资源操作方式 | 降低团队协作成本 |
| 分层系统 | 客户端不感知中间层 | 安全、负载均衡可独立添加 |
| 按需代码（可选） | 服务器可返回可执行代码 | 小程序/插件场景 |

### 1.3 设计规范速查

```
✅ 好的设计                          ❌ 差的设计
GET    /users/{id}                  GET    /getUser?id=123
POST   /users                       POST   /createUser
PUT    /users/{id}                  POST   /updateUser
DELETE /users/{id}                  POST   /deleteUser
GET    /orders?status=paid          GET    /getPaidOrders
```

**命名规则**：
- 资源用**名词复数**：`/users`、`/orders`，不用 `/user`
- 操作用 **HTTP Method** 表达，不在 URL 里写动词
- 嵌套资源：`/users/{id}/orders`（但不超过 2 层）
- 查询参数：过滤 `?status=paid`，分页 `?page=2&size=20`，排序 `?sort=created_at:desc`

### 1.4 状态码规范

| 范围 | 含义 | 常用码 |
|------|------|--------|
| 2xx 成功 | 操作成功 | 200 OK / 201 Created / 204 No Content |
| 3xx 重定向 | 资源移动 | 301 Moved / 304 Not Modified |
| 4xx 客户端错误 | 请求有问题 | 400 Bad Request / 401 Unauthorized / 403 Forbidden / 404 Not Found / 409 Conflict / 422 Unprocessable / 429 Too Many Requests |
| 5xx 服务器错误 | 服务端故障 | 500 Internal Error / 502 Bad Gateway / 503 Service Unavailable |

**PM 要点**：错误响应必须包含结构化信息（error code + message + details），不能只返回 "error"。这直接影响用户体验和客服排查效率。

### 1.5 版本管理

| 策略 | 示例 | 优缺点 |
|------|------|--------|
| URL 路径 | `/v1/users` | 简单直观，URL 膨胀 |
| Header | `Accept: application/vnd.api.v1+json` | URL 干净，调试不便 |
| Query Param | `/users?version=1` | 容易缓存污染 |

**推荐**：URL 路径方式（`/v1/`），最直观，适合大多数团队。

## 二、GraphQL vs REST 选型

### 2.1 核心差异

```
REST：一个资源一个端点，前端组装数据
┌──────┐    GET /users/1      ┌──────┐
│Client├──────────────────────►│Server│
│      │◄──────────────────────│      │
│      │    { user data }     │      │
│      │                       │      │
│      │    GET /users/1/orders│      │
│      ├──────────────────────►│      │
│      │◄──────────────────────│      │
│      │    { order data }    │      │
└──────┘                       └──────┘

GraphQL：一个端点，前端声明需要什么
┌──────┐    POST /graphql     ┌──────┐
│Client├──────────────────────►│Server│
│      │  { user(1) { name,   │      │
│      │    orders { total }  │      │
│      │  } }                 │      │
│      │◄──────────────────────│      │
│      │  { 按需返回 }         │      │
└──────┘                       └──────┘
```

### 2.2 选型决策表

| 维度 | REST 更适合 | GraphQL 更适合 |
|------|------------|----------------|
| 数据需求 | 固定、可预测 | 多变、客户端差异大 |
| 团队规模 | 小团队、快速迭代 | 大团队、多端（Web/App/小程序） |
| 缓存需求 | HTTP 缓存天然支持 | 需要额外方案（Apollo Cache） |
| 文件上传 | 原生支持 | 需要额外处理 |
| 学习成本 | 低 | 中高（Schema、Resolver） |
| 实时性 | 需配合 WebSocket | Subscription 内置 |
| 监控 | 成熟（按 URL 统计） | 需按 Operation Name 统计 |

### 2.3 混合架构

实际项目中常混用：

```
                    ┌─────────────┐
                    │  API Gateway │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
        ┌─────┴─────┐ ┌───┴────┐ ┌────┴─────┐
        │ REST API  │ │GraphQL │ │ WebSocket│
        │(CRUD操作) │ │(复杂查询)│ │ (实时推送)│
        └───────────┘ └────────┘ └──────────┘
```

**PM 建议**：80% 的场景用 REST 就够了。GraphQL 适合 BFF（Backend for Frontend）层，尤其是多端产品。

## 三、微服务 vs 单体架构

### 3.1 对比总览

```
单体架构                          微服务架构
┌─────────────────────┐          ┌─────┐ ┌─────┐ ┌─────┐
│  用户  │ 订单 │ 支付  │          │ 用户 │ │ 订单 │ │ 支付 │
│  模块  │ 模块 │ 模块  │          │ 服务 │ │ 服务 │ │ 服务 │
├─────────────────────┤          ├──┬──┤ ├──┬──┤ ├──┬──┤
│      共享数据库       │          │DB│  │ │DB│  │ │DB│  │
└─────────────────────┘          └──┘  └ └──┘  └ └──┘  └
```

### 3.2 选型决策矩阵

| 维度 | 单体优先 | 微服务优先 |
|------|---------|-----------|
| **团队规模** | < 20 人 | > 50 人，多团队并行开发 |
| **业务复杂度** | 领域边界模糊、快速试错 | 领域边界清晰、业务成熟 |
| **发布频率** | 统一发布即可 | 各模块需独立发布 |
| **技术栈** | 统一技术栈 | 不同模块需要不同技术栈 |
| **运维能力** | 有限，依赖简单部署 | 有 K8s、服务网格等基础设施 |
| **性能瓶颈** | 整体可扩展 | 单独扩展热点服务 |
| **阶段** | 0→1 验证期 | 1→100 规模化期 |

### 3.3 "先单体，后拆分"策略

```
阶段一（0→1）          阶段二（1→10）           阶段三（10→100）
┌──────────┐          ┌──────────┐            ┌────┐ ┌────┐ ┌────┐
│  单体应用  │    →    │  模块化单体 │     →     │微服│ │微服│ │微服│
│ (Monolith) │         │(Modular)  │            │务A │ │务B │ │务C │
└──────────┘          └──────────┘            └────┘ └────┘ └────┘
  快速验证               领域边界探索              独立扩展
  低成本迭代             模块解耦准备              技术异构
```

**关键决策点**：
1. 模块化单体阶段，用**领域边界**（而非技术层）划分模块
2. 当模块间的耦合度 < 模块内的耦合度时，才考虑拆分
3. 拆分优先选择：变更频率高 + 团队独立 + 扩展需求差异大的模块

### 3.4 微服务带来的新问题

| 问题 | 描述 | 解决方案 |
|------|------|---------|
| 分布式事务 | 跨服务数据一致性 | Saga 模式 / 最终一致性 |
| 服务发现 | 服务地址动态变化 | Consul / Nacos / K8s Service |
| 链路追踪 | 请求跨多个服务 | Jaeger / Zipkin / SkyWalking |
| 配置管理 | 多服务配置统一 | Apollo / Nacos Config |
| 熔断限流 | 防止级联故障 | Sentinel / Resilience4j |
| 数据孤岛 | 每个服务独立数据库 | 事件驱动 + 数据同步 |

## 四、事件驱动架构

### 4.1 三种核心模式

#### 消息队列（Message Queue）

```
Producer ──► [Queue] ──► Consumer

典型场景：异步处理、流量削峰、系统解耦
技术选型：
  - RabbitMQ：功能全面，适合企业级
  - Kafka：高吞吐，适合日志/事件流
  - RocketMQ：阿里系，事务消息支持好
  - Pulsar：计算存储分离，云原生
```

#### Event Sourcing（事件溯源）

```
传统模式：存储当前状态
  Order { id: 1, status: "paid", amount: 100 }

事件溯源：存储所有变更事件
  Event 1: OrderCreated { id: 1, amount: 100 }
  Event 2: OrderPaid { id: 1, paymentId: "xxx" }
  Event 3: OrderShipped { id: 1, trackingNo: "yyy" }
  
  → 当前状态 = 重放所有事件
```

**PM 要点**：Event Sourcing 天然支持审计、回溯、"时间旅行"，适合金融、医疗、合规要求高的场景。

#### CQRS（命令查询职责分离）

```
        ┌───────────────┐
        │   Command     │  写操作：复杂业务逻辑
        │   (写端)       │  → 写入 Event Store
        └───────┬───────┘
                │ Events
        ┌───────▼───────┐
        │   Query       │  读操作：优化查询
        │   (读端)       │  → 物化视图 / 缓存
        └───────────────┘
```

### 4.2 事件驱动 vs 请求驱动

| 维度 | 请求驱动（同步） | 事件驱动（异步） |
|------|----------------|-----------------|
| 耦合度 | 紧耦合，调用方需知道被调方 | 松耦合，发布者不关心订阅者 |
| 实时性 | 实时响应 | 最终一致性 |
| 可靠性 | 依赖对方可用性 | 消息持久化，不丢失 |
| 扩展性 | 加机器即可 | 加消费者即可 |
| 调试 | 链路清晰 | 需要链路追踪 |
| 适用 | 查询、即时操作 | 状态变更通知、跨系统同步 |

### 4.3 PM 需要关注的事件设计问题

1. **事件粒度**：太粗（OrderUpdated）→ 无法精确消费；太细（FieldChanged）→ 事件爆炸
2. **事件版本**：Schema 变更时如何兼容旧消费者？
3. **幂等性**：消费者重复收到事件时如何处理？
4. **顺序性**：同一订单的事件是否需要保序？
5. **死信队列**：处理失败的事件去哪了？如何重试？

## 五、API 设计文档（OpenAPI / Swagger）

### 5.1 为什么 PM 要关注 API 文档

| 关注点 | 价值 |
|--------|------|
| 需求准确性 | API 是需求的技术表达，文档不清 = 需求不清 |
| 前后端并行 | 契约先行（Contract First），前后端可并行开发 |
| 第三方集成 | 开放 API 时，文档质量 = 开发者体验 |
| 测试依据 | QA 可根据文档写接口测试用例 |
| 知识沉淀 | 人走了，文档还在 |

### 5.2 OpenAPI 规范结构

```yaml
openapi: 3.0.3
info:
  title: 订单服务 API
  version: 1.0.0
paths:
  /orders:
    get:
      summary: 获取订单列表
      parameters:
        - name: status
          in: query
          schema:
            type: string
            enum: [pending, paid, shipped, completed]
      responses:
        '200':
          description: 成功
          content:
            application/json:
              schema:
                type: array
                items:
                  $ref: '#/components/schemas/Order'
components:
  schemas:
    Order:
      type: object
      properties:
        id:
          type: string
        status:
          type: string
        amount:
          type: number
```

### 5.3 API 设计工作流

```
PM 写 PRD
    │
    ▼
PM/技术 Lead 定 API 契约（OpenAPI YAML）
    │
    ├── 前端：Mock 数据，开始 UI 开发
    └── 后端：实现接口逻辑
    │
    ▼
联调 → QA 测试 → 上线
    │
    ▼
API 文档自动发布（Swagger UI / Redoc / Stoplight）
```

**PM 工具推荐**：
- **Swagger Editor**：在线编辑 OpenAPI，实时预览
- **Postman**：API 设计 + 测试 + 文档一体
- **Stoplight Studio**：可视化 API 设计，支持 Mock

## 六、技术债管理

### 6.1 技术债的四种来源

```
               故意的                    无意的
           ┌─────────────┬──────────────┐
  策略性的  │ "我们知道这   │              │
  （有意识）│  样做有问题，  │              │
           │  但先上线再说" │              │
           ├─────────────┼──────────────┤
  鲁莽的    │ "不管了，     │ "原来这样做   │
  （无意识）│  先跑起来"    │  会有问题啊"  │
           └─────────────┴──────────────┘
```

### 6.2 技术债量化框架

| 指标 | 度量方式 | 阈值 |
|------|---------|------|
| 代码重复率 | 工具扫描（SonarQube） | > 5% 需关注 |
| 测试覆盖率 | 单元测试覆盖比例 | < 60% 需改善 |
| 构建时间 | CI/CD 构建耗时 | > 15min 需优化 |
| 缺陷密度 | 每千行代码 Bug 数 | > 3 个需重构 |
| 依赖过期率 | 过期依赖占比 | > 20% 需升级 |
| 文档覆盖率 | API 文档完整度 | < 80% 需补充 |

### 6.3 技术债管理策略

```
评估 → 排序 → 计划 → 执行 → 度量
 │       │       │       │       │
 ▼       ▼       ▼       ▼       ▼
量化    影响矩阵  每个迭代  20%产能  跟踪改善
技术债  优先级    预留额度  分配     效果
```

**影响矩阵**：

| | 业务影响高 | 业务影响低 |
|---|---|---|
| **技术风险高** | 🔴 立即修复 | 🟡 排入计划 |
| **技术风险低** | 🟡 排入计划 | 🟢 暂不处理 |

**PM 实践**：每个迭代预留 **15-20%** 产能给技术债，不要等"有空再说"。

## 七、PM 需要问工程师的 10 个架构问题

### 7.1 问题清单

| # | 问题 | 为什么要问 | 好的回答示例 |
|---|------|-----------|-------------|
| 1 | **这个需求对现有架构的影响范围有多大？** | 评估改动风险和工期 | "需要改 3 个服务，主要影响订单模块，预计 5 天" |
| 2 | **有没有现成的方案或开源组件？** | 避免重复造轮子 | "可以用 XX 库，2 天搞定；自研需要 2 周" |
| 3 | **这个方案的扩展性如何？** | 未来需求增长时能否支撑 | "当前支持 10 万 QPS，翻倍需要加 Kafka 分区" |
| 4 | **数据一致性怎么保证？** | 分布式场景下的核心问题 | "采用最终一致性，补偿机制保证数据最终对齐" |
| 5 | **出问题时的降级方案是什么？** | 线上故障时的兜底 | "核心链路有熔断，降级后走缓存数据" |
| 6 | **需要哪些上下游团队配合？** | 跨团队协调成本 | "需要基础架构组开放一个 API，排期 2 周" |
| 7 | **有没有安全或合规风险？** | 数据隐私、权限控制 | "涉及用户手机号，需要脱敏处理，符合 PIPL" |
| 8 | **这个方案的技术债有多少？** | 短期 vs 长期的权衡 | "快速方案有 30% 技术债，标准方案多 1 周" |
| 9 | **监控和可观测性怎么做的？** | 线上问题发现和排查 | "有 Grafana 面板 + 告警，P99 延迟 > 500ms 触发" |
| 10 | **上线后的回滚方案是什么？** | 安全上线的最后保障 | "Feature Flag 控制，5 分钟可回滚" |

### 7.2 提问技巧

- **不要问"能不能做"** → 问"怎么做，成本和风险是什么"
- **不要说"这个很简单吧"** → 说"这个需求的复杂度体现在哪"
- **不要只关注功能** → 关注非功能需求（性能、安全、可观测性）
- **不要跳过技术方案评审** → PM 应参加 Tech Design Review，至少听一遍

## 八、架构决策记录（ADR）

### 8.1 什么是 ADR

ADR（Architecture Decision Record）记录重要的架构决策，包括背景、选项、决策和后果。

### 8.2 ADR 模板

```markdown
# ADR-001: 订单服务选择事件驱动架构

## 状态
已采纳（2026-07-10）

## 背景
订单创建后需要通知库存、支付、物流等多个系统。
同步调用导致耦合度高、故障传播。

## 决策
采用 Kafka 事件驱动，订单服务发布 OrderCreated 事件。

## 选项
1. 同步 RPC 调用 — 简单但耦合高
2. 消息队列（RabbitMQ） — 功能够但吞吐不足
3. Kafka 事件流 — 高吞吐、可回放 ✅

## 后果
- 正面：系统解耦，支持独立扩展
- 负面：引入最终一致性，需要处理幂等
```

**PM 价值**：ADR 是理解"为什么这样设计"的最佳文档。新成员入职、需求变更评估时，先看 ADR。
