## 一、数据管道架构

### 1.1 ETL vs ELT vs Streaming

```
ETL（Extract → Transform → Load）
┌────────┐    ┌───────────┐    ┌────────┐
│ 数据源  │───►│ 转换引擎   │───►│ 数据仓库│
│(Source) │    │(Transform)│    │ (DW)   │
└────────┘    └───────────┘    └────────┘
  先转换，再加载。传统方式。
  工具：Informatica / Talend / DataStage

ELT（Extract → Load → Transform）
┌────────┐    ┌────────┐    ┌───────────┐
│ 数据源  │───►│数据仓库 │───►│ 仓库内转换 │
│(Source) │    │(Raw)   │    │(Transform)│
└────────┘    └────────┘    └───────────┘
  先加载原始数据，在仓库内转换。现代方式。
  工具：dbt / Fivetran / Airbyte

Streaming（实时流处理）
┌────────┐    ┌───────────┐    ┌────────┐
│ 数据源  │───►│ 流处理引擎 │───►│ 实时表/ │
│(Event) │    │(Flink等)  │    │ 消费者  │
└────────┘    └───────────┘    └────────┘
  数据产生即处理，延迟秒级。
  工具：Apache Flink / Kafka Streams / Spark Streaming
```

### 1.2 选型决策表

| 维度 | ETL | ELT | Streaming |
|------|-----|-----|-----------|
| **延迟** | 小时级 | 分钟级 | 秒级 |
| **数据量** | 中等 | 大 | 实时持续 |
| **复杂度** | 高（需维护转换引擎） | 中（利用仓库算力） | 高（分布式状态管理） |
| **成本** | 中 | 低-中 | 高 |
| **适用场景** | 遗留系统迁移 | 现代数仓建设 | 实时监控、风控、推荐 |
| **典型工具** | Informatica, Talend | dbt, Fivetran | Flink, Kafka Streams |

### 1.3 现代数据栈（Modern Data Stack）

```
数据源                 采集层              存储层            转换层          消费层
┌──────┐           ┌──────────┐      ┌──────────┐     ┌─────┐      ┌──────────┐
│MySQL │──────────►│ Airbyte  │─────►│Snowflake │────►│ dbt │─────►│ BI 工具   │
│API   │           │ Fivetran │      │ BigQuery │     │     │      │ Hex      │
│日志  │           │ Debezium │      │ Redshift │     │     │      │ Metabase │
│文件  │           └──────────┘      └──────────┘     └─────┘      └──────────┘
└──────┘
```

**PM 关注点**：
1. **采集层**：数据源有哪些？格式是什么？更新频率？
2. **存储层**：选哪个云数仓？成本和性能如何？
3. **转换层**：数据清洗和业务逻辑在哪一层？
4. **消费层**：谁在用数据？用什么工具？需要实时吗？

## 二、数据建模

### 2.1 三种主流模型

#### 星型模型（Star Schema）

```
                    ┌──────────────┐
                    │  时间维度表   │
                    │ date_key     │
                    │ year/month   │
                    └──────┬───────┘
                           │
┌──────────────┐    ┌──────┴───────┐    ┌──────────────┐
│  产品维度表   │───►│   销售事实表   │◄───│  客户维度表   │
│ product_key  │    │ date_key     │    │ customer_key │
│ name/category│    │ product_key  │    │ name/region  │
└──────────────┘    │ customer_key │    └──────────────┘
                    │ amount       │
                    │ quantity     │    ┌──────────────┐
                    └──────┬───────┘◄───│  门店维度表   │
                           │            │ store_key    │
                    ┌──────┴───────┐    │ name/city    │
                    │  地区维度表   │    └──────────────┘
                    │ region_key   │
                    └──────────────┘
```

特点：一个事实表 + 多个维度表，查询简单，JOIN 少。

#### 雪花模型（Snowflake Schema）

```
维度表进一步规范化拆分：

产品维度表 → 产品类别表 → 产品大类表
客户维度表 → 地区表 → 省份表 → 国家表

特点：减少数据冗余，但查询需要更多 JOIN。
适用：维度层次深、存储成本敏感的场景。
```

#### 宽表模型（Wide Table / Denormalized）

```
┌──────────────────────────────────────────────────────┐
│                    销售宽表                            │
│ order_id | date | product_name | category |          │
│ customer_name | region | city | store_name |         │
│ amount | quantity | discount | ...                    │
└──────────────────────────────────────────────────────┘

特点：所有字段平铺在一个表，零 JOIN，查询最快。
适用：OLAP 查询、BI 展示、自助分析。
代价：数据冗余大，更新成本高。
```

### 2.2 建模选型决策

| 维度 | 星型模型 | 雪花模型 | 宽表 |
|------|---------|---------|------|
| 查询性能 | 好 | 中（多 JOIN） | 最好（零 JOIN） |
| 存储效率 | 中 | 高（少冗余） | 低（大量冗余） |
| 维护成本 | 中 | 高（多表关联） | 低（单表） |
| 灵活性 | 高 | 高 | 低（变更成本大） |
| 适用 | 通用 BI | 复杂维度 | 自助分析、实时看板 |

### 2.3 建模层次

```
ODS（操作数据层）     → 原始数据，不做处理
  │
  ▼
DWD（明细数据层）     → 清洗、标准化、去重
  │
  ▼
DWS（汇总数据层）     → 按主题聚合（日/周/月粒度）
  │
  ▼
ADS（应用数据层）     → 面向具体业务场景的表
                       （报表、看板、API 输出）
```

**PM 要点**：分层的意义是**复用**。DWD/DWS 做好一次，ADS 层多个业务场景都能用。不分层 = 每个需求都从 ODS 重新算一遍。

## 三、数据治理

### 3.1 数据治理四大支柱

```
                   ┌─────────────┐
                   │  数据治理     │
                   └──────┬──────┘
          ┌───────────┬───┴───┬───────────┐
          │           │       │           │
    ┌─────┴─────┐ ┌──┴──┐ ┌──┴──┐ ┌─────┴─────┐
    │ 数据质量   │ │血缘 │ │目录 │ │ 数据安全   │
    │ Quality   │ │Linea│ │Cata│ │ Security  │
    └───────────┘ └─────┘ └─────┘ └───────────┘
```

### 3.2 数据质量

| 维度 | 定义 | 检测方式 | 示例 |
|------|------|---------|------|
| 完整性 | 数据不缺失 | NULL 值检查 | 订单表 99.5% 的记录有用户 ID |
| 准确性 | 数据正确 | 交叉验证 | 金额合计与财务系统一致 |
| 一致性 | 多处数据一致 | 主题比对 | CRM 和订单系统的客户数一致 |
| 及时性 | 数据按时到达 | 延迟监控 | T+1 报表在 8:00 AM 前产出 |
| 唯一性 | 无重复记录 | 去重检查 | 订单 ID 全局唯一 |
| 有效性 | 符合业务规则 | 规则校验 | 年龄字段 0-150 之间 |

**数据质量 SLA 示例**：

| 指标 | SLA | 监控方式 | 告警阈值 |
|------|-----|---------|---------|
| 核心表产出时间 | T+1 8:00 AM 前 | 调度系统监控 | 延迟 > 30min |
| 数据完整率 | > 99.9% | NULL 比例检查 | < 99.5% |
| 数据准确率 | > 99.99% | 抽样校验 | < 99.9% |
| 异常数据率 | < 0.1% | 规则引擎 | > 0.5% |

### 3.3 数据血缘（Data Lineage）

```
MySQL.orders ──► DWD.dwd_order_detail ──► DWS.dws_sales_daily ──► ADS.rpt_sales_dashboard
     │                    │                        │
     │                    ▼                        ▼
     │            DWD.dwd_order_item        ADS.rpt_inventory
     │                    │
     └──────────────────► DWS.dws_order_summary ──► ADS.rpt_order_funnel
```

**PM 价值**：
1. **影响分析**：改了上游字段，哪些下游报表受影响？
2. **问题溯源**：报表数据不对，从哪个环节开始出错？
3. **合规审计**：敏感数据从哪来，流向了哪？

### 3.4 数据目录（Data Catalog）

| 信息 | 说明 | 谁负责维护 |
|------|------|-----------|
| 表名 / 字段名 | 技术标识 | 数据工程 |
| 业务含义 | 字段的业务定义 | 数据产品 / 业务方 |
| 数据类型 | STRING / INT / DATE | 数据工程 |
| 更新频率 | 实时 / T+1 / 手动 | 数据工程 |
| 数据 Owner | 谁对数据质量负责 | 数据治理委员会 |
| 敏感级别 | 公开 / 内部 / 机密 | 安全团队 |
| 关联指标 | 这个字段对应哪些业务指标 | 数据产品 |

**工具推荐**：Apache Atlas / DataHub / Amundsen / OpenMetadata

## 四、BI 产品设计

### 4.1 Dashboard 设计原则

#### 原则一：信息层次（Information Hierarchy）

```
┌─────────────────────────────────────────────────┐
│  L1: 关键指标（一眼看到）                          │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐            │
│  │ GMV  │ │订单量│ │转化率│ │ 客单价│            │
│  │ ¥2.3M│ │12.5K│ │3.2% │ │ ¥184 │            │
│  └──────┘ └──────┘ └──────┘ └──────┘            │
├─────────────────────────────────────────────────┤
│  L2: 趋势分析（看走势）                            │
│  ┌─────────────────────────────────────┐         │
│  │  GMV 30 天趋势图                     │         │
│  └─────────────────────────────────────┘         │
├─────────────────────────────────────────────────┤
│  L3: 下钻分析（找原因）                            │
│  ┌───────────────┐ ┌───────────────┐            │
│  │ 按品类拆解     │ │ 按渠道拆解     │            │
│  └───────────────┘ └───────────────┘            │
├─────────────────────────────────────────────────┤
│  L4: 明细数据（具体操作）                          │
│  ┌─────────────────────────────────────┐         │
│  │ 异常订单列表                          │         │
│  └─────────────────────────────────────┘         │
└─────────────────────────────────────────────────┘
```

#### 原则二：MECE 指标拆解

```
GMV（总成交额）
├── 订单量
│   ├── 新客订单
│   └── 老客订单
└── 客单价
    ├── 商品均价
    └── 件单价 × 件数

转化率
├── 流量（UV）
├── 浏览→加购率
├── 加购→下单率
└── 下单→支付率
```

#### 原则三：对比才有意义

| 对比维度 | 示例 | 价值 |
|---------|------|------|
| 时间对比 | 本月 vs 上月 / 去年同期 | 趋势判断 |
| 目标对比 | 实际 vs 目标 / 预算 | 达成率评估 |
| 维度对比 | 品类 A vs 品类 B | 找最佳实践 |
| 均值对比 | 门店 vs 全国均值 | 找异常门店 |

### 4.2 自助分析设计

```
自助分析平台的功能层次：

┌─────────────────────────────────────┐
│  L1: 预置看板（所有人都能看）         │
│  → 核心业务指标，标准化呈现           │
├─────────────────────────────────────┤
│  L2: 自助查询（有一定 SQL 基础）      │
│  → 拖拽式查询、条件筛选              │
├─────────────────────────────────────┤
│  L3: SQL 工作台（数据分析师）          │
│  → 自由 SQL + 结果可视化             │
├─────────────────────────────────────┤
│  L4: 数据 API（数据工程师）           │
│  → 程序化访问数据                    │
└─────────────────────────────────────┘
```

**自助分析的关键设计点**：

| 设计点 | 说明 |
|--------|------|
| 指标定义一致性 | 同一个指标在不同看板的计算逻辑必须一致 |
| 权限控制 | 不同角色看到不同粒度的数据 |
| 数据解释 | 每个指标有业务含义说明和计算公式 |
| 导出能力 | 支持 CSV/Excel 导出，满足汇报需求 |
| 告警订阅 | 指标异常时自动推送 |

### 4.3 指标一致性治理

**问题场景**：财务说 GMV 是 100 万，运营说 GMV 是 120 万，两个都对，口径不同。

**解决方案：指标管理体系**

```
┌─────────────────────────────────────┐
│          指标字典（Single Source）     │
│                                     │
│  指标名：GMV                         │
│  定义：用户实际支付的订单总金额        │
│  公式：SUM(order.amount)             │
│  口径：不含退款、不含未支付订单        │
│  数据源：DWS.dws_order_daily         │
│  Owner：电商运营部                    │
│  更新频率：T+1                        │
└─────────────────────────────────────┘
         │
    ┌────┴────┐
    ▼         ▼
  看板 A     看板 B     （都从同一个指标定义派生）
```

**PM 职责**：
1. 建立指标字典，明确每个指标的业务定义和计算口径
2. 定期 Review，发现口径漂移及时纠正
3. 新增指标必须走评审流程，避免重复定义

## 五、数据隐私与合规

### 5.1 全球主要隐私法规对比

| 维度 | GDPR（欧盟） | CCPA（加州） | PIPL（中国） |
|------|-------------|-------------|-------------|
| 适用范围 | 处理欧盟居民数据 | 处理加州居民数据 | 处理中国境内数据 |
| 同意要求 | 明确同意（Opt-in） | 退出权（Opt-out） | 明确同意（Opt-in） |
| 数据主体权利 | 访问、删除、可携带、限制处理 | 知情、删除、退出出售 | 知情、决定、查阅、复制、删除、可携带 |
| 处罚力度 | 最高年营收 4% 或 2000 万欧元 | 每次违规 $7,500 | 最高 5000 万元或年营收 5% |
| 跨境传输 | 需充分性认定或 SCC | 无明确限制 | 需安全评估或认证 |
| DPO 要求 | 特定情况必须设立 | 无强制要求 | 处理量达标需设立 |

### 5.2 数据隐私产品设计清单

```
□ 数据分类分级（公开/内部/机密/绝密）
□ 个人信息识别和标记
□ 数据脱敏策略（手机号、身份证、银行卡）
□ 用户同意管理（Consent Management）
□ 数据访问权限控制（RBAC / ABAC）
□ 数据审计日志（谁在什么时间访问了什么数据）
□ 数据删除能力（Right to be Forgotten）
□ 数据导出能力（Data Portability）
□ 跨境传输评估
□ 数据泄露应急响应预案
```

### 5.3 脱敏策略示例

| 数据类型 | 脱敏方式 | 示例 |
|---------|---------|------|
| 手机号 | 中间 4 位替换 | 138****6789 |
| 身份证 | 保留前 3 后 4 | 310***1234 |
| 银行卡 | 仅显示后 4 位 | **** **** **** 5678 |
| 邮箱 | 用户名部分替换 | z***@example.com |
| 姓名 | 保留姓 | 张** |
| 地址 | 省市区保留，详细地址替换 | 上海市浦东新区**** |
| IP 地址 | 最后一段替换 | 192.168.1.*** |

## 六、数据产品案例

### 6.1 Metabase — 开源 BI

```
定位：面向非技术人员的自助分析工具
核心能力：
  ├── 无需 SQL 即可创建图表（Question）
  ├── 仪表盘组合和分享
  ├── 自然语言查询（实验性）
  └── 嵌入式分析（Embed）

架构：
  用户 → Metabase → 数据库（直连查询）
                 → 应用数据库（存储问题/仪表盘配置）

PM 取经点：
  ✅ 降低数据使用门槛（非技术人员也能用）
  ✅ 权限到表/字段级别
  ❌ 复杂分析能力有限（需要 SQL）
  ❌ 大数据量下性能一般（直连模式）
```

### 6.2 Hex — 协作数据笔记本

```
定位：数据分析的"Figma"——协作 + 交互 + 分享
核心能力：
  ├── SQL + Python 混合编写
  ├── 交互式参数和控件
  ├── 一键发布为独立 App
  └── 实时协作（多人同时编辑）

PM 取经点：
  ✅ 分析过程可见、可复现
  ✅ 从 Notebook 到 App 的一键转换
  ✅ 协作功能降低知识传递成本
  💡 "分析即产品"的新范式
```

### 6.3 dbt — 数据转换工具

```
定位：数据转换层的"Git + CI/CD"
核心能力：
  ├── SQL 编写转换逻辑（SELECT 语句）
  ├── 模型依赖关系自动管理（DAG）
  ├── 内置测试（唯一性、非空、引用完整性）
  ├── 文档自动生成
  └── 版本控制和 CI/CD

工作流：
  编写 SQL 模型 → 定义依赖 → 运行测试 → 合并部署
  
  models/
  ├── staging/        ← 清洗层
  │   ├── stg_orders.sql
  │   └── stg_customers.sql
  ├── intermediate/   ← 中间层
  │   └── int_order_enriched.sql
  └── marts/          ← 应用层
      ├── finance/
      │   └── fct_revenue.sql
      └── marketing/
          └── dim_customer_segment.sql

PM 取经点：
  ✅ 数据转换逻辑代码化，可 Review、可测试
  ✅ 依赖关系可视化，影响分析透明
  ✅ 自动生成文档，降低沟通成本
  💡 dbt 让数据工程有了"软件工程"的最佳实践
```

## 七、数据产品经理的能力模型

### 7.1 核心能力

```
               ┌─────────────────┐
               │   数据产品 PM    │
               └────────┬────────┘
        ┌───────────────┼───────────────┐
        │               │               │
  ┌─────┴─────┐   ┌─────┴─────┐   ┌─────┴─────┐
  │ 数据理解力  │   │ 产品设计力  │   │ 推动力     │
  └─────┬─────┘   └─────┬─────┘   └─────┬─────┘
        │               │               │
  ├── SQL 基础     ├── 用户研究     ├── 跨团队协调

  └── 数据架构     └── 效果度量     └── 数据素养培训
```

## 八、总结 — 数据产品设计核心原则

```
1. 数据可信   → 质量 SLA + 血缘追踪 + 指标一致性
2. 数据可用   → 自助分析 + 降低使用门槛 + 权限清晰
3. 数据安全   → 隐私合规 + 脱敏策略 + 访问审计
4. 数据可复用 → 分层建模 + 元数据管理 + 标准化
5. 数据可行动 → 从"看数据"到"做决策"的闭环设计
```

> **核心心法**：数据产品的价值不在于"有多少数据"，而在于"多少人能用数据做出更好的决策"。PM 的终极目标是让数据从"报表"变成"生产力"。
