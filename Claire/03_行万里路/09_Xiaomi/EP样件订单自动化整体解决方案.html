🏷️ A/B/C/D 订单分类处理

按价格唯一性 × 供应商唯一性双维度分类，价格判断在 EP CLI 内部完成，Skill 层只做分类标注。

分类条件处理方式供应商选择人工介入
A类唯一价格 + 唯一供应商自动汇总 → 一键下单不需要无
B类唯一价格 + 多个供应商推送供应商选择 → 选择后下单需要低
C类多个价格 + 唯一供应商CLI 内部自动选价格 → 下单不需要无
D类多个价格 + 多个供应商CLI 内部选价格 → 推送供应商选择 → 下单需要中

⚙️ 核心 Skill（5 个）

①
demand-import · 需求导入
Skill dx-ep sapo order import-json
从多维表格读取【样件导入状态=待导入】记录，按固定字段映射转换为 records JSON（27个字段），输出导入批次报告。EP 账号缺失、预算主数据缺失等异常记录原因，转入确认单，不阻塞其余记录。
📥 输入：多维表格待导入记录 📤 输出：records JSON + 导入报告 ⏱️ 典型耗时：~3.2s ✅ 验证：23条 → 20成功 + 3异常
②
demand-check · 需求检查
Skill demand-check（本地校验）
对 records JSON 执行 16 项规则校验：必填字段、需求数量>0、日期格式（YYYY-MM-DD）、预算编号与预算行号一致性、行号连续、EP 账号存在、样件用途合法。每条记录判定 PASS / WARN / REJECT，并给出原因。WARN/REJECT 转入确认单。
📥 输入：records JSON 📤 输出：PASS/WARN/REJECT 判定 + 原因 ⏱️ 典型耗时：~0.8s ✅ 验证：PASS 20 · WARN 1 · REJECT 1
③
demand-query-ready · 可下单查询
Skill dx-ep sapo order query-ready
调用 EP CLI 查询可下单需求，按到货日期筛选（>=今天往前推2个月，含未来），输出 ReadyOrders JSON（含创建订单所需基础数据）。内置登录错误检测（not logged in/auth/token/401/403/expired），登录超时时返回明确报错提示执行 dx-garagehub auth login。
📥 输入：需求范围（可配置） 📤 输出：可下单需求列表 JSON ⏱️ 典型耗时：~1.2s ✅ 验证：查询136条 → 筛选后7条可下单
④
demand-order-create · 订单创建
Skill dx-ep sapo order create-order
读取 ReadyOrders，按 originType 分组（SZ→试制/EP→散件），按4条件分组（预算编号|预算行号|采购工程师ID|公司主体ID），剔除多供应商分组，调用 EP CLI 创建订单。价格判断、提交/草稿由 EP 内部完成。A/B/C/D 分类标注，多供应商分组保留完整供应商选项信息。
📥 输入：已确认的可下单需求 📤 输出：订单创建批次报告 ⏱️ 典型耗时：~5.6s ✅ 验证：已提交审批2 · 草稿待核实2 · 失败1
⑤
demand-interact · 交互确认
Skill feishu-mcp（多维表格）
通过飞书多维表格《确认单》表承载所有待人工拍板事项及决策回执。支持 create/list/poll/wait 四个子命令，8 种决策类型（待确认/确认执行/驳回/跳过/强制通过等）。wait 子命令创建确认项后轮询等待用户决策，决策完成后工作流继续。
📥 输入：待确认事项 📤 输出：决策回执 ⏱️ 典型耗时：人工 ✅ 验证：确认单创建 + 轮询等待正常
📦 统一输出格式（WorkflowOutput）

每个 Skill 都输出统一的 WorkflowOutput JSON，是工作流编排器能够自动串接各阶段的基础。

{ "workflow_id": "WF20260914_001", "stage": "order_create", "status": "success", "summary": { "total": 10, "success": 8, "failed": 1, "skipped": 1 }, "data": { ... }, "next_action": "auto_continue", "confirmation_required": false, "execution_time_ms": 12345, "errors": [] }

🔀 供应商选择智能分流

< 5 条 推送详细卡片

每个需求一张独立卡片，展示：

  • 需求信息：零件号/名称/数量/到货日期/预算编号
  • 供应商报价表格：供应商名称/单价/交货期/MOQ
  • 供应商选择按钮（最多4个）

≥ 5 条 走多维表格批量

推送汇总卡片 + 多维表格链接，用户在多维表格批量完成选择：

  • 19 个真实字段（零件号/供应商选项/已选供应商等）
  • 填写「已选供应商ID」后自动切换状态为「已选择」
  • 自动填写「选择时间」
✅ 自动状态切换：用户填写「已选供应商ID」后，系统下次轮询自动将状态从「待选择」切换为「已选择」，并自动填写「选择时间」。清空已选供应商ID则自动回退为「待选择」。

💡 经验与避雷

🐛 飞书卡片相关踩坑（4 条）
Card 2.0 不支持 action tag
按钮不能放在 action 容器中。解决：按钮直接放 body 根节点，或用 column_set 包裹。form 容器内按钮用 form_action_type: "submit"。
number 类型列不能设置 width
table 组件中 number 列设置 width 会报 230099 错误，多列同时设置 width 也可能报错。解决：全部去掉 width，让飞书自动分配列宽。
table 只能放 body 根节点，不能嵌套
table 不能嵌套进 column_set、interactive_container 等容器中。解决：table 直接作为 body 的子元素，不要包裹在其他容器内。
应用机器人缺少 im:message:send 权限
首次使用应用机器人发送卡片时报错缺少权限，开通后仍失败因为需要发布新版本。解决：① 开通权限 ② 创建新版本并发布 ③ 等待审核通过。
🐛 feishu-mcp 相关踩坑（6 条）
get_meta 参数是 url_or_token 不是 app_token
传错参数会报错。解决：使用 url_or_token 参数，支持 /base/XXX、/wiki/XXX URLs，或裸 app_token。
search_records 返回格式是 records 不是 data.items
返回格式是 {records: [...], has_more: ..., total: ...}。解决：用 result.get("records", []) 获取记录列表。
文本字段返回富文本格式需提取
返回的是 [{'text': 'xxx', 'type': 'text'}]，不是纯字符串。解决：封装 _get_field_text() 方法递归提取纯文本。
没有 delete_field 操作，需删表重建
bitable_ops 工具集中没有 delete_field。解决：需要删除字段时，删除整个表后用精简字段重新创建。
list_fields 返回格式是 fields 不是 items
和 search_records 的返回格式不一致。解决：用 result.get("fields", []) 获取字段列表。
batch_create 封装有问题，改用循环单条
批量创建记录调用失败。解决：改用循环单条 create_record，每条之间 sleep(0.3) 避免限流。
🐛 CLI 与环境相关踩坑（4 条）
auth_base_url 末尾斜杠导致双斜杠
末尾有斜杠时 CLI 拼接 URL 出现 //oauth，导致登录失败。解决：auth_base_url 末尾不要加斜杠。
登录回调端口 7777 被占用
旧进程占用端口导致登录失败。解决：lsof -i:7777 找到 PID，kill 掉旧进程后重新登录。
macOS 无 PowerShell，PS 版脚本无法运行
用户下载的 skill 是 PowerShell 版（.ps1）。解决：用 Python 重写 PS 版脚本，保持原逻辑完整。
环境切换后旧 token 不兼容
auth_base_url 从 test 改为 uat 后旧 token 不兼容。解决：修改环境地址后必须重新执行 dx-garagehub auth login。
✅ 实战经验总结（6 条）
统一输出格式是工作流编排的基础
每个 Skill 都输出统一的 WorkflowOutput JSON，是编排器自动串接各阶段的基础。stdout 输出 JSON，stderr 输出日志。
共享模块抽离避免重复代码
将卡片发送、多维表格记录、角色管理、供应商选择、工作流编排等通用能力抽离到 _shared/ 目录，5个订单 Skill 都可以复用。
双通路降级保证通知可靠性
飞书卡片发送采用应用机器人 API（优先）+ lark-cli（降级）双通路，应用机器人失败时自动降级，保证通知不丢失。
智能分流提升用户体验
供应商选择按数量智能分流：<5条推送详细卡片（直接交互），≥5条走多维表格（批量处理）。避免少量需求也跳转多维表格的繁琐，也避免大量需求卡片刷屏。
自动状态切换减少用户操作
用户填写「已选供应商ID」后，系统下次轮询自动切换状态为「已选择」并填写选择时间。用户不需要手动修改状态字段，减少操作步骤和出错概率。
角色化内容过滤实现权限隔离
4个角色看到的内容不同，采购员只看到采购相关错误，需求用户只看到错误数量。实现了基于角色的内容过滤和信息最小化原则。
💡 实用技巧（5 条）
feishu-mcp 调用前先看 schema
工具参数格式容易记错，调用前先用 schema 命令查看参数结构，避免猜参数导致调用失败。
dry-run 模式验证订单创建
测试订单创建时使用 --dry-run 参数跳过实际 CLI 调用，只验证分组、分类、剔除等逻辑，避免误创建真实订单。
多维表格字段用真实字段名，不要自造
字段名应该对应 CLI 真实输出的字段名（如 brNo、partNo、supplierOptions），不要自己造字段名。这样数据映射清晰，后续维护方便。
错误信息表格化提升可读性
异常记录展示从纯文本列表（每条记录的错误信息用分号连接，非常长）改为表格形式（# / 记录ID / 错误数 / 主要错误），大幅提升可读性。
登录错误检测关键词要全面
dx-ep CLI 登录错误表现形式多样，检测关键词要全面覆盖：not logged in、未登录、登录、auth、token、401、403、unauthorized、forbidden、expired、过期等。
⚠️ 注意事项（3 条）
价格选择逻辑依赖 CLI 内部实现
PRD 中 C/D 类场景需要用零件号匹配台账取最新价格，这部分逻辑目前在 dx-ep CLI 内部实现，Skill 层只做分类标注。如果 CLI 内部未实现，需在 Skill 层补充。
卡片按钮无服务端回调
飞书卡片按钮目前为 open_url 跳转，没有配置服务端回调 URL。用户点击按钮后无法直接回传选择结果，需要通过多维表格回传。
真正创建订单尚未测试
order_create 仅 dry-run 验证通过，尚未真正创建订单测试。实际创建订单可能遇到预算不足、供应商拒绝、跨公司主体采购等异常情况。建议先用测试数据真正创建一笔订单验证全流程。
