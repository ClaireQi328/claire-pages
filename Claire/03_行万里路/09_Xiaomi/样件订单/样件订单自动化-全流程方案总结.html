📋 业务场景

样件订单是汽车研发流程中的高频场景。研发工程师在产品开发各阶段（散件/SM/M/VP/PT/PP/MP）需要大量样件用于验证测试。需求提交后，采购工程师需在 EP 系统中完成：查询可下单需求、核对预算与物料、选择供应商、创建订单、跟踪交付状态。整个流程重复度高、操作繁琐，单次下单需人工核对16+字段，日均处理数十条需求，耗时且易出错。

⚠️ 核心痛点
  • 效率低：人工逐条查询、核对、下单，日均耗时1-2小时
  • 易出错：16+字段人工核对，预算/物料/账号格式易出错
  • 不透明：订单执行情况分散在EP系统，缺乏统一统计视图
  • 难追溯：手动下单无完整审计日志，问题排查困难
项目目标：通过 dx-ep CLI 暴露的接口，封装为可复用的 Skill，再由 Agent 编排执行，实现样件订单的自动化导入、查询、确认、下单和统计全流程。将采购工程师从重复性操作中解放出来，聚焦于供应商谈判和异常处理等高价值工作。
项目内容与范围 做什么 / 不做什么
✅ 项目覆盖（In Scope）
  • 需求导入：本地文件 → EP系统（Skill支持）
  • 需求查询：query-ready 分页拉取 + 标准化
  • 确认下单：HTML确认页 + 用户确认 + 批量下单
  • 执行统计：日报/周期报，全量订单统计
  • 环境检查：环境检查 + 自动修复
  • 异常处理：20+场景降级通路
❌ 项目不覆盖（Out of Scope）
  • 需求提报：研发工程师在EP系统手动提交
  • 供应商选择：EP系统内部自动匹配最低价
  • 供应商接单：供应商在其系统确认
  • 物流交付：第三方物流系统跟踪
  • 收货验收：仓库质检 + 入库确认
  • 付款结算：财务系统处理

业务流程详细说明 每个环节做什么

📥 环节 1：提报需求（研发工程师手动）

做什么：研发工程师在产品开发各阶段（散件/SM/M/VP/PT/PP/MP），在 EP 系统手动提交样件需求。
关键字段：物料号、需求数量、样件用途（A-G）、要求到货日期、项目编号、预算编号、预算行号
为什么不自动化：需求提报是业务源头，由研发工程师根据实际需要提报，自动化没有意义。

📤 环节 2：需求导入（Skill 支持）

做什么：把研发工程师提的需求，通过 demand-import skill 导入到 EP 系统。
输入：本地 Excel/CSV 文件，或飞书多维表格导出
处理：17 字段映射 + 样件用途匹配表 A-G + EP 账号校验
输出：records JSON + 导入报告（成功/无效数量）
为什么需要这一步：有时候需求是在飞书表格里收集的，需要批量导入 EP，不用逐条手动录。

🔍 环节 3：查询可下单需求（Agent/Skill 自动化）

做什么：调用 dx-ep sapo order query-ready 分页拉取所有可下单需求，按 60 天到货日期过滤，生成 HTML 确认页。
处理细节：
• 分页拉取：page-size=100，自动翻页，最多 20 页
• 日期过滤：只保留 60 天内要求到货的需求
• 字段标准化：16 个字段统一格式（金额、日期、账号等）
• HTML 确认页：6 项统计卡片 + 16 字段明细表 + 一品多供选择交互
• 上传 FDS：生成公开可访问链接
为什么自动跑：查询是只读操作，出错成本低，可以自动跑。

✅ 环节 4：人工确认（用户决策点）

做什么：采购工程师查看确认页，确认需求数据正确，选择供应商（一品多供场景），然后回复"确认"执行下单。
两种情况：
• 不改供应商：直接回复"确认"或"执行"，Agent 自动下单
• 要改供应商：打开 HTML 确认页，点前置单选圆圈切换供应商 → 点"生成确认结果" → 复制 JSON → 粘贴回对话
为什么必须人工确认：下单是写操作，不可逆，必须人工拍板。一品多供选择是唯一需要人工决策的点。

📦 环节 5：创建订单（Agent/Skill 自动化）

做什么：读取确认后的需求 JSON，调用 dx-ep sapo order create-order 批量创建样件订单。
处理细节：
• 逐条调用 CLI，单条失败不影响其他
• EP 内部自动判断价格（最新且最低价）
• 支持 dry-run 预览模式（默认开启）
• 结果分类：成功 / 草稿（非最低价）/ 失败
• 按供应商和采购员汇总统计
为什么是写操作：创建订单会修改 EP 系统数据，不可逆，所以必须人工确认后才执行。

🚚 环节 6-7：供应商接单 & 物流交付（人工/其他系统）

做什么：供应商在其系统确认接单，安排生产/发货；物流第三方跟踪运输状态；仓库质检入库。
为什么不自动化：这两个环节涉及外部供应商和物流系统，不在我们的范围内。

📊 环节 8：执行统计（Agent/Skill 自动化）

做什么：按天查询指定周期内的已提交订单，生成统计报告 HTML。
两层统计：
• 执行层：订单总数、Agent 下单数、手动下单数、日均订单
• 业务层：涉及项目、涉及供应商、涉及采购员、订单总金额（含税/不含税）
为什么自动跑：统计是只读操作，出错成本低，可以自动跑。
最终方案 6个Skill + 4个Agent
🔧 env-check-test
功能：环境检查，6项检查（Node.js/CLI版本/登录态/连通性/FDS配置/SDK），settings.json运行时自动写入
特色：--auto-fix 自动修复（安装CLI、修改配置、安装SDK、写入FDS配置），修复后自动重新检查
命令：python3 env_check.py --config config.json [--auto-fix]
📥 demand-import
功能：从本地 Excel/CSV 读取需求，17字段映射+校验，样件用途匹配表A-G，生成 records JSON
特色：支持 --execute 直接调用 CLI 导入；无效记录只进报告不导入
命令：python3 demand_import.py --input <file> [--execute]
🔍 demand-query
功能：调用 query-ready 分页查询（20页），日期过滤（60天），16字段标准化
特色：生成 HTML 确认页（6项统计卡片+16字段明细表），上传 FDS 输出链接，保存需求JSON
命令：python3 demand_query.py --config config.json
📦 demand-order
功能：读取需求JSON，逐条调用 create-order，EP内部完成价格判断
特色：支持 --dry-run 预览模式；单条失败不影响其他；返回数量统计
命令：python3 demand_order.py --input <json> [--dry-run]
📊 execution-stats（目录名 daily-report）
功能：调用 submit-list 查询全量订单（含Agent+手动），支持单日/周期，两层统计
执行层：订单总数、Agent下单、手动下单、日均订单
业务层：涉及项目、涉及供应商、涉及采购员、订单总金额（含税/不含税）
命令：python3 daily_report.py --config config.json [--date YYYY-MM-DD] [--start-date ... --end-date ...]
技术实现 CLI-Skill-Agent 三层架构
L1 CLI 层
dx-ep CLI
• query-ready：查询可下单需求
• create-order：创建订单
• import-json：导入需求
• submit-list：查询已提交订单
输出：JSON 格式（-f json）
L2 Skill 层
Python 封装
• 调用 CLI + 解析 JSON
• 字段映射 + 数据标准化
• 异常处理 + 降级通路
• 生成 HTML + 上传 FDS
输出：结构化 JSON + HTML
L3 Agent 层
4个 Agent
• WS-环境检查：env-check
• WS-需求查询：demand-query
• WS-自动下单：demand-order
• WS-下单报告：execution-stats
交互：自然语言 + HTML链接
关键设计决策：
① 剔除飞书MCP：MCP有两个核心使用场景（从多维表格获取需求、日志落到多维表格），但登录态2小时过期无法自动化，因此整体剔除
② 需求导入改为本地文件：用户从多维表格导出 Excel/CSV，通过 demand-import skill 读取并导入，不依赖MCP
③ 日志改为本地JSON+HTML：执行记录保存为本地JSON文件，统计报告生成HTML上传FDS，不依赖多维表格
④ env-check增加--auto-fix：解决AgentSpace环境与本地差异问题（CLI版本、settings.json、FDS配置），自动修复后输出ok
⑤ 确认方式改为HTML+FDS链接：飞书卡片按钮在AgentSpace不支持回调，改为生成HTML确认页上传FDS，用户自然语言回复确认

发现飞书卡片不支持回调 死路
飞书交互卡片的按钮在 AgentSpace 平台无法触发回调，用户点击后无法执行下单。尝试多维表格轮询方案，复杂度高且不稳定。
飞书MCP登录态频繁失效 死路
飞书MCP的两个核心使用场景：
① 从多维表格获取需求：需求导入环节需要从飞书多维表格读取待导入记录（37个字段映射）
② 日志落到多维表格：所有执行记录（查询/下单/统计）需要写入飞书多维表格形成审计日志

放弃原因：feishu-mcp-pro 的 access token 有效期仅2小时，refresh token 30天。tools/list 是本地元数据不触发校验，必须真实API调用才刷新。AgentSpace上每次运行都可能遇到登录过期，需要人工浏览器重新授权，无法自动化。
env-check在AgentSpace频繁失败 死路
AgentSpace环境与本地差异：
① CLI版本：AgentSpace默认是 1.0.7，测试环境要求 1.0.3-beta.3
② settings.json：AgentSpace默认是 prod环境配置（gateway.ev.mioffice.cn），测试环境需要 dev+uat组合
③ FDS配置：AgentSpace上未配置 ~/.fds-upload-config.json，galaxy-fds-sdk未安装

解决方案：env-check增加 --auto-fix 参数，自动修复后重新检查。
需求导入环节复杂易错 简化
需求导入涉及37个字段映射、样件用途匹配表A-G、EP账号校验等，开发量大且容易出错。决定去掉导入环节，直接查询已导入的可下单需求。
确定简化版方案 决策
剔除飞书MCP、去掉需求导入、去掉强制环境检查。保留核心三步：查询需求→确认下单→执行统计。HTML产物上传FDS获取链接，自然语言交互确认。
字段映射基于真实数据确认 验证
通过查询2026-09-01历史订单，确认submit-list返回的真实字段结构：含税金额(orderTotalPrice)、不含税金额(orderTotalPriceNoTax)、货币(currency)、供应商嵌套对象(supplier.orgName)等。
异常通路全覆盖 + dev环境统一 完成
补充20+异常场景的降级通路，确保主流程不中断。增加env-check-test环境检查Skill，统一使用dev环境。
9.20 飞书MCP授权混乱（20029错误） 反复踩坑
现象：demand-import 自起 feishu-mcp-pro，access token 过期后走浏览器 OAuth，报 20029"重定向 URL 有误"。
踩坑过程：
1. 用户反复拒绝"样件订单自动化助手"应用外壳，要求用自己的小米账号
2. 走 device flow 授权，还是不对
3. 最终确认：20029 错误本质是把飞书 MCP 授权和 garagehub CLI 授权搞混了
决策：demand-import 改成纯本地 JSON 输入，不自起 MCP。从飞书读数据的能力保留，但不自己启动 MCP 服务。
9.20 CLI容器授权问题（GARAGEHUB_AUTH_MODE=device） 容器坑
现象：AgentSpace 容器里跑 CLI 报错，说要走浏览器授权。
根因：CLI 自带的环境判断逻辑有 bug，在容器里会错误检测到存在浏览器，走了需要本地回调的授权流程，而容器里根本没有浏览器。
解决方案：加 GARAGEHUB_AUTH_MODE=device 环境变量，强制走 device flow。
9.20 HTML确认页多轮迭代（一品多供交互） UX迭代
迭代过程：
1. 第 1 版：原生下拉框，用户说"选择效果不好"
2. 第 2 版：卡片按钮样式，用户说"样式太丑了，也不对齐"
3. 第 3 版：复选框（checkbox），用户说"不要下拉框，要前置的复选框"

其他修改：

二、P0 级问题（反复踩坑，花时间最长）

P0-1：CLI 授权 20029 错误，同一个问题改了 4 轮
现象：AgentSpace 容器里跑 CLI 永远报「重定向 URL 错误」，本地跑一切正常。
踩坑时间线：
1. 第 1 轮：以为是登录态过期，让用户反复重新登录，没用
2. 第 2 轮：以为是 settings.json 配置不对，反复改 base_url，没用
3. 第 3 轮：以为是 CLI 版本不对，从 1.0.3-beta.3 升到 1.0.7-beta.3，还是没用
4. 第 4 轮：看了 ep-agno 代码库才发现，容器里 CLI 误判有浏览器，走了 browser flow，必须加 GARAGEHUB_AUTH_MODE=device 环境变量强制走 device flow
根因：CLI 自带的环境判断逻辑有 bug，在容器里会错误检测到存在浏览器，走了需要本地回调的授权流程，而容器里根本没有浏览器。
建议解法（和开发讨论）：
1. CLI 本身应该修复容器环境判断，或者在文档里明确说明容器部署必须加 GARAGEHUB_AUTH_MODE=device
2. 平台层面应该在容器启动时默认注入这个环境变量，不用每个业务方自己加
3. 长期方案：参考 ep-agno，做平台层 token 注入，业务方根本不需要自己处理 CLI 授权
P0-2：公共逻辑重复，改一处漏一处，前后漏了 3 次
现象：
1. 第 1 次：device 模式只加了 demand-query，漏了 demand-order 和 daily-report
2. 第 2 次：FDS 占位符替换只改了 demand-query，漏了 demand-order
3. 第 3 次：登录态缓存只加了 demand-query，漏了其他 skill
根因：我们一开始就定了「每个 skill 完全独立自包含，不抽公共模块」，结果 4 个调 CLI 的 skill 各抄了一份 _get_env、check_login、upload_to_fds，加起来重复代码至少 300 行。改的时候永远会漏一个。
建议解法：
1. 必须抽公共层 ep_common.py，所有 skill import 复用，一次修改全局生效
2. 之前说的「不抽公共」是错误的，独立自包含不等于代码复制，公共逻辑应该下沉到共享模块，业务逻辑才独立
3. 这也是 ep-agno 已经验证过的做法，他们所有 handler 都用同一个 auth.py 和 fds.py
P0-3：不同审查 Agent 互相矛盾，改了又改
现象：
1. 第 1 个审查报告说「要抽公共层」，我们说用户不让抽
2. 第 2 个审查报告说「不要抽公共层，要每个 skill 独立」，我们又改回去
3. 第 3 个审查报告说「import 中文是断点」，我们改了，第 4 个报告又说「import 用中文是对的，收回之前的结论」
4. 第 5 个报告说「env_check 硬编码版本是问题」，我们改了，第 6 个报告又说「env_check 应该写死版本」
根因：每个审查 Agent 都不了解业务背景和之前的决策历史，拿着通用代码规范就来挑错，完全不考虑我们之前为什么这么设计。
建议解法：
1. 以后做代码审查，必须先把「之前的决策历史和约束条件」喂给审查 Agent，不能让它凭空挑错
2. 审查报告要分「必须改的 bug」和「建议优化的点」，不能把所有问题都标成 P0
3. 不要相信多个 Agent 的「对轰」结果，最终决策必须由业务方拍板，不能 Agent 说什么就改什么

三、P1 级问题（影响稳定性，踩过至少 2 次）

P1-1：FDS 上传反复失败，链接打不开
现象：
1. 第 1 次：用 galaxy-fds-sdk，容器里初始化报错，说参数不对
2. 第 2 次：我们自己写了签名，结果把 ${FDS_ACCESS_ID} 字面量当密钥去签名了，上传成功但链接打开是空白
3. 第 3 次：FDS 密钥硬编码在 config.example.json 里，存在泄露风险
4. 第 4 次：daily-report 忘了调用 check_and_setup_fds，全新机器上跑直接报文件不存在
建议解法：
1. FDS 上传逻辑必须下沉到公共模块，所有业务方用同一个实现
2. 文档里明确说明容器部署 FDS 必须注入 FDS_ACCESS_ID 和 FDS_ACCESS_SECRET 环境变量
3. 长期：平台应该提供统一的文件上传能力，不用每个业务方自己对接 FDS
P1-2：输出契约不统一，skill 串联失败
现象：
1. demand-query 输出 stats，demand-order 读 summary，字段名对不上
2. demand-import 不带 --json 参数的时候直接 return，什么都不输出，下游拿不到数据
3. 有的 skill 输出 html_url 在顶层，有的在 outputs 里
建议解法：
1. 定死统一输出格式：status / stage / batch_id / summary / details / outputs / message，所有 skill 必须遵守
2. 所有错误分支也必须输出这个格式，不能输出纯文本
3. 公共层提供统一的 build_result 函数，业务方直接调用
P1-3：环境检查逻辑混乱，重复检查
现象：主控 Agent 要检查，每个业务 skill 又要检查，跑一次查三遍，用户等半天。
建议解法：
1. 明确分工：主控 Agent 只做基础环境检查（Node.js、CLI 版本、配置文件），业务 skill 只做登录态检查
2. 登录态检查要加进程内缓存，同一个任务里不要重复检查

📥 需求导入 SOP

两种数据来源
方式一：从飞书多维表格导入（推荐）
1. 确认飞书 MCP 可用
2. 执行：python3 demand_import.py --config config.json --source feishu
3. 自动拉取【样件导入状态=待导入】的记录
4. 自动完成字段映射、校验、生成导入 JSON

方式二：从本地文件导入
1. 准备好 Excel/JSON 文件
2. 执行：python3 demand_import.py --config config.json --source file --input 你的文件路径
3. 自动完成校验、生成导入 JSON

注意：加 --execute 参数才会实际调用 CLI 导入，默认只生成 JSON

🔍 需求检查 SOP

检查规则（7 大类）
必填字段校验：预算编号、零部件号、样件用途、需求数量、样件类型、要求到货日期等
数量校验：需求数量 > 0
EP 账号校验：格式匹配 ^[a-z][a-z0-9._-]*$
行号连续性：10 的倍数且包内连续
日期校验：要求到货日期格式正确
预算一致性：包内预算编号一致
样件用途校验：必须在 A-G 范围内
✓ 输出结果：PASS / WARN / FAIL 三级，异常记录只进报告不阻断流程

📊 查询可下单需求 SOP

执行步骤
1. 执行：python3 demand_query.py --config config.json
2. 自动分页拉取所有可下单需求
3. 自动按 60 天日期过滤，剔除过期需求
4. 自动生成 HTML 确认页并上传 FDS
5. 输出结构化统计 + items 数据（供下单使用）

输出统计：可下单需求数、涉及零件数、涉及供应商、涉及采购员、需求总数量

🚀 执行下单 SOP

⚠️ 重要提醒
下单操作不可逆！执行前务必确认需求数据正确。

两种执行方式：
① 预览模式（推荐先跑一遍）：加 --dry-run 参数，只预览不实际下单
② 正式下单：不加 --dry-run，实际创建订单

数据传递：直接用 --items 传 JSON 字符串（工作流变量传递），或用 --input 传文件路径
✓ 输出结果：成功 / 草稿（非最低价）/ 失败，按供应商和采购员汇总统计

📈 执行统计 SOP

支持三种统计方式
单日统计：python3 daily_report.py --config config.json --date 2026-09-20
周期统计：python3 daily_report.py --config config.json --start-date 2026-09-14 --end-date 2026-09-20
默认当天：不加参数默认统计当天

统计内容：订单总数、Agent 下单数、手动下单数、日均订单、涉及项目/供应商/采购员、含税/不含税总金额、状态分布、按日分布

什么场景适合 Agent 化
✓ 适合 Agent 化的场景
1. 高频重复操作：如每天查询需求、创建订单、生成报表，规则固定、重复度高
2. 有明确 CLI/API 接口：业务系统已暴露命令行或API接口，可直接调用
3. 需要人工确认节点：如下单前需要用户确认，Agent可以生成确认页并等待回复
4. 多步骤编排：需要按顺序调用多个接口、处理异常、汇总结果
5. 非实时性要求：允许秒级到分钟级的执行延迟
✗ 不适合 Agent 化的场景
1. 强实时性要求：需要毫秒级响应的交易、监控告警等
2. 复杂UI交互：依赖图形界面拖拽、可视化编辑的操作
3. 需要回调的交互：如飞书卡片按钮回调，在AgentSpace不支持
4. 登录态频繁失效的外部系统：如飞书MCP的2小时token，无法自动化
5. 高并发/高吞吐：Agent串行执行，不适合批量高并发场景
开发方式建议
维度AI辅助开发（本项目）专职开发
开发速度快（5天完成5个Skill + 4套方案探索）慢（需需求评审、排期、开发、测试）
代码质量中等（需大量测试验证，细节易遗漏）高（专业编码规范、Code Review）
业务理解深（开发者即业务方，理解需求细节）浅（需需求文档，可能理解偏差）
问题排查快（直接看CLI输出，定位问题）慢（需复现、查日志、沟通）
维护成本低（自己开发自己维护，随时修改）高（需走变更流程）
风险中（AI生成代码可能有隐藏bug）低（经过完整测试流程）
适用阶段探索期、MVP、内部工具生产级、对外服务、核心系统

本项目时间投入：约5个工作日（含4套方案探索、踩坑、简化、优化、测试）。如果由专职开发完成同等功能，预计需要2-3周（含需求沟通、开发、测试、上线）。AI辅助开发在探索期效率优势明显，但生产级稳定性仍需专业开发介入。

红蓝军校验的价值
为什么要用其他 Agent 做红蓝军对轰？
1. 发现盲区：开发者自己测试容易陷入思维定式，其他Agent可以从不同角度发现问题
2. 统计口径验证：发现日报只统计Agent下单，遗漏手动下单的问题
3. 字段映射验证：发现金额字段名、供应商嵌套结构等与预期不符
4. 异常场景覆盖：发现配置缺失、CLI失败、空数据等场景下的崩溃问题
5. 用户体验审视：从第三方视角评估交互流程是否顺畅、输出是否清晰

建议：每个Skill开发完成后，用另一个Agent实例模拟用户操作，尝试各种异常输入，记录发现的问题并修复。这是成本最低、效果最好的质量保障方式。
AgentSpace vs 工作流 选型思考
维度AgentSpace（本项目选用）工作流编排
交互方式自然语言对话，灵活固定流程，节点式
CLI对接支持（可执行shell命令）部分支持（取决于平台）
飞书发送不支持（需自己实现）通常内置支持
人工确认自然语言回复，简单审批节点，正式
异常处理Agent自主判断，灵活需预设分支，僵化
可观测性对话记录可追溯执行日志结构化
适用场景探索性、需要人工判断、半自动化确定性、全自动、高可靠要求

本项目选择 AgentSpace 的原因：样件下单需要人工确认（不能全自动），CLI接口已就绪，异常场景多样需要灵活处理。工作流方案虽然更稳定，但在人工确认和异常处理上不够灵活。未来如果流程完全标准化，可以考虑迁移到工作流。

双版本路径思考 为什么先做 skill 版再做 agno 版
🟡 为什么先做 skill 版？
  • 快：独立脚本，改完直接跑，不用等框架启动
  • 灵活：随便改、随便试，不怕改坏
  • 易调试：print 直接看输出，不用看日志
  • 验证业务：先把业务逻辑跑通，确认需求对不对
🟢 为什么再做 agno 版？
  • 性能好：3.2s vs 26s，快 8 倍
  • 可扩展：继承 BaseHandler，加新功能只要加新 Handler
  • 框架集成：集成到 ep-agno 后，LLM 可以用自然语言触发
  • 生产级：统一接口、统一返回格式、统一错误处理
💡 迁移成本高吗？不高。因为业务逻辑是一样的，只是封装形式不同。核心业务逻辑（拉数据、过滤、生成 HTML）直接搬过来就行。这也是为什么我们选择"先 skill 后 agno"的路径——先跑通业务，再优化架构。
