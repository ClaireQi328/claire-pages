项目目标

将EP样件订单从"人工逐单操作"升级为"Agent自动化+关键节点人工确认"的半自动化流程，实现：

  • 效率提升：需求导入、查询可下单、订单创建全流程自动化，减少人工操作80%
  • 风险可控：关键节点（导入确认、供应商选择、下单确认）保留人工决策权
  • 交互友好：飞书机器人卡片 + 多维表格双通路，适配不同场景
  • 全程可追溯：所有执行记录沉淀在多维表格，支持查询、统计、审计

🔄工作流程（6阶段+3个人工确认点）

阶段1：需求导入前置检查 自动
从多维表格拉取【待导入】状态的需求记录，执行字段校验、EP账号匹配、样件用途分类、预算一致性检查
校验规则：必填字段检查（16项）、需求数量>0、EP账号格式校验、行号连续、包内预算一致、样件用途在A-G范围内
输出：可导入X条 / 异常Y条 / 异常原因列表
👉 人工确认点1：需求导入确认 人工
将校验结果推送给【需求导入人】，结构化展示需求关键信息，用户确认后执行导入
推送内容：可导入总数、零件清单（零件号/名称/供应商/采购员/数量）、异常记录及原因
交互方式：飞书机器人卡片（汇总+详情+确认按钮）+ Agent自然语言交互
用户动作：确认导入 / 查看详情 / 取消
阶段2：执行需求导入 自动
调用 dx-ep CLI import-json 命令，将校验通过的需求批量导入EP系统
CLI命令：dx-ep sapo order import-json --json records.json
输出：成功X条 / 失败Y条 / 失败原因（登录超时/导入失败/字段错误等）
异常处理：登录超时→报错提示重新登录；导入失败→记录失败原因，跳过继续
阶段3：查询可下单需求 自动
调用 dx-ep CLI query-ready 命令，分页获取全部可下单需求，自动过滤到货日期太远的需求
CLI命令：dx-ep sapo order query-ready -f json --page-index N --page-size 100
分页逻辑：先获取第一页获知总页数，循环拉取全部数据，安全上限10页
过滤规则：到货日期超过30天的需求自动过滤
输出：今日可下单需求清单（零件/供应商/数量/日期），含汇总统计
👉 人工确认点2：可下单需求确认 人工
将可下单需求清单推送给【订单管理员】，用户确认后进入供应商选择和下单流程
推送内容：可下单总数、零件清单（零件号/名称/供应商/采购员/数量/到货日期）、统计汇总
交互方式：飞书机器人卡片（汇总+详情表格+确认按钮）+ Agent输出
用户动作：确认下单 / 查看详情 / 取消
阶段4：一价一供/一价多供判断 自动
分析可下单需求，判断每个零件是一价一供还是一价多供，智能选择交互通路
判断逻辑：同一零件只有1条记录/1个供应商/1个价格 → 一价一供；同一零件有多条记录/多供应商/多价格 → 一价多供
智能分流：一价多供 < 5家 → 卡片交互通路；一价多供 ≥ 5家 → 多维表格通路
输出：一价一供X个零件 / 一价多供Y个零件 / 智能分流路径
👉 人工确认点3：供应商选择 人工
一价多供的零件需要用户选择供应商，根据数量智能选择交互方式
卡片通路（<5家）：飞书卡片展示可选供应商，用户点击选择；Agent支持自然语言交互
多维表格通路（≥5家）：推送一价一供执行清单+多维表格链接，用户到多维表格批量选择；选择完成后自动切换状态
用户动作：选择供应商 / 全部确认 / 部分放弃
阶段5：创建订单 自动
调用 dx-ep CLI create-order 命令，EP系统内部完成价格判断（最新且最低价）与提交/草稿
CLI命令：dx-ep sapo order create-order --args "key=value"
价格策略：EP系统内部判定（最新且最低价），Skill只传数据不判价格
结果分类：成功/审批中、草稿（非最低价需人工核实）、失败
输出：成功X条 / 草稿Y条 / 失败Z条 / 订单号列表
阶段6：执行记录沉淀 + 结果通知 自动
所有执行记录写入多维表格，结果通过飞书机器人卡片通知相关人员
记录字段：执行人员、执行命令、执行时间、零件号、供应商、数量、用户动作、状态、耗时、摘要、批次号
通知内容：订单创建结果汇总（成功/草稿/失败）、关键订单信息、后续操作建议
通知对象：订单管理员、采购员、需求用户（按角色区分可见内容）

流程状态机

待导入 → 校验中 → 待导入确认 👈 → 导入中 → 导入完成
→ 查询可下单 → 待下单确认 👈 → 供应商判断 → 待供应商选择 👈 → 创建订单中 → 订单完成

👈 人工确认节点 自动执行节点 异常节点：登录超时/导入失败/创建失败 → 报错+记录+人工介入

💡经验与避雷

❌ 飞书卡片 data_type 兼容性
问题：Card 2.0 table 组件的列定义中，data_type: "text" 会导致 HTTP 400 错误
解决：必须使用 data_type: "string"
教训：飞书卡片组件的参数值必须严格匹配文档，text≠string
❌ CLI JSON 解析路径
问题：dx-ep CLI 的 JSON 输出格式是 {ok: true, data: {content: [...]}}，不是直觉上的 {orders: [...]}
解决：解析时尝试多种路径（data.content / data.items / orders / items），兼容不同命令的输出格式
教训：CLI输出格式必须实测后固化，不能凭直觉猜测
❌ 供应商名称格式解析
问题：CLI返回的供应商字段格式是 id|code|名称12|type，名称后带数字后缀
解决：新增 _parse_supplier_name() 方法，按 | 分割取第3段，再去掉末尾数字
教训：外部系统返回的字段格式必须实测，不能假设是纯名称
❌ 一价多供判断逻辑
问题：最初只判断"同一零件多供应商"，忽略了"同一零件多条记录即使供应商相同也需要用户确认"
解决：修正判断逻辑：同一零件有多条记录 / 多供应商 / 多价格 → 一价多供
教训：业务规则必须与业务方确认，不能凭技术直觉判断
✅ 分页获取全部数据
设计：先获取第一页获知总页数，再循环拉取全部数据，安全上限10页
效果：从只获取100条（第一页）提升到获取全部136条，零件从54→64种，供应商从7→11家
价值：数据完整性是自动化的基础，分页逻辑必须内置
✅ 双通路智能分流
设计：一价多供 < 5家用飞书卡片（交互便捷），≥ 5家用多维表格（批量操作）
价值：不同数据量适配不同交互方式，既保证少量数据的便捷性，又保证大量数据的可操作性
扩展：阈值可配置，根据业务场景调整
🎯 统一输出格式
设计：所有Skill遵循 workflow_schema，输出 summary + details + next_action 标准化结构
价值：Agent可解析、可编排、可展示；用户能看懂关键信息；上下游Skill可无缝衔接
原则：summary给机器看（结构化字段），details给人看（可读列表），next_action给流程看（明确下一步）
🎯 角色可见性设计
设计：4个业务角色（需求导入人/订单管理员/采购员/需求用户），不同角色看不同内容
价值：信息最小化原则，每个人只看到与自己相关的信息，避免信息过载
实现：飞书卡片按角色推送不同内容；多维表格通过视图权限控制；仪表盘按角色提供不同视图
❌ auth_base_url 末尾斜杠
问题：settings.json 中 auth_base_url 末尾带斜杠，导致拼接URL时出现 //oauth 双斜杠
解决：去掉末尾斜杠，或在拼接时自动处理
教训：配置文件的URL格式必须规范，末尾斜杠是常见坑
✅ 执行记录全程沉淀
设计：每个Skill执行后都写入多维表格，含执行人/时间/命令/零件/供应商/数量/结果/耗时
价值：可审计（谁在什么时候做了什么）、可统计（执行次数/成功率/耗时趋势）、可优化（基于数据持续改进）
原则：无记录不执行，执行必留痕
🎯 人机协同节点设计
设计：3个人工确认节点（导入确认/下单确认/供应商选择），其余全自动
原则：高风险/高成本/不可逆的操作必须人工确认；低风险/可回滚的操作全自动
价值：既提升效率（80%操作自动化），又控制风险（关键节点人工把关）
❌ 字段映射必须实测
问题：CLI返回的英文字段（materialNum/materialName/buyer/requiredQuantity/deliveryDate）需要映射到中文字段
解决：新增 _normalize_cli_order() 方法，完整映射12个字段
教训：外部系统的字段名必须实测，不能假设是中文或英文；映射关系必须显式定义
