EP CLI 接口权限校验优化

统一 CLI 与页面权限基线 · 补齐数据隔离缺口 · 配置化替代硬编码

申请人：齐岳（品类管理 / 数字化转型） 日期：2026-08-13 关联会议：CLI 权限问题讨论（08-13 10:02） 状态：待评审立项

一、项目背景

EP 系统推出 CLI 工具，允许采购、品类、工程等角色绕过前端页面、直接调用后端接口，以提升寻源定点、品类管理、报价分析等场景的操作效率。但 CLI 的权限校验沿用的是"页面时代"的设计——而页面时代的权限本就是为"人点页面"设计的，CLI 直调把原本被前端按钮/菜单遮住的后端缺口全部暴露了出来。

2026-08-13 的权限问题讨论会上，研发侧逐接口对齐了现状，确认了核心矛盾：数据权限全部硬编码在后端每个接口里，没有一套配置化的数据权限体系。本次立项即针对这一矛盾，目标是建立 CLI 与页面同源的统一权限校验，并以最小变动补齐最紧迫的数据隔离缺口。

二、当前遇到的问题（现状梳理）

会议逐接口核对后，问题可归为两类：数据裸奔类（安全风险，最紧迫）与架构债类（可维护性 / 扩展性风险，根因）。

2.1 数据裸奔类 · 敏感数据可被任意调取

问题点严重度现状（会议确认）
SOR 三个详情接口
车型信息 / 零件装配比例 / 审批历史		 P0 高危 张宁确认（10:34）："现状是没有控制的，只要能看到页面就能点进来查全量，没有'仅查自己'的控制"。三个详情接口同理。
RFQ 询报价相关接口
报价条目 / 参与供应商 / 预选供应商 / 当前轮次		 P0 高危 齐岳（12:30）确认：报价条目"无权限控制，只要能看到 RFQ 列表或详情页就能点击查看"。郑佳佳确认这些接口前端靠角色/按钮隐控，后端无校验，CLI 直调可绕过。
品类 · 采购员敏感信息未隔离
人员关系 + VPPS 关系		 P1 合规 陈千钧（19:18）提出疑问，齐岳（20:48）确认：采购员在列表已看到所需信息，唯一差别是"谁负责什么品类"，该信息严格不应让采购员知道 → 应隔离 VPPS 相关接口（详情 / 绑定）。

2.2 架构债类 · 根因（为什么问题反复出现）

问题点严重度现状（会议确认）
权限硬编码，无配置化数据权限体系 根因 张宁（03:34 / 22:24）：控制都在接口上，"每次改动没有办法通过配置改，只能去改代码"。加一个角色配了页面，还得同步去改 CLI 代码，端到端。
角色写死会卡死后续新角色 扩展风险 张宁（22:58）明确约束：CLI 侧"仅查自己"可以实现，但"不能把角色限定死，否则后面加一个角色能看页面，可能被代码直接卡死"。
权限模式碎片化，无统一标准 维护 约 25 个接口并存 4 种控制模式：无控制 / 菜单控制 / 代码内数据过滤 / 角色校验（Annotation）。标准不一、不可审计。
审批流角色盲区 维护 张宁（02:41）：审批人员（物流工程师、研发经理、SQE 等）无菜单权限，但可经审批待办点进页面看全量——当前页面允许，CLI 若只认"写死的几个角色"会漏掉他们。
文档与现状不符 文档 陈千钧（17:57）：品类 8 接口在环境上仅"列表 + 变更记录"有控制且变更记录校验与 wiki 不一致；详情 / VPPS 列表当前环境根本无控制。wiki"是否一致"列对品类模块标注不准。
⚠️
一句话总结问题：CLI 把后端权限缺口暴露无遗——SOR/RFQ 的敏感详情接口"裸奔"，品类未隔离采购员敏感信息；而根因是权限被硬编码在接口里、没有配置化体系，导致每次改角色都要动代码、且写死角色会卡死未来的业务扩展。

三、为什么不得不做（立项理由）

以下六条均源自 08-13 会议确认的事实，不是推测。前两条是已经发生的安全/合规风险，后四条是不解决就会持续放大的技术与组织成本。

① 敏感数据裸奔，安全合规风险已发生

SOR 车型/装配比例/审批历史、RFQ 报价条目与供应商信息，目前任何能进页面的人（含经审批待办进入的审批角色）均可经 CLI 调取全量。含供应商报价、车型规划等敏感数据，一旦外泄难以追溯。

不得不做：这是既成风险，不是未来风险。CLI 已在推广，缺口随使用人数放大。

② 信息隔离缺失，违反最小权限原则

品类模块中采购员本不应知道"谁负责什么品类"（人员 + VPPS 关系），但当前设计与文档均存在偏差，隔离未落地。暴露内部职责关系，既不符合数据最小化，也易引发内部协作摩擦。

不得不做：会议已对齐"必须隔离"，属明确的合规/管理诉求，不补即持续违规。

③ 维护成本不可持续（端到端改代码）

权限硬编码在接口，无配置化。每新增/调整一个角色，需同步改页面 + CLI 代码，张宁称为"端到端"改动。人力随角色数线性增长。

不得不做：CLI 受众一旦扩大（会议已提及 CE、财务等），改动频率与回归风险将失控。

④ 角色写死会卡死业务扩展

若 CLI 把"能看的人"写死成固定几个角色，业务后续新增一个可看页面的角色，会被代码直接卡死、看不到数据——反而阻碍业务灵活性。

不得不做：张宁明确点名的风险。不做配置化，越用越僵。

⑤ CLI 规模化推广的前置条件

CLI 要作为正式工具推广给更多角色（品类、工程、CE、财务），必须先有权限基线。没有基线，推广即等于把全量数据接口公开出去。

不得不做：推广路线图已启动，权限基线是 release gate，绕不过去。

⑥ 技术债累积，现状已不可审计

4 种权限模式并存、文档与现状脱节，无人能在一张图上说清"谁现在能看什么"。出问题时无法快速定位，审计无从谈起。

不得不做：债只会随接口增长越积越深，早还比晚还便宜。

📌
会议已留的口子：齐岳在会末明确"今天可能没有结论性的东西，先找业务明确场景，再把改动范围缩紧"。本立项不主张大改底层权限中台，而是以"最小变动补缺口 + 配置化替代硬编码"为边界——与会议"不投大力气做底层改造"的基调一致。

四、目标与范围

✅ 目标

  • 建立 CLI 与页面同源 的统一权限校验（不复刻独立体系）
  • 补齐 SOR / RFQ 数据隔离缺口，收敛裸奔风险
  • 品类模块按会议结论落地采购员 VPPS 隔离
  • 权限从硬编码 → 配置化/白名单，解除扩展卡死

📦 范围

  • 只改后端 API 层，不动前端、不动菜单结构
  • 完全复用已有 ACL 资源树 + 角色绑定，不新建权限表
  • 复用 SOR/RFQ "基本信息"接口已有的过滤逻辑
🚫
非目标（明确不做）：本次不重构底层权限中台、不新建统一的配置化权限平台、不改动前端页面与菜单。若业务场景确认需更彻底的方案，单独立项，不在本次范围内。

五、实施方案（最小变动路径）

总策略：只改后端 API 层，复用已有体系与逻辑，以配置化替代硬编码。按 4 个阶段推进，阶段 0 为前置决策点。

阶段 0 · 业务场景对齐 前置 · 约 1 周
负责人：齐岳 ｜ 依赖：无 ｜ 产出：场景清单 + 受众确认

按会议结论，先反馈业务并明确：CLI 的受众是谁？哪些场景确实需要严格数据隔离？输出"必须做 / 可暂缓"的接口清单，把改动范围缩到最紧。此为后续所有阶段的决策基线。

阶段 1 · 基础设施：CLI 身份透传 前置依赖
负责人：后端 ｜ 依赖：阶段 0 ｜ 改动：中

CLI 请求在 Header 携带用户 Token / UserId；后端统一 Interceptor 解析并注入 SecurityContext，与页面请求走同一套认证。定时任务使用独立服务账号 + 白名单角色。这是所有 CLI 接口权限能生效的前置条件。

阶段 2 · 配置化数据权限（替代硬编码） 解除根因
负责人：张宁 / 郑佳佳 ｜ 依赖：阶段 1 ｜ 改动：中

将"谁能看全量 / 谁仅看自己"从写死角色改为角色白名单 / 配置中心。满足张宁约束：不写死角色，保留其他角色看全量的通道，新增角色不再需要改代码。这是解决"维护成本 + 扩展卡死"两个根因的关键。

阶段 3 · 缺口补齐（最小代码改动） 收敛风险
负责人：张宁(SOR) / 郑佳佳(RFQ) / 陈千钧(品类) ｜ 依赖：阶段 1+2 ｜ 改动：小

SOR：3 个详情接口补"仅查自己"过滤，直接复用 designReq/find 已有逻辑（每行约 3–5 行 if 判断），角色走白名单不写死。
RFQ：4 个接口补后端校验，复用 rfq/find 已有过滤逻辑。
品类：采购员隔离 VPPS——列表 + 变更记录可见，详情 / 绑定不可见；同步定点供应商接口角色收敛（移除"品类专家"，保留品类管理员 + ADMIN + 定时任务服务账号）。

阶段 4 · 文档与现状对齐 收尾 · 0.5 周
负责人：齐岳 ｜ 依赖：阶段 3 ｜ 改动：极小

修正 wiki §9 权限矩阵（采购员详情 / VPPS 列表改为不可见）、修正"是否一致"列使其与环境对齐；沉淀一份"CLI 接口权限现状总表"供后续审计。

六、预期收益

🔒 风险收敛

SOR/RFQ 敏感数据不再裸奔，合规与数据安全缺口闭环。

🔧 维护降本

权限配置化，新增/调整角色不再端到端改代码。

🚀 扩展解卡

角色走白名单，业务加角色不再被 CLI 代码卡死。

七、风险与依赖

项级别说明 / 缓解
业务场景未确认即动手中阶段 0 为硬前置；若业务迟迟不确认，先交付 P0 的 SOR/RFQ 裸奔修复（纯补过滤，风险低）。
回归风险低只改后端 API 层、不动前端与菜单，页面行为不变；复用已有过滤逻辑降低新代码量。
审批流角色覆盖不全低白名单机制 + 保留"其他角色看全量"通道，避免漏判；审批流角色后续按需纳入白名单。
定时任务服务账号低同步接口收敛时确认服务账号白名单，不受角色收敛影响。

排期：阶段 0 ≈ 1 周 ｜ 阶段 1–3 ≈ 2–3 周 ｜ 阶段 4 ≈ 0.5 周 ｜ 合计约 4–5 周（视业务确认速度）
