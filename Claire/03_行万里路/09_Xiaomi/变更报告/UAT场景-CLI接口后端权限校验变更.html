5. 通过标准

  • 所有标注 P0 的场景 100% 通过，无越权成功（即无关角色成功读取他人数据）记为致命失败。
  • owner 类接口：非全量角色返回数据条数 = 该登录人 owner 名下数据，不得包含他人数据。
  • 边界开关 delayStatus="all" 仅在显式传入时跳过过滤，默认仍按 owner 过滤。
  • 创建类接口（nominationAf/create）非采购工程师一律拒绝并报权限错误。
  • 品类写/CLI 专用接口：普通页面用户调用一律 403，仅 CLI/定时任务/授权管理员可成功。
  • 供应商类 ❌ 缺口接口：补校验后，无权限角色调用返回拒绝（不再裸奔）。

6. 风险与回归关注点

风险点说明 / 建议
供应商类接口 ❌ 裸奔4 个供应商查询接口现状无权限控制，是最大越权风险点，必须作为 P0 回归重点。
delayStatus="all" 越权开关RFQ 查询的“全量跳过过滤”开关若未校验调用角色，可被普通用户用于看他人 RFQ。
“能点就能查”类接口查询当前轮次信息等接口依赖前端入口控制，后端无校验，存在 id 遍历越权。
品类 CLI 专用接口暴露页面不调用的写接口若未限制调用方，存在被普通用户直接调用的写风险。
角色权限灰度多角色叠加（如采购工程师同时是审批流Owner）时数据范围需明确优先级，避免过宽。

建议 UAT 执行顺序：先跑全部 P0 越权场景（验证无裸奔）→ 再跑 owner 过滤场景 → 最后跑边界开关与品类 CLI 专用接口。
