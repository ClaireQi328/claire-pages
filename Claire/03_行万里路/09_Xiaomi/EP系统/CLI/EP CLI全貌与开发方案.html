1. CLI 全貌

1.1 定位：API → CLI → Skill → Agent 四层架构

Agent（智能体）
自主决策，串联多个 Skill 完成复杂任务（例：零件定点全流程追踪、供应商风险预警、样件自动下单）
Skill（能力包）
可复用"菜谱"：触发条件 + 执行步骤 + 输入输出规范（例：供应商信息查询、SOR 进度追踪）
CLI（命令行入口）dx-ep <模块> <资源> <动作> [flags]
人可直接调用，程序 / Skill / 定时任务统一消费
API（基础能力）
后端接口：POST /custom/supplier/getById.api 等 EVEP 接口
Agent→Skill→CLI（@mi/dx-ep-cli）→API 网关（dx-garagehub）→EVEP 后端 / oa-contract / sampleOrderCli

3. 权限设置

3.1 权限模型：三层控制

角色层（功能权限：ADMIN / ViewAllSOR / 采购工程师 / 品类管理员…） + Owner 控权（数据权限：All / Owner / 审批流 Owner） + 来源维度（页面 / CLI / 定时任务 / Agent）

3.2 权限矩阵摘要（25 项）

模块接口现状应覆盖角色Owner 控权后端动作
供应商列表 / 详情 / 变更记录无权限控制；变更单有菜单权限不区分角色❌无
供应商变更申请单有供应商管理菜单权限不区分角色❌无
SOR基本信息ADMIN/ViewAllSOR 全量，否则查自己的ADMIN、ViewAllSOR、研发工程师All/All/Owner无
SOR车型 / 零件 / 审批历史页面角色+审批角色控权；CLI 无角色但可查13 类角色 + 审批流 OwnerAll×7/Owner×2/审批流×3补数据权限

3.3 设计原则

  1. 查询类默认按 Owner 控权，全域角色例外（ADMIN/ViewAll 查全量，审批流角色按审批关系控权）。
  2. 写操作必须前置校验操作角色（如 nomi af create、change process、sapo create-order），非目标角色报权限错误，不静默降级。
  3. 不限定死角色清单：权限配置化（角色→接口→数据范围映射），新增角色只配置不写死代码。
  4. 纯 CLI / 定时任务接口收紧来源；供应商端接口按 supplierId 数据权限校验。
  5. CLI 侧鉴权（HUB 账号）与后端角色+owner 数据权限双保险。

4. 开发方案

4.1 开发时间线（WAVE1 · 17 接口 · 23~35 天）

Phase 1 · API 文档定义（产品 + 后端）
6~9 天：产品场景说明 2~3d + 后端接口文档 3~5d + 评审对齐 1d
Phase 2 · 并行开发（后端 + CLI）
7~10 天：后端 API 5~8d + CLI 开发 5~8d + 单元测试 2~3d（17 个并行）
Phase 3 · 联调 + 测试
7~11 天：逐个接口联调 3~5d + 集成测试 2~3d + Bug 修复 2~3d
Phase 4 · 验收 + 发布
3~5 天：业务验收 2~3d + 文档与发布 1~2d
