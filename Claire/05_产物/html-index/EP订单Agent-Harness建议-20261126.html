目标架构

把渠道、编排、业务、副作用和证明机制分开。

01 · Contract

业务契约

输入、输出、计数口径、错误状态、证据要求。

02 · Channel

入口适配

飞书、HTTP、A2A、CLI、Harness 测试入口。

03 · Runtime

任务编排

Task、Plan、Approval、工具选择、暂停恢复。

04 · Tools

统一工具运行时

权限、超时、重试、幂等、审计、契约校验。

05 · Harness

评测与运营

Case、Fixture、Replay、Grader、Baseline、门禁。

关键边界：供应商选择、剔除范围和预算处理继续由人确认；Agent 替代重复操作，不替代关键判断。

当前差距

不是能力清单，而是会影响可靠性的结构性缺口。

优先级问题当前表现影响目标

P1契约偏告警，不够阻断部分校验只 warning。错误状态可能继续回写。执行前/后分级校验，未知状态禁止冒充成功。
P1线上失败没有自动回流发现问题后手工补测试。问题依赖记忆，难持续积累。audit → 脱敏 Case → replay → regression。

核心状态机

最先解决“重启、超时、EP 已建单但回执未知”。

EXECUTING
→
UNKNOWN
→

SUCCEEDED / FAILED

UNKNOWN 不是失败。 它表示外部系统状态尚未确认，系统必须先查证，再决定补记账、重试或人工接管。

Harness 最小 Case

每个业务场景同时定义输入、Fixture、期望轨迹和硬门禁。

id: order.multi.confirm.budget_001
risk: P0
input: "确认执行这批订单"
identity:
  user: qiyue
fixture:
  query_result: fixtures/ep/query_multi.json
  ep_response: fixtures/ep/budget_draft.json
expected:
  route: confirm_order_multi
  status: partial_success
  order_count: 3
must_not:
  - duplicate_order
  - write_before_confirmation
  - silent_success

硬门禁

  • 未授权用户不能执行下单
  • 确认前不能产生外部写入
  • 同一 execution 不能重复建单
  • 无订单号不能标记“已下单”
  • EP 无回执必须进入 UNKNOWN

建设路线

先可靠运行，再系统评估，最后再考虑模型增强。

P0 · 可靠运行
P1 · 评测闭环
P2 · 扩展能力
P0-1

Task / Execution

任务对象、执行对象、状态机、过期和 UNKNOWN。

P0-2

统一 Tool Runtime

收拢 fast_path、diagnose 和主链路的 EP 调用。

P0-3

安全门禁

确认前无写入、结果契约阻断、幂等键和对账。

P1-1

Case / Fixture

查询、预演、确认、执行、失败、安全六类场景。

P1-2

Replay / Grader

验证 route、tool_calls、state、writeback 和文案事实。

P1-3

Baseline / Gate

按 commit 输出报告，硬门禁失败即阻断发布。

P2-1

Durable Backend

共享存储、队列、多实例和跨机器恢复。

P2-2

线上失败回流

审计脱敏后自动生成待审核回放 Case。

P2-3

模型增强

只在确定性边界稳定后，引入 LLM 做澄清和规划。

验收标准

完成标准从“测试通过”升级为“业务结果可证明”。

P0 完成定义

  • 每次下单都有 task_id、execution_id、idempotency_key
  • 服务重启后能恢复或明确标记 UNKNOWN
  • 所有 EP 调用统一进入 Tool Runtime
  • 确认前不会产生 EP、台账或工作台写入
  • 结果契约失败时禁止写入“已下单”

Harness 完成定义

  • Case 可脱离生产凭证重复执行
  • 报告能显示 route、tool、状态和副作用
  • 安全硬门禁一票否决
  • 待补：baseline 对比、CI、线上失败脱敏回流
