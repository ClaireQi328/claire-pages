03

Harness 每一层怎么做

从输入到判定，每一层都有明确职责、产物和失败方式。

L1
Case 层
业务场景 → 可执行用例
输入用户原话、身份、批次、待选表状态
判据必须覆盖查询/预演/确认/执行/失败/安全六类
产物eval/cases/manifest.json
L2
Fixture 层
隔离外部依赖，固定 EP / 表 / 会话
输入脱敏后的查询结果、下单结果、表内已选
约束不连生产凭证；不允许手写 trace
产物eval/fixtures/traces/*.json
L3
Replay 层
真实运行，记录 route / tool_calls / 副作用
入口eval/record.py + SampleAgent.run_traced
观测app/agent_trace.py 请求级 trace
产物trace + reply，含 source=runtime
L4
Grader 层
逐条比对期望与实际
判据route、状态、写入、工具、文案事实
规则未知状态禁止冒充成功
产物eval/grader.py 结构化结果
L5
Gate 层
P0 一票否决，阻断发布
接入run_tests.sh 回归后自动跑
失败缺 trace / 手写样例 / 确认前写入
产物退出码 + eval/reports/local.json
L6
Baseline 层
按 commit 记录通过率与失败项
当前report 已带 commit；对比/趋势待做
下一步baseline + CI 阻断
产物历史报告 / 差异清单

最小 Case 长什么样

id · risk · input · expected.route/status/write_allowed · must_not

示例：order.multi.confirm.budget_001，期望 handle_confirm_execute + 写工具 + 草稿结果。

硬门禁规则

  • P0 必须 source=runtime，且带 case_id
  • 未声明 write_allowed 却出现写工具 → 失败
  • 缺失 trace、空 trace、手写占位 → 失败
  • 未知状态冒充成功 → 失败

人机交互：怎么输入、怎么判断

确定性路由优先，LLM 只做兜底；所有写入必须经过显式确认。

输入路径

入口输入路由/处理输出
飞书消息自然语言 / 需求号 / 批量号intent_router.route()文本卡 / 按钮卡 / 话题卡
卡片按钮action + chat_id + message_id/callback → card_actions秒回执 + 后台执行
EP / A2Aep_chat / ep_actiona2a_adapter → Agent文本 / eval_result
HarnessCase inputrun_traced（与线上同路径）trace + reply

判断原则

  • 先判执行类，再判查询类：避免“查询可下单”被当成下单
  • 权限闸统一：auth_control.gate()，未授权直接拒绝
  • 写入必须确认：确认前不产生 EP / 台账 / 工作台写入
  • 未知不装成功：无回执 → UNKNOWN，不写“已下单”

05

记忆：放在哪里、为什么

不同生命周期的数据分开存，不把“对话上下文”和“业务凭证”混在一起。

会话记忆
sessions/*.json：按 chat_id 存最近 12 轮 + pending，24h 过期
任务状态
app/data/tasks/*.json：task_id / execution_id / 状态机 / 失败原因
下单台账
app/data/order_record.jsonl：append-only，只有订单号才记账
审计日志
audit/audit-YYYYMMDD.jsonl：谁/何时/什么动作/是否允许
评测轨迹
eval/fixtures/traces/*.json：route / tool_calls / violations / result
运行结果
app/skills/*/output/*.json：下单结果、查询结果，作为对账真值

写入原则

  • 先落本地 md / JSON，飞书表只做镜像
  • 会话记忆只存“指针”，不存全量业务数据
  • 敏感信息不进 trace / fixture

读取原则

  • 执行时读“当前真值”（表内已选），不读查询时快照
  • 读不到就明确报错，不静默回退全量
  • 重启后靠 TaskStore 区分“没做过”和“不知道”
06

评测：怎么做才算“证明”

不是跑通一次，而是可重复、可比较、可阻断。

Case 设计

  • 查询 / 预演 / 确认 / 执行 / 失败 / 安全六类
  • 每条 Case 写清“用户原话 + 前置状态”
  • P0 先覆盖：越权、确认前写入、重复下单、未知状态

录制与回放

  • record.py 隔离数据目录，跑真实路由
  • trace 记录真实工具调用与业务结果
  • 拒绝手写 fixture 冒充真实轨迹

评分与门禁

  • route / status / write_allowed / 工具 / 文案
  • P0 硬门禁一票否决
  • 报告带 commit，可做 baseline 对比

建设路线与验收

先把可靠运行做实，再补评测闭环，最后才引入模型增强。

P0

可靠运行

  • Task / Execution 状态机
  • 统一 Tool Runtime
  • 安全门禁与幂等
  • 已：1336 回归 + 4/4 Harness
P1

评测闭环

  • Case 六类场景补齐
  • baseline 对比
  • CI 自动阻断
  • 线上失败脱敏回流
P2

扩展能力

  • 共享存储 / 队列
  • 多实例与跨机恢复
  • LLM 澄清与规划

P0 完成定义

  • 每次下单都有 task_id / execution_id / idempotency_key
  • 重启后能恢复或明确标记 UNKNOWN
  • 所有 EP 调用统一进入 Tool Runtime
  • 确认前不产生 EP / 台账 / 工作台写入
  • 结果契约失败时禁止写“已下单”

Harness 完成定义

  • Case 可脱离生产凭证重复执行
  • 报告能显示 route / tool / 状态 / 副作用
  • 安全硬门禁一票否决
  • 待补：baseline、CI、线上失败回流
