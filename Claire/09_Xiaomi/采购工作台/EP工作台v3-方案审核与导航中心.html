B

审核结论：v2 方案与现有原型，砍什么、留什么、加什么

审核对象：v2 方案与原型（8 模块 + 一个流 + AI 入口）、对标 wiki 落地建议、FDS 融合版原型。总判断：方向对、顺序错、太重了。真实第一痛点是"找不到"，不是"看板不够多"。
v2 / wiki 方案项审核判定理由
导航治理（菜单重组 + 收藏 + 最近访问 + 搜索）新增为 P0 第一位v2 把它排在收藏 chip 的次要位置，实测证明这是最大痛点：19 个一级、10 个藏在溢出区、12 组重复。老板吐槽、张平找不到页、会议纪要里唯一"改动量不大但可以实现"的项——性价比最高，先做。
待办策展排序 + 行内操作保留 P0真实需求。但数据源改为复用个人中心「待处理任务」接口，不新建待办存储；先做排序与行内审批，看板视图缓一缓。
流程状态矩阵（子步骤/停留时长/执行人）收窄为 P1全节点停留时长要后端统计接口，短期没有数据源。首期只做「询报价与定点」主线的节点状态表，子步骤展开等接口就绪再上。
预警卡片分级降为 P1依赖预警规则引擎，没有规则就没有可信预警；先靠"待处理任务 + SLA 字段"排序顶上。
待办统计 / 指标卡下钻保留 P1复用待办统计开放接口，前端只做展示，成本低；PM/主管角色上线后价值才显现，不必抢 P0。
消息/动态中心（新建模块）合并，不新建系统已有「通知管理」，新建 MessageCenter 是重复建设；改为增强通知管理：三级分类 + 已读追踪。
AI 能力地图（skill 卡 + Agent 任务卡）拆分降级skill 清单 + 点击注入助手 = P1 保留（会议已确认可行）；Agent 任务卡、AI 主动推送 = P2，等 L2 行动能力上线再说。
组件化自定义（显隐/排序/拖拽设计器）砍掉业务要"自由组合"的本质是"我要的入口在前排"——收藏 + 最近访问 + 角色默认视图已覆盖 80%；拖拽设计器是工程上的无底洞，砍。
一个流 Workspace（NIO 式）降为 P2 观察项NIO 只作思路参考不作主对标；EP 单据流已有 BPM 审批链，再造一个"流程驾驶舱"与现有流程中心重复。先观察导航治理后业务是否还提。
角色 × 模块矩阵（六角色配置引擎）轻量化实现角色概念保留，实现从"模块级配置系统"改为"角色默认收藏 + 默认落地视图"——一张配置表解决，不建配置引擎。

判断一 · 顺序倒过来

原方案"工作台模块驱动"，改为"导航治理驱动"：先让用户 3 次点击内到达任意页面，再谈首页信息设计。前者零新接口、纯配置整合，两周内可见效。

判断二 · 重复建设红线

待办不建新存储（复用待处理任务接口）、消息不建新模块（增强通知管理）、流程不建新驾驶舱（BPM 已有）、AI 不建第二助手（NPM 包注入）。四条红线全部写进方案，回应老板关切。

判断三 · 对标角色调整

主对标 = 阿里云控制台导航范式（本次用户明确要学）+ EP 自身实测；NIO / Miracle / IDP 降为参考项，只在"角色化思路、一个流概念"两处引用，不再作为方案骨架。

2

方案：三层架构，导航先行

L1 · 导航中心（P0）

菜单信息架构治理 + 阿里云式全量菜单 + 收藏 + 最近访问 + 全局搜索。解决 R1/R3 大部分：3 次点击到任意页面，角色默认收藏。零新接口：菜单重组=前端路由与权限配置整合；收藏=1 张表 2 个接口；最近访问=本地存储先行；搜索=纯前端索引。

L2 · 任务中心（P0-P1）

首页=待办摘要卡 + 我的项目 + 通知，全部复用既有接口：待处理任务（排序+行内审批）、通知管理（三级分类增强）、待办统计开放接口（完成率/逾期视角）。解决 R2/R5/R6，不新建任何存储。

L3 · 智能层（P1-P2）

skill 清单挂载 + 点击注入 EP 智能助手（切 Agent、带上下文）；AI 摘要推送与 Agent 任务卡等 L2 行动能力就绪后再上。解决 R4，不自建助手。

3

菜单重组：19 个一级 → 9 个业务域

重组原则：单一维度 MECE（按业务阶段 + 对象域，不再按单据类型和角色动作混排）；同名合并、散落归位、测试下线、命名统一；一级 ≤ 9 个保证横向全露出、不再有"···"。
