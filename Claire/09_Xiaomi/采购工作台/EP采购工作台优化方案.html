1

为什么要改：EP 完成了上线化使命，但四个新矛盾正在消耗用户

先客观评价现状：EP 今天 19 个一级菜单、60 多个页面，SOR→BDL→RFQ→定点→合同→订单→履约单据链全线在线——"把线下工作搬进系统"这个使命，EP 完成得很好。但系统在线 ≠ 工作顺手。功能越加越多之后，矛盾浮现（以下均有 2026-10-13 ep-dev 实测佐证）：

矛盾一 · 系统按功能摆，人按任务干

菜单是跟着功能一起长出来的：19 个一级里 10 个藏进"···"溢出区；同一个功能 2-4 个入口（采购定点×2、移地生产×2、物流价格变更 4 个近似项）；两个「采购任务管理」同名并存。

后果：首页成了"系统地图"而不是"工作入口"，找一个已知功能的页面也要凭记性或问人。

矛盾二 · 单据里都有流程，单据外看不见流程

每张单据的审批流是在线的（BPM 有完整节点记录），但跨项目、跨单据没有一处能回答："我负责的包各走到哪一步？哪个卡住了、卡在谁手上？"

后果：流程数据在系统里，"进度"却靠群里问、手工拉表——系统把活干了，没把话说明白。

矛盾三 · 待办处处有，没人替你管

12 类任务（寻源定点、价格变更、样件、售后、SQMS…）各有各的列表页，没有统一聚合：谁也不知道今天一共几件事、哪件最要紧；回标到了、审批转来了，都得自己翻。

后果："今天要做什么"的答案散在 12 个页面里，靠腿脚补齐。

还有一个正在长大的矛盾：AI 已经能替采购干不少活（比价、催办、查单、材料摘要，一批 skill 已开发），但用户看不见它、不知道它会什么、升级了也不知道——已建设的能力没有形成实际使用。
四个矛盾指向同一件事：EP 的下一步不是"更多功能"，而是"让在系统里干活的人顺手"
2

往哪个方向改：EP 承载定位的再一次升级

第一阶段，EP 是业务在线化的载体——单据、审批、台账进系统；本方案进入第二阶段：EP 要成为采购工作的主战场——不是"能用系统"，而是"在系统里干活"。工作台就是这个主战场的指挥部：
今天（待办列表式）升级为（任务中心）判断标准
系统地图：按功能模块组织工作入口：按人和任务组织任何页面 3 次点击内到达
单据堆叠：数据在线但沉默流程视图：进度、卡点自己说话进度不用群里问
人找事：待办散在各页自己翻事找人：按属性聚合、按轻重排队一进首页答得上"今天做什么"
AI 藏在工具里AI 亮在首页上，升级可见能力看得见、点开就能用
这个升级不动业务底盘：单据、审批、数据、AI 助手全是现成的——改的是组织方式和呈现方式，把"系统的样子"换成"工作的样子"。
3

这一版做六件事

角色化

分角色设计工作台

  • 六个岗位六套默认视图：待办属性、流程链、数据范围、默认收藏全按岗位定义
  • 每个角色看自己的流程：采购员看 SOR→合同、CE 看核价→台账、SIE 看准入→PPAP→样件、SQE 看不符合→8D→关闭、物流看到货→对账
  • 待办分层视角：个人看自己、组长看本组、管理员看全员；个人可再微调
  • 实现 = 一张角色配置表 + 各卡片的数据过滤，不做配置引擎

为什么：现在所有角色共用同一页——PM 想看的项目进度和采购员想看的回标待办混在一起，谁也看不清自己那摊。

卡片化

卡片自由编排

  • 首页拆成八张卡：晨报 / 待办 / 项目 / 流程 / 通知 / 收藏 / 最近 / AI 地图
  • 每张卡可显示、可隐藏、可调顺序，一键恢复默认
  • 后期升级：拖拽摆放 + 从部件库添加新卡片

为什么：不同岗位、不同项目阶段的重点不一样，固定布局永远顾此失彼——把"摆哪张卡"的决定权交给干活的人。

今天要做什么

待办按任务属性归组

  • 沿用 EP 已有的任务类型：寻源定点 / 价格变更 / 颜色件定价 / 样件 / 售后件 / 物流价格变更 / SQMS 确认…
  • 每组带数量角标，一眼知道哪类压着几件
  • 点组直达对应任务中心；状态沿用待处理 / 已处理
  • 行内动作：去提交 / 去催办 / 去审批，办完一条少一条

为什么：现在 12 类任务各占一个页面、没有数量没有聚合，"今天做什么"要挨页点开才知道——按业务本来就有的任务类型归组，首页直接给出每类的数量和清单。

流程到哪了

流程可视化

  • 我负责的每个包一张流程卡：SOR→BDL→RFQ→定点→合同
  • 当前节点高亮带进度，卡住的红标置顶
  • 点节点展开：该节点单据 + 子步骤 + 责任人 + 停留时长
  • 一键跳单据、一键催办——看到即可处理

为什么：审批流数据都在系统里，但跨项目没有一张聚合视图——进度靠群里问、卡点靠人肉盯，数据在线却没有说话。

AI 增强

AI 能力地图

  • 能力按域分组上首页：寻源与定点 / 成本与价格 / 供应商 / 通用效率
  • 每项能力点开可见：干什么、执行步骤、一键发起
  • 新上架 / 升级 / 内测带标 + 本周更新动态——升级看得见
  • 点击即把指令递给 EP 智能助手，自动带上下文

为什么：一批 skill 已经开发完成，但缺少统一入口，多数用户不知道系统具备哪些能力——先在首页集中展示能力与更新，才有人用、才有人反馈。

去哪找

菜单重组 + 可收藏

  • 19 个一级沿业务主线合并为 9 个域，全部露出顶栏，不再有"···"
  • 「全部」面板：左边选业务域、右边看该域所有页面
  • ★ 收藏自动上顶栏；最近访问排最前；搜索两个字直达
  • 12 组重复入口归一，测试菜单下线
  • 节奏：菜单和工作台是两件事——先做工作台内的收藏卡，菜单整体重排待研发评估工作量后分步走

为什么：菜单跟着功能自然生长到今天，找页面靠记性——把"系统地图"重描成"业务地图"，是任务中心成立的前提。

▲ 界面依赖平台能力 ▲
第二层 · 平台能力中层：决定"能不能复用"的一层
技术栈：React + antd 3.26拖拽布局引擎 0→1卡片编排框架 0→1权限点与角色配置消息与已读服务文档编辑器（AI 文档）储备

技术栈是根因所在：EP 用 React（组件写法 JSX + Hooks），Miracle 用 Vue（模板语法 + 选项式组件），IDP 也是另一套自研栈——组件是框架的产物：语法、生命周期、状态管理、事件与样式方案全不同，构建工具也不同。两个框架的组件就像两种语言的源码，即使交互长得一模一样，代码也无法跨运行。所以 Miracle 的卡片拖拽、IDP 的面板，只能当"效果图"看，不能当"代码"搬。

0 到 1 新开发

无捷径：平台能力长在各自框架上

▲ 平台构建于原子组件之上 ▲
第三层 · 原子级组件底层：现成可用的积木
开源组件：antd 3.26（表格/页签/表单/徽标/抽屉）EP 业务原子：面包屑/状态标/权限指令设计令牌与主题

这层是"能共用"的部分：antd 是开源库，React 生态直接用；Vue 系统看的是它的"设计"而非"代码"。EP 已有的业务原子组件（面包屑、状态标识、权限点）在新工作台零成本复用——这是「不换框架」的前提：底盘够用，缺的只是上面两层的组织方式。

A2 · 为什么代码跨不过框架：四条技术原因 + 一堵版本墙

① 组件模型不同

React 组件是函数/类返回 JSX，数据单向流动（props 进、回调出），逻辑复用靠 Hooks；Vue 组件是单文件组件（template + script + style 三合一），v-model 双向绑定、自定义指令、mixin——同一个"收藏面板"在两种模型里是两套完全不同的写法，没有自动翻译器。

② 生态 API 不互通

组件库跟着框架走：antd 是 React 生态，Vue 侧对应的是 Element 等——同样是"表格"，antd 用 columns 配置 + render 函数，Vue 系用模板插槽 + scoped-slot，API 形态完全不同。换框架复用 = 每个组件的调用方式全部重写。

③ 运行机制不同

React 靠虚拟 DOM diff 重渲染，副作用集中在 useEffect；Vue 靠响应式依赖追踪做组件级更新，生命周期是 created/mounted/watch 三段。状态逻辑与渲染时机对不上，业务代码无法整体移植。

④ 工程隔离：强行打包 = 双运行时

peerDependencies、构建链（umi vs Vue CLI）、样式编译（less 变量 vs scoped style）互不兼容。把 Vue 源码打进 React 应用，等于同时加载两套框架运行时：包体积翻倍、全局样式冲突、两套状态管理互相看不见——工程上不可接受。

版本墙：即使同为 React 生态，antd 3.26 与 4.x/5.x 存在破坏性 API 差异（Form 重写、图标系统独立、样式方案从 less 转向 CSS-in-JS）——EP 版本冻结不升级，所以沉淀包必须显式声明 peerDependencies: react@16 + antd@3.26，同栈但版本不同的系统也不能直接共享同一个组件包。这是"沉淀"一节里复用模式的硬约束。
A3 · 决策记录（三条，评审可追溯）

D1 · 不换前端框架

antd 3.26 不是落后框架，冻结使用不升级。换框架 = 现有全部页面重新适配，成本远大于收益——SCP 有先例：评估过主流自研框架后仍沿用内化技术栈。本方案全部基于 React + antd 3.26，不动底盘。

D2 · 平台层 0 到 1，用开源内核不搬代码

拖拽编排基于 React 生态成熟开源内核（dnd-kit / react-dnd）+ 自研布局配置服务——不重复造轮子，但也不指望搬 Miracle 的 Vue 代码。文档编辑器与 AI 文档需求合并评估，一次立项。

D3 · 分工与产出

第一层界面由产品主导（原型即需求）；第二、三层技术架构说明由研发产出：每层有什么、缺什么、工作量多大。产品给命题，研发出方案，周会同步、周四评审。

B

沉淀视角：不能复用别人，但可以沉淀自己的

Vue / React 互不兼容的另一面：凡是"纯 UI + 数据源注入"形态的东西都可沉淀；凡是长在 EP 框架上的，对同栈系统（React + antd 的外采内化平台，如 SCP）就是即插即用的资产。
可沉淀资产形态谁能复用沉淀动作

D

回到组件清单：为什么"看起来有"的组件实际不能用

2026-10-13 与前端团队评审结论：本方案组件均需在 EP 侧重新开发，没有可直接复用的成品。三条硬约束——这也是排期的前提，先对齐再开工。

① 技术栈不同，代码不可迁移

Miracle / IDP 与 EP 底层框架不同（10-13 前端评审结论：Miracle 工作台为独立开发，与 EP 框架不同，代码不能搬运）——代码不是"搬过来改改"的关系，只能参考交互形态，落回 EP 自己的技术栈重写。

② 不是通用组件的形态

那些平台的工作台组件是和各自业务耦合的定制实现（两边不是通用组件的形态）——没有开源库 / 内部 npm 包可装，抽不出一个能跨系统安装的组件。

③ 唯一能复用的只有"原子"

EP 自己的组件库（Ant Design 3.26）里的表格、页签、徽标等原子组件可以直接用，拼出来的样式和线上页面天然一致；但工作台需要的"组合层"（菜单面板、属性待办、流程卡、晨报卡…）EP 没有做过，都要新写。原子拼装 = 快；组合层 = 新开发工作量所在。和 Miracle 的关系：Miracle 侧愿意提供"拖拽框架、需求进度视图、甘特时间轴"三个组件的代码作参考，但同时注明前提"主要看底层技术框架能不能兼容"——EP 前端评估两边框架不同、不能直接复用。这三项仍按新开发排期，Miracle 代码定位为实现思路参考，不是复用通道。

  • 工作台 = 武器库：区域分区 + 拖拽挪位，banner / 通知 / 收藏 / 看板都是可添加的部件定位是"武器库"：想要就加，不想要就删

IDP 零部件全生命周期平台 · 做得好的与组织方式差异

2026-10-10 内部请教打开 IDP 一页纸 ↗

他们做得好的地方

  • 工作台 = 作战单元：不按功能菜单切，按"一批零件的一次开发"组织——条目 = 零件 + 车型 + 阶段，需求、方案、任务全挂在作战单元上
  • 权威数据源原则：零件变更履历 / 全景图由上游 BOM 系统提供完整接口，下游不自拼自己拼不一定准也不一定全，拼错了说不清
  • 消灭手工台账：DR、采购各自用 Excel 画零件变更图谱正是他们要治理的反模式
  • 组件治理清醒：多套组件库并存（自研 / antd / 设计标准库），新项目用标准库、老系统逐步迭代，不强行一步到位

组织方式与我们不同 · 仍可借鉴

  • 差异：IDP 按作战单元组织（一批零件一次开发），我们按任务属性 + 单据流程组织（12 类任务、BPM 审批链驱动）——EP 单据强流程，照搬作战单元会和现有单据体系打架
  • 但思路同源：我们的流程卡已经按"项目 / 包"聚合（一次定点 = 一次作战），没照抄形态、吸收了内核
  • 数据治理原则吸收：工作台不自存业务数据、全部读源系统——正是我们"四样不重复建"的出处
  • 共同诉求：两边都想补项目管理视图（项目 / 包维度的进度与负荷）——可共建设法，避免两套系统各做一个

工作台本身是消耗品（会随业务改版），沉淀下来的组件、平台能力、规范是耐用品。这张图回答三件事：沉淀什么、什么时候沉淀、谁能用——并给每一步设了触发闸门，避免"为沉淀而沉淀"变成新的重复建设。
STEP 1 · 随建随沉淀
建工作台时顺手攒P0 · 本项目内 · 不额外立项
沉淀什么
  • 8 张卡片按"纯 UI + props 数据注入"写，不与 EP 接口耦合——这是能不能复用的分水岭
  • 设计令牌：状态色 / 间距 / 字号语义抽成 JSON
  • 收藏、最近访问、布局的数据协议先定义（1 表 2 接口）
产出物
  • 组件清单 + 设计令牌 JSON + 接口协议草案
触发闸门：本项目已具备——写代码时多花 5% 解耦成本，不额外排期
→
STEP 2 · 抽包成平台
私有 npm 组件库P1 · 有第二个使用者时启动
沉淀什么
  • 组合组件库 v1 发私有 npm（peerDependencies: react@16 + antd@3.26）
  • 拖拽布局引擎 + 布局配置服务独立成包（不与 EP 页面绑定）
  • EP 前端交互规范一页纸（卡片体系 / 状态色语义 / 下钻模式）
首个复用对象
  • SCP 等同栈（React + antd）商采内化系统的工作台 / 列表页
触发闸门：P0 组件数 ≥ 8 且 第二个系统有明确需求——没有真实第二个使用者，就不发版
→
STEP 3 · 配置化生态
工作台 = 配置，不是开发P2 · 跨栈只输出规范
沉淀什么
  • 组件"武器库"（添加部件市场，Miracle 已验证形态）
  • 新系统工作台 = 选组件 + 配数据源，从"开发项"变"配置项"
  • AI 能力桥（填 prompt + 切 Agent 方法）沉淀为公共层
跨框架怎么办
  • 星河云等自研栈系统不搬组件，只复用规范层：设计令牌 / 交互规范 / 接口协议
触发闸门：≥2 个系统真实在用组件库（有多租户验证），才投"配置化"这笔钱
飞轮：为什么越早解耦越划算
组件被更多项目复用→ 真实场景打磨，组件更完备→ 单项目边际成本下降→ 更容易被下一个项目选用↻ 飞轮的起点是 STEP 1 的"解耦写法"——现在不解耦，以后翻旧代码补包的成本远高于顺手做
谁能拿走什么（受益矩阵）
系统技术栈关系可复用资产时点
EP 工作台本体全部（组件 / 平台能力 / 规范）P0
SCP 等同栈商采系统React + antd 同栈组合组件库 + 拖拽引擎 + 交互规范，接入即用P1
未来新采购域系统同栈工作台配置模板（选组件 + 配数据源）P2
星河云等自研平台不同栈（Vue / 自研）只复用规范层：设计令牌、交互规范、接口协议——组件代码不跨框架随时

成本账

STEP 1 的解耦是写代码的姿势，多花约 5%；STEP 2 的发版是有第二个用户才做的工程动作。全程不立"平台组"、不预养团队——沉淀是项目的副产品，不是独立投资项目。反过来，若每个商采系统各做一套工作台，才是真正的大重复建设。

反面清单：这些不叫沉淀

① 现在就去搬 Miracle 的 Vue 代码（框架不兼容，是重复建设不是复用）；② 没有第二个使用者就抽空件库（会变成维护负担）；③ 为跨栈统一强推换框架（全页面重适配，成本失控）；④ 把业务接口写进组件（永远出不了 EP）。
