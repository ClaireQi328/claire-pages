一、一品一点 / 一品多点：拆成三个按钮

之前要下两轮：先下一品一点，再去表里选完供应商说「按表下单」。现在查询后直接给三个按钮，一次点击即可。

按钮下什么出现条件
✅ 下单一品一点（N 单）单供应商需求本批有一品一点
✅ 下单一品多点（M 条）只下表里已选好供应商的行表里至少有 1 行选了供应商
✅ 一键全下（一点 N 单 + 多点 M 条）两条一起下上面两个都满足

三条安全约束（已用测试锁定）

  • 多点只下「已选供应商」的行 —— 没选就不会出现按钮，绝不替用户挑供应商
  • 点「下单一品多点」时强制清空一品一点部分 —— 不会误下
  • 多点下完保留一点待办 —— 可以接着点「下单一品一点」

下单结果如何返回

成功、失败、失败原因分别列出，失败原因同时写入表格「匹配说明」列：

🎉 一键下单完成 · 批次 ORD… ✅ 成功 1 条需求（1 张订单） - 本次提交：一品一点 0 条 · 一品多点 2 条 ❌ 失败 1 条需求 - EP2｜供应商[SUPT00416]非SAP正式供应商编码 💡 失败原因已写入「一品多点待选」表「匹配说明」列

二、剔除需求表：一个写法导致两条全失效

事故：CGFP202611100001 / CGFP202611100002 被下掉了

剔除表里写的是 CGFP202611100002.CGFP202611100001（中间是英文句点）。旧解析只按「空格 / 逗号 / 分号 / 顿号」切分，不认句点，整串被当成一个无效需求号 → 两条剔除全部失效。

写法修复前修复后
CGFP202611100002.CGFP2026111000010 个（全部失效）2 个 ✅
CGFP…596、CGFP…595（顿号）2 个2 个
换行分隔正常正常
大小写混写可能失败自动统一大写

新做法：不再依赖分隔符，直接从文本里提取所有 CGFP… / EP… 形态的单号。线上验证：剔除总数 607 → 609，两条已生效。

三、升版需求：为什么它总能"逃"过拦截

EP 的 cantPoReason 是什么

EP 后端实时计算的可下单性判定，六个条件任一不满足就写原因：

条件提示文案
不是最新版本最新版需求才能创建订单
状态不是待下单（PASS）待下单状态才能创建订单
需求数量 = 0数量大于0才能创建订单
没有定点供应商未定点不能创建订单
需求已删除删除需求不能创建订单
历史版本存在进行中订单当前或历史版本存在进行中订单

关键：什么算「进行中订单」

只有 CANCEL（关闭）和 operationType=DELETE 被排除，其余全部算进行中 —— 包括 DRAFT（草稿）。

状态中文算进行中？
DRAFT草稿算
SUBMIT审批中算
PASS待供应商确认算
EFFECTIVE供应商已确认算
CANCEL关闭不算

当前拦截逻辑（三级）

升版需求（operationType=02） ├─ ① cantPoReason 非空？ → 拦截 ├─ ② 本地下单台账有记录？ → 拦截 └─ ③ 都通过 → 进可下单池（带 v2 标识）

下单时还有两道闸：默认拦升版；即使加 --allow-upgrade，cantPoReason 非空仍然拦住。

发现的问题：EP 对升版需求不回填 cantPoReason

实测 11 条（CGFP202609242352 等）：11-09 下单成功（订单 4900048158），11-10 再查询时 cantPoReason 仍为空，于是又被当成「可下单」进池。直接调 CLI 复查，至今依然为空。

所以增加了第二道兜底：本地持久化下单台账（app/data/order_ledger.jsonl），只要我们自己下过单，一律拦截。

六、执行日志：按批次号一搜就能定位

根因：JS 一直在读，Python 从来没传

表格「批次号」列长期为空 —— 因为 log_event 只把整段文本塞进「摘要」，从未传 batch_id 字段。

新增 7 个日志字段

字段用途

pr_nos / pr_count定位具体单据

⚠️ 注意事项

1. 剔除表写法：建议用顿号或换行

虽然现在句点也能解析，但为稳妥，多个需求号请用 顿号 、 或 换行 分隔。一个单元格塞几百个单号时，尤其要用换行，便于人工核对。

2. 「非最低价」草稿不会自动提交

EP 建了单但停在草稿，不是失败。需要人工到 EP「我的草稿」确认价格后提交。结果卡会单独列出这类单，不要当成系统异常。

3. 草稿单在提交列表里查不到

EP 的提交列表只返回 EFFECTIVE / PASS / SUBMIT 三种状态。草稿（DRAFT）和关闭（CANCEL）都查不到，只能到 EP「我的草稿」页面看。

4. 已知未修：订单被关闭后，台账仍拦着

实测：订单 4900048141 / 4900048142 / 4900048158 在 EP 中已被关闭（CANCEL），但台账仍记为「已下单」→ 相关需求（共 229 条）被永久拦住，无法重新下单。

下一轮要做的改动：台账增加「订单关闭检测」，关闭的自动放行。

5. 多点历史数据不会自动纠正

回写逻辑已修，但表里已有的 274 行历史记录不会自动更正。新产生的数据是准确的；历史行如需修正，要单独跑一次数据订正。

6. 一键下单仍是"人确认后才执行"

三个按钮都需要用户主动点击，系统不会自动下单。点完按钮会先返回「正在下单中」，结果由后台推送。重复点击会被拦截。
