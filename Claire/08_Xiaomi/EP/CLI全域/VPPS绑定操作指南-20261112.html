一、先搞清楚在改什么

VPPS 是零件的「结构位置编码」，品类是采购分类。绑定就是把某个位置的零件挂到某个采购品类下，并指定负责的人。一次绑定同时影响四件事：

影响对象说明
品类归属零件从「无归属」或「A 品类」变成「B 品类」的成员
采购工程师品类下的采购负责人，绑定后由他/她维护
SQE 工程师质量负责人，选填
财务 CE成本负责人，选填
关键：绑定粒度是「编码」，不是「一行记录」

同一个 VPPS 编码可能对应多条记录（历史遗留、不同零件名）。绑定一个编码，会把该编码下所有记录一起处理——包括已失效的。这是后端设计，不是 CLI 的取舍。

完整链路

查待绑定编码
→
查目标品类
→
dry-run 预览
→
执行绑定
→
回查确认

二、查：确认现状

2.1 查某个编码当前挂在哪个品类

dx-ep mvps vpps list --vpps-code 1015-B009 -f json

这是执行前必做的一步。返回里会带品类归属和人员信息：

字段含义示例
bindStatus绑定状态BIND / TO_BIND
categoryCode当前所属品类CAT-00284
categoryName品类名称高压连接器
buyerName当前采购工程师程家琛
financeCeName当前财务 CE杨枫
activeStatus编码是否生效ACTIVE / INACTIVE
判断动作类型

bindStatus = TO_BIND → 首次绑定，安全。
bindStatus = BIND 且 categoryCode 不是目标品类 → 改绑，会把零件从原品类移走。

2.2 查目标品类是否可绑

dx-ep mvps category detail --code CAT-00009 -f json

重点看三项：categoryStatus 必须是 EFFECTIVE；vppsList 里现有成员，判断语义是否匹配；categoryExpert 是否为空。

2.3 查一批待绑定的编码

# 全部待绑定（7582 条，分页取）
dx-ep mvps vpps list --status 待绑定 --page-size 100

# 按品类看现有成员
dx-ep mvps category list --vpps-codes 1015-B009

# 按采购工程师反查他负责哪些品类
dx-ep mvps category list --buyer-id <用户ID>

三、绑：发起绑定

3.1 命令

dx-ep mvps vpps bind \
  --vpps-code 1015-B009 \
  --category-code CAT-00009 \
  --buyer-name 路梦瑶 \
  --sqe-name 郑雄
参数必填说明
--vpps-code是VPPS 编码，多个用逗号分隔
--category-code是目标品类编码，须为生效状态
--buyer-name是采购工程师姓名，只能填一人
--sqe-name否SQE 姓名，只能填一人
--finance-ce-name否财务 CE 姓名，只能填一人
--dry-run否只预览请求，不写入
姓名只填一个人

三个人员字段都不接受逗号分隔。填「张三,李四」会直接报错 最多一人，不支持逗号分隔多个姓名。需要多人分管时，拆成多次调用。

3.2 先 dry-run

dx-ep mvps vpps bind --vpps-code 1015-B009 --category-code CAT-00009 \
  --buyer-name 路梦瑶 --sqe-name 郑雄 --dry-run

输出会显示实际发出的请求体：

{
  "vppsCode": "1015-B009",
  "categoryCode": "CAT-00009",
  "buyerName": "路梦瑶",
  "sqeName": "郑雄",
  "financeCeName": ""
}
dry-run 不校验业务规则

dry-run 只组装请求体，不检查「品类是否冻结」「VPPS 是否已绑定」。所以 dry-run 通过 ≠ 一定能绑定成功，仍要先做第 2 节的核查。

3.3 批量绑定

# 多个编码绑到同一品类
dx-ep mvps vpps bind --vpps-code 1015-B001,1015-B002,1015-B003 \
  --category-code CAT-00284 --buyer-name 程家琛

编码之间用英文逗号，不要加空格。批量时三个人员字段会应用到全部编码。

3.4 执行后回查

dx-ep mvps vpps list --vpps-code 1015-B009 -f json

确认 bindStatus 变成 BIND、categoryCode 是目标品类、buyerName 是新负责人。

四、解：发起解绑

4.1 命令

# 解绑指定编码
dx-ep mvps vpps unbind --category-code CAT-00009 --vpps-code 1015-B009

# 解绑该品类下全部 VPPS（谨慎）
dx-ep mvps vpps unbind --category-code CAT-00009
参数必填说明
--category-code是要从哪个品类解绑
--vpps-code否要解绑的编码，多个用逗号分隔；不传则解绑该品类下全部
--dry-run否只预览请求
不传 --vpps-code 等于全量解绑

这条命令没有二次确认，也没有 --all 开关。少写一个参数，整个品类的 VPPS 关联会被清空。执行前务必 dry-run 看清 vppsCode 字段是否为空串。

4.2 解绑会清空人员字段

解绑后，该编码在品类下的采购工程师、SQE、财务 CE 关联一并消失。如果只是换人而不是解除归属，应该用 bind 重新绑一次覆盖人员，不要先解再绑。

4.3 解绑 vs 标记无需绑定

动作状态变化适用场景
unbindBIND → TO_BIND绑错了，需要重新绑到别的品类
标记无需绑定TO_BIND → NO_BIND这个位置不需要采购分类，永久排除

当前 CLI 只有 unbind，没有「标记无需绑定」命令。如果遇到本该排除的编码，暂时只能保留在待绑定列表里。

五、六个必须知道的坑

⚠️
编码不存在时毫无提示 输入一个不存在的编码，list 返回 0 条，bind 的 dry-run 依然会输出正常请求体。不会报「编码不存在」。执行前必须先用 list 确认编码真实存在。
⚠️
一个编码可能对应多条记录 例如 1013-A001 同时对应「旅充线缆」和「无线充电模组（车端）」两条。绑定时这两条一起处理。如果其中一个零件名明显不该归到目标品类，说明数据本身有问题，应先修数据。
⚠️
已绑定的编码不会提示「改绑」 对 BIND 状态的编码执行 bind，不会报错也不会提示，会静默改变归属。执行前查 categoryCode，确认是否有旧归属。
⚠️
品类冻结不会在 CLI 层拦截 目标品类如果已冻结，CLI 不校验，请求会发出去。查 category detail 确认 categoryStatus = EFFECTIVE。
⚠️
没有 Excel 批量导入 文档设计过 --from-file 读 xlsx，正式版没有实现。批量只能靠命令行逗号多值，一次几十条会超出合理长度。超过 20 条建议分批。
⚠️
写操作需要额外权限 查询用普通账号即可，bind / unbind 需要品类管理员或 ADMIN 角色。权限不足时返回 403 insufficient role for B level API，此时命令拼得再对也执行不了。

六、给 Agent 的建议

如果要把这套操作交给 Agent（对话式助手），按下面的场景设计。

6.1 建议 Agent 承担的四个场景

场景用户会说Agent 该做的
编码核对 「帮我看看这几个编码在不在」 批量跑 vpps list，输出「存在 / 不存在」清单，标出当前归属品类
绑定前体检 「把 A 绑到 B」 先查 A 的 bindStatus 和 categoryCode，再查 B 的 categoryStatus 和现有成员，最后判断是首次绑还是改绑
人员核对 「这个品类的采购是谁」 用 category detail 或 vpps list 返回的 buyerName 直接回答
批量盘点 「哪些编码还没绑」 vpps list --status 待绑定 分页取回，按结构码分组呈现

6.2 Agent 不该做的事

不要让 Agent 直接执行写操作

理由有三：
1. 编码不存在时 CLI 不报错，Agent 可能「以为成功」；
2. 改绑会静默改变归属，Agent 无法判断用户是否知道这一点；
3. 解绑不传编码会全量清空，一次误判就是整品类丢失关联。

正确做法：Agent 负责核查与生成命令，把可执行的命令连同核查结论一起交给用户，由用户确认后自己跑。

6.3 推荐的三段式交互

1

先答复核结果，不急着执行

用户说「把 1015-B009 绑到 CAT-00009」，Agent 的第一次回复应该是核查表：

1015-B009  高压线束分线器-二分四
  当前归属：CAT-00284 高压连接器（已绑定）
  执行影响：改绑，会从「高压连接器」移出
目标品类：CAT-00009 底护板（生效，现有 5 个成员）
语义提示：高压线束零件绑到底护板，分类可能不匹配
2

给出命令，明确标注风险

把 dry-run 命令放在前面，正式命令放在后面，并标出「这条会改变归属」。

3

执行后必须回查

用户执行后让 Agent 回查一次，确认 bindStatus、categoryCode、buyerName 三项都符合预期。这一步能兜住「编码不存在却以为成功」的问题。

6.4 值得沉淀成 Agent 规则的四条

规则内容
先查后写任何 bind/unbind 之前，必须先跑 vpps list 和 category detail，把核查结果摆出来
标注改绑查到 bindStatus = BIND 且 categoryCode 不是目标品类时，明确提示这是改绑
拒绝全量解绑用户说「解绑这个品类」但没指定编码时，要求二次确认，并说明会清空全部关联
不猜编码编码查不到时，直接报「不存在」，并列出同前缀的现有编码供用户比对，不要自行替换

6.5 一个具体的对话示例

用户：把 1015-B009 绑到 CAT-00009

Agent：核查结果如下——
· 1015-B009「高压线束分线器-二分四」当前已绑在 CAT-00284「高压连接器」
· CAT-00009 是「底护板」，现有 5 个成员都是 1031 开头的护板零件
· 这会把高压线束零件从「高压连接器」移到「底护板」

品类语义看起来不匹配，确认是 CAT-00009 吗？
另外还需要补充采购工程师姓名（必填）。
