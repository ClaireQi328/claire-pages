做一个「能替人办事」的 Agent

从样件订单助手提炼的设计方法 · 2026-11-13 · 每条都有实际出处

这不是功能清单，是做决策时的判断依据。写的时候我一直在问一个问题：如果换一个业务场景，这些原则还成立吗？只写成立的。

零、先回答一个问题：它到底该做什么

这个 Agent 是在「替代人的判断」，还是在「替代人的操作」？

这两者的设计完全不同。样件订单这个场景的答案是：替代操作，不替代判断。理由很实际——下单涉及钱、涉及供应商、涉及审批流，判断错了追不回来。

维度替代判断（不该做）替代操作（该做）
供应商选择系统根据价格/账期自动挑列出候选，人必须选一个
剔除范围系统猜"这些应该不用下"读人维护的剔除表，严格执行
预算不足自动跳过或拆分停下来，把 BR 号/差额/找谁 说清楚
数据汇总自动算清、自动分组、自动拆单—
为什么：「替代操作」出错是效率问题，「替代判断」出错是责任问题。前者可以道歉重做，后者没人敢签字。所以边界要划在「人必须做决定的地方」，其他地方越自动越好。

一、四层结构：每一层只干一件事

① 入口层 飞书机器人 / HTTP / A2A / CLI —— 只做协议转换，不含业务 ↓ ② 编排层 意图路由 → 动作分发 —— 只决定"做哪件事、能不能做" ↓ ③ 业务层 查询 / 下单 / 日报 —— 只含本领域的规则 ↓ ④ 共享层 表格读写 / 渲染 / 凭证 —— 无业务语义的纯工具 ↓ 外部 EP 系统 / 飞书

判断标准：这一层能不能独立测试？

如果一层的测试必须启动整个系统，说明分层没做对。样件订单的做法是——共享层纯函数、业务层可单独 CLI 调用、编排层用 mock 替掉业务层。

反例（我们踩过）

同一份「剔除表读取」在查询 skill 和工具层各写了一遍，签名还不一样。结果缓存指纹按 A 的签名调 B 的实现，每次 TypeError 被 except 吞掉——缓存从上线起一次都没命中过，每次查询白跑 40 秒，没人发现。

规则：跨层共享的逻辑只能有一个物理位置。

二、七条设计原则

原则 1 · 先定「不做什么」，再定「做什么」

Agent 最容易犯的错是「什么都想接」。用户问「这个单为什么没下成」，Agent 就开始猜原因；用户说「帮我选个供应商」，Agent 就挑一个最便宜的。

做法：把「不确定就停下、把选择权交回给人」写成硬规则。

  • 供应商多选 → 必须人点，系统只给候选
  • 需求不在可下单池 → 列出可能原因，让人去 EP 核对，不猜
  • 预算不够 → 停下报数，不自动拆分

实际实现：read_multi_selected 只返回「用户已选」的行；没选就是 0 条，绝不兜底挑一个。

原则 2 · 每个「写操作」都必须有人点的那一下

「自动下单」听起来很美，但它意味着 Agent 可以在人不知情时花钱。样件订单里所有下单都要用户点卡片按钮，且按钮上有明确的数量。

保护机制
谁点的卡片记 operator，别人点会被拒："这张确认卡不是你生成的"
点几次会话级互斥锁，执行中再点回"正在下单中"
点什么pending 落会话，按钮只执行对应那段，不会"点 A 执行 B"
执行完立即清 pending，防重复下单
原则 3 · 时间窗口要显式，不要让数据自己「过期」

「可下单」是一个有时效的判断。今天能下不代表明天能下——需求会被别人下掉、会升版、会超窗口。

做法：把「这一批」当成一个明确的实体，有批次号，从查询一路传到下单。

  • 查询产出批次号 → 卡片显示 → 下单时校验批次一致
  • 跨批次执行会被拒（"确认页是旧批次的快照"）
  • 待选表按批次清理，不跨批累积

我们踩的坑

一开始卡片是「读磁盘上最新的文件」，靠 mtime 猜。异步推送和同步查询撞在一起时就会读到上一批——用户看到「本批没有需求」+ 下面列了 12 行物料，自相矛盾。

规则：能透传就别推断。「刚刚这次操作产出的东西」，产出时记下标识，一路传下去。

原则 4 · 失败必须能被区分，不能返回"合法的空值"

这是最隐蔽的一类 bug。看这段真实的代码演进：

错误做法：读剔除表失败 → 返回空集合 ↓ 调用方看到空集合 → 以为"用户没配剔除" → 继续查 ↓ 该剔的全进了可下单池 → 208 条被误下单 正确做法：读失败 → 返回 None（或抛异常） ↓ 调用方知道"没读到" → 不走缓存、让用户重试 ↓ 宁可查询失败，不给错结果

规则：一个函数返回「空」时，必须让调用方能分清三种情况——

  • 查了，确实是空（合法）
  • 没查到（失败）
  • 不知道该不该查（参数缺失）

用一个值表达三种含义，一定会出错。

原则 5 · 保护性代码要按正常路径的标准测试

为「防止出错」写的代码，如果不常跑，就最容易带 bug。样件订单里三个 P0 都出在这种地方：

兜底逻辑it 自己出的问题
剔除表读不到时强制重查用了没 import 的 sys → 一触发就报错
防重复下单的「终态冻结」把「EP 重新判定可下单」的需求也冻住了
防误删的清理逻辑遇到空清单时把整张表清空

规则：凡是「只在异常时才跑」的分支，必须有专门的用例触发它。写的时候问一句——这段代码上次被执行是什么时候？如果答不上来，就是没测过。

原则 6 · 给用户的数字，只能有一个口径

用户拿去和别的系统对数时，口径不一致比数字错了更麻烦——因为他不确定该信谁。

场景曾经的表述现在
下单结果已下单 110 条已下单 44 张订单（覆盖 110 条需求）
多点待选要选 35 条 / 表格 32 行35 个需求号（展开 42 行物料）
预算不足1 张单预算不足订单 4900048245｜BR 剩余 ¥3100｜本单 ¥6480｜差 ¥3379.98
怎么判断口径够不够：用户能不能拿这个数去 EP 里搜到对应的东西？搜不到，就是口径不够。
原则 7 · 慢操作要秒回执 + 后台推送

真实查询要 30~60 秒，飞书回调 3 秒就超时。如果同步跑，用户看到的是「点了没反应」。

用户点击 → 立刻回执「已收到，正在处理…」（< 1 秒） → 后台线程执行 → 结果主动推送到会话 → 任何异常都要推送出来，绝不让用户"点了没下文"

实现：run_slow_async()，带 inflight 去重（同一 action 不并发跑两遍）。

三、必须承认做不到的事

这一段最容易写得漂亮但空洞。我说点具体的。

例：预算并发占用，Agent 无法判断

EP 的预校验各自都看到余额充足，但真正占用时互相争抢——失败的那部分不抛错、不回滚，只静默记账（SaPoServiceImpl.doSynOccupyToEmsForAdd 里 overBudget=true 时只调 doCountBalance）。建单响应里的 isOccupy 又是提交前的快照（实测 41/41 全 false）。

能做的：同 BR 强制串行 + 加间隔，把并发窗口收窄；结果卡标「预算占用待确认」并交出 BR 号，让人去核。

不能做的：准确判断"到底占上没有"。

写文档时我把这段写清楚了，而不是包装成"已解决"。

四、怎么证明它是对的

测试分两层，缺一不可

层管什么样件订单的做法
单测逻辑正确性672 条，mock 掉网络和 CLI
E2E「用户真的能点」真实启服务，发真实指令，检查回复和按钮

只跑单测会发生什么

612 条单测全绿，但跑真实 E2E 第一条指令就崩——name 'sys' is not defined。原因是那个分支只在「剔除表读失败」时触发，所有单测都在正常路径上。

规则：全绿之后必须再跑一遍 E2E，否则等于没验收。

修完要反向验证

改完 bug，把修复临时回退，确认测试真的会变红，再恢复。

为什么：如果回退后测试还是绿的，说明它根本没测到这段代码——这次修复等于没有保护。样件订单用这个办法发现过两次「测试假绿」（一次是 mock 打空，一次是断言写错位置）。

测试本身也会有 bug

遇到过三种「假绿」：

现象真相
测试通过，但跑 38 秒importlib 加载的模块没注册到 sys.modules → mock.patch 打空 → 真的在调 CLI
单独跑过，全量跑挂请求级状态（contextvar）跨测试残留
断言"通过"但没测到匹配到了另一处相同文案

五、如果重新做一遍，我会怎么做

#做法理由
1第一天就建「口径字典」「单 / 条 / 组 / 行」这些词一开始就定义清楚，后面所有文案引用它。我们花了三轮才统一。
2先写 E2E，再写单测E2E 逼你想清楚「用户从哪进来、看到什么」，单测容易陷入函数细节。
3任何删除/覆写操作先 dry-run删 209 行前先落备份、先看清单——这个习惯救过一次（发现要删 64 行而不是预期的 7 行）。
4跨语言/跨模块的字段名，用一处常量Python 传 进度节点、JS 读 u.status，静默错了两周。
5把「不知道」写进文案「预算占用待确认」比「已下单」诚实，也更实用。

一句话收尾

好的业务 Agent，不是"什么都能做"，而是"知道自己不该做什么，并且让人随时能接手"。

具体到三条：

  • 不该替人做的判断，坚决不做（供应商、剔除、预算）
  • 该做好的操作，做到人不用想（分组、拆单、对数、报错）
  • 做不到的事，明确说清、给出核对路径（并发占用、草稿查询）
