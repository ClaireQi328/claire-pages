EP 采购 AI · 分层架构与场景一条故事线：问题 → 方案 → 去向

一句话主线→ 我们要的不只是一个机器人，而是让 AI 能干活、但权力收得回来的一套分层架构： 入口（你在哪说话）→协议（怎么把话说进来）→ 服务层（实际干活的一层）→通道（连 EP 系统）。
四阶段本质看两条线：交互怎么变（命令 → 对话 → 卡片 → 回系统）· 权限怎么收（凭证随意 → AI 拿通道 → 白名单+闸 → 系统接管）

WHY

为什么要分层——问题驱动

AI 采购不是「做个机器人」。踩过的坑告诉我们：入口会换，能力不该重写；权限不能散；敏感数据不能跟着对话跑出去；每一次下单都要能追到人。分层就是把这几件事各归各位。
A究竟基于什么做建设？六条原则架构理论的根：不是「做个机器人」，是「能力分层、权限单点、敏感锁死」
能力唯一实现single-source
业务逻辑只写一次放服务层。所有入口、协议、客户端都调同一份代码——「入口可以换，服务层不动」。
权限一道闸single-gate
所有动作过同一个 gate(user_name, action)：白名单 + cron，加新入口零成本复用。
分层只向下依赖layered
入口 → 协议 → 服务 → 通道。上层只依赖下层，入口换掉服务层一行不改。
确定性收进代码deterministic
路由表、过滤、分组、口径全写死成代码，LLM 只做「听懂人话」兜底，绝不编造能力。
敏感数据不越层data-boundary
价格等敏感值只进 EP 系统，对话/CLI 只回结论和口径，脱敏在回传前。
全程留痕audit
谁/何时/指令/argv 单管道；CLI 原始日志与服务层审计双向对账。
BAPI / CLI / MCP 怎么触达？三种方式收敛进同一个服务层——多一种通道只是多一种「发现能力的方式」
API · 已知的固定调用方
谁用：飞书桥 / cron 定时 / EP 窗口
怎么触达：HTTP 调 FastAPI：/handle 收消息、/callback 收卡片、/push 推送
鉴权：BRAIN_TOKEN 服务间暗号
已上线 · 主通道
CLI · 人 + 自动化脚本
谁用：采购/管理员补数、脚本批处理、skill 内部
怎么触达：dx-ep 命令：query-ready 查、create-order 下单、submit-list 统计
鉴权：credentials.json 凭证 + 网关登录态（只验你是谁）
已锁定 · channel=cli 不降级
MCP · 未知的 AI 客户端
谁用：未来第三客户端，无需硬编码即可发现能力
怎么触达：把 L3 包成 MCP Server：暴露 tools + input schema
鉴权：只许包服务层 → 过同一个 gate；按工具分级授权
规划中 · 有异构客户端再上
C权限在 CLI / 网关 / GarageHub 如何控制？三层各管一段，「该不该做」永远回到服务层 gate
CLI 层 · 凭证（你是谁）
credentials.json + 网关登录态：本地凭证，登录一次所有命令可调
能力：只能防「假身份」——防不住真人越权、复制凭证
防假冒 · 不防越权
网关层 · 路由鉴权（能不能到）
n-cli-gateway：所有请求先过网关：验凭证 + 路由到 EP 服务
能力：管「这个凭证能不能通过」——不管「该不该做这个动作」
验身份 · 不判动作
GarageHub 层 · 能力分发（能装什么）
ai-hub-marketplace：skill 市场 MCP：发现、搜索、安装 skill
能力：管「谁能发现和安装哪些能力」——管分发，不管执行
管分发 · 不管执行
结论：CLI 管「你是谁」、网关管「你能不能到」、GarageHub 管「你能装什么」，「该不该做这个动作」只能由服务层 gate 判。权限必须组合：L4 凭证 + 网关路由 + L3 gate + 治理（轮换、绑定机器、双向对账）。任何单层放开，都会重演 R1-R6：凭证即权力、可复制、无操作级授权、敏感带出、不可追溯。

④

权限怎么做——组合控制

三个抓手：核心三问 C 讲了「谁来控」；这里讲「风险是什么、每一道怎么布」
R1
凭证即权力
只验「你是谁」，不验「该不该做」——登录一次所有命令可调
后果：越权调用
R2
凭证可复制
credentials.json 可拷贝共享——装即得权
后果：权力扩散
R3
无操作级授权
无二次确认，价格查询、下单直接执行
后果：误操作/越权写
R4
敏感数据带出
价格进终端 stdout，可复制截图脚本抓取
后果：敏感泄漏
R5
无审计上下文
只留服务端原始日志，无业务上下文
后果：不可追溯
R6
权限粒度不足
只有「能不能用」，没有「能用哪个字段」
后果：脱敏失效
结论：通道层权限只能防「假身份」，防不住「真身份的越权、泄漏、误操作」。权限必须组合：身份靠 L4 凭证，授权靠 L3 gate，治理靠凭证轮换。
身份真实性L4 通道层凭证鉴权（你是谁）——保留，但仅此而已
操作授权L3 服务层gate(user_name, action)——通道层永远替代不了
敏感命令收口L3 服务层价格查询从 CLI 移除或改「只读+脱敏」
数据脱敏L3 服务层回传前处理：只给结论与口径
审计闭环L4 + L3CLI 原始日志 + 服务层业务审计，双向对账
凭证治理治理层定期轮换、绑定机器、服务账号隔离
WHERE

往哪去——路线与终局

④

权限控制：五层各管一段，权威层唯一

层层不信任上一层
不是「Agent 管」或「CLI 管」二选一——garagehub 管身份凭证，Coordinator/Agent 管动作，CLI 只是执行通道不控权，MCP 管文档读取范围，EP 后端管数据行级过滤。任何一层单独拿出来都不足以控权。
A六层总览从「谁在调接口」到「系统最终给多少」，每层只回答一个问题
层组件回答什么为什么必须是这一层
L0通道层
BRAIN_TOKEN		谁在调接口（桥 ↔ 大脑服务间认证）防内网任何人直连 7777 端口。不承载任何用户权限
L1身份层
飞书 open_id / A2A X-User-Id		你是谁（平台身份 → 域账号）入口不可信（网关配置错误、header 伪造）。只解析不授权，解析失败一律拒绝
L2意图层
Coordinator 路由		你能做什么（意图 → Agent → 最小角色）动作权限的权威层。用户不直接调 Agent，用户调「意图」
L3工具层
MCP / KB / CLI 分发		工具本身允许谁碰兜底，不是重复。防未来新入口或新路由绕过 L2
L4凭证层
garagehub + profile		以谁的身份执行（凭证登录人 == 触发人）只颁发/刷新凭证，证明「这个 token 是谁的」
L5数据层
EP 后端 / WeKnora 分库		系统最终给多少（token 行级过滤 / KB 物理分库）最终裁判。EP 后端看到的是每个用户自己的 token
BL2 是权威层：意图 → Agent → 最小角色「谁能用哪个 Agent」= 这一张表
意图Agent最小角色额外约束
查询 / 预演 / 日报sample-orderbuyer—
下单sample-orderORDER_ALLOWED 名单独立白名单，比 buyer 严
知识问答 / 文档 / 帮助knowledgebuyer只读公共 KB
报错诊断 / 库表 / SQLdiagnosisdev内部 KB
为什么 L3 还要再判一次：internal KB 的 dev+ 检查既在 L2（路由时）也在 L3（工具内）——两层同判，防未来新入口或新路由绕过 L2。L3 的原则是：不重复「谁能用」的全量逻辑，只保留关键约束的兜底。
C下单的四道闸一个完整示例：从点按钮到 EP 落单，中间过了什么
1 · 身份闸
点「确认下单」→ 校验登录人 == 卡片所属人
别人点了直接拒（防冒名）
2 · 在途闸
同 chat + action 在途时不启第二个线程
防重复点击出两单
3 · 动作闸
gate(user_name, "order") → ORDER_ALLOWED 名单
服务层单点，通道层替代不了
4 · 幂等闸
飞书重投回调 → 60 秒窗口内只执行一次
防飞书重投造成重复下单
四道闸缺一不可：身份闸管「是不是本人」，在途闸管「是不是重复操作」，动作闸管「有没有权限」，幂等闸管「是不是重复消息」。每一道对应一类真实事故，不是设计冗余。
D通道层权限的六个风险（R1–R6）通道层权限只能防「假身份」，防不住「真身份的越权、泄漏、误操作」
编号风险说明后果
R1凭证即权力只验「你是谁」，不验「该不该做」——登录一次所有命令可调越权调用
R2凭证可复制credentials.json 可拷贝共享——装即得权权力扩散
R3无操作级授权无二次确认，价格查询、下单直接执行误操作 / 越权写
R4敏感数据带出价格进终端 stdout，可复制截图脚本抓取敏感泄漏
R5无审计上下文只留服务端原始日志，无业务上下文不可追溯
R6权限粒度不足只有「能不能用」，没有「能用哪个字段」脱敏失效
结论：权限必须组合——身份靠 L4 凭证，授权靠 L3 gate，治理靠凭证轮换。三道缺一不可。

F三个常见疑问开会时最常被问到的
「garagehub 不是能管权限吗？」
garagehub 只干一件事：颁发/刷新凭证，证明「这个 token 是谁的」。它不关心「这个人能不能查这个需求」。真正的身份一致性在 identity_guard。
「CLI 权限校验不够吗？」
CLI 只能防「假身份」。防不住真人越权（有凭证就能调所有命令）、防不住复制凭证、防不住敏感数据带出。见上方 R1–R6。
「为什么不做在入口层？」
入口不可信——网关配置错误、header 伪造都可能带来假身份。所以 L1 只做「解析」，权限结论永远不在入口层下。

BCLI 与 Skill 的边界最容易混淆：既然有 CLI，为什么还要 Skill？两者不是替代关系，是两种不同的东西
CLI（通道）

输入：命令行参数
输出：stdout / 退出码

踩坑实录：把 CLI 参数当成 Agent 的输入
最初 Agent 直接拼 dx-ep 的命令行参数。结果：参数名一改，Agent 静默拼错，EP 返回 0 条，被当成「没有需求」； --br-line ↔ brLineNumber 这类命名差异，两边各自维护。
现在：demand-order 的 --dry-run 输出三份对照——intent（通道无关意图）· cli_argv · api_body，并给出 equivalent 判断两者是否语义等价。
Skill职责契约规模关键约束
demand-query只读查询 / 过滤 / 分组418 行 SKILL.md不写任何东西，5 分钟内同参复用
demand-order下单（写，不可逆）488 行 SKILL.md必须真人触发且身份=触发人

#根因类型典型表现本质
1用结果推断原因EP 失败也返回「0 条」，被当成「没有需求」只判断数量，没判断错误类型
2共享可变状态未隔离两个任务共用凭证文件，一个刷新把另一个顶成 401把「凭证」当成无状态只读资源
3把多态压成单态EP 订单有建单/提交/审批多维状态，代码压成一个布尔用简单模型描述复杂现实
4口径未定义就开用「说要选 35 条，表格只有 32 条」需求号 / 物料行 / 入表行三个数混用
5没有幂等的副作用飞书重投回调，一次点击出两张结果卡把「收到回调」等同于「用户点了一次」
6同步模型套异步场景飞书回调要求 3 秒，业务要 30~60 秒把长任务塞进短响应里
7别名解析优先级反了金额写进自动建的同名列，用户看的真实主列恒为空。905 项测试全绿，因为只断言「写了某列」，没断言「写进了对的列」验证断言停在「有副作用」，没到「副作用正确」
8跨链路取数查一品一点时读了多点待选表，卡片里冒出「待选供应商」分链后仍有路径没隔离
这 8 类的共同点：都是在「用简单模型描述复杂现实」——把会变的东西当不变、把未知当已知、把长任务当短任务。特征是：平时不出错，一旦并发/异常/超时就集中爆发。

服务内部S1 路由 → S3 闸 → S2 执行；S3 是根基；gate 单点；脱敏在回传前
服务 → 通道channel=cli 锁定；exit 3 环境异常 ≠ 0 暂无数据；fetch_error 非空必须说明
不越层入口不直连 CLI；服务层不直连用户；敏感值不跨层外流
💭 十个开放问题（开会用）
#问题为什么要想
1AI 的边界画在哪——系统角色还是数据脱敏？角色管能不能做，脱敏管能看到多少——先落地哪个？
2价格敏感锁到什么粒度？只锁对话？还是 CLI 也收口？
3系统内嵌后飞书机器人还要吗？高频入口 vs 执行入口——并存还是收一个？
4「AI 无写权限」是真无还是「必须系统确认」？决定终局：AI 只出建议单 vs AI 代执行
5MCP 开放后工具授权分多细？按工具 / 角色 / 数据域？越细越贵
6确定性逻辑都进代码后 AI 还剩什么价值？AI 只做「听懂人话」，和规则引擎的边界在哪？
7审计要记多细？现在记谁/何时/指令；以后要记 AI 每一步推理吗？
8单机版怎么升级？会话记忆在本地——先共享存储还是直接系统内嵌？
9AI 的操作单元是什么？EP 最小操作单元不变；AI 按组/按单/按需求提？
10「崩回系统」谁牵头？EP 侧改系统，还是我们这侧改接入？
一句话总结：AI 采购不是「做个机器人」，而是「能力分层、权限一道闸、敏感锁死」的系统工程。入口可以换，服务层不动；场景可以加，架构不变。
