Agent 的难点不在模型，而在口径、权限、外部系统、失败兜底。这四件事没做好，模型再强也会在生产里翻车。

一句话结论

模型决定上限，工程决定下限。把权限、口径、幂等、失败兜底、人工闸门做好，Agent 才是可用的系统；否则只是一个会说话的 Demo。

CORE五条铁律

如果只能记住五件事，记这五件。

01先定口径订单、需求、件、组先定义，再写代码。
02权限前置别等点确认才发现账号没权限。
03映射不猜人员/供应商映射歧义时宁可不填。
04写表幂等重跑不重复建行，不覆盖用户选择。
05人工闸门高风险动作必须有人确认 + 留审计。

01先定口径，再写代码

同一个数出现三种说法，比没有数更危险。

01订单、需求、件、组，先定义再开发

口径是所有页面、卡片、报表的共同语言。

坑：同一个批次，卡片写「58 组」，页面写「531 张订单」，用户不知道哪个是订单。
做法：所有出口统一「订单=张、需求=条、升版=条」；卡片、页面、工作台、仪表盘逐一对账。
本项目：最终统一为：一品一点报「73 张订单（试制 55 / 散件 18）」，一品多点报「179 条需求」。

02同一事实多视角，必须做一致性检查

接口返回正确，不等于用户看到的正确。

坑：查询卡写「升版 82 条」，核对页写「31 张」；两个数都“对”，但用户以为系统在乱报。
做法：把「卡片 / 页面 / 工作台 / 仪表盘 / 结果」列成视角矩阵，每个数字问三遍：单位是什么、和谁对齐、与哪个批次对齐。
本项目：升版统一为「82 条（涉及 32 张订单）」；核对页指标从「需求组数/数量总量」改为「订单/需求/升版」。

03会议和需求里最贵的是细节

“大概按这个改”通常意味着后面还要返工。

坑：会上说「失败要一条一条列」「换行」「预算不足给我订单号/BR/剩余」，如果只记“优化失败展示”，最后一定漏字段。
做法：会后把需求拆成可验收的 checklist：字段、单位、顺序、换行、按钮文案、不要做什么；逐条回读确认。
本项目：预算不足最终逐需求输出「订单号 / BR号:行 / 剩余 / 需求号 / 零件号 / 需求人 / 总价 / 差额」，就是逐条回读出来的。

02权限和身份要前置，不要等最后一步

权限问题发现得越晚，代价越大。

04执行前预检角色，不要等 EP 报 403

“能不能点”与“能不能成”是两件事。

坑：用户点完确认、等了 1.4 秒，才收到英文报错 Forbidden: insufficient role for B level API。
做法：下单前读 EP 令牌 ep-route；viewer:A 直接中文提示，不调用 EP、不产生半成品订单。
本项目：qiyue 是 viewer:A，fanxueting 是 editor:A,B；预检上线后，qiyue 直接收到「无下单权限，订单未创建」。

05权限错误要翻译成用户动作

用户不需要知道 HTTP 403，只需要知道下一步找谁。

做法：错误文案四件套：是什么错 + 影响什么 + 下一步做什么 + 不要做什么。
本项目：「当前账号权限不足：创建订单需要 B 级编辑权限（editor:A,B），当前令牌角色为 viewer:A；本次订单未创建。请换有权限账号，或找 EP/GarageHub 管理员开通后重新登录。」

03外部系统的数据映射不能想当然

人员、组织、供应商，是最容易“看起来有值、其实是空”的地方。

06人员映射：同名、外包、别名，一个都不能猜

飞书搜索不是精确查询，EP 登录名也不一定等于飞书登录名。

坑：王龙生同时命中 wanglongsheng 和外包账号 v-wanglongsheng，旧逻辑要求唯一命中，结果 61 行采购员为空；另有 1 行 EP 别名 yixing 搜不到，真实登录是 chengang26。
做法：优先按唯一 user_id/精确登录名匹配；排除 v- 外包账号；歧义时用中文姓名精确唯一兜底；仍然不确定就留空并告警，绝不猜人。
本项目：修复后 179/179 条需求采购员全部有值；空值从 62 行降到 0 行。

07字段映射失败要“显性失败”，不要静默留空

空字段比错误字段更难发现。

做法：同步结束输出「解析成功/失败数量」；失败名单落日志；页面上给出「未解析」标记或文本兜底。

04写外部系统要幂等、可重跑、保护用户数据

一次重跑就把用户选择清空，是 Agent 最致命的体验事故之一。

08字段 PUT 可能是整体替换，不是增量修改

API 文档里一个“更新”，可能把你没传的选项全删掉。

坑：改多维表格单选字段时只传了新选项，历史选项被整体覆盖，历史行值被清空。
做法：改字段前先 GET 全量选项，合并后再 PUT；改类型前备份数据；改完回灌并核对。

09同步必须幂等，且区分“系统写的”和“用户写的”

系统只能写候选，不能覆盖用户的选择。

做法：按唯一业务键去重；重复跑只更新不新建；用户选择字段同步时永不覆盖；大表用 batch_update，不逐行 PUT。
本项目：「候选供应商」由系统同步，「选择供应商」只由人选；机器人执行时只读选择，并由后端校验必须在候选范围。

05危险动作必须有闸门

只要按钮能造成真实后果，它就不是普通按钮。

10全量确认按钮，本身就是风险入口

坑：测试时为了看效果点「确认执行 · N 张订单」，可能真的下一批单。
做法：测试用 1 条需求/工作台选 1 行；生产按钮明确写「全量」；只下部分走「下单 <需求号>」；确认后置灰 + 幂等锁。

11规则不能只在入口检查一次

预演到确认之间，世界会变。

坑：剔除表只在查询/预演时过滤；用户预演后新增剔除，确认时仍可能把已剔除需求下掉。
做法：执行前再读一次剔除表/权限/批次；任何一条不一致就中止并提示重新查询。
本项目遗留：剔除表执行前复查尚未补，已列入 P1。

06异步链路必须三段式：回执、结果、失败兜底

用户点完确认后没有反馈，就会重复点；后台失败没有兜底，就会变成“黑盒”。

12回执要快，结果要主动推

做法：① 立即回执「已收到确认，正在下单中」；② 后台执行完成主动推结果卡片；③ 失败也要推，不能只写日志。
坑：订单创建完成但没推飞书卡片，用户以为没执行，反复操作。

13结果要区分成功、草稿、创建失败

做法：成功=已提交审批；草稿=创建成功但自动提交失败；失败=订单根本没建出来。三种处理方式完全不同，绝不能混成「failed」。
本项目：卡片标题按结果变色；全部失败改「❌ 下单失败」；草稿提示去 EP「我的草稿」，不要整批重下。

07错误信息要能指导下一步

好的错误提示，是产品能力的一部分。

14报错四件套：是什么 + 影响 + 下一步 + 不要做什么

示例：「当前账号无下单权限（viewer:A）→ 订单未创建 → 换有 B 级权限账号或找管理员开通 → 不要重复点击」。
本项目：预算不足逐需求输出订单号、BR号:行、BR剩余、需求号、零件号、需求人、订单总价、差额，用户可以直接对单处理。

08Agent 设计：能确定性就不要交给模型自由发挥

LLM 适合理解与表达，不适合绕过规则执行。

15高风险动作走确定性链路

做法：意图识别可以用 LLM；下单、权限、金额、审批必须走规则 + CLI/API + 人工确认。所有动作留审计：谁、何时、什么批次、做了什么、结果如何。
本项目：路由确定、工具确定、执行 CLI 确定；LLM 只负责理解和解释，不直接下单。

16人工确认是产品能力，不是流程累赘

做法：高风险 Agent 至少保留一次人工闸门；确认前展示「范围 + 数量 + 供应商/需求明细」；确认后原卡置灰，避免重复。

09UI 和字段设计要服务流程，不是服务“看起来规范”

最规范的数据模型，不一定是最好用的操作界面。

17原子候选行看起来精确，实际把用户逼疯

坑：「1 需求 × 1 候选 = 1 行」让同一需求出现多行，用户不知道勾哪行，还要自己判断供应商范围。
做法：改回「一需求一行 + 候选多选 + 选择单选」；范围由后端校验，界面保持简单。
本项目：最终定为「一品多点待选」一需求一行，候选人选、选择单选、历史参考。

18有限项用下拉、人员用人员字段，但后端仍要校验

做法：状态/类型/项目用单选，人员用 User；下拉是全局的，不代表范围正确——后端必须校验「选择必须在候选范围」。

19API 做不了的，要明确写成「手工配置」

做法：飞书视图分组、隐藏列、Base 仪表盘组件这类 UI 配置，API 往往做不了；写成一次性手工清单，不要假装自动完成。

10测试数量不等于质量

363 项测试全绿，仍然漏掉了「卡片 82 条 vs 核对页 31 张」。

20要专门测「用户看到的界面」

做法：除接口测试外，增加：跨视角数字/单位一致性、人员解析、失败明细字段、全失败卡片、旧链接、空值/重复数据。
本项目：补了核对页口径测试、预算不足六字段测试；JS 工作台动作仍缺自动化，是后续风险。

21真实数据永远比测试夹具脏

做法：用真实批次做抽样：重复 PR、数组长度不一致、别名账号、空采购员、历史草稿；每个异常都要有降级展示。

11旧链接、旧文档、旧配置是「活代码」

用户不会区分“代码”和“欢迎语里的链接”。

22改表后要全量搜旧 table_id / 旧链接 / 旧文案

坑：新工作台上线后，欢迎语仍指向已归档的旧表，用户点进去看到旧数据。
做法：改表、改视图、改字段后，全仓搜旧 ID/旧 URL/旧字段名；欢迎语、帮助、文档、卡片链接都算产品面。

23文档要跟着功能一起发版

做法：操作指引、验收表、仪表盘同一次更新、同一次上传；版本日期写清楚；文档里保留“什么时候看什么”的入口。
