一这轮到底在修什么

表面看是一堆零散的体验优化，其实是同一条主线： Agent 说出来的话，和它实际做的事，对不上。

用户看到→「成功 3 条需求」 │ 实际发生→3 张订单 / 1 条需求 │ 结论→单位混用，用户无法对账

所以这轮的修复分三层递进：

层问题典型表现
看得见等待期间没有反馈查询 40~140 秒，只有一句静态「收到，正在处理」
信得过说出来的数不对「3 张订单（3 条需求）」实际只有 1 条需求
查得到写进表里的值落错列预算表金额写进自建空列，主列恒为空

二看得见：把等待变成过程

根因不是「做不了」，是三个环节都没接上。

环节修复前修复后
飞书桥发文本拿到了 message_id 但没传给大脑传下去
大脑请求模型HandleReq 没有这个字段加上
/handle全程同步，跑完才返回慢指令转异步 + 话题卡
先验证再动手
飞书话题是否有独立名称字段？我穷举了三种路径： GET /threads（404）、PATCH /threads（404）、 reply 带 thread_title（返回 200 但回读消息顶层 13 个字段里没有）。

结论：没有。所以话题名只能取「话题内首条卡片的标题」—— 这不是取巧，是飞书的产品设计。最终标题定为 查询一品一点｜qiyue｜11-18 18:50。

顺带解决的一个真 bug

卡片上的「🔁 重新查询」按钮写死用「查询可下单需求」调路由。 但底部入口改了之后，这句话会被路由拦成「请先指定链路」—— 按钮点了不查任何东西。

修法：查询成功后记住 last_query_path，重试时回放原链路。

这个 bug 之前的测试没覆盖到，因为测试里 mock 掉了路由。

三信得过：五套口径与七种状态

用户问：「m 个需求 / n 个订单 / x 个失败原因，这个逻辑映射清楚了吗？」 —— 之前没有。现在定义了。

口径定义单位何时用
需求数 mdistinct 需求号条用户按单号数
组数grouping 长度组内部概念，不外露
零件行数各组 records 之和行只解释拆行时
订单数 nsummary.order_count张下单后真实张数
失败原因 x按 reason 归类后类数类「失败 3 张，分 2 类」
踩过的坑：success + draft + failed ≠ order_count
实测批次 ORD20261118134311：
order_count = 16　|　 success 7 + draft 4 + failed 2 = 13 ← 差 3 张

差的 3 张是 blocked_abnormal（数量≤0 / 金额为负）。 EP 那边中止后会留下无法删除的订单，所以不下单。

只看前三项，必然对不上账——这就是「数字不对」的根源之一。

细节：为什么会有 7 种状态

status含义计入

四查得到：写进表里的值落错了列

这是本轮最隐蔽的一个 bug——测试全绿，但生产数据是错的。

字段修复前修复后
订单金额（未税，向上模糊取整）null ← 用户看的那列26285.31
订单金额（未税）26285.31（自建列）26285.31
差额5901.985901.98
两层原因叠加
  • 字段规格同时声明了「未税」和「向上取整」两列，自动建列后它们成了真实列
  • 别名解析是「精确命中优先」，自建列挡住了真正的主列
第一版修复我改粗了：全局改成「别名优先」， 结果「差额」被误解析成公式列「不足差额」，5 个测试报错。 最终方案：只对金额列别名优先。

验证方式：真实写入生产表 → 回读核对 → 立即删除。 确认表回到 15 行、无残留、历史数据完好。

顺带发现：机器人应用没有多维表格读取权限（99991672）， 同步器用的是 auth.json 里的用户身份。我第一次验证时用错了身份，结论不可信，重做了。

六过程本身的教训

这轮最有价值的不是修好了什么，是发现了自己验证方式的漏洞。

问题证据改正
历史回归脚本有 3 条是源码字符串匹配 "_PHENOMENON" in src 这类断言，代码写反了也能过 重写为行为级，15 条全部跑真实函数
测试全绿但生产数据是错的 金额落错列，905 项测试一条都没拦住 改为真实写入 → 回读核对
用错身份验证 机器人 token 读不了多维表格，返回空让我误判 改用同步器自己的用户身份
断言写错还怪代码 row_key 的候选和值搞混，误报「非候选被选中」 修正断言，确认函数本身是对的
「测试通过」和「功能正确」是两件事。
前者只证明你想到的场景没坏，后者需要拿真实数据走一遍。
