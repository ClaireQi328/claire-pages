CLI 时代有凭证就能干一切；卡片时代要按钮确认；内嵌时代 AI 连通道都不碰。

二CLI 与 Skill 的边界：一条实测出来的线

最容易混淆的是：既然有 CLI，为什么还要 Skill？两者不是替代关系，是两种不同的东西。

CLI（通道）
一次进程调用。
输入：命令行参数
输出：stdout / 退出码

回答「怎么连到 EP」
Skill（契约）
一段有语义的能力。
输入：结构化意图
输出：结构化结果 + 人读文案

回答「这件事怎么算做完」
Agent（编排）
决定「现在该做哪件」。
输入：人话
输出：动作 + 卡片 + 留痕

回答「用户到底要什么」
踩坑实录：把 CLI 参数当成 Agent 的输入
最初 Agent 直接拼 dx-ep 的命令行参数。结果是——
· 参数名一改，Agent 静默拼错，EP 返回 0 条，被当成「没有需求」
· --br-line ↔ brLineNumber 这类命名差异，两边各自维护

现在 demand-order 的 --dry-run 会输出三份对照： intent（通道无关意图）· cli_argv · api_body， 并给出 equivalent 判断两者是否语义等价。

Skill职责契约规模关键约束

「必须真人触发且身份=触发人」这条不是文档口号，是代码里的硬闸门： run_cli 会校验 EP 令牌角色，不是 editor 级直接拒绝，不白跑一次、不产生半成品订单。

三低码的正确用法：不是「少写代码」

很多人把低码理解成「拖拽代替写代码」。在 Agent 场景里，它的真实价值是 把「人做决定」的部分，放到人能看见的地方。

决定事项放哪为什么
选哪家供应商多维表格（人勾选）涉及价格与关系，AI 不该替人判断
要不要下这一批卡片按钮（人点）写操作不可逆，必须有一次明确确认
哪些需求要剔除剔除需求表（人维护）业务判断，AI 只读不猜
预算不足怎么办处置表（人跟）加额度是人的动作，AI 只能把「差多少、找谁」说清
踩坑：把「导出 JSON 再贴回」当成交互
一期确认页让用户导出一份 JSON、改完再贴回来。
开发视角可行，业务视角不可行——飞书里没有这个习惯。

现在：确认页只读展示，选择在多维表格里做。
踩坑：「一格里塞多家供应商」
最初按「需求」组织：一个需求一行，候选供应商放一列。
但供应商是按物料行指定的——一个需求的多行物料可能对应完全不同的供应商组合。

现在：拆原子候选行（一行一候选，勾「选择这家」），行主键 = 需求号|供应商组合。

四高码的方向：AI 不该拿钥匙

这是你之前那份架构文档里最重要的一条判断，我完全认同： 终局不是「AI 什么都能干」，是「AI 只出建议单」。

内嵌时代（目标）只出建议单系统系统自身权限模型

身份闸

在途去重

五架构：为什么必须是分层

不是「分层好看」，是不分层就会重复实现，然后两份实现必然漂移。

真实案例：同一份逻辑写了两遍
「读剔除表」这个逻辑，sample_tools.py 和 demand_query.py 各写了一份， 签名还不一样。

结果：缓存指纹用 A 的签名去调 B 的实现，每次抛 TypeError 被 except 吞掉， 表现为「剔除表偶发不生效」。

这类问题不会报错、不会崩溃，只会悄悄给出错误结果。
层只做一件事判断标准
入口层协议转换（飞书 / HTTP / A2A / CLI）这里不该出现业务判断
编排层决定「做哪件事、能不能做」能否用 mock 替掉业务层单测
业务层本领域规则（查询 / 下单 / 日报）能否脱离 Agent 单独 CLI 调用
共享层无业务语义的工具（表格 / 渲染 / 凭证）是否全为纯函数
我现在的判断标准是：这一层能不能独立测试？
如果一层测试必须启动整个系统，说明分层没做对。

六踩过的坑：按「根因类型」归类

149 个提交里 61 个是修复。把这些修复按根因归类，会发现只有 6 类。

#根因类型典型表现本质
1用结果推断原因 EP 失败也返回「0 条」，被当成「没有需求」 只判断数量，没判断错误类型
2共享可变状态未隔离 两个任务共用凭证文件，一个刷新把另一个顶成 401 把「凭证」当成无状态只读资源
3把多态压成单态 EP 订单有建单/提交/审批多维状态，代码压成一个布尔 用简单模型描述复杂现实
4口径未定义就开用 「说要选 35 条，表格只有 32 条」 需求号 / 物料行 / 入表行三个数混用
5没有幂等的副作用 飞书重投回调，一次点击出两张结果卡 把「收到回调」等同于「用户点了一次」
6同步模型套异步场景 飞书回调要求 3 秒，业务要 30~60 秒 把长任务塞进短响应里
这 6 类的共同点：都是在「用简单模型描述复杂现实」——
把会变的东西当不变、把未知当已知、把长任务当短任务。

特征是：平时不出错，一旦并发/异常/超时就集中爆发。

七验证方式本身的演进

这轮最有价值的不是修好了什么，是发现自己的验证方式有漏洞。

阶段做法漏在哪
1写单测只测想到的场景
2历史 bug 转回归用例有些断言是源码字符串匹配，代码写反了也能过
3真实数据跑一遍「测试通过」≠「功能正确」
4（现在）真实写入 → 回读核对 → 清理需要生产权限，操作要谨慎
三个具体的教训
  • 历史回归脚本有 3 条断言是 "_PHENOMENON" in src 这类，重写为行为级后才发现不严谨
  • 金额 bug：905 项测试一条没拦住，因为断言的是「写了某个字段」而不是「写进了对的那一列」
  • 用错身份验证：机器人 token 读不了多维表格，返回空让我误判「数据没写进去」

九下一步该往哪走

优先级方向理由
P0真实下单全链路验证目前只验证到 --plan 和回写，真实建单未跑
P1身份鉴权改为 (chat_id, open_id) 绑定表现在只校验 user_name 字符串，持 token 可伪造
P2话题卡持久化注册表进程重启后未完成的卡会永久停在「正在处理」
P3向「内嵌」形态演进需要 EP 前端改造，AI 只出建议单
一句话总结这条路
从 CLI 到 Skill，是把能力从入口里解耦；
从 Skill 到卡片，是把交互从文档里解放；
从卡片到内嵌，是把权限从 AI 手里收回来。

每一步都不是因为技术更先进，而是因为上一步把人挡在了外面，或者把权力放得太松。
