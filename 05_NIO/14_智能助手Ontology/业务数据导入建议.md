下面给你一个 **非常务实、可以立刻执行的导入优先级清单**：基于你现在已经有了 **Neo4j 的完整 Ontology**、也有你 PDF 里定义的典型 Usecase（寻源→合同执行链路、订单链路诊断、跨域协同、权限诊断等）。

你现在最关键的不是“导数据越多越好”，而是 **导入最能体现“推理能力”和“Agent 智能升级”的数据**。

下面我给你一个明确的答案：

# 🎯 一句话总览

**第一优先导入订单域（PO/PR/需求/定价任务），第二优先导入寻源域（RFQ/SOR/价格），第三优先导入合作伙伴域（Supplier/准入/合同），再导入异常/日志/错误链路。**

这些能最快让 LLM + KG 解决“链路诊断 + 根因分析 + 下一步建议”，也就是你 PDF 中指明的 L3-L4 能力。

---

# 🥇 第一优先：订单执行链路数据（最能体现推理价值）

这是你们 Usecase2（订单自动化执行链路诊断）的核心场景。
导完这些后，你能实现完整的：

* “订单为什么卡住了？”
* “PR 为什么不能下 PO？”
* “定价任务为什么没到采购员手里？”
* “用户问题链路复现与自动诊断”

PDF 中你们实际的链路（PR → 需求 → 定价 → PO生成 → PO确认）已经非常标准化。

## **必须导入的数据表（MYSQL业务表）**

### 1. PR（采购申请）

* PR 基本信息（号、金额、预算中心、品类、申请人）
* PR 状态（审批中、通过、驳回）
* PR 与需求编号映射

### 2. 用户需求 / Requirement

* 需求编号、关联 PR
* 执行状态（待定价、定价中、失败…）
* 报错原因（非常重要，用于 root cause）

### 3. 定价任务（Pricing Task）

* 定价任务号
* buyer 归属
* 是否生成？
* 当前 owner
* 状态（未开始、进行中、审批中、完成）
* 失败原因（如 “历史定价任务在 xxx 名下”）

### 4. PO（采购订单）

* PO 号、行号、金额、数量
* 下单结果（成功/失败）
* 失败原因（如 BOM 缺失）
* 订单确认状态（未确认/已确认/双签）

### 5. 物料主数据（Item/Part）

* 零件号、物料类型（标准件、委外件）
* BOM 信息（是否存在）
* 零件类别（CATXXXX）

---

## **优先验证的 Usecase（特别能体现 KG 推理价值）**

### ✔ Case A：PR → 需求 → 定价 → PO 链路诊断（你 PDF 的 Usecase 2）

用户问：

> “这几单为什么没有收到定价任务？”

KG 推理路径：

```
PR -> Requirement -> PricingTask (missing?) -> Owner -> ErrorLogs
```

Example Root Causes：

* 历史定价任务占住 → 要转单
* 同一零件类 buyer 权限错误
* 非标需求没有生成定价任务
* 需求状态未导入成功

这种问题是 SQL 查不到的，但 KG 图遍历能自动找断点。

---

### ✔ Case B：订单下单失败 → 自动找根因

用户问：

> “这个物料为什么下不了单？”

KG 推理路径：

```
PO → Item → BOM → MDM系统 → 失败原因日志
```

例如 PDF 里的真实案例：

* “P0386684AF 缺 BOM 导致下单失败”

LLM + KG 可自动复现整条链路。

---

### ✔ Case C：用户权限诊断（你 PDF 中提得很明确）

用户问：

> “为什么我不能审批采购单？”

KG 推理路径：

```
User → Role → Permission → Domain → PO所属部门
```

能清楚告诉用户权限断点在哪。

# 🥈 第二优先：寻源域（RFQ / SOR / 报价包 / 评估）

能跳到 PDF 里的 Usecase1：**寻源到合同执行链路诊断。**

导入这些后，你能支持：

* RFQ 与 Buyer 归属查询
* SOR 是否下发、成熟度
* 评估任务是否完成（项目评估/准入评估）
* 报价状态（第一轮、第二轮）
* 定点（Award）记录
* 报价限制的业务规则（如准入未完成不能报价）

## 必须导入的表

* RFQ 基本信息
* RFQ Buyer
* SOR（成熟度、质量SOR 是否下发）
* 准入评估记录（by category）
* 项目评估任务状态
* 报价轮次、报价价格
* 定点评委/定点结果

## 可验证的 Usecase

* “为什么这个合作伙伴在报价包里选不到？”
* “SOR 是否下发？”
* “准入是否完成？”
* “报价是否可以进入下一轮？”

这些在 PDF 中也有完整的规则定义，非常适合做 KG 推理模板。

# 🥉 第三优先：合作伙伴域（Supplier / 准入 / 合同）

导入这些后，可以测试：

* 合作伙伴准入
* 合作伙伴账期
* 合作伙伴属地（制造地）
* 电子签状态
* 合作伙伴历史合同、订单情况

### 必须导入数据表

* Supplier 基本信息
* Buyer 属地
* Category 准入
* Category 下评估记录
* 合同基础信息
* 电子签状态

### 可验证 Usecase

* “帮我查一下这个供应商准入了哪些品类？”
* “这个供应商合同状态如何？”
* “这个供应商在该品类的准入是否过期？”

---

# 🟩 可选第四优先：异常日志（错误码）、系统间事件（状态变迁）

这是做 **根因诊断、高级推理（L4）** 的关键。

你 PDF 中的典型问题都是：

* “物料缺 BOM”
* “委外总成，没有对应的 BOM”
* “价格未同步”
* “定价任务在某某名下，需要人工转单”
* “物料分类不一致导致 PO 失败”
* “接口数量卡住 5700 个”
* “接口报错：Material XXX is categorized as subcontracted item”

真实场景需要：

### 导入

* 错误日志（ErrorCode、ErrorMessage、发生时间）
* 异常事件（Event: PricingError, CreatePOFailed, RequirementImportFailed）
* 审批历史（workflow）

KG 能将这些 **关系化**，LLM 才能做语义推理。

---

# ⭐ 最终推荐的导入顺序（可执行）

| 优先级  | Domain    | MySQL 表                                 | 验证 Case           | 对应 PDF   |
| ---- | --------- | --------------------------------------- | ----------------- | -------- |
| 🥇 1 | 订单执行链路    | PR/Requirement/Pricing/PO/Item/BOM/错误日志 | 链路诊断 + root cause | Usecase2 |
| 🥈 2 | 寻源        | RFQ/SOR/评估/报价/定点                        | 寻源链路诊断            | Usecase1 |
| 🥉 3 | 合作伙伴      | Supplier/准入/合同/账期                       | 准入/合同查询           | 合作伙伴域    |
| 🟩 4 | 跨域异常与系统状态 | Error Log / Event Log                   | 复杂根因分析            | L3-L4推理  |

这样分阶段导入，**每一阶段都能在 Neo4j + LLM 上产生可见的业务价值**。
