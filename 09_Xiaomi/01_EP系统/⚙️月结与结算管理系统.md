# 月结与结算管理系统

> 从采购到付款（P2P）全链路视角，系统梳理月结业务逻辑、账期管理、对账机制、结算系统架构，并给出可运行 Demo。

---

## 💡 核心发现

> [!tip]- 一句话总结
> - **月结的本质**：把 N 笔零散交易"攒到月底一起算"，通过账期延后付款，优化双方现金流
> - **结算系统的核心**：三单匹配（PO ↔ 收货 ↔ 发票）→ 自动对账 → 异常处理 → 审批付款
> - **账期不是越长越好**：长账期压供应商现金流导致断供风险，短账期占用 OEM 现金，需要平衡

## 一、业务逻辑 — 月结到底在结什么？

### 1.1 P2P 全流程中的"结算"位置

```
采购寻源 → 合同签订 → 下 PO → 收货(IQC) → [月结] → 付款
                              ↑                    ↑
                           物流完成              财务完成
```

月结是 **采购到付款（Procure-to-Pay, P2P）** 的核心财务节点，连接"物流"和"资金流"。

### 1.2 月结 vs 其他结算模式

| 模式 | 结算频率 | 付款时点 | 适用场景 | 典型账期 |
|------|----------|----------|----------|----------|
| **月结** | 每月 1 次 | 月末对账 + N 天后付款 | 量产零部件（高频、稳定） | 月结 30/60/90 天 |
| **批结** | 每批次 | 到货验收后 N 天 | 大型设备、模具 | 批结 30 天 |
| **预付** | 一次性 | 发货前付全款/定金 | 定制化、首次合作 | 0 天（提前付） |
| **到付（COD）** | 每次 | 货到付款 | 小额、零散采购 | 0 天（即时） |
| **里程碑** | 按节点 | 项目阶段完成 | 研发服务、EPC | 里程碑+30 天 |

**汽车量产零部件 = 月结的绝对主力**。每月收货数十甚至数百次，不可能逐笔付。

### 1.3 月结完整业务流程

以"月结 60 天"为例，完整时间线：

```
7 月 1 日 ~ 7 月 31 日          ← 交货月（结算月）
  ├─ 7/03: 供应商送货 [[1，仓库收货过账]] → GR #1
  ├─ 7/08: 供应商送货 [[2，仓库收货过账]] → GR #2
  ├─ 7/15: 供应商送货 [[3，仓库收货过账]] → GR #3
  └─ 7/28: 供应商送货 [[N，仓库收货过账]] → GR [[N]]

8 月 1 日 ~ 8 月 10 日          ← 对账窗口
  ├─ 8/01: 系统自动生成对账单（汇总 7 月所有 GR）
  ├─ 8/03: 供应商确认对账单 / 提出差异
  ├─ 8/05: 采购 + 仓库核查差异
  └─ 8/10: 对账完成，生成应付账款

8 月 10 日 ~ 9 月 29 日         ← 账期倒计时
  ├─ 8/10: AP（应付）确认，入账
  ├─ 9/05: 财务审批付款计划
  └─ 9/29: 到期付款（7 月 31 日 + 60 天 ≈ 9 月 29 日）
```

### 1.4 账期 — 商业博弈的核心

#### **账期的本质**

```
                OEM 视角                          供应商视角
┌─────────────────────────────┐    ┌─────────────────────────────┐
│  收货 → 不付钱 → 等 N 天再付  │    │  发货 → 拿不到钱 → 等 N 天   │
│  = 占用供应商资金做自己的事    │    │  = 被占用资金，现金压力大     │
│  = 短期免费融资（0 息贷款）    │    │  = 变相给 OEM 提供无息贷款   │
└─────────────────────────────┘    └─────────────────────────────┘
```

**公式**：
```
资金占用成本 = 月采购金额 × 账期天数 × 日利率

示例：
月采购金额：5,000 万元
账期：60 天
年化利率：4%
资金占用成本 = 5,000万 × (60/365) × 4% = 32.88 万元/月
```

#### **不同账期的博弈分析**

| 账期 | OEM 现金流 | 供应商现金流 | 供应链稳定性 | 行业惯例 |
|------|-----------|-------------|------------|----------|
| **月结 0 天（现金）** | 🔴 差 | 🟢 极好 | 🟢 稳定 | 初创期/强势供应商 |
| **月结 30 天** | 🟡 一般 | 🟢 好 | 🟢 稳定 | 通用标准 |
| **月结 60 天** | 🟢 好 | 🟡 一般 | 🟡 一般 | 汽车 OEM 常见 |
| **月结 90 天** | 🟢 极好 | 🔴 差 | 🔴 风险 | 强势 OEM（特斯拉等） |
| **月结 120 天+** | 🟢 极好 | 🔴 极差 | 🔴 高风险 | 濒临断供 |

#### **行业账期对标**

| 企业 | 采购规模 | 常见账期 | 说明 |
|------|----------|----------|------|
| 🇨🇳 比亚迪 | 万亿级 | 月结 90-120 天 | 强势，供应商抱怨 |
| 🇨🇳 小米汽车 | 千亿级 | 月结 60-90 天 | 新入局，逐步压账期 |
| 🇩🇪 大众 | 万亿级 | 月结 30-60 天 | 德国惯例，较规范 |
| 🇺🇸 特斯拉 | 千亿级 | 月结 90 天 | 现金流充裕，账期长 |
| 🇯🇵 丰田 | 万亿级 | 月结 30 天 | 精益理念，尊重供应商 |
| 🇰🇷 现代 | 千亿级 | 月结 60 天 | 韩系标准 |

### 1.5 对账 — 结算的核心难题

#### **为什么需要对账？**

理想情况：PO 数量 = 收货数量 = 发票数量 → 完美匹配 → 自动付款

实际情况：

| 差异类型 | 原因 | 频率 | 处理方式 |
|----------|------|------|----------|
| **数量差异** | 多收/少收/退货/损耗 | 🟡 中 | 查 GR 记录，确认退货单 |
| **价格差异** | PO 价格 vs 发票价格不一致 | 🟡 中 | 核对框架协议、调价通知 |
| **时间差异** | 收货在上月 vs 发票在本月 | 🟢 低 | 跨月对账，归属争议 |
| **质量问题** | 不良品退货但未更新 | 🔴 高 | 查 IQC 记录、退货单 |
| **税费差异** | 税率变动/发票错误 | 🟢 低 | 退票重开 |
| **汇率差异** | 跨境采购汇率波动 | 🟡 中 | 约定汇率基准日 |

#### **三单匹配原则（3-Way Matching）**

```
┌─────────┐    ┌─────────┐    ┌─────────┐
│ PO 单   │ ←→ │ 收货单  │ ←→ │ 发票    │
│(Purchase│    │(Goods   │    │(Invoice)│
│ Order)  │    │Receipt) │    │         │
└────┬────┘    └────┬────┘    └────┬────┘
     │              │              │
     ▼              ▼              ▼
  数量/价格      数量/质量       金额/税额
     │              │              │
     └──────────────┼──────────────┘
                    ▼
            ┌──────────────┐
            │  匹配引擎    │
            │  ──────────  │
            │  完全匹配 ✓  │ → 自动过账 → 等待付款
            │  容差内 ✓    │ → 自动过账（标记偏差）
            │  超出容差 ✗  │ → 人工干预 → 差异处理
            └──────────────┘
```

#### **容差规则（Tolerance）示例**

| 差异维度 | 容差范围 | 处理 |
|----------|----------|------|
| 数量差异 | ≤ ±2% | 自动匹配 |
| 数量差异 | > ±2% | 人工核查 |
| 金额差异 | ≤ ¥500 | 自动匹配 |
| 金额差异 | > ¥500 | 人工核查 |
| 单价差异 | = 0 | 自动匹配 |
| 单价差异 | ≠ 0 | 人工核查 |

### 2.4 核心流程设计

#### **月结自动对账流程**

```
┌─────────────────────────────────────────────────────┐
│                  月结对账引擎                          │
│                                                       │
│  触发条件：每月 1 日 00:00 自动执行                     │
│                                                       │
│  Step 1: 汇总上月 GR                                  │
│  ┌───────────────────────────────────┐               │
│  │ SELECT supplier_id, po_no,        │               │
│  │   SUM(quantity) as gr_qty,        │               │
│  │   SUM(amount) as gr_amount        │               │
│  │ FROM gr_detail                    │               │
│  │ WHERE gr_date BETWEEN             │               │
│  │   @period_start AND @period_end   │               │
│  │   AND quality_flag = 'PASS'       │               │
│  │ GROUP BY supplier_id, po_no       │               │
│  └───────────────────────────────────┘               │
│                     ▼                                │
│  Step 2: 匹配供应商发票                                │
│  ┌───────────────────────────────────┐               │
│  │ 对每个 GR 汇总行：                  │               │
│  │   查找同供应商、同 PO 的发票         │               │
│  │   执行三单匹配（PO ↔ GR ↔ Invoice）│               │
│  └───────────────────────────────────┘               │
│                     ▼                                │
│  Step 3: 计算差异                                      │
│  ┌───────────────────────────────────┐               │
│  │ diff = gr_amount - invoice_amount │               │
│  │ IF |diff| <= tolerance → 自动通过  │               │
│  │ IF |diff| > tolerance → 进入差异池 │               │
│  └───────────────────────────────────┘               │
│                     ▼                                │
│  Step 4: 生成对账单                                    │
│  ┌───────────────────────────────────┐               │
│  │ 状态：Draft → 待供应商确认          │               │
│  │ 供应商可在供应商门户查看/确认/申诉   │               │
│  └───────────────────────────────────┘               │
│                     ▼                                │
│  Step 5: 确认后生成 AP（应付账款）                      │
│  ┌───────────────────────────────────┐               │
│  │ AP 入账日期 = 对账确认日            │               │
│  │ 付款到期日 = 结算月末 + 账期天数    │               │
│  │ 例：7 月结算，月结 60 天             │               │
│  │     → 付款日 = 7/31 + 60 = 9/29   │               │
│  └───────────────────────────────────┘               │
└─────────────────────────────────────────────────────┘
```

#### **付款日计算逻辑**

```python
def calculate_payment_due_date(settlement_month_end, payment_terms_days):
    """
    付款日计算

    Args:
        settlement_month_end: 结算月最后一天 (date)
        payment_terms_days: 账期天数 (int)

    Returns:
        付款到期日 (date)

    示例：
        结算月 = 2026-07，月结 60 天
        settlement_month_end = 2026-07-31
        payment_terms_days = 60
        → due_date = 2026-09-29
    """
    due_date = settlement_month_end + timedelta(days=payment_terms_days)

    # 遇到周末顺延到下一个工作日
    while due_date.weekday() >= 5:  # 5=周六, 6=周日
        due_date += timedelta(days=1)

    # 遇到法定节假日顺延
    if due_date in public_holidays:
        due_date = next_business_day(due_date)

    return due_date
```

### 2.6 关键业务规则（BR）

| 编号 | 规则 | 逻辑 | 优先级 |
|------|------|------|--------|
| **BR-01** | 账期继承 | PO 账期 > 合同账期 > 供应商默认账期 | P0 |
| **BR-02** | 三单匹配 | PO 数量 ≥ GR 数量 ≥ Invoice 数量（容差内） | P0 |
| **BR-03** | 付款日计算 | 结算月末 + 账期天数，遇节假日顺延 | P0 |
| **BR-04** | 部分收货 | GR < PO → 未收货部分不参与本月对账 | P1 |
| **BR-05** | 退货扣减 | 质量退货在当月 GR 中扣减，不影响历史对账 | P1 |
| **BR-06** | 提前付款折扣 | 2/10 Net 30：10 天内付打 98 折 | P2 |
| **BR-07** | 超额预警 | 单供应商月结算金额 > 信用额度 → 触发审批 | P1 |
| **BR-08** | 跨月发票 | 发票日期晚于收货月 3 个月 → 标记异常 | P2 |

## 五、关键指标（KPI）

### 5.1 结算效率指标

| 指标 | 计算方式 | 目标值 | 说明 |
|------|----------|--------|------|
| **自动匹配率** | 自动匹配笔数 / 总笔数 | ≥ 85% | 越高越省人力 |
| **对账周期** | 月末到对账完成天数 | ≤ 5 天 | 越短越好 |
| **差异率** | 有差异笔数 / 总笔数 | ≤ 10% | 反映数据质量 |
| **按时付款率** | 按时付款笔数 / 总笔数 | ≥ 95% | 避免违约金 |
| **付款准确率** | 正确金额付款 / 总付款 | ≥ 99.9% | 事后差错率 |

### 5.2 资金指标

| 指标 | 计算方式 | 说明 |
|------|----------|------|
| **DSO（应收周转天数）** | 应收 / 日均销售 | 从供应商视角看 |
| **DPO（应付周转天数）** | 应付 / 日均采购 | 从 OEM 视角看，越大越好 |
| **现金转换周期** | DSO + DIO - DPO | 越短越好 |
| **提前付款折扣收益** | 已用折扣金额 × 折扣率 | 年化收益 |

## 六、常见坑与最佳实践

### 6.1 常见坑

| 坑 | 表现 | 根因 | 解法 |
|----|------|------|------|
| **对账拖延** | 月结变成了"季结" | 差异太多、人工处理慢 | 自动对账 + 容差规则 + 差异池管理 |
| **退货未及时处理** | 已退货但仍付款 | GR 和退货系统不打通 | 退货单自动扣减 GR |
| **价格更新滞后** | PO 调价通知未同步 | 人工操作、无系统联动 | 合同变更为事件驱动，自动更新 PO |
| **账期混乱** | 同一供应商不同 PO 不同账期 | 合同/PO 多层覆盖 | 明确优先级：PO > 合同 > 供应商 |
| **跨月收货/发票** | 7 月收货、8 月发票、归属争议 | 跨月结算边界不清 | 约定"以收货月为结算月" |
| **汇率差异** | 跨币种采购对不上 | 汇率基准日不统一 | 约定"以月末最后工作日央行中间价" |

### 6.2 最佳实践

| 实践 | 说明 | 价值 |
|------|------|------|
| **供应商自助门户** | 供应商自己上传发票、确认对账单 | 减少 80% 对账沟通成本 |
| **电子发票直连** | 对接税务局电子发票平台，自动验真 | 杜绝假发票 |
| **智能容差** | 根据供应商信用等级动态调整容差 | 优质供应商自动过账率更高 |
| **付款日历** | 可视化展示每日到期应付，辅助资金计划 | 资金部提前安排资金 |
| **对账 KPI 看板** | 实时监控各供应商对账状态 | 及时发现卡点 |
| **合同到期预警** | 框架协议到期前 90 天提醒续签 | 避免"合同过期仍交易"的合规风险 |

## 七、与固定资产分摊的联动

> 回到 linked note [[00_Self/04_供应链/06_出海与国际贸易/💰固定资产投入与分摊策略|固定资产投入与分摊策略]] 的上下文。

结算管理系统不仅管"买零件"，还要管"付模具/设备款"：

| 场景 | 结算模式 | 账期 | 特殊处理 |
|------|----------|------|----------|
| **量产零件** | 月结 | 60 天 | 常规三单匹配 |
| **模具费** | 里程碑付款 | 30-30-40 | 按开发节点验收后付 |
| **设备采购** | 预付 + 验收 | 50-50 | 预付款需资金审批 |
| **开发服务费** | 里程碑 | 按节点+30 天 | 需研发确认交付物 |

模具分摊费可通过结算系统"反向收取"：
```
OEM 垫付模具 $10M → 按产量 $10/件向供应商收取 → 月结时自动扣减
```
