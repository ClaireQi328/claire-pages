# API 与 CLI 开发指南 — 产品经理版

> 📌 **目标读者**：产品经理、业务分析师、测试人员
> 📌 **核心目标**：理解 API 和 CLI 的关系，能参与需求评审和验收

---

## 一、一句话理解

| 概念 | 通俗比喻 | 技术定义 |
|------|----------|----------|
| **API** | 餐厅菜单 | 后端系统对外提供的"功能接口"，定义了能做什么、需要什么、返回什么 |
| **CLI** | 服务员 | 命令行工具，帮用户把需求翻译成 API 能理解的格式，再把结果翻译成人能看懂的格式 |

**核心关系**：API 是"能力"，CLI 是"使用方式"。同一个 API 可以被 CLI、Web 页面、AI Agent 等多种方式调用。

## 二、API 是什么？

### 2.1 用餐厅打比方

| 餐厅场景 | 技术对应 | 说明 |
|----------|----------|------|
| 菜单 | API 文档 | 列出所有"菜品"（功能）和"配料要求"（参数） |
| 点菜窗口 | API 地址（URL） | `http://ep-system/custom/supplier/getById.api` |
| 你的点菜单 | 请求（Request） | 你告诉窗口"我要查供应商 V10001" |
| 端上来的菜 | 响应（Response） | 窗口返回供应商的完整信息 |

### 2.2 真实例子：查供应商信息

**场景**：你想知道供应商"苏州智选电子"的详细信息（银行账号、账期等）。

#### 后端要做的事（定菜单）

```yaml
接口路径: POST /custom/supplier/getById.api
输入参数:
  - id (string, 必填) — 供应商ID，比如 "963833799075766"
输出内容:
  - orgCode — 供应商编码 "V10001"
  - orgName — 供应商名称 "苏州智选电子有限公司"
  - accountingPeriodDay — 账期天数 "90"
  - paymentCashRatio — 现金比例 "50"
  - settlementBank.bankName — 电汇银行 "中国工商银行苏州分行"
```

这就是 EP CLI 文档中 **接口 1** 的内容。

### 2.3 API 文档必须包含的 6 件事

| # | 要素 | 通俗解释 | 示例 |
|---|------|----------|------|
| 1 | **接口路径** | 在哪里调用 | `/custom/supplier/getById.api` |
| 2 | **请求方式** | 用什么方式传信息 | `POST`（提交）/ `GET`（查询） |
| 3 | **输入参数** | 需要传什么 | `id: string, 必填` |
| 4 | **请求示例** | 实际调用长什么样 | `{"id":"963833799075766"}` |
| 5 | **输出结构** | 返回什么字段 | `orgCode, orgName, accountingPeriodDay...` |
| 6 | **输出示例** | 实际返回长什么样 | 完整 JSON 响应 |

## 三、CLI 是什么？

### 3.1 CLI 的四层命名空间

EP CLI 统一采用 `dx-ep <模块> <资源> <动作> [参数]` 格式：

```
dx-ep  supplier  info  list  --name "电子" --page 1
  ↑       ↑       ↑     ↑         ↑
工具名   模块    资源   动作     参数（flags）
```

| 层级 | 示例 | 说明 |
|------|------|------|
| 工具名 | `dx-ep` | 固定前缀，代表"钉选 EP 系统" |
| 模块 | `supplier` / `sor` / `rfq` | 业务域（供应商 / SOR / 询报价） |
| 资源 | `info` / `quote` / `nomiaf` | 具体资源（信息 / 报价 / 定点申请） |
| 动作 | `query` / `list` / `create` | 操作（查一条 / 查列表 / 创建） |

### 3.2 CLI 内部做了什么？

```
用户输入：dx-ep supplier profile query --id 963833799075766

CLI 内部步骤：
1. 解析用户输入 → 提取 id = "963833799075766"
2. 构造请求 → POST /custom/supplier/getById.api，body = {"id":"963833799075766"}
3. 发送 HTTP 请求 → 等待后端返回
4. 解析响应 → 从 JSON 中提取关键字段
5. 格式化输出 → 易读的表格或 JSON
```

### 3.3 CLI 输出格式

统一返回结构：

```json
{
  "state": "success",
  "message": "success",
  "data": { ... }
}
```

- `state = "success"` → 成功，看 `data` 内容
- `state != "success"` → 失败，看 `message` 错误信息

## 四、完整开发流程

### 4.1 角色分工

| 角色 | 职责 | 输出物 |
|------|------|--------|
| **产品经理** | 定义场景、功能说明 | 需求文档、验收标准 |
| **后端开发** | 实现 API 接口 | 接口文档、API 代码 |
| **CLI 开发** | 实现命令行工具 | CLI 代码、使用说明 |
| **测试** | 验证功能正确性 | 测试用例、验收报告 |

### 4.2 开发时间线（以 WAVE1 的 17 个接口为例）

```
Phase 1: API 文档定义（产品 + 后端）—— 6~9 天
├─ 产品写场景说明 ............. 2~3 天
├─ 后端写接口文档 ............. 3~5 天
└─ 评审对齐 ................... 1 天

Phase 2: 并行开发（后端 + CLI）—— 7~10 天
├─ 后端实现 API ............... 5~8 天（17个接口，并行）
├─ CLI 开发 ................... 5~8 天（17个指令，并行）
└─ 单元测试 ................... 2~3 天

Phase 3: 联调 + 测试 —— 7~11 天
├─ 逐个接口联调 ............... 3~5 天
├─ 集成测试 ................... 2~3 天
└─ Bug 修复 ................... 2~3 天

Phase 4: 验收 + 发布 —— 3~5 天
├─ 业务验收 ................... 2~3 天
└─ 文档 + 发布 ............... 1~2 天

总计：23~35 天（约 5~7 周）
```

### 4.3 单个接口开发时间

| 接口类型 | 后端开发 | CLI 开发 | 联调 | 总计 |
|----------|----------|----------|------|------|
| 简单查询（单表） | 0.5~1 天 | 0.5~1 天 | 0.5 天 | **1.5~2.5 天** |
| 复杂查询（多表关联） | 1~2 天 | 1~2 天 | 1 天 | **3~5 天** |
| 写操作（创建/更新） | 1~2 天 | 1~2 天 | 1 天 | **3~5 天** |
| 跨系统调用 | 2~3 天 | 1~2 天 | 1~2 天 | **4~7 天** |

## 五、产品经理参与要点

### 5.1 需求评审时要确认

| # | 确认项 | 为什么重要 |
|---|--------|-----------|
| 1 | **接口路径是否已定义** | 没有路径 → 开发无法开始（陈千钧的阻塞点） |
| 2 | **输入参数是否完整** | 缺参数 → 功能不全，后期补成本高 |
| 3 | **输出字段是否满足业务需求** | 字段不够 → 业务用不了，要返工 |
| 4 | **错误场景是否覆盖** | 没定义 → 用户看到莫名其妙的报错 |
| 5 | **验收标准是否明确** | 没标准 → 测试无法验收，上线质量不可控 |

### 5.2 验收标准模板

```markdown
## 接口 X：查询 XXX

### 正常场景
- Given 有效输入 When 执行命令 Then 返回正确结果

### 异常场景
- Given 无效输入 When 执行命令 Then 返回友好错误提示
- Given 缺少必填参数 When 执行命令 Then 返回参数校验错误

### 边界场景
- Given 空结果 When 执行命令 Then 返回"无数据"提示
- Given 大数据量 When 执行命令 Then 分页正常
```

### 5.3 常见问题 FAQ

| 问题 | 回答 |
|------|------|
| **CLI 和 Web 页面有什么区别？** | 同一个 API，不同入口。CLI 适合批量操作和自动化，Web 适合人工操作 |
| **为什么不能直接查数据库？** | 绕过业务逻辑，数据不安全，维护成本高 |
| **API 文档谁来写？** | 后端开发写技术文档，产品写场景说明，双方评审对齐 |
| **没有 API 能先开发 CLI 吗？** | 可以 Mock 数据先跑通流程，但最终必须对接真实 API |
| **开发周期怎么算？** | 单个接口 1.5~5 天，17 个接口约 5~7 周（含联调测试） |

## 六、Skill 是什么？

### 6.1 一句话理解

| 概念 | 通俗比喻 | 技术定义 |
|------|----------|----------|
| **Skill** | 厨师的拿手菜谱 | 一组可复用的"能力包"，包含触发条件、执行步骤、输入输出规范 |

**核心关系**：API 是"原材料"，CLI 是"加工工具"，Skill 是"菜谱"——告诉 AI 在什么场景下、用哪些 CLI、按什么步骤完成任务。

### 6.2 Skill 的组成

一个完整的 Skill 包含：

```yaml
名称: 供应商信息查询
触发条件: 用户问"供应商 XXX 的信息"或"查一下供应商"
执行步骤:
  1. 调用 dx-ep supplier info list --name "XXX"  # 先查列表
  2. 从结果中提取 supplier id
  3. 调用 dx-ep supplier profile query --id <id>  # 再查详情
  4. 格式化输出关键信息
输入: 供应商名称或编码
输出: 供应商完整信息（编码、名称、账期、银行等）
```

### 6.3 EP 系统中的 Skill 示例

| Skill 名称 | 功能 | 依赖的 CLI |
|------------|------|-----------|
| 供应商信息查询 | 查供应商详情 | `dx-ep supplier info query` |
| SOR 进度追踪 | 查 SOR 审批状态 | `dx-ep sor info list` + `dx-ep sor process-history query` |
| 询报价分析 | 查报价详情和供应商状态 | `dx-ep rfq quote list` + `dx-ep rfq bidder review` |
| 定点申请创建 | 自动创建定点申请单 | `dx-ep nomi apply generate` |
| 价格台账查询 | 查零件价格构成 | `dx-ep price ledger` |

### 6.4 Skill 开发流程

```
Step 1: 识别高频场景
  └─→ 产品经理梳理用户高频操作（如"查供应商信息"）

Step 2: 设计 Skill 定义
  └─→ 明确触发条件、输入输出、执行步骤

Step 3: 串联 CLI 指令
  └─→ 确定需要调用哪些 CLI、按什么顺序

Step 4: 实现与测试
  └─→ 开发 Skill 代码，验证端到端流程

Step 5: 接入业务流
  └─→ 嵌入工作台、飞书机器人等入口
```

### 6.5 Skill 开发时间

| 复杂度 | 说明 | 时间 |
|--------|------|------|
| 简单 | 单个 CLI 调用 + 格式化 | **1~2 天** |
| 中等 | 多个 CLI 串联 + 参数传递 | **3~5 天** |
| 复杂 | 跨模块 + 条件分支 + 错误处理 | **5~8 天** |

## 七、Agent 是什么？

### 7.1 一句话理解

| 概念 | 通俗比喻 | 技术定义 |
|------|----------|----------|
| **Agent** | 采购专家团队 | 能自主决策、调用多个 Skill、完成复杂任务的 AI 系统 |

**核心区别**：
- **CLI** = 你告诉它"查什么"，它返回结果（被动执行）
- **Skill** = 你告诉它"做什么"，它按菜谱执行（半自动）
- **Agent** = 你说"帮我搞定"，它自己决定怎么做（自主决策）

### 7.2 Agent 的能力层级

| 层级 | 能力 | 举例 | 状态 |
|------|------|------|------|
| **L1 知识问答** | 回答"是什么" | "EWO 设变询是什么？" | ✅ 已启动 |
| **L2 单域操作** | 执行单个 CLI | "查供应商 V10001 的信息" | ✅ 已启动 |
| **L3 跨域协同** | 串联多个 CLI | "从零件号追到定点进度" | 🟡 规划中 |
| **L4 智能分析** | 数据洞察 + 预警 | "哪些供应商有风险？" | 🟡 规划中 |
| **L5 智能推荐** | 主动推送建议 | "这个零件建议换供应商" | 🔴 远期 |

### 7.4 Agent 的真实场景

#### 场景 1：零件定点全流程追踪

```
用户："帮我查一下零件 MOT-ED-2025-001 的定点进度"

Agent 自动执行：
1. 意图识别 → 定点进度查询
2. 调用 Skill：SOR 信息查询
   └─→ dx-ep sor info list --material-num MOT-ED-2025-001
3. 调用 Skill：RFQ 信息查询
   └─→ dx-ep rfq info list --sor-code <sor_code>
4. 调用 Skill：定点进度查询
   └─→ dx-ep nomi progress --rfq-id <rfq_id>
5. 汇总结果 → 输出完整进度报告
```

#### 场景 2：供应商风险预警

```
Agent 自主监控：
1. 定时扫描 → 每天检查所有在途定点申请
2. 发现异常 → 某供应商报价超预算 20%
3. 自动告警 → 推送给采购员："供应商 V10001 报价偏离过大，请关注"
4. 建议措施 → "建议：① 要求供应商重新报价 ② 启动备选供应商"
```

### 7.5 Agent 开发时间

| 阶段 | 内容 | 时间 |
|------|------|------|
| 架构设计 | Agent 整体方案、组件划分 | **2~3 周** |
| 单域 Agent | 一个功能域的 Agent（如供应商） | **3~4 周** |
| 多 Agent 协同 | 跨域协作、任务编排 | **4~6 周** |
| 智能分析 | 数据洞察、预警、推荐 | **6~8 周** |

## 十、给非技术同事的一句话总结

> **你只需要知道**：API 是"后端能做什么"，CLI 是"你怎么用"。你需要参与的是——**把需求说清楚，把验收标准定好**。技术实现交给开发，但需求模糊的锅不能甩给开发。
