## 1. 背景与目标（Why）

### 1.1 业务背景

2026 下半年 EP 平台建设采用"双轨协同"：数据资产沉淀（品类 / 供应商 / 成本三维数据仓库）+ AI 赋能功能板块。主数据 PRD（品类资源池 + VPPS 绑定）已完成"地基"，但**数据尚未反哺业务**——SOR / EWO / CWO / SWO / 样件 / 框架等任务仍靠人工匹配采购员下发。

### 1.2 核心痛点（量化）

| 痛点 | 量化影响 |
|---|---|
| 人员映射靠人工 | 年度 **94,440 次**任务分配，分配流程冗长低效，物料错配风险居高不下 |
| 人员变动响应慢 | 采购员离职 / 调岗需人工排查并转移其负责的所有单据，易遗漏、影响业务连续性 |
| 品类主数据缺失 | 线上仍以零件 PN 维度，缺少聚合品类概念，跨部门协同缺统一口径 |
| 规则写死代码 | 改一次派活规则发一次版，无法业务自助配置 |

### 1.3 目标

把"人工派活"改为**三级自动路由**：`任务分类（品类）→ 匹配 MVPS 级别 → 落到角色（采购工程师 / 财务CE / SQE）`，做到**派得准、派得清（可解释、可改派）**。

- **北极星指标**：自动路由准确率（正确派活 / 总派活，人工改派记为不正确），目标 ≥ 96%。
- **驱动指标**：人工派活占比（目标 → 0%）、异常队列积压（目标 ≤ 5 条 / 日）、平均派活耗时（目标 < 5s）。
- **健康指标**：规则覆盖率（有对应规则的场景 / 总场景）、负载均衡度（采购员 loadRate 标准差）。

## 4. 功能 a：项目路由和应用

### 4.1 目标与用户故事

> 作为 **采购项目经理（PM）**，我希望在维护项目进度时只需选择「品类」，系统自动带出该品类对应的**采购员 & SQE**，以便减少人工查表、避免错配，并保证项目维度下任务分工可统一追溯。

> 作为 **采购主管**，我希望以"项目 + VPPS"维度查看某车型项目下所有任务分工，以便人员变更 / 离职时一次性统管转移，而非零散排查。

### 4.2 项目管控表（主数据 PRD 表1）的路由应用

主数据 PRD 表1「项目管控表」将项目列表提升一级（车型项目下建项目编号）。其**进度管理**页是本次应用重点：

- PM 导入项目进度时，必填**品类、SQE、计划定点时间**；**采购员默认带出品类资源池（表2）的采购员**，导入时填写则以填写为准。
- SOR 审批到 PM 时，PM 不再填采购员 & SQE & 定点时间，应**选择品类，系统自动带出采购员 & SQE**（数据来源：品类-VPPS-采购工程师关系 + 品类专家）。
- 进度管理表字段含：SOR编号、SOR名称、**品类**、**采购员**、采购组、DRE、**SQE**、开发策略、计划定点时间、定点状态、关联BDL/RFQ、核价完成进度、合同签署进度、操作（转派人员 / 冻结）。

**路由应用规则（a）**：当某 SOR / 任务关联「品类 + 车型项目」时，系统按 `品类 → VPPS（如可解析）→ 采购工程师` 自动填充负责人；无法解析 VPPS 的（紧固件 / 胶水 / 面料 / 样件 / 框架无车型字段）走原有 PM / 专员手工下发。

### 4.3 项目维度任务 / 人员路由视图

- **项目详情 → 人员路由面板**：展示该项目下按「项目 + VPPS」聚合的任务分工（采购工程师 / 财务CE / SQE 三类角色），支持按 VPPS 维度批量转派。
- **人员变更统管**：采购员离职 / 调岗时，以"项目 + VPPS"维度**同时**操作品类资源池（表2）与项目进度表（表1）的转派，两者合并才能索引到车型项目层面下 VPPS 的采购工程师（替代现有散落的"一键转派"）。

### 4.4 页面与交互（原型待补）

- 项目管控列表（车型项目 / 涉及工厂 / M0时间 / 采购项目经理 / SOR包数量 / 定点状态 / 基础车型数量 / 详情）。
- 项目详情：基本信息 + 节点计划 + 项目明细 + 项目产销规划 + **进度管理（品类自动带出采购员&SQE）** + 人员路由面板。

## 5. 功能 b：自动找人路由（核心）

> 本功能直接采用《品类自动派活PRD.html》的 M1–M5 模块，并补齐**财务CE / SQE 角色维度**（主数据 PRD 的"品类-VPPS-采购工程师关系"仅含采购工程师，不足以支撑定点申请单 / 框架协议审批的财务CE 路由）。

### 5.1 三级自动路由模型

```
任务 / 单据
  → 认品类（classify：零件号 / 台账 → 品类）
    → 匹配 MVPS 级别（结构简码 + 位置码 → VPPS → 品类）
      → 落到角色（采购工程师 / 财务CE / SQE，按场景取对应角色）
        → 写回任务表 + 飞书通知
```

### 5.2 路由基座：品类-VPPS-【角色】关系（数据模型扩展）

主数据 PRD 现有「品类-VPPS-采购工程师关系」仅含采购工程师。本期**扩展为角色化关系**，同一 VPPS 节点下挂三类角色：

| 字段 | 类型 | 说明 |
|---|---|---|
| 品类编码 | VARCHAR | 关联品类 |
| VPPS节点 | VARCHAR | VPPS 节点（结构简码 + 位置码） |
| 角色 | ENUM | `BUYER`(采购工程师) / `FINANCE_CE`(财务CE) / `SQE`(质量工程师) |
| 人员ID | VARCHAR | 该角色对应人员 |
| 创建人 / 时间 / 更新人 / 时间 | — | 系统记录 |

> 与主数据 PRD 的"品类-VPPS-采购工程师关系"表**兼容并存**：采购工程师关系沿用原表，财务CE / SQE 关系新增；统一由 `dx-ep mvps category detail` 返回。

### 5.4 规则引擎（派活"大脑"）

规则 = `优先级 + 条件组(AND) + 动作(assign) + 溢出(overflow)`。纯函数：输入 Task，输出 `{assigneeId, ruleId, reason}`，无状态、可解释。

**示例规则 R-002**：
```json
{
  "id": "R-002", "priority": 1, "enabled": true,
  "conditions": [
    {"field":"module", "op":"in", "value":["SOR","BDL"]},
    {"field":"category", "op":"eq", "value":"动力总成"},
    {"field":"mvps", "op":"in", "value":["V1"]},
    {"field":"amount", "op":"between", "value":[1000000,5000000]}
  ],
  "action": {"assign": "张明"},
  "overflow": {"when":"buyer.loadRate>80", "fallback":"王磊"}
}
```
**匹配算法**：规则按 priority 升序扫描，第一条全条件命中即用；主+备用均溢出或无命中 → 进异常队列。

**字段 × 操作符**：`module(in/not_in)`、`category(eq/in)`、`mvps(eq/in)`、`amount(between)`、`project(eq)`、`sourcing(eq)`、`stage(eq)`、`urgency(eq)`、`region(eq)`。

**可解释输出标准（routeReason）**：
- 命中：`"命中 R-002（动力总成 ∩ V1 ∩ 金额区间 100~500万）→ 派张明；负载62%未溢出"`
- 异常：`"无命中规则：category=内饰,mvps=V3 无对应规则 → 建议李娜"`

### 5.7 异常与兜底（派不出也不卡死）

| 异常类型 | 触发 | 系统动作 | 人处理 |
|---|---|---|---|
| 无命中规则 | route-match 返回 null | 进异常队列 + 建议采购员（按品类最近似规则） | 点「改派」 |
| 采购员全溢出 | 主+备用 loadRate>80% | 进异常队列 + 建议闲时人员 | 改派 / 调阈值 |
| 同类连改≥3次 | 同规则/品类人工改派≥3 | 标记规则疑似有误，通知优化 | 修规则 |
| 准确率降级 | 近7日准确率<90% | 自动降级回"人严格审核"，停自动派 | 复盘后手动恢复 |
| 通知超时 | 飞书卡片 24h 未确认 | 49h / 72h 分链升级提醒上级 | 确认 / 改派 |

> **兜底原则**：任何自动派活都可解释、可改派；派不出必进异常队列（不丢、不卡）；准确率跌破阈值自动退回人审。

### 5.8 验收标准（b）

- **Given** 配置 R-002（SOR+动力总成+V1+金额区间→张明） **When** 新建 SOR 任务 **Then** 5s 内「指派采购员」自动填充且状态✅，routeReason 含 R-002。
- **Given** 无命中规则的任务 **When** 进入系统 **Then** 状态=❌且不丢，出现在异常队列。
- **Given** 每条派活 **When** 落库 **Then** RouteLog 可查（命中规则 + 原因），DB 必有 routeReason。
- **Given** 准确率掉到 89% **When** 系统检测 **Then** 自动降级并通知。

## 6. 功能 c：采购组赋权

### 6.1 目标与用户故事

> 作为 **采购主管 / 专业组总监**，我希望在自己的管辖范围内（专业组 → 功能组 → 采购工程师）查看量产SOR、售后SOR、台账、RFQ、BDL 等数据，以便履行管理职责而不越权查看无关数据。

> 作为 **品类专家 / 采购工程师**，我希望赋权关系清晰可追溯，以便人员调整时权限随组织层级自动收敛。

### 6.2 组织层级模型

```
专业组（如 电子架构 / 机械架构 / 内饰 / 车身外饰 / 增程&热管理 / 电池 / 电驱）
  └─ 功能组（功能组组长）
       └─ 采购工程师（含 财务CE / SQE 角色）
```
- **专业组总监**：管辖整个专业组的数据查看权限。
- **功能组组长**：管辖本功能组。
- **采购工程师 / 财务CE / SQE**：仅查看自身名下单据。

### 6.3 赋权与权限模型

- **赋权入口**：采购组管理页 → 选择专业组 / 功能组 → 配置总监 / 组长 / 成员（含角色）。
- **查看权限判定（采用 docx 方案2）**：通过**单据条目的归属人** → 反查其所属专业组 / 功能组 → 判断当前用户是否在该层级管理链上（专业组总监 / 功能组组长 / 采购工程师）。（已否决方案1：通过零件号找专业组。）
- **覆盖范围**：量产SOR、售后SOR、台账、RFQ、BDL。
- **与现有权限矩阵关系**：在《MVPS品类管理与VPPS绑定品类-PRD》权限矩阵基础上，**新增"采购组维度"的数据行级权限**，不影响品类管理 / VPPS 绑定的既有功能权限。

| 功能 | 专业组总监 | 功能组组长 | 采购工程师 | 普通用户 |
|---|---|---|---|---|
| 查看本组量产SOR / 售后SOR / 台账 / RFQ / BDL | ✅ 全组 | ✅ 本组 | 仅自身名下 | ❌ |
| 赋权 / 调整组内成员 | ✅ | ✅（受总监约束） | ❌ | ❌ |
| 查看其他组单据 | ❌ | ❌ | ❌ | ❌ |

### 6.4 页面与交互（原型待补）

- **采购组管理**：专业组树 + 功能组 + 成员列表（含角色标签 采购工程师/财务CE/SQE）+ 赋权操作。
- **数据查看边界提示**：越权访问时提示"无权限查看该专业组单据"。
- **变更记录**：赋权 / 调整成员写入变更记录（复用主数据 PRD 变更记录实体）。

### 6.5 验收标准（c）

- **Given** 当前用户为专业组总监 **When** 查看本组 RFQ **Then** 展示全组 RFQ；查看其他组 RFQ 提示无权限。
- **Given** 当前用户为功能组组长 **When** 查看本组台账 **Then** 仅展示本组成员名下台账。
- **Given** 采购工程师调组 **When** 管理员调整成员 **Then** 其数据查看边界同步变更并写入变更记录。

## 7. 智能层：CLI / Skill / Agent

> 核心原则：**人和 Agent 走同一个 CLI → 调同一个 Skill → 用同一条规则引擎规则**。所以点按钮和 Agent 自动跑结果永远一致、说得清。

### 7.1 五层架构映射

| 层 | 能力 | 角色承担 | 本文对应 |
|---|---|---|---|
| ① 品类主数据搭建 | 多级品类树、绑定 品类×VPPS→角色、人员树、实效管理 | CLI 拉取 + Skill 管理 | 主数据 PRD + 本文 5.2 |
| ② 定点供应商匹配 | 品类新建触发推荐、RFQ定点回写映射池 | Skill 推荐 + Agent 回写 | 本文 b + M4 |
| ③ 任务路由和通知 | 规则引擎、自动派活、飞书推送、超时升级 | Agent 监听 + Skill 统计 | 本文 b + c |
| ④ 封装成 MCP | Tool 封装 supplier.recommend / task.route | API 总开关 | M6 |
| ⑤ 资源池与策略基座 | 合规供应商池、品类红黑策略、AI决策 | Future | Future |

### 7.2 CLI 命令扩展（`dx-ep` / `ep` 命名空间）

在现有 `dx-ep mvps`（WAVE1 查询 / WAVE2 操作）基础上，应用层新增：

| 命令 | 参数 | 作用 | 对应功能 |
|---|---|---|---|
| `ep route dispatch` | `--task <id>` | 单条路由（Agent 自动调） | b |
| `ep route batch-dispatch` | `--module SOR --date today` | 批量路由 | b |
| `ep route rule add/test` | `--file rule.json` / `--id --task` | 规则新增 / 试跑预览 | b |
| `ep route explain` | `--task <id>` | 查派活原因 | b |
| `ep route reassign` | `--task --buyer --reason` | 人工改派 | b |
| `ep category link` | `--category --mvps --buyer/--ce/--sqe` | 绑定 品类×VPPS→角色 | b/c |
| `ep group grant` | `--group --role --user` | 采购组赋权 | c |
| `ep group view` | `--user` | 查用户数据边界 | c |
| `ep agent run/pause/status` | `--module` | 启停自动路由 | b |
| `ep agent feedback/eval` | `--task --correct-buyer` / `--period` | 反馈 / 算准确率 | b |
| `ep mcp serve/tools` | `--port` | 启动 MCP / 列 Tool | ④ |
| `ep observe stats/exceptions` | `--module` | 监控 / 异常队列 | b |

### 7.3 Skill 定义（工具箱）

| 能力 | Skill | 说明 |
|---|---|---|
| 品类识别 | `category-classify` | 零件号 / 台账 → 品类 |
| 路由计算 | `route-match` / `rule-evaluate` | 调规则引擎，返回 assignee + reason |
| 负载均衡 | `load-balance` / `buyer-resolve` | 溢出时自动转备用 |
| 写入通知 | `task-assign` / `task-reassign` | 写回页面 + 飞书推卡 |
| 异常处理 | `exception-detect` / `route-explain` | 无命中→异常队列 |
| 供应商匹配 | `supplier-recommend` | RFQ 完成后自动回写映射 |

### 7.4 Agent 应用（事件驱动）

- **自动派活 Agent**：监听「新任务创建」事件 → `classify` → `route-match` → `task-assign` → 飞书推送 → 超时升级（24h→49h→72h）。
- **供应商回写 Agent**：订阅 `rfq.quotation_awarded` 事件 → `supplier-recommend` 校验 → 写 SupplierMap。
- **监控 Agent**：采集路由准确率；跌破 90% 自动降级回人审。
- **多 Agent 协排**：MCP 统一协议，外部业务系统可调 `task.route` / `supplier.recommend`。

> **端到端时序**（一条 SOR）：前端/Agent 发起 `ep route dispatch` → `buyer-resolve`+`classify` 查候选+负载 → `route-match` 命中 R-002 → `task-assign` 写回 → 飞书推卡 → `ep route explain` 查原因。人点按钮与 Agent 事件殊途同归，都走 ep CLI。

## 10. 风险与约束

| 风险 / 约束 | 处理建议 |
