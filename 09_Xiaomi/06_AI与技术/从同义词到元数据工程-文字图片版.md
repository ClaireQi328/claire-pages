# 从同义词到元数据工程-文字图片版

来源：[[从同义词到元数据工程]]

## 一句话提炼

这篇文章的核心判断是：**DataAgent 听不懂人话，通常不是模型不够强，也不是 prompt 不够巧，而是企业没有把业务知识结构化成 AI 可消费的元数据。**

同义词只能解决“同一个东西有不同叫法”的问题；真正让 Agent 查得准、答得稳，需要继续补齐描述、口径、路由、权限、新鲜度、血缘、禁用场景等上下文层信息。

## 文章主线

文章从一个真实翻车场景切入：用户问“上个月交付了多少单？”，AI 识别出了“交付”，但查错了表。原因是同义词只告诉 AI“交付”这个词是什么意思，却没有告诉它在“上个月完成量”这个语境下应该走动作明细表，而不是订单状态快照表。

因此，文章提出一个更底层的结论：让 DataAgent 变准，不是继续堆同义词，而是把数据背后的业务语义和使用规则工程化。

## 三层能力拆解

| 层级 | 解决的问题 | 典型内容 | 局限 |
|---|---|---|---|
| 同义词层 | 解决“叫法” | 销售额、成交额、GMV、营业额 | 只能识别词，不能判断该用哪张表、哪个口径 |
| 描述层 | 解决“边界” | 字段含义、适用范围、业务解释、口径说明 | 能帮助理解，但仍缺少可执行规则 |
| 业务规则层 | 解决“路由” | 场景禁用、默认口径、表选择、权限、时间粒度、新鲜度 | 需要持续维护和治理，不能一次性配置完 |

这三层合起来，才从“词典”升级为“元数据工程”。

## 语义层与上下文层

文章里最重要的框架，是把 BI 时代的语义层和 AI Agent 时代的上下文层区分开：

| 层 | 主要回答 | 服务对象 | 典型能力 |
|---|---|---|---|
| 语义层 Semantic Layer | 指标怎么算 | BI、报表、分析师 | 指标定义、维度、口径一致、血缘溯源 |
| 上下文层 Context Layer | 何时、按什么规则使用 | DataAgent、智能分析系统 | 路由、权限、禁用场景、默认口径、新鲜度、业务规则 |

BI 时代更关注“算得一致”；Agent 时代还必须关注“用得正确”。因为 Agent 不只是展示数据，它会自动理解问题、选择数据、生成 SQL、解释结果，任何一步缺少上下文都会放大错误。

## 真实问题不是词不够，而是业务上下文缺失

文章提到的“交付”案例，本质上是典型的数据路由问题：

- 如果问“当前有多少单在途”，应该查订单状态快照表。
- 如果问“上个月交付了多少单”，应该查交付动作明细表。
- 如果只配置“交付=履约=delivery”这类同义词，AI 会知道词义，但不知道业务场景。

这说明同义词解决的是 NLU 里的词汇识别，而元数据工程解决的是业务语义选择。

## 对 DataAgent 产品的启发

| 产品问题 | 如果只靠模型/prompt | 如果做元数据工程 |
|---|---|---|
| 用户问法多样 | prompt 越写越长，规则互相打架 | 用同义词和描述沉淀稳定语义 |
| 表太多不知道查哪张 | 让模型猜，错了再调 | 用业务规则定义路由和禁用场景 |
| 指标口径争议 | 答案看似合理但不可信 | 用指标定义、默认口径、适用范围约束 |
| 数据新鲜度不一 | Agent 可能拿过期数据回答 | 明确数据更新时间和可用范围 |
| 权限复杂 | 容易越权或答非所问 | 把权限作为上下文层的一部分 |
| 跨域问题 | 语义冲突难以控制 | 按业务域治理词典、描述和规则 |

真正可信的 DataAgent，不是“模型能写 SQL”，而是“它知道什么时候不该写、该去哪写、按什么口径写、写完后怎么解释”。

## 和岗位虾的关系

这篇文章可以作为 [[国际交付岗位虾业务落地]] 的底层补充。岗位虾解决的是“AI 怎么承接岗位动作”，元数据工程解决的是“AI 凭什么理解业务对象”。

| 方向 | 岗位虾 | 元数据工程 |
|---|---|---|
| 关注对象 | 业务动作和流程执行 | 业务语义和数据上下文 |
| 解决问题 | 谁来做、怎么做、做到哪一步 | 查什么、怎么算、按什么规则用 |
| 典型产物 | Skill、任务流、通知卡片、异常处理 | 同义词、字段描述、指标口径、路由规则 |
| 成熟标志 | 能稳定执行岗位任务 | 能稳定理解业务问题 |
| 组合价值 | 让 AI 能执行 | 让 AI 执行得对 |

如果没有元数据工程，岗位虾会变成“动作很快但可能理解错”；如果没有岗位虾，元数据工程会停留在“知识很全但不能自动干活”。真正的业务 AI 落地，需要两者合在一起。

## 对供应链场景的迁移价值

供应链场景天然适合做元数据工程，因为业务里存在大量“同词不同义、同义不同词、口径随场景变化”的情况。

| 供应链概念 | 常见歧义 | 需要补的元数据 |
|---|---|---|
| 交付 | 当前在途、已签收、已发运、已完成履约都可能被叫交付 | 状态定义、时间口径、动作表/快照表路由 |
| 订单 | 销售订单、采购订单、样件订单、调拨单、DN 单 | 单据类型、主键关系、上下游状态映射 |
| 库存 | 可用库存、在途库存、残品库存、超期库存、冻结库存 | 库存类型、库龄规则、可售/不可售边界 |
| 成本 | 采购成本、物流成本、仓储成本、索赔金额、预算占用 | 成本归集口径、币种、期间、责任对象 |
| 供应商 | 法人主体、工厂、联系人、承运商、服务商 | 主数据映射、组织层级、权限边界 |
| 履约时效 | 下单到发货、发货到签收、清关到入库、订单到回款 | 起止节点、异常剔除规则、SLA 分层 |

这些内容如果不结构化，Agent 就只能根据字段名和表名猜；一旦结构化，它才有可能稳定地服务采购、物流、仓储、售后、索赔等复杂场景。

## 元数据工程的落地路线

建议按“先高价值、后全覆盖”的方式推进，而不是一开始就试图治理所有表字段。

| 阶段 | 目标 | 交付物 | 验证指标 |
|---|---|---|---|
| 1. 选高频问题 | 找出业务最常问、最容易错的问题 | Top 问题清单、错误案例集 | 问题覆盖率、错误复现率 |
| 2. 建术语词典 | 解决同义词和业务叫法 | 术语、同义词、业务域归属 | 意图识别准确率 |
| 3. 写字段描述 | 明确字段边界和适用范围 | 字段说明、表说明、样例值 | 字段选择准确率 |
| 4. 定指标口径 | 统一核心指标算法 | 指标公式、维度、时间口径 | 指标一致率 |
| 5. 配路由规则 | 告诉 Agent 不同场景查什么 | 问题类型到表/指标/规则的映射 | 表路由准确率 |
| 6. 做评测闭环 | 持续发现和修正语义缺口 | Golden Set、错误归因、覆盖率看板 | 答案准确率、可解释率 |

## 对你当前工作的启发

如果把这篇文章迁移到你的业务工作，可以直接服务三个方向：

1. **样件订单自动化**：先建立样件订单的状态、单据、审批、SAP 动作、预算占用等元数据，再让 Agent 做预校验、提醒和状态流转。
2. **报价/逆向索赔**：沉淀供应商、物料、价格、索赔原因、责任归属、证据材料的术语和规则，避免 Agent 在相似概念之间误判。
3. **国际交付岗位虾借鉴**：岗位虾要稳定扩展，必须把每个 Skill 背后的业务对象、字段口径、路由规则和异常边界沉淀成上下文层。

## 最终判断

这篇文章真正有价值的点，是把“AI 变聪明”从模型能力问题，改写成了企业知识工程问题。模型是外部变量，元数据是内部资产。谁能把业务知识沉淀得更结构化、更干净、更可治理，谁的 DataAgent 就会更准、更稳、更可规模化。

可以把它和岗位虾文章合并成一个更完整的方法论：

> **元数据工程让 AI 听懂业务，岗位虾让 AI 承接执行；前者解决“理解正确”，后者解决“动作闭环”。**
