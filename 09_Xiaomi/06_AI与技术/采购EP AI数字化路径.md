### 1.2 实现架构

```
用户提问
  ↓
Query 改写（LLM）→ 多角度子查询
  ↓
```

### 1.3 技术选型

| 组件 | 推荐方案 | 选型理由 |

| 重排模型 | bge-reranker-large | 中文重排效果好 |

### 1.4 防幻觉：Grounded Retrieval

**核心原则：每句话必须有据可查。**

| 机制 | 实现 | 目的 |
|------|------|------|
| **来源标注** | 每个片段标注文档名 + 页码 | 答案可溯源 |
| **相关性过滤** | 余弦相似度 < 0.6 的片段丢弃 | 过滤无关内容 |
| **实体一致性** | 答案中的实体必须在检索结果中出现 | 防止数据幻觉 |
| **拒答机制** | 相关度不足时明确说"文档中未找到" | 防止编造答案 |

**答案格式**：

```
EWO 设变询是指工程工作令变更询价，是采购工程师在 EP 系统中发起的变更流程。

📌 来源：EP操作手册_v3.2.pdf#page=45、业务规则文档.md#section=3.2
⚠️ 注意：本文档未提及 EWO 设变询的审批时限，建议咨询采购工程师。
```

### 2.4 防幻觉：Schema 约束 + 指令白名单

**核心原则：AI 只能执行预定义的命令，参数必须通过校验。**

| 机制 | 实现 | 防护目标 |
|------|------|---------|
| **指令白名单** | 只允许 18 条 WAVE1 命令 | 防止生成不存在的指令 |
| **参数 Schema** | 每个参数限定类型/格式/枚举 | 防止参数注入 |
| **实体校验** | 零件号/供应商编码正则 + 数据库验证 | 防止编造不存在的实体 |
| **意图分类** | 查询/操作/闲聊分类，操作类必须二次确认 | 防止误操作 |
| **低温解码** | temperature=0.1 | 减少随机性 |

**参数校验规则**：

```yaml
实体校验:
  零件号:
    pattern: "^[A-Z]{2,4}-[A-Z]{2,4}-\\d{4}-\\d{3}$"  # 如 MOT-ED-2025-001
    validation: "SELECT part_no FROM parts WHERE part_no = '{value}'"
    on_fail: "零件号不存在，请检查格式：XX-XX-XXXX-XXX"
  供应商编码:
    pattern: "^SUP-\\d{6}$"
    validation: "SELECT supplier_id FROM suppliers WHERE supplier_id = '{value}'"
    on_fail: "供应商编码不存在"
  RFQ编号:
    pattern: "^RFQ-\\d{4}-\\d{4}$"
    validation: "SELECT rfq_id FROM rfqs WHERE rfq_id = '{value}'"
    on_fail: "RFQ 编号不存在"
```

### 3.3 编排引擎实现

**技术方案**：

| 组件 | 方案 | 说明 |
|------|------|------|
| 流程定义 | YAML DAG | 声明式定义，版本可控 |
| 执行引擎 | Python + asyncio | 轻量、易调试、可嵌入 |
| 状态存储 | Redis | 支持断点续跑、超时回滚 |
| 人工兜底 | 飞书审批流 | 关键节点嵌入审批 |

**编排 YAML 示例（定点可行性评估）**：

```yaml
name: nomi-feasibility-check
version: "1.0"
input:
  - name: part_no
    type: string
    required: true
steps:
  - id: check_sor
    cli: dx-ep sor info list --material-num {{part_no}}
    next:
      - when: data.state == "ACTIVE"
        goto: check_rfq
      - when: true
        fail: "SOR 未激活，无法继续"

  - id: check_rfq
    cli: dx-ep rfq info list --material-num {{part_no}}
    next:
      - when: data.quote_round >= 1
        goto: check_bidder_review
      - when: true
        fail: "RFQ 未完成报价"

  - id: check_bidder_review
    cli: dx-ep rfq bidder review --rfq-id {{data.rfq_id}}
    next:
      - when: data.research_approved && data.quality_approved
        goto: check_logistics
      - when: true
        fail: "预选评审未完成：{{data.pending_approvals}}"

  - id: check_logistics
    cli: dx-ep rfq logistics --rfq-id {{data.rfq_id}}
    next:
      - when: data.logistics_confirmed
        goto: generate_nomi
      - when: true
        fail: "物流确认未完成"

  - id: generate_nomi
    cli: dx-ep nomi apply generate --rfq-id {{data.rfq_id}} --supplier-id {{data.supplier_id}}
    output: "定点申请单已生成：{{data.nomi_apply_id}}"
```

### 3.4 防幻觉：状态校验 + 失败兜底

**核心原则：每个编排步骤必须验证前置条件，失败必须有明确兜底。**

| 机制 | 实现 | 目的 |
|------|------|------|
| **前置条件校验** | 每步执行前检查数据状态 | 防止在错误状态上执行 |
| **断点提示** | 失败时提示具体断点和原因 | 用户知道卡在哪里 |
| **失败回滚** | 写操作失败自动回滚 | 防止部分执行导致数据不一致 |
| **重试机制** | 网络超时自动重试 3 次 | 应对瞬时故障 |
| **升级机制** | 连续失败升级人工处理 | 防止无限重试 |

|------|--------|

| 端到端执行时间（P99） | < 10s |

### 4.3 规则引擎设计

```yaml
rules:
  - id: sor滞留告警
    trigger:
      event: sor.status_change
      condition: sor.status == "PENDING" && sor.pending_days > 3
    action:
      - type: alert
        target: "{{sor.buyer}}"
        channel: feishu
        message: "SOR {{sor.code}} 已滞留 {{sor.pending_days}} 天，请关注"
      - type: escalate
        when: sor.pending_days > 7
        target: "{{sor.manager}}"

  - id: 价格异常波动
    trigger:
      event: price.update
      condition: abs(price.new - price.old) / price.old > 0.15
    action:
      - type: alert
        target: "price-team"
        message: "零件 {{part.no}} 价格波动 {{price.change_pct}}%，需审核"
```

### 4.4 防幻觉：数据一致性 + 置信度标注

**核心原则：分析结论必须基于数据，不确定的结论必须标注置信度。**

| 机制 | 实现 | 目的 |
|------|------|------|
| **数据源标注** | 每个分析结论标注数据来源和时间范围 | 结论可追溯 |
| **置信度评分** | 低置信度结论标注"⚠️ 需人工确认" | 防止过度自信 |
| **异常检测** | 数据缺失/异常值自动检测 | 防止基于脏数据分析 |
| **对比校验** | 分析结果与历史基线对比 | 发现明显偏差 |

| ③ 询报价域 | 8 种报价类型、报价包、商务条件 | 讨价还价的艺术 |
| ④ 价格构成域 | 材料费→制造费→模具分摊→物流→管理费 | 出厂价是怎么算出来的 |
| ⑤ 采购定点域 | 定点申请、价格变更、移地生产 | 花落谁家 |
| ⑥ 订单与框架域 | 5 种订单类型、框架协议、返利结算 | 签了合同还得执行 |
| ⑦ 合同签署域 | 合同的生老病死 | 白纸黑字 |

**8 条关键业务规则**：

1. 商务条件唯一性：一家供应商零件量产/样件结算只能有一种商务条件
2. 银行信息必填：首次定点时按结算方式决定哪些必填
3. 承兑月份联动：商务前提为现金时无需填，为承兑时必填
4. 放弃报价不可逆：需联系采购工程师重开轮次
5. 样件费计算：样件价格 =（出厂价 + 物流费）× 倍数
6. 价格汇总逻辑：零件层级>1 时汇总下级第一层细项费用
7. 同意按钮限制：返利/大宗申请单的同意只能从首页待办进入
8. 主体切换双重确认：新主体同意后，老主体也需点击同意

### 岗位虾方法论（L3 可复用）

> 先找高频重复场景 → 抽象岗位动作 → 做成可执行 Skill → 接入真实业务流 → 用指标验证价值 → 再串成端到端岗位体系。

| 模块 | 要定义的问题 | 示例（采购域） |
|------|------------|--------------|
| 岗位职责 | 替哪个岗位做哪些事 | 定点虾负责定点可行性核查、预填申请单 |
| 输入对象 | 消费什么业务数据 | 零件号、SOR、RFQ、预选单、物流确认单 |
| 输出对象 | 产出什么可承接结果 | 可行性结论、定点草稿、异常清单 |
| 决策权限 | 哪些自动做、哪些人确认 | 只读 / 建议 / 待确认执行 / 自动执行 四级 |
| 异常机制 | 失败如何处理 | 重试、转人工、派任务、挂起、升级 |
| 指标闭环 | 怎么证明持续有价值 | 节省工时、准确率、异常率、履约时效 |
