1.0

基本盘 · 一分钟版

第一次接触这个项目，看完这一节就够了。

🧭 它是什么

样件订单自动化数字助理：Agent 按固定链路完成「查需求 → 分组 → 生成确认页 →（人拍板后）下单 → 日报」，人只在两个节点拍板——一品一点的核对和一品多点的选供应商。

🚫 它不碰什么

价格判定（EP 在 create-order 内部匹配台账判价）；供应商选择（一品多点必须人选）；需求导入质量（散件导入已移交石海琳团队）；试制价格对比（等价格小 AI 就绪，已搁置）。

⚖️ 黄金原则

价格交给 EP，供应商留给人。绝不静默下单；没拿到一品多点的 selections 就不下单；草稿不是失败，但不重试——去 EP 页面人工确认。

⚠️
三条最容易搞错的前提
① 查询结果的数字口径统一用「组」，不用「条」；②「标准环境」是网关规格，判断生产实例只看 EP_ENV；③ 飞书群卡片只做通知，不能点确认，确认一律回 AgentSpace 对话框。

AI 怎么做 · 四层架构与五个 Skill

渐进式落地：CLI → Skill → Agent → 平台，四层递进、逐层验证；寄生增强，不替换 EP 系统。

四层能力架构（L1–L4）

L1
CLI · 原子能力层
EP 能力下沉为命令行，先验证「自动能不能做」。dx-ep sapo 域：query-ready / create-order / submit-list / import-json。
→
L2
Skill · 场景封装层
命令流封装为可复用技能，输入输出标准化，单环节独立可用。共 5 个 Skill（见下表）。
→
L3
Agent · 智能编排层
技能串成业务流：自然语言发起 + 定时任务 + 人工拍板。人只留 2 个拍板点。
→
L4
平台 · 业务承载层
飞书工作台执行日志唯一权威 + 需求进度表实时刷新 + 三层留痕 + 群通知分层。

五个 Skill 全景

Skill职责读写触发条件状态

demand-check试制需求：检查 PASS / WARN / FAIL，通过后确认导入写试制需求提交搁置 等价格小 AI

确认页与四种下单状态

📄 确认页两种

一品一点页（one_url）：同组即一个订单，看一眼即可，无需操作。
一品多点页（multi_url）：需要人工——勾选要下的零件、选供应商、点「确认执行」，页面输出一段 JSON（批次号 + kind=multi + selections），原样贴回 AgentSpace。

🚦 下单结果四状态

成功 已自动提交审批 → 说「已提交审批」
草稿 价格非最低价，EP 自动存草稿 → 必须明说哪几条、什么原因，去 EP 页面人工确认，不重试
失败 审批校验异常等，如实转述原因
待选/无供 被拦截，说明需人工介入

六条铁律级业务规则 · 方案的地基

📅 60 天窗口

要求到货日期超出 60 天的需求剔除，不进确认页、报告剔除数；到货日期为空必须单独计数+告警，不能静默吞。

🔑 六字段分组键

originType|brNo|brLineNumber|companyEntityId|supplierId|buyerId；供应商取 supplierOptions 去重稳定排序。

🚦 多供不静默

一品多点全部进确认页人工选，不按首供自动下单；同键多需求合并一条 create-order，--pr-ids 逗号拼全部成员。

💰 价格归 EP 判

create-order 没有 --price-type 参数；EP 内部匹配台账：最新价=最低价 → 自动提交；最新价≠最低价 → 存草稿 + 「存在更低价，需人工确认」。页面 priceType 只是只读诊断标签。

📝 草稿 ≠ 失败

草稿是 EP 判价拦下的，需求号已被占用（实测与 query-ready 重叠为 0），重下无效；去 EP 页面人工确认提交。

🧮 采购员真名解析

buyer_name_concurrency ≤ 4——实测并发 10 时 CLI 全部限流失败；与分页拉取并发（默认 5）是两个参数。

2.1

怎么做 Skill · 从业务环节到可调用能力

Skill 不是「一段提示词」，而是一个有触发条件、有输入输出契约、有守门、能单独验证的业务原子。这套做法可复用到任何 EP 场景。

2.1.1 先定粒度：一个 Skill 该有多大

判据一 · 有独立触发点

用户会单独说「查一下」「下这一批」「出个日报」。能被一句话单独唤起，才配独立成 Skill。

判据二 · 有明确输入输出

输入是可描述的 JSON / 参数集，输出是结构化结果。说不清边界的，说明业务还没想清楚。

判据三 · 能单独验证

不跑全链也能验对错：查询可只读跑、下单可 --plan 预演。验不了的，不敢上线。

❌ 拆太粗

把「查询 + 下单」合成一个 Skill：无法在下单前插入人工拍板，等于把最危险的动作变成黑盒。这就是必须拆开的理由。

❌ 拆太细

把「拉取 / 归一化 / 分组 / 上传」拆成四个 Skill：契约成本陡增，上下文要在四次调用间搬运。它们是一个 Skill 的内部步骤。

2.1.2 SKILL.md 的七段骨架

段落写什么写不好的后果
① 触发条件何时该用我、何时不该用我；关键词与前置判断被错误唤起，或该用时唤不起
② 输入参数、类型、必填/默认值、来源（上环节产物 or 用户输入）Agent 猜参数，静默用错数据
③ 输出契约固定字段 status / stage / batch_id / summary / details / outputs / message编排层取不到字段，工作流断链
④ 执行步骤编号步骤、可复现；标明哪步只读、哪步写换人换会话就跑不出同样结果
⑤ 守门顺序env_guard → env_check → auth_mismatch，逐层拦截带病执行，错误在最深处才爆
⑥ 降级与错误每种异常的正确动作：停手 / 重试 / 降级 / 转人工Agent 自由发挥，重试造成重复下单
⑦ 示例一次正确调用 + 三类异常返回的真实样例文档好看但跑不通
# 示例：demand-query 的输出契约（编排层唯一依赖的接口）
{
  "status":   "ok | error",
  "stage":    "env_guard | env_check | auth_mismatch | query | group | upload | done",
  "batch_id": "20261013-02",
  "summary":  { "total": 1434, "one_group": 1292, "multi_group": 71, "no_supplier": 71 },
  "details":  [ ... ],        # 明细可达数 MB，禁止整段打印/回显
  "outputs":  { "one_url": "...", "multi_url": "...", "json_path": ".output/query-result-*.json" },
  "message":  "可原样转述给用户的一段话"
}
📌
message 字段是给 Agent 的「嘴」——Agent 只允许原样输出 message，最多补一行交互提示。格式约束写进代码，行为约束写进提示词。这条规矩直接来自「审查 Agent 对轰 5 版」的教训。

2.1.4 公共层怎么收敛

🎯 只留一份

FDS 上传、CLI 调用封装、群通知、progress_sync 各抽一个模块，放在唯一的 common/。v2 之前实测：三份 common 目录 12 个文件有 11 个字节级相同，FDS 签名实现存在 4–5 份。

🔁 改公共层 = 全量回归

公共逻辑没有「局部影响」。改一处必须三个 Skill 全跑四连自检。曾经的坑：webhook / base token / table id 三处硬编码同一值，改一处漏三处。

✅
判断标准
同一个值或同一段逻辑写第二遍之前先问：它会不会变？会变就必须抽出来。不变的常量可以复制，会变的配置绝不能复制。

2.1.5 怎么写对：三层验证

层级怎么验通过标准
① 静态python3 -m py_compile 全目录 + 依赖 import 检查无语法错、无缺失模块
② 契约五类用例：正常 / 空结果 / 部分页失败（fetch_error 非空）/ 权限不足 / 身份不匹配每类都有确定返回与正确 stage，不抛裸异常
③ 真实只读链路真跑；写操作先 --plan，再由真人触发跑一单小批量订单号真实产生；草稿能在 EP 页面看到并人工提交
⚠️
0 条结果不代表没需求
CLI 版本旧、登录态失效、网关不通，都表现为「0 条」而不是报错。Skill 必须能区分「真的没有」和「环境坏了」——先跑 2.2 的自检排除环境，再说「暂无需求」。

对象：agent-space.ev.mioffice.cn。v2 包结构 = Agent 设定 md + 三个 Skill 目录 + prototype（视觉参考，不参与运行）。

前置条件 · 四件事不满足就别开始

P0 B 级 API 权限

实测生产报 Forbidden: insufficient role for B level API，create-order 在生产会被拦。需找 EP 侧申请。

P0 触发人身份

下单前硬校验「CLI 登录账号 == 触发人」。若容器用共享服务账号登录 dx-ep，全部下单都会被 auth_mismatch 拦掉。必须先确认 dx-ep 以触发人身份运行。

P0 FDS 凭证走环境变量

config.json 不含密钥（v2 已改）；FDS_ACCESS_ID / FDS_ACCESS_SECRET 必须注入。容器里读不到个人电脑的凭证是常态，配好前页面只能本地生成、链接不可分享。

P1 EP_ENV 与定时任务身份

EP_ENV=prod 时 FDS / 群 webhook / 留痕 base 缺一项即拒启动（env_guard）。日报 19:00 定时跑不注入触发人——查询/日报缺省 system 身份，需显式决策。

2.3

部署运行 · 六个必须盯住的点

这些不是「最佳实践」，是上线后一定会撞上的现实。

① 身份链 · 最容易全军覆没

CLI 登录账号必须等于触发人。查询可以 system 身份，下单不行。容器用共享账号 = 所有下单被拦。上线前先跑一次 dx-ep user info query 确认「我是谁」。

② 密钥 · 只从环境变量读

FDS AK/SK 一律环境变量注入，配置文件中不出现。凭证错一个字符的表现是「签名不匹配」，会浪费三轮排查——别手敲，别贴进对话。

③ 容器行为 · 与本地不同

容器里 CLI 会误判「有浏览器」，走需要本地回调的登录流程，报 20029 重定向错误。必须 GARAGEHUB_AUTH_MODE=device。容器也没有个人电脑上的 FDS 凭证。

④ 定时任务 · 没有触发人

19:00 日报、9:30 查询都是 system 身份。需要写操作时必须显式注入 EP_SAMPLE_ORDER_CREATED_BY 或决策为只读。

⑤ 体积与并发 · 两条硬上限

结果 JSON 实测 3.9MB，禁止整段 cat；采购员真名解析 buyer_name_concurrency ≤ 4（并发 10 全部限流失败）；分页拉取并发默认 5，与服务端 page-size 100 配套。

⑥ 通知接线 · outputs 是数据接口

html_url 必须固定在 outputs 字段——编排层按位置取值。卡片只做通知与引流，不能回调确认，确认一律回 AgentSpace。

守门与异常速查（stage 语义）

返回 / 现象含义正确动作
stage=env_guardEP_ENV=prod 但必配环境变量缺失，或取值非法停手，让用户去环境变量页补齐，不重试
stage=env_check连 dx-ep 登录凭证里都解析不出操作人让用户 dx-garagehub auth login 或注入 AGENTSPACE_USER；不替登录
stage=auth_mismatchCLI 登录账号 ≠ 触发人必须触发人本人登录后重试；禁止以他人登录态冒名下单
insufficient role / Forbidden缺 B 级 API 权限找 EP 侧申请，不是 Agent 的问题
fetch_error 非空部分页拉取失败，结果可能不完整降级给出已拿到的数据，明说可能不完整
「已推送过，跳过重复推送」防重生效（同批次两分钟内不重复推）不重跑；若同批数据被跑两遍，查是定时+手动双触发
上传失败查询/下单会降级为只输出本地路径告诉用户页面在本地、链接别人打不开
2.4

Agent 要具备什么能力 · 六项最小能力集

同一个模型，差距在「会不会守住边界、会不会管上下文、会不会说实话」。以下六项缺一项，链路就会漏。

🧠 ① 任务理解与拆解

把「把今天能下的单都下了，供应商别动」翻译成：查询 → 过滤 → one 直接下 / multi 交人。理解不了就问，不猜。

🛠️ ② 工具编排

知道该调哪个 Skill、传哪些参数、先 plan 后执行。知道自己能做什么、不能做什么——没有的能力如实说没有，不硬编。

🚦 ③ 状态守门

读得懂 stage，并按 stage 做正确动作：env_guard 停手、auth_mismatch 换人登录、草稿不重试。不做「报错就重试」的条件反射。

💾 ④ 上下文预算

只取必要字段，不整段读 3.9MB 结果；长结果用摘要 + 分页 + 落盘路径；跨轮对话记住批次号与已确认范围，不重复询问。

💬 ⑤ 表达与确认

四段式回复（结论 / 链接 / 覆盖 / 异常）；数字口径统一用「组」；下单前必给 plan 摘要并等明确确认，绝不静默下单。

🩺 ⑥ 自诊断与降级

六项环境自检（Python / dx-ep 版本 / 登录态 / 网关 / 环境变量 / FDS）；拿不到链接说原因；能力缺失时给替代路径，不假装成功。

能力 × 场景 × 缺失后果

能力在样件订单场景的具体表现缺了会怎样
任务理解「只下试制的、普利司通的」→ 拆成 source + supplier 双条件筛选理解偏差，下一批不该下的单
工具编排query → filter → plan → order → report，每步选对参数跳过 plan，或把 query 结果当 order 输入格式
状态守门auth_mismatch 立即停，草稿标注「去 EP 页面确认」重试导致重复提交；把草稿说成失败
上下文预算结果落盘只回摘要与路径；批次号跨轮记忆上下文爆掉、截断、重复询问
表达与确认四段式 + 明确「确认执行」才下单口径混乱；误以为已下单 / 静默下单
自诊断0 条先查环境；FDS 失败跑 fds_doctor把环境故障说成「今日无需求」
🎛️
三个决策点，决定 Agent 好不好用
何时问：范围不明、涉及多供、价格异常时必须问；何时做：只读查询、已有明确确认的写操作直接做；何时停：身份不匹配、环境缺失、结果不完整时立刻停并说明。
记住这条底线：宁可少做一步，不可做错一步。
2.5

能力落地 · 命令 / 筛选 / 口径速查

Agent 的能力最终要落到三件事：会敲哪条命令、会把人话翻成哪个参数、会怎么回话。这三张表就是能力的具体形态。

命令速查表

命令作用关键注意
python3 demand_query.py --config config.json查询可下单需求，生成确认页并上传 FDS数据量大时加 --json；绝不 cat 整个结果 JSON（实测 3.9MB，会截断落盘）

结果口径 · Agent 回复模板四段式

第一段 结论：一句话说清多少组可直接下单、多少组需选供应商，带批次号。数字口径统一用「组」，不混用条和组。
第二段 链接：one_url / multi_url 两个可点链接各一行，标注各自要做什么；拿不到链接要写明原因，不许用「详见 AgentSpace」代替。
第三段 覆盖：本次涉及哪些采购员、多少零件（供应商数量只在追问时给）。
第四段 异常与下一步：只在真有异常时写（不写「无异常」占位）；fetch_error 非空必须说明结果可能不完整；告诉用户把确认页导出的 JSON 贴回来。

🔑 坑 1 · FDS 密钥错一个字符

事：上传失败，连环排查三轮。中途几轮测试「成功」——因为那次读的是配置文件里的真值，不是手敲的值。
根因：手敲凭证 + 验证来源与使用来源不一致。
教训：必须逐字符精确的东西绝不手敲；验证时确保「测的东西」和「用的东西」同源。

🧱 坑 2 · 容器 20029，四轮排查

事：AgentSpace 容器里跑 CLI 永远报「重定向 URL 错误 / 20029」，本地一切正常。先后怀疑登录态、settings.json、CLI 版本，全错。
根因：翻 ep-agno 源码才发现容器里 CLI 误判有浏览器，走了需要本地回调的 browser flow。
对策：容器强制 GARAGEHUB_AUTH_MODE=device。C

📉 坑 3 · CLI 契约跳变，造出 4900022810

事：1.0.7 稳定版移除 sapo 域；beta.3 源码确认 buildBody 无 createdBy，服务端却新增必填校验——升级无解、文档没写。
对策：锁版本 env-check + 翻源码 + 降级通道（读 credentials.json 的 access_token 直连 garagehub API，body 带 createdBy）→ 真实订单 4900022810 创建成功。
教训：CLI 是外部契约，不能假设稳定；三板斧应成为所有 CLI 依赖型 skill 的默认动作。

🖥️ 坑 4 · 静态正确 ≠ 渲染正确

事：确认页布局错乱，HTML 结构检查完全正常。根因是 td 上的 display:flex——单元格一旦不是 table-cell 就脱离表格布局算法。
教训：静态检查看不出的问题，只有真渲染才暴露；环境受限无法验证时，明确说「我无法验证渲染」，别反复猜然后下「修好了」的结论（事后补装 headless chromium 一次定位）。

🧩 坑 5 · rowspan 2619 处脆弱

事：主行 9 个 td 全部 rowspan=N，rowspan 出现在 2619 处；与 CSS display、单元格数量一变就出错，修 colspan、加 min-width 都不是根因。
对策：直接取消候选行和 rowspan，改主行 10 个 td、候选装第 10 列 flex 竖排——rowspan 归零，问题一次性消失。
教训：结构简单优先；反复出问题的机制就换掉，别修。

🎯 坑 6 · 237 条需求在做无效操作

事：确认页让用户选 priceType，但 create-order 根本没有 --price-type 参数，EP 不接收——237 条需求（占多供应商组 81%）在选一个「选了也没用」的价格。

九条可复制经验 · 带走的才是你的

来源：踩坑全记录 09-23 经验教训章。这九条不限于样件订单，适用于所有 Agent/Skill 建设。

1 · 输出强约束

统一 status/stage/batch_id/summary/details/outputs/message；Agent 只允许「原样输出 message + 至多一行交互提示」。格式约束写进代码，行为约束写进提示词。

2 · 契约三防

外部依赖（CLI/API）锁版本、翻源码、留降级通道。不能假设外部契约稳定。

3 · 授权地图

把「用什么身份、能干什么」画成地图前置确认；凭证从配置文件读，绝不手敲。

4 · 公共收敛

公共层只保留一份；改公共逻辑必须全量回归，别让「改一处漏三处」反复发生。

5 · 边界先测

平台能力边界（回调/凭证/容器行为）先探测再设计，别拿本地经验推容器。

6 · 字段分口径

字段名、字段类型、中英文口径三张皮；映射必须按类型处理（人员/日期/多选/附件各有形态）。

7 · 通知即接线

html_url 固定在 outputs 字段——「输出契约」是编排层的数据接口，字段位置稳定，工作流才稳定取用。

8 · 审查喂料

审查 Agent 要给清单和判据，不给「自由找茬」；否则互相找茬跑偏，改了又改。

9 · 先跑通

先跑通最小闭环再优化。不在架构上追求完美——业务闭环通了才有资格谈收敛。

为什么必须上升到系统层 · 样板间住不进人

样件订单证明了一件事：AI 能端到端跑完一条业务链。但它证明不了第二件事：这套东西能不能变成整个采购系统的能力底座。

① 它只是一个切片

样件订单在 EP 里是订单履约域的一条支线，上游有需求、寻源、定点、合同，平行有价格、供应商、主数据。这条链跑通，不代表其他六个域能复用它的任何一层——除了踩过的坑。

② 单点最优 ≠ 系统最优

为了一个场景做到极致，很容易做出「只服务这个场景」的实现：硬编码的规则、私有字段、专用页面。每多一个这样的样板间，系统就多一处不可复用的资产。

③ 各自造 Agent = 重复建设

七个业务域各自找模型、各自写 Skill、各自定义口径，结果是：七套语义、七份权限、七种交互、七条成本线，治理无从下手，投入边际成本不降反升。

维度场景级（今天的样件订单）系统级（要去的方向）
目标这条链能不能自动跑完任意业务链能不能被按需拼出来

失败模式这个场景不好用七个孤岛 + 口径分裂 + 治理失守

4.3

什么是系统级原生 AI · 六条判据

场景级看四条（能不能听懂、有没有原子、上下文够不够、结果可不可验）；系统级必须再加两条，否则规模一上来就崩。

① 意图即接口 · 跨域版

用户说的是业务目标（「这个月 MS11E 的样件齐了没，缺的补上」），系统要能跨需求、订单、履约三个域自己组织。反例：一句话只能映射到一条预置链路。

② 能力即原子 · 目录版

不只是「有原子」，而是有一张可发现、可调用、有契约、有 SLA 的能力目录。新场景来了先查目录，查不到才新建。反例：原子散落在各团队仓库，谁也说不清系统一共能干什么。

③ 上下文自足 · 对象版

上下文不是「会话记忆」，是业务对象的状态：这张需求单、这个 RFQ、这个供应商现在到哪一步。系统级要求同一对象在全域只有一份状态。反例：跨页面靠复制粘贴、跨系统靠 Excel。

④ 闭环自证 · 全域版

任何一次 AI 动作都能回答：依据什么数据、用了哪条规则、谁批的、结果对不对。系统级要求这些是统一采集的，不是每个场景自己写日志。

⑤ 治理内建 系统级新增

谁能用、能做什么、不能做什么、做过的能不能查——必须是系统能力，不是场景自觉。七个域各写一遍权限校验，等于没有权限。

⑥ 边际递减 系统级新增

第 1 个场景花 3 个月，第 5 个场景应该 ≤ 2 周。接入成本不降，说明你做的是一堆项目，不是一个系统。这是判断「系统级」最硬的一条。

4.8

三条系统级红线 · 比技术难点更致命

这三条一旦踩了，不是某个功能不好用，是整个方向走偏，且很难回头。

🚫 红线一 · 各域自建 Agent

七个业务域各招一拨人、各选一个模型、各写一套 Skill。半年后你会拥有七个互不相通的助手，口径、权限、成本三线全部分裂。
正解：能力由平台供给，场景只做编排。

🚫 红线二 · 让模型直连生产写操作

「AI 判断完直接改数据」看起来很爽，一旦判错就是数据事故，且无法归因。
正解：写操作必须过策略层 + 留痕 + 可回滚；高风险动作强制人工签核。

🚫 红线三 · 语义层没建好就铺场景

每铺一个场景就固化一批私有口径，铺得越多、清理越贵。这是典型的技术债复利。
正解：字典可以薄，但必须先有；新场景不许绕过。

4.10

组织与投入 · 谁建地基、谁盖房子

系统级原生 AI 失败，八成不是技术失败，是分工失败：没人负责地基，所有人都在盖房子。

🏗️ 能力供给方

EP 平台 + CLI 团队。负责原子、契约、目录、SLA、策略中心。KPI 应该是「被复用次数」，不是「发了多少个接口」。

🧩 场景编排方

业务 PM + FDE（前端 + 数据 + 工程一体）。负责把域能力拼成业务闭环、定义验收标准。KPI 是接管率与一次通过率。

⚖️ 治理方

数据 + 安全 + 架构。负责口径主权、权限模型、审计与合规。KPI 是口径一致率与零越权。

投入模型 · 一次性 vs 边际

投入类型内容性质回本逻辑

场景投入某域编排、交互、业务规则可变、随场景数线性增长（应递减）靠省工时 / 减少返工

4.11

必须先定的七个问题 · 谈不清就只能在 demo 里跑

这些不是技术问题，是责任、边界与主权问题。系统级比场景级更尖锐，因为影响面是全公司。
问题为什么必须先谈可选的答案
① 决策边界哪些判断永远不能交给 AI？价格承诺、供应商准入、合规例外——越界就是事故列一张「永不让渡清单」，写进策略中心
② 责任归属AI 判错了谁负责？现在靠「人拍板」兜底，N3 之后拍板会变少关键节点人工签核 + 完整决策留痕 + 明确的兜底人
③ 口径主权语义层是新时期的「主数据项目」，没人认领就会二次分裂指定唯一 owner + 变更评审机制 + 新场景不得绕过
④ 能力归属原子谁来建、谁来维护、坏了谁修、SLA 谁承诺平台统一供给，业务提需求；按「被复用次数」考核
⑤ 评估标准接管率高不等于价值高；准确率高不等于省时间接管率 + 一次通过率 + 节省工时 + 单均成本，四者同看
⑥ 交互终态对话框是终态吗？还是嵌在 EP 里的副驾？还是根本没有界面？按场景定：例行操作走副驾，例外处理走对话，结果走群
⑦ 投入节奏地基先行意味着前期「看不到业务效果」，能不能接受绑定业务目标立项；每个阶段用 Gate 证明没走偏

一句话收口
原生 AI 不是一个功能，是一套让 AI 能自己完成判断的系统设计：词有定义、动作有原子、对象有状态、边界有策略、结果有度量、接入有递减。
样件订单已经证明「AI 能跑腿」；系统级要证明的是——「换一个业务域，AI 依然跑得动，而且越来越快」。前者是样板间，后者才是整栋楼。
