基本盘 · 一分钟版

🧭 它是什么

样件订单自动化数字助理：Agent 按固定链路完成「查需求 → 分组 → 生成确认页 →（人拍板后）下单 → 日报」，人只在两个节点拍板——一品一点的核对和一品多点的选供应商。

🚫 它不碰什么

价格判定（EP 在 create-order 内部匹配台账判价）；供应商选择（一品多点必须人选）；需求导入质量（散件导入已移交石海琳团队）；试制价格对比（等价格小 AI 就绪，已搁置）。

⚖️ 黄金原则

价格交给 EP，供应商留给人。绝不静默下单；没拿到一品多点的 selections 就不下单；草稿不是失败，但不重试——去 EP 页面人工确认。

⚠️
三条最容易搞错的前提
① 查询结果的数字口径统一用「组」，不用「条」；②「标准环境」是网关规格，判断生产实例只看 EP_ENV；③ 飞书群卡片只做通知，不能点确认，确认一律回 AgentSpace 对话框。

场景痛点 · 为什么做这件事

来源：2026-04-27 需求优化讨论会纪要（P-01～P-07）、07-13 流程对比（改造前 / 改造后）、09-21 全流程方案总结、10-10 验证会实测口径。
💡
一句话说清痛在哪
不是「EP 难用」，而是一条需求身上的动作没分层——查询、抄字段、建单、汇总这类搬运占了绝大多数，真正需要人判断的只有「一品多点选谁」和「价格异常怎么办」，两者被混在同一段人工里，于是人既做机器的事，也腾不出手做判断的事。

五类痛 · 逐条对上现场证据

编号痛点现场是怎么发生的代价（历史口径）根子在哪
P-01 量大人肉
吞吐		 每天手动查询 100+ 条可下单需求 → 逐条在 EP 建单 → 字段靠复制粘贴；一个批次能有 4699 条原始需求、分 47 页拉取。 ~30 分钟/单 · 重复操作占工程师 30%+ 时间 · 日耗约 2 小时 没有批量入口，把人当批处理机用

数据		 价格为 0 却含软模费的无效记录；同零件号 + 同供应商 + 同价格的重复项；同一供应商同时挂定点价与快速定点价两条价。 清洗后可多释放约 40% 的自动下单场景 数据质量没有 owner，脏数据由下游兜底
P-04 维度缺
契约		 项目名称 / 车型只写在备注文本里；米Tab 的项目编码没映射到采购界面；下单不带送货地，而物流价按工厂不同。 采购反复回问、成本口径不准；预算用的项目编号被误当采购维度 上游字段没进 EP 的字段契约
P-05 追踪靠表
状态		 每天手工统计订单执行情况；进度散在群聊和 Excel；升版 V1 / V2 撤批时机不当。 日报靠人攒、需求方追着采购员问；下游订单失效、无法收货 状态没有单一事实源

三笔账 · 痛点到底贵在哪

⏱ 时间账

  • 100+ 条/天 × ~30 分钟/单，一个人一整天只够干这一件事。
  • 早期低配流程（捞需求 → 校验 → 下单 → 出周报）每周 2–3 小时，只是「能跑」，谈不上规模。
  • 人力没法弹性扩：项目一上量，只能靠加班扛。

🧠 判断账

  • 真正需要人拍板的只有两件：一品多点选谁、价格异常怎么处理。
  • 改造前让用户在页面选 priceType——实测 create-order 根本没有 --price-type，237 条（占多点组 81%）在做无效判断。
  • 无效判断比没有判断更贵：它消耗注意力，还制造「我确认过了」的错觉。

💸 风险账

  • 漏单 / 错单：一条需求被静默跳过，可能停掉一条试制线。
  • 升版：V1 / V2 撤批时机不对，下游订单直接失效、无法收货。
  • 无供需求：不显式分流，就会被当成「已处理」。

痛点的共同结构 · 三类动作被混成一段人工

🖥 机器该做的

  • 查：拉可下单需求、过滤过期
  • 填：字段搬运、拼装订单
  • 汇总：日报、执行结果、留痕

🗂 数据该给的

  • 价格：由 EP 台账匹配，人不参与
  • 供应商：一品多点给候选项
  • 送货地 / 项目 / 车型：进字段契约

🧑‍⚖️ 人该拍的

  • 一品多点选哪家
  • 价格异常要不要认
  • 这批要不要跳过
📌
所以方案只做前两层，第三层坚决留给人——这正是「价格交给 EP，供应商留给人」的来源。反过来，凡是把第三层也自动掉的方案，都会在下单事故里被打回来。

⚖️
设计判断：上游可以不同，下游必须同构
不要把 MIPEC 和研发样件硬合成一个系统——两套业务节奏、两个责任主体，合并只会互相拖慢。真正要统一的是进入 EP 的字段契约与状态机。否则每接一条新上游，就要把下游重做一遍，这正是「做了很多项目、却没做成一个系统」的根源。
📌
现状边界：MIPEC 侧目前仍以导出 / 线下表为主，接口自动拉取尚未落地；研发样件侧的导入能力已由石海琳团队自行维护。Agent 的起点是 EP 需求池，不是上游系统——这条边界不写清，后面所有「为什么不全自动」的讨论都会跑偏。

一句话结论
改造的不是「下单」这一个动作，而是把两条上游 + 一道价格判断 + 一条执行链从人工搬运变成规则接力。只做下单自动化，最多省 30%；上游不标准化，永远省不干净。

① 总览：一天的工作长什么样

BEFORE · 人工搬运
  • 要数据：从 MIPEC 导出，再找石海琳团队要研发样件清单，两张表手动拼
  • 补字段：项目 / 车型写在备注文本里，缺了就群里追问
  • 去重靠眼看：同一零件在不同表里反复出现，重复建单是常态
  • 判价格靠经验：翻台账，有价 / 无价 / 一品多点全凭记忆判断
  • 逐单点：47 页需求一页页过，一天约 2 小时 耗在重复操作
  • 追进度靠问：Excel 记状态，研发工程师在群里问「我的单下了吗」
人的角色：搬运工 + 判断者 + 执行者，三件事同时做，哪件都不能少。
AFTER · 规则接力
  • 收数据：MIPEC 接口 / 研发样件模板两条通道进 EP，不再手工导
  • 事前拦：导入即校验，缺项目 / 车型直接拦截并回问，不往下走
  • 机器分组：六字段键分组，4699 条原始过滤为 1434 条有效
  • EP 内部判价：有价自动、无价建定价任务、一品多点强制人确认
  • 先预演再下单：--plan 看清将生成几张单，确认后自动执行，一批约 60 秒
  • 自动留痕：日报 + 需求进度表 + 自然语言查询，谁都能自己看
人的角色：审核者 + 拍板者，只在两处出现——核对一品一点、选一品多点供应商。

口径说明：4699 不是「错误需求」，是过滤前的原始条目；1434 是 60 天窗口内的有效需求。95.0% = 1363 / 1434，指本批有效需求的自动处理率，不等于「所有订单永久全自动」——一品多点、无价格、异常仍会落到人工。

④ 三个没有被自动化的地方（也是三条责任边界）

仍然人工为什么不能自动谁负责
一品多点选供应商需求方常填不准供应商，选错就是下错单；这是责任不是计算。291 → 71 组已把量压到最低，但这 71 组必须人选订单管理员 / 采购员
无价格与异常价格台账没有有效价，或存在更低价、软模费、重复记录；机器无法替人承担定价后果触发定价任务 → 采购员
协议与合同条款、账期、多方签署、补充协议，本质是商务谈判与法务确认采购工程师 + 法务（EP 合同管理承接）
🚦
自动化的边界不是技术边界，是责任边界
凡是「谁签字谁负责」的环节，都不该由 Agent 静默完成。所以方案里才有两道硬闸门：需求锁定（不锁不准往下走）与下单前人工确认（A 全自动路径也要留痕）。

⑤ 参考 EP 合同管理：把链路补到「协议」这一层

EP 合同管理已有「合同清单管理 → 关联定点申请单 → 定点价格协议 / 框架协议 → 模板同步 → 终版上传 → 供应商确认 → 审批」的完整链路，样件订单不需要重造，只需要读它的状态、写回它的实绩。
EP 合同管理已有能力现在样件订单怎么用建议补上的一步
合同清单管理
可按项目 / 定点申请单 / 供应商查		人工出问题时才去查有没有合同，属于事后追溯下单前置校验：按「零件 + 供应商 + 工厂」查是否存在有效协议
定点价格协议
价格来源的法定依据		EP 内部判价，能拿到可执行价，但不区分价格来自协议还是暂作价给价格打「来源标签」：协议价 / 暂作价 / 临时价，日报可按来源统计
框架协议 V2 · 价格中心
台账与框架合并、跨工厂跨供应商、已拉动数量		样件订单取价后，拉动量没有回写框架实绩回写：下单成功后把数量回写「已拉动数量」，框架看到真实消耗
合同审批 + 供应商在线确认
审批流、待确认状态		样件小额订单是否要签合同，目前靠人判断免签阈值：低于阈值直接下单，超阈值自动挂起并触发合同流程
合同变更 / 补充协议需求升版（V1/V2）时线下改，容易和合同脱节升版触发协议复核：价格或范围变了，联动合同变更而不是只改订单
直采合同清单
模板唯一入口、版本统一		样件协议模板各自找、版本不一直接复用合同模板库，Agent 只填变量，不生成自由文本

① Before · 价格不可追溯

台账上有个数字就下单，这个数字来自哪份协议、是否覆盖当前工厂、是否在有效期，没人说得清。

② After · 价格可执行

EP 内部判价，Agent 做三态分流，价格能落地、能下单；但仍停留在「能执行」，没回答「凭什么」。

③ Next · 协议驱动

下单前「三查」：有无有效协议、协议价是否覆盖该供应商与工厂、是否在有效期。全通过才自动下单，并回写拉动量。

🧭
这一层的意义
合同管理不是「另一个模块」，它是样件订单的价格合法性底座。Before 的根问题是「价格从哪来」没人说得清；Next 要把协议 → 价格 → 订单 → 拉动量串成一条可审计的链——这条链打通，自动下单才从「跑得快」变成「跑得对」。

⑥ 一句话记住这次改造

✅ 能自动的

搬运、映射、分组、匹配、执行、留痕——规则明确、可批量、可回放的事。

🙋 不能自动的

选供应商、例外定价、协议谈判——谁签字谁负责的事。

⚠️ 顺序不能反

先有协议与价格，再有自动下单。顺序反了，就是「自动化地犯错」，而且错得更快。

📅 60 天窗口

🔑 六字段分组键

🚦 多供不静默

💰 价格归 EP 判

📝 草稿 ≠ 失败

草稿是 EP 判价拦下的，需求号已被占用（实测与 query-ready 重叠为 0），重下无效；去 EP 页面人工确认提交。

🧮 采购员真名解析

buyer_name_concurrency ≤ 4——实测并发 10 时 CLI 全部限流失败；与分页拉取并发（默认 5）是两个参数。

2.1

怎么做 Skill · 从业务环节到可调用能力

Skill = 有触发条件、有输入输出契约、有守门、能单独验证的业务原子。

2.1.1 先定粒度：一个 Skill 该有多大

判据一 · 有独立触发点

用户会单独说「查一下」「下这一批」「出个日报」。能被一句话单独唤起，才配独立成 Skill。

判据二 · 有明确输入输出

输入是可描述的 JSON / 参数集，输出是结构化结果。说不清边界的，说明业务还没想清楚。

判据三 · 能单独验证

不跑全链也能验对错：查询可只读跑、下单可 --plan 预演。验不了的，不敢上线。

❌ 拆太粗

把「查询 + 下单」合成一个 Skill：无法在下单前插入人工拍板，等于把最危险的动作变成黑盒。这就是必须拆开的理由。

❌ 拆太细

把「拉取 / 归一化 / 分组 / 上传」拆成四个 Skill：契约成本陡增，上下文要在四次调用间搬运。它们是一个 Skill 的内部步骤。

2.1.2 SKILL.md 的七段骨架

段落写什么写不好的后果
① 触发条件何时该用我、何时不该用我；关键词与前置判断被错误唤起，或该用时唤不起
② 输入参数、类型、必填/默认值、来源（上环节产物 or 用户输入）Agent 猜参数，静默用错数据
③ 输出契约固定字段 status / stage / batch_id / summary / details / outputs / message编排层取不到字段，工作流断链
④ 执行步骤编号步骤、可复现；标明哪步只读、哪步写换人换会话就跑不出同样结果
⑤ 守门顺序env_guard → env_check → auth_mismatch，逐层拦截带病执行，错误在最深处才爆
⑥ 降级与错误每种异常的正确动作：停手 / 重试 / 降级 / 转人工Agent 自由发挥，重试造成重复下单
⑦ 示例一次正确调用 + 三类异常返回的真实样例文档好看但跑不通
# 示例：demand-query 的输出契约（编排层唯一依赖的接口）
{
  "status":   "ok | error",
  "stage":    "env_guard | env_check | auth_mismatch | query | group | upload | done",
  "batch_id": "20261013-02",
  "summary":  { "total": 1434, "one_group": 1292, "multi_group": 71, "no_supplier": 71 },
  "details":  [ ... ],        # 明细可达数 MB，禁止整段打印/回显
  "outputs":  { "one_url": "...", "multi_url": "...", "json_path": ".output/query-result-*.json" },

2.1.4 公共层怎么收敛

🎯 只留一份

FDS 上传、CLI 调用封装、群通知、progress_sync 各抽一个模块，放在唯一的 common/。v2 之前实测：三份 common 目录 12 个文件有 11 个字节级相同，FDS 签名实现存在 4–5 份。

🔁 改公共层 = 全量回归

公共逻辑没有「局部影响」。改一处必须三个 Skill 全跑四连自检。曾经的坑：webhook / base token / table id 三处硬编码同一值，改一处漏三处。

✅
判断标准
同一个值或同一段逻辑写第二遍之前先问：它会不会变？会变就必须抽出来。不变的常量可以复制，会变的配置绝不能复制。

部署运行 · 六个必须盯住的点

① 身份链 · 最容易全军覆没

CLI 登录账号必须等于触发人。查询可以 system 身份，下单不行。容器用共享账号 = 所有下单被拦。上线前先跑一次 dx-ep user info query 确认「我是谁」。

② 密钥 · 只从环境变量读

FDS AK/SK 一律环境变量注入，配置文件中不出现。凭证错一个字符的表现是「签名不匹配」，会浪费三轮排查——别手敲，别贴进对话。

③ 容器行为 · 与本地不同

容器里 CLI 会误判「有浏览器」，走需要本地回调的登录流程，报 20029 重定向错误。必须 GARAGEHUB_AUTH_MODE=device。容器也没有个人电脑上的 FDS 凭证。

④ 定时任务 · 没有触发人

19:00 日报、9:30 查询都是 system 身份。需要写操作时必须显式注入 EP_SAMPLE_ORDER_CREATED_BY 或决策为只读。

⑤ 体积与并发 · 两条硬上限

结果 JSON 实测 3.9MB，禁止整段 cat；采购员真名解析 buyer_name_concurrency ≤ 4（并发 10 全部限流失败）；分页拉取并发默认 5，与服务端 page-size 100 配套。

⑥ 通知接线 · outputs 是数据接口

html_url 必须固定在 outputs 字段——编排层按位置取值。卡片只做通知与引流，不能回调确认，确认一律回 AgentSpace。

Agent 要具备什么能力 · 六项最小能力集

六项缺一项，链路就会漏。

🧠 ① 任务理解与拆解

把「把今天能下的单都下了，供应商别动」翻译成：查询 → 过滤 → one 直接下 / multi 交人。理解不了就问，不猜。

🛠️ ② 工具编排

知道该调哪个 Skill、传哪些参数、先 plan 后执行。知道自己能做什么、不能做什么——没有的能力如实说没有，不硬编。

🚦 ③ 状态守门

读得懂 stage，并按 stage 做正确动作：env_guard 停手、auth_mismatch 换人登录、草稿不重试。不做「报错就重试」的条件反射。

💾 ④ 上下文预算

只取必要字段，不整段读 3.9MB 结果；长结果用摘要 + 分页 + 落盘路径；跨轮对话记住批次号与已确认范围，不重复询问。

💬 ⑤ 表达与确认

四段式回复（结论 / 链接 / 覆盖 / 异常）；数字口径统一用「组」；下单前必给 plan 摘要并等明确确认，绝不静默下单。

🩺 ⑥ 自诊断与降级

六项环境自检（Python / dx-ep 版本 / 登录态 / 网关 / 环境变量 / FDS）；拿不到链接说原因；能力缺失时给替代路径，不假装成功。

八个坑故事 · 发生了什么 → 根因 → 教训

🔑 坑 1 · FDS 密钥错一个字符

事：上传失败，连环排查三轮。中途几轮测试「成功」——因为那次读的是配置文件里的真值，不是手敲的值。
根因：手敲凭证 + 验证来源与使用来源不一致。
教训：必须逐字符精确的东西绝不手敲；验证时确保「测的东西」和「用的东西」同源。

🧱 坑 2 · 容器 20029，四轮排查

事：AgentSpace 容器里跑 CLI 永远报「重定向 URL 错误 / 20029」，本地一切正常。先后怀疑登录态、settings.json、CLI 版本，全错。
根因：翻 ep-agno 源码才发现容器里 CLI 误判有浏览器，走了需要本地回调的 browser flow。
对策：容器强制 GARAGEHUB_AUTH_MODE=device。C

📉 坑 3 · CLI 契约跳变，造出 4900022810

事：1.0.7 稳定版移除 sapo 域；beta.3 源码确认 buildBody 无 createdBy，服务端却新增必填校验——升级无解、文档没写。
对策：锁版本 env-check + 翻源码 + 降级通道（读 credentials.json 的 access_token 直连 garagehub API，body 带 createdBy）→ 真实订单 4900022810 创建成功。
教训：CLI 是外部契约，不能假设稳定；三板斧应成为所有 CLI 依赖型 skill 的默认动作。

🖥️ 坑 4 · 静态正确 ≠ 渲染正确

事：确认页布局错乱，HTML 结构检查完全正常。根因是 td 上的 display:flex——单元格一旦不是 table-cell 就脱离表格布局算法。
教训：静态检查看不出的问题，只有真渲染才暴露；环境受限无法验证时，明确说「我无法验证渲染」，别反复猜然后下「修好了」的结论（事后补装 headless chromium 一次定位）。

🧩 坑 5 · rowspan 2619 处脆弱

事：主行 9 个 td 全部 rowspan=N，rowspan 出现在 2619 处；与 CSS display、单元格数量一变就出错，修 colspan、加 min-width 都不是根因。
对策：直接取消候选行和 rowspan，改主行 10 个 td、候选装第 10 列 flex 竖排——rowspan 归零，问题一次性消失。
教训：结构简单优先；反复出问题的机制就换掉，别修。

🎯 坑 6 · 237 条需求在做无效操作

九条可复制经验 · 带走的才是你的

来源：踩坑全记录 09-23 经验教训章。

1 · 输出强约束

统一 status/stage/batch_id/summary/details/outputs/message；Agent 只允许「原样输出 message + 至多一行交互提示」。格式约束写进代码，行为约束写进提示词。

2 · 契约三防

外部依赖（CLI/API）锁版本、翻源码、留降级通道。不能假设外部契约稳定。

3 · 授权地图

把「用什么身份、能干什么」画成地图前置确认；凭证从配置文件读，绝不手敲。

4 · 公共收敛

公共层只保留一份；改公共逻辑必须全量回归，别让「改一处漏三处」反复发生。

5 · 边界先测

平台能力边界（回调/凭证/容器行为）先探测再设计，别拿本地经验推容器。

6 · 字段分口径

字段名、字段类型、中英文口径三张皮；映射必须按类型处理（人员/日期/多选/附件各有形态）。

7 · 通知即接线

html_url 固定在 outputs 字段——「输出契约」是编排层的数据接口，字段位置稳定，工作流才稳定取用。

8 · 审查喂料

审查 Agent 要给清单和判据，不给「自由找茬」；否则互相找茬跑偏，改了又改。

9 · 先跑通

先跑通最小闭环再优化。不在架构上追求完美——业务闭环通了才有资格谈收敛。

4.2

① 知识 · 对话 · 把散落的「怎么规定的」变成能问的人

门槛最低、最容易做，也最容易被业务吐槽「答得不对」——差别全在知识有没有人管。

✅ 它擅长什么

  • 口径解释：这个字段什么意思、为什么这么取数
  • 流程导航：这事儿该找谁、走哪一步、要什么材料
  • 历史回溯：上次类似问题怎么解的、踩过什么坑
  • 新手陪跑：EP 操作手册变成可追问的师傅

❌ 它做不了什么

  • 查实时业务数据：「今天有多少条可下单」——知识层没有这个数，硬答就是编
  • 改系统状态：它只读，任何写操作都不该从这里走
  • 替代口径 owner：三份文档打架时，它只会更自信地答错

要落地，先解决三件事

要素具体要求不做会怎样
知识源明确收哪些：操作手册、口径定义、制度、踩坑记录、历史问答；每类有 owner 和更新频率半年前的旧流程被当成现行规则答出去
口径统一同一个词只能有一个定义；冲突文档先合并再入库模型学会的是三套口径，答得越流畅越危险
出处可点每个结论必须能点到原文段落，不能只有「模型说的」业务不敢用于决策，用两次就没人再问

4.3

② Skill · 把一条固定流程封装成「一句话就能跑」

样件订单就是这一类。它不是「更聪明的对话」，而是把确定性流程固化下来，让模型只负责表达与编排。

什么值得做成 Skill · 五条判据

判据含义样件订单的对照
① 高频每天 / 每周都要走一遍，人工做烦了每天 100+ 条需求待查
② 步骤固定顺序不常变，分支有限且可枚举查询 → 分组 → 确认 → 下单 → 日报
③ 输入输出清晰进来的字段、出去的格式都能说死records JSON → 订单结果 + 日报
④ 有明确的人工确认点知道该在哪一步停下来等人一品多点选供应商、确认执行
⑤ 错了代价可控失败可回滚、可重跑、不产生不可逆承诺批次幂等、草稿不重试

做对了得到什么

  • 一句话触发：也能被定时任务、群机器人、其他 Agent 调用
  • 行为可复现：同一输入永远同一路径，出了问题能对得上
  • 可交接：换人接手不需要重新理解一套隐性经验

代价与前提

  • 要维护：接口一变、字段一改，Skill 就得跟着改
  • 公共逻辑必须收敛：各抄一份，改一处漏一处（历史上漏了 3 次）
  • stage 守门 + 幂等：没有这两样，跑得越快错得越大
⚠️
不该做成 Skill 的三种情况：① 只干一次的事（封装成本 > 收益）；② 判断占大头、规则说不清（不如做成对话 + 人拍板）；③ 上游数据还没有字段契约（今天封装，明天重写）。
4.4

③ 原生能力 · 按钮或链接，直接跳到大模型去用

前两种是「另开一个地方用 AI」；这一种是把入口长在业务流程里——用户在哪看数据，按钮就在哪。
形态示意 · 价格中心某条报价明细页

「这条为什么异常」——一个按钮能省掉多少来回

  • 人在 EP 报价明细页看到某条单价明显高于同类，页面右侧有个 「🧠 用 AI 分析」 按钮。
  • 点下去，自动带上这条明细的全部上下文：零件、供应商、历史价、报价细项、同批次其他报价。
  • 大模型在这份上下文里拆解：是材料涨了、工时算多了，还是该项本就不该报。
  • 结论回到原页面，形成一条可留痕的分析说明；需要改字段的，给人一个「采纳」按钮再写回。

三个设计要点 · 少一个就退化成「开了个新窗口」

① 入口

  • 放在痛点上，不放在导航栏
  • 按对象给按钮：这条明细、这家供应商、这份合同
  • 文案说清干什么：「分析差异」而不是「AI 助手」

② 上下文

  • 带这一条，不是整个模块
  • 用户不该再描述一遍，也不该复制粘贴
  • 带不动的部分要显式标出来（缺什么数据说清楚）

③ 回写

  • 结论回到原页面原位，不是另存一个文档
  • 写字段必须人点采纳，不能静默改
  • 留痕：谁点的、基于什么、采纳没采纳

你面对的情况该用哪种理由

顺序上建议 Skill 先行——它逼你把原子、契约、幂等、留痕都做出来；这些是原生按钮的底座。知识问答可以并行推进，成本最低、见效最快，但要先把口径和 owner 定下来。
