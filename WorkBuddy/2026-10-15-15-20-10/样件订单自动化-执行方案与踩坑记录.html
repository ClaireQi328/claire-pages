!今天踩的坑

按影响面排序。多数不是算法问题，而是「验证方式不对」和「口径没对齐」。

1

FDS 密钥我给错了一个字符，连环排查三轮

403 Signature Does Not Match · 影响：3 小时返工

▶
现象

配置了正确的环境变量，上传仍报 403。穷举了 header 大小写、charset、客户端实现都试过。

根因

我手敲凭证时第 39 位写错了：给了 ...WRDsRv，正确是 ...WRDsNv。差一个字母，HMAC 就完全不同，而错误信息只说「签名不匹配」。

为什么难发现

中途有几轮测试是「成功」的——因为那次读的是 ~/.fds-upload-config.json 里的真值，不是手敲的值。这种时好时坏最容易误导判断。

教训：给凭证这种必须逐字符精确的东西，绝不手敲，一律从配置文件读取。更重要的是：验证时要确保「测的东西」和「用的东西」是同一个来源。
2

静态结构正确 ≠ 渲染正确

td 上的 display:flex 破坏表格布局 · 影响：2 轮返工

▶
现象

确认页布局错乱，候选跑到表格左边单独成行。检查 HTML 结构完全正常——colspan 已去、rowspan 正确、列数对齐。

根因

.mat-cell{display:flex}。表格单元格一旦不是 table-cell 就脱离表格布局算法，后面的列位置全错。这个问题静态检查看不出来，只有真渲染才暴露。

当时的困境

没有浏览器渲染能力，playwright 没二进制、系统 Chrome 起不来、safaridriver 要密码。我只能在静态层面猜——连猜两次都错了。

教训：环境受限导致无法验证时，应该明确说「我无法验证渲染」，而不是反复猜测然后下「修好了」的结论。事后补装了 headless chromium，这类问题一次就定位了。
3

rowspan 方案本身太脆弱

连续两次修补都没解决根因

▶
原方案

主行 9 个 td 全部 rowspan=N + 额外 N 个候选行填第 10 列。rowspan 出现在 2619 处。

问题

rowspan 是表格里最脆弱的机制：和 CSS 的 display、和单元格数量一变就出错。我先后修了 colspan、加了 min-width，都不是根因。

换结构

直接取消候选行和 rowspan，改成主行 10 个 td，候选装在第 10 列内用 flex 竖排。rowspan 归零，问题一次性消失。

教训：当某个机制反复出问题，换结构比修参数有效。别在脆弱设计上反复修补，该重构就重构。
4

dict.get(key, default) 对 None 无效

数量列全是 0 · 根因藏在数据源头

▶
现象

确认页数量列大面积显示 0。

根因（两层）

① CLI 根本不返回 quantity 字段，只有 requiredQuantity
② 原写法 item.get("quantity", item.get("requiredQuantity", 0)) —— 默认值只在 key缺失 时生效，对 None 不生效，必须用 or

错误做法

我在下游一层层加兜底（group 层、records 层、row_data 层），改完发现没用——因为问题在上游。

教训：字段异常要从数据源头查起，先确认「这个字段到底存不存在」，而不是在下游层层加补丁。
5

删掉「自检」时连带删掉了关键约束

Agent 又去全盘 find，120s 超时

▶
背景

上午你说「零、先确认自己装对了」这节没必要，我删了——因为那个检查动作模型根本不会触发（它不会 cd 进 skill 目录自检）。

副作用

那节里还夹着一条真正有用的约束：「不要用全盘查找找脚本，会超时」。删掉后，Agent 立刻又去跑 find，卡满 120 秒。

教训：精简文档时，要区分冗余（该删）和兜底（该留）。删掉看似啰嗦的段落，可能连带删掉唯一的防护。后来补回时改成明确写固定路径，更有效。
6

口径没对齐 PRD，人在做无效操作

237 条需求在选一个「选了也没用」的价格

▶
现象

确认页让用户在「定点价 / 快速定点价」之间点选，看起来很合理。

真相

create-order 没有 --price-type 参数（实测确认），价格判断完全在 EP 内部。所以用户在页面上选的 priceType，EP 根本不接收——237 条需求（占多供应商组的 81%）在做无效操作。

改法

去重键从 (sid, priceType) 改为 sid，同一供应商��多条价合并为一个候选，价格类型降级为只读提示。

效果：多供应商组 291 → 71（-76%），1363 条走全自动。教训：动手前先读 PRD 确认「谁负责什么」，别凭直觉设计交互。
7

工具层面的几个小坑

grep 返回空 / zsh glob 中断 / 正则吃掉引号

▶
grep 对中文返回空

多次 grep 搜含中文或特殊字符的 Python 文件返回空，误判成「文件不存在」或「内容为空」。改用 Python 的 pathlib.read_text() + in 判断才准。

zsh glob 无匹配会中断循环

for f in dir/*.py 遇到没有 common/ 子目录时直接中断整个循环，导致后面的文件没被校验。批量校验应该走 Python。

正则替换吃掉闭合引号

用正则改 CSS 时把字符串结尾的引号一起吞了，导致 SyntaxError。改完必须 py_compile 校验。

教训：编辑代码后立刻编译验证，别攒到最后。这些问题都会自己浮出来，但那时你已经忘了改了什么。
8

上传失败 ≠ 密钥配错

FDS 403 的四种可能

▶
容易走偏的地方

403 出现后，我先怀疑 signing 算法（header 大小写、charset、客户端实现），甚至写了段注释说 add_unredirected_header 能保住大小写——实测是错的，它照样规范化。

排查方法

最后靠穷举维度才定位：凭证形态（干净 / 带换行 / 带空格 / 截断）× header 形态 × 客户端实现。很快发现尾随空格就会失败。

教训：错误信息指不到根因时，做维度穷举比逐个猜测快得多。另外给 fds_doctor.py 加了指纹自检——现在能一眼看出「配的值与已知可用凭证是否一致」，不用再猜。

→如果只记三句话

1. 静态检查通过不等于渲染正确——有浏览器就自己验，没有就明说，别猜。
2. 动手前先读 PRD 确认「谁负责什么」，别凭直觉设计交互。
3. 一个机制反复出问题就换结构，别在脆弱设计上反复修补。
