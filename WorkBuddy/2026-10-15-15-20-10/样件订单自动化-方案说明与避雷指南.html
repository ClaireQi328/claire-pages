场景痛点：重复劳动 + 认知盲区

问题从哪来 · 为什么值得做

😤 传统流程：采购工程师在 EP 里「逐条建单」

样件订单（研发打样要的零件）原来靠人肉在 EP 系统里一条条创建。三个痛点叠在一起，既慢又容易出错：

  • 量大人肉：可下单需求原始就有 4699 条，60 天窗口内有效 1434 条。逐条看、逐条建，重复操作占采购工程师 30%+ 的时间。
  • 一品多供要人判断：同一零件有多个候选供应商，得人工决定选哪家 —— 仅「多供应商组」就有 291 个，每个都要拍板。
  • 价格 / 定点纠缠：旧流程让人去选「价格类型」，但 EP 内部才判价，结果 237 条（占多供应商组 81%）在做无效操作。
  • 留痕难追溯：结果散落各处，谁下了、下了什么、为什么草稿，事后说不清。
⚠️
真正的痛，不只是「慢」。慢还能熬，慢 + 易错 + 不可追溯组合起来，才是采购流程数字化最该先切的那一刀。

🎯 要解决的，和明确不解决的

✅ In Scope（自动化覆盖）❌ Out of Scope（边界）
拉取需求、按供应商分组、生成可视化确认页不选价（价格由 EP 内部台账判定，人工不参与）
人工拍板后自动下单、草稿态透出不覆盖无供（无候选供应商的，先走 EP 定点）
下单结果自动写飞书多维表格留痕不催审批（草稿需人工去 EP 提交，系统只透出）
日报汇总推送不做价格谈判（人工线下）

AI 做法：三层架构 + 一个黄金原则

怎么做的 · 设计哲学

🧱 CLI — Skill — Agent 三层架构

EP CLI 是数据唯一权威（query-ready / create-order / submit-list）→ 3 个 Skill（demand-query 查询 / demand-order 下单 / daily-report 日报）封装业务逻辑 → Agent 负责编排与人工交互。

💡
黄金原则：价格交给 EP，供应商留给人。
人从头到尾只做一个动作 —— 在确认页上「选供应商」（或勾掉不要的行）。判价在 EP 内部完成，create-order 只收 --supplier-id，根本不存在 --price-type。把「需要人判断的」和「能自动的」一刀切干净，才换来后面的自动化率。

一句话看懂：EP 拉数据 → 自动分组生成确认页 → 推群通知 → 人只做「选供应商」→ 系统下单 → 价格 EP 判 → 结果留痕进日报。草稿不是失败，是「存在更低价需人工确认」的业务分支，日报单独列出等跟进。

📡 同一批数据，推三处、按「谁需要什么」分层

  • L1 围观者 · 飞书群卡片：批次号 + 一句话结论 + 确认页链接。5 秒看懂，不需操作。
  • L2 跟进者 · AgentSpace Issue：状态流转 + 三组核心数 + 链接。事后可追溯。
  • L3 操作者 · Agent 对话回复：唯一可交互，可替代群机器人，含结论/链接/待办/异常/下一步。

🚀 三种使用入口：同一业务逻辑，三种封装

演进路径是 对话验证业务逻辑 → 工作流自动化日常 → 高码框架上生产。Skill 版跑 Agent Space，Agno 版跑 ep-agno 框架，两边并行、互不依赖 —— 业务一样，封装形式、运行环境、使用场景不同，按需选用。

📊 几个关键数字背后的故事

  • 查询吞吐：47 页 / 4699 条，全流程约 60s。并发上限实测锁在 5 —— 盲目拉到 20 并发反而从 5.6s 劣化到 9.8s（服务端限流）。

📖 精选坑故事（最有代表性的 8 个）

坑 A · FDS 密钥手敲错一个字符，连环排查三轮（3 小时返工）

现象配置了正确的环境变量，上传仍报 403 Signature Does Not Match。穷举了 header 大小写、charset、客户端实现都试过。
根因手敲凭证时第 39 位写错（给了 ...WRDsRv，正确是 ...WRDsNv）。差一个字母，HMAC 完全不同，而错误信息只说「签名不匹配」。更坑的是中途有几轮「成功」——因为那次读的是配置文件里的真值，时好时坏最误导判断。
✅ 解法：凭证这类必须逐字符精确的东西，绝不手敲，一律从配置文件读取；验证时要确保「测的东西」和「用的东西」是同一来源。

坑 B · 静态结构正确 ≠ 渲染正确（2 轮返工）

现象确认页布局错乱，候选跑到表格左边单独成行。检查 HTML 结构完全正常 —— colspan 已去、rowspan 正确、列数对齐。
根因.mat-cell{display:flex}。单元格一旦不是 table-cell 就脱离表格布局算法，后面的列全错。这问题静态检查看不出，只有真渲染才暴露。当时没浏览器渲染能力，连猜两次都错。
✅ 解法：环境受限无法验证时，明确说「我无法验证渲染」，而不是反复猜然后下「修好了」的结论。事后补装 headless chromium，这类问题一次就定位。

坑 C · rowspan 方案太脆弱（连续两次修补没解决根因）

现象主行 9 个 td 全部 rowspan=N + 额外 N 个候选行填第 10 列，rowspan 出现 2619 处。先后修了 colspan、加了 min-width，都不是根因。
✅ 解法：直接取消候选行和 rowspan，改成主行 10 个 td、候选装在第 10 列内 flex 竖排。rowspan 归零，问题一次性消失。当某个机制反复出问题，换结构比修参数有效。

坑 D · 口径没对齐 PRD，人在做无效操作（237 条 / 81%）

现象确认页让用户在「定点价 / 快速定点价」之间点选，看起来很合理。
真因create-order 根本没有 --price-type 参数（实测确认），价格判断完全在 EP 内部。用户在页面选的 priceType，EP 根本不接收 —— 237 条需求（占多供应商组 81%）在做无效操作。
✅ 改法：去重键从 (sid, priceType) 改为 sid，同供应商多价合并为一个候选、价格类型降级为只读提示。多供应商组 291 → 71（−76%）。动手前先读 PRD 确认「谁负责什么」，别凭直觉设计交互。

坑 E · 20029 授权坑改了 4 轮，花了 ~6 小时（最深的雷）

现象AgentSpace 容器里跑 CLI 永远报「重定向 URL 错误 / 20029」，本地一切正常。4 轮排查：① 当登录态过期反复重登 → ② 改 base_url → ③ 升 CLI 版本 → ④ 翻 ep-agno 代码库才发现根因。
真因自己账号的飞书 MCP 与订单自动化助手的 MCP 同时挂载，环境变量被覆盖成后者的预设值，CLI 误判「有浏览器可用」，强行走了需要本地回调的 browser flow → 而容器根本没有浏览器，2 小时必断、反复重演。
底层雷飞书 MCP 要同时干两件身份相反的事 —— 既要「以你的身份读」又要「以助手身份发」。MCP 登录态本就是「用户在场」设计，不适合无人值守。环境变量冲突是引爆点，身份双轨才是底雷。
✅ 解法：加 GARAGEHUB_AUTH_MODE=device 强制 device flow；无人值守场景别用「用户在场」型 MCP 既读又写。

坑 F · 飞书卡片回调坑了 3 轮，~4 小时

现象想在飞书消息卡片上直接点「确认下单」，结果群机器人 webhook 卡片点了没反应。
根因群机器人 webhook 是单向推送通道，没有回调机制；交互式卡片需要应用机器人 + 事件订阅 + 权限，而应用机器人缺 bitable:app 权限（99991672）。
✅ 解法：人工确认改到 HTML 确认页（FDS 上传，浏览器操作）→ 回填 JSON 给 Agent；通知卡片只做「提醒 + 链接」，不做交互。「推送」和「交互」是两种能力，群机器人只有前者。

坑 G · 公共逻辑重复 300+ 行，改一处漏一处（漏 3 次）

现象device 模式只加了 demand-query 漏了 demand-order；FDS 占位符替换只改了一处；登录态缓存只加了 query 漏了其他 skill。4 个调 CLI 的 skill 各抄一份环境检查 / FDS 上传 / 登录态检查。
✅ 解法：公共层收敛（logger / feishu_bot / fds / config_loader / result_builder 下沉 common/），环境检查归 Agent 预设统一调用。「独立自包含」≠「代码复制」。

坑 H · 审查 Agent 对轰 5+ 版本，2 天白改

现象审查报告 1 说「要抽公共层」，报告 2 说「不要抽要独立」，报告 5/6 对 env_check 硬编码版本互相矛盾。很多修改最后证明是错的。
根因每个审查 Agent 都不了解业务背景和决策历史，拿通用规范凭空挑错。
✅ 解法：审查前必须把决策历史 / 约束条件喂给审查 Agent；报告分「必改 bug / 建议优化」，最终决策由业务方拍板，不信 Agent 对轰。
🧭
边界清单（明确不做什么，比「能做什么」更重要）：① 不选价（EP 内部判）② 不覆盖无供（先走定点）③ 不催审批（草稿人工去 EP 提交）④ 草稿 ≠ 失败（是业务分支，日报单列）⑤ 推送 ≠ 交互（要操作就给页面）。

可复制经验：9 条方法论 + 3 句金句

把学费变成资产 · 下一个项目直接套
① 输出强约束定死输出契约，禁自由发挥。统一 status/stage/batch_id/summary/details/outputs/message；Agent 只「原样输出 message + 至多一行提示」，禁重写/开场白/重复。
② 契约三防外部依赖锁版本、翻源码、留降级。CLI 跳变靠 env-check 锁 + 直连 API 兜底（订单 4900022810 就是降级通道跑通的）。
③ 授权地图先建「谁需要什么登录态」清单。feishu-mcp(用户态) 与 GarageHub(device flow) 两套，失败按图引导，禁 AI 猜。
④ 公共收敛公共逻辑下沉 common/，业务各自独立。环境检查归 Agent 预设统一调用，避免 N 份重复 + N 份不一致。
⑤ 边界先测平台能力矩阵先探测再设计（通道 × 操作 × 权限）。卡片回调、视图筛选、应用权限，不支持的直接排除出方案。
⑥ 字段分口径提交口径（账号/邮箱前缀）与展示口径（姓名/中文）分离；日期统一格式化；人员字段按类型转换。
⑦ 通知即接线写完 notify 函数立刻在主流程接线并 grep 验证；卡片必带日期 + 链接（无链接 = 无效通知）。
⑧ 审查喂料审查 Agent 先喂决策历史；报告分「必改 bug / 建议优化」，业务方拍板，不盲信对轰。
⑨ 先跑通先最小闭环再优化。调试纪律：报错读全、同错两次换方向、路径以脚本目录为基准。
🔑 如果只记三句话：
① 静态检查通过 ≠ 渲染正确 —— 有浏览器就自己验，没有就明说，别猜。
② 动手前先读 PRD 确认「谁负责什么」，别凭直觉设计交互。
③ 一个机制反复出问题就换结构，别在脆弱设计上反复修补。

📜 一句话总结这段旅程

我们花了 60% 的时间，不是在解决业务问题，而是在补「非专业开发者的认知盲区」——授权方式、系统边界、接口设计、基础设施规则。这些东西专业开发一眼就懂，我们（和 AI）却只能瞎猜，猜错再改，浪费大量时间。

✅
但正是这些坑，沉淀出上面 9 条方法论。下一个项目，跳过这 60%，就是这套指南最大的价值。
