业务背景 Why
小米整车工程部研发样件采购，在产品开发各阶段（散件/SM/M/VP/PT/PP/MP）需要大量小批量定制样件。 传统流程是采购工程师手动在 EP 系统逐条创建订单，重复度高、效率低、容易出错。
😤 传统流程痛点
• 每天手动查询 100+ 条可下单需求
• 逐条创建订单，复制粘贴容易出错
• 一品多供场景需要人工判断选哪家
• 每天手动统计订单执行情况
• 重复操作占采购工程师 30%+ 时间
✅ 自动化目标
• 自动查询可下单需求（只读，安全）
• 生成 HTML 确认页，人工拍板后自动下单
• 一品多供场景可视化选择供应商
• 自动统计每天/每周订单执行情况
• 采购工程师只做决策，不做重复操作

方案细节：5 个模块的职责 Modules
模块 skill / handler 做什么 输出什么
① 需求导入 demand-import 把用户导出的 Excel 需求，按 37 个字段映射成 EP 系统能接收的 JSON 格式，做基础校验 records JSON + 导入预览 HTML
② 需求校验 demand-check 对导入的需求做完整性校验：必填字段、预算行号连续、日期合理、EP 账号匹配 校验报告（PASS / WARN / FAIL）
③ 查询可下单 demand-query-ready 调用 EP CLI 分页拉取 60 天内可下单的需求，过滤过期数据，生成可视化确认页 HTML 确认页 + 统计概览
④ 创建订单 demand-order-create 用户确认后，批量调用 EP CLI 创建订单，区分成功/草稿/失败，生成结果汇总 下单结果 JSON + 执行统计
⑤ 执行统计 daily-report 按天/按周查询已提交的订单，按采购员/供应商/零件分类统计，生成报告 统计报告 HTML

🔒 安全设计
• 只读查询：query_ready 只查数据，不改任何东西，安全
• 人工确认：下单前必须用户回复「确认」，系统不会自动下单
• 幂等执行：重复点确认不会重复下单（同一批次号只处理一次）

关键决策：为什么放弃，为什么选择 惨痛教训
⚠️ 先说结论：这 4 个决策，每一个都花了至少半天时间踩坑才想明白。不是我拍脑袋选的，是踩坑踩出来的。
🔴 决策 1：为什么放弃飞书 MCP？
📉 踩坑过程（改了 4 轮，花了 ~6 小时）
第 1 轮： 以为 access token 过期了，重新登录了一遍，好了 2 小时又坏了
↳ 错在哪：重新登录只重置了临时的"用户在场"会话，没碰"为什么被迫走 browser flow"这个根——而 browser flow 无法无头刷新，所以 2 小时必断、反复重演。
第 2 轮： 以为是 settings.json 配置不对，改了好几版 base_url，还是报 20029 错误
↳ 错在哪：20029 是授权重定向错误，根因是环境 / 凭证错配，不是网关地址写错。改 base_url 只是换连法、没动"该用哪套环境、谁的凭证"，反而可能连错网关、越改越乱。
第 3 轮： 以为是 CLI 版本不对，升级降级试了好几个版本，还是不行
↳ 错在哪：故障在环境 / 配置里，不在二进制里。每换一个版本，CLI 读的是同一套被覆盖的环境变量，自然复现同一处 browser flow 误判——版本迭代对配置型 bug 是零作用，纯属往错误的方向烧时间。
第 4 轮： 去看 ep-agno 源码才发现：容器里 CLI 误判有浏览器，走了 browser flow！
🔗 四轮的共同盲区：前 3 轮都在"症状邻居"上迭代——token / 地址 / 版本，没一轮怀疑过"环境变量被谁偷换了"。第 4 轮跳出表象、直接看源码，才摸到真因。
🔧 根因：同时挂上了自己账号的飞书 MCP 和订单自动化助手的 MCP，环境变量被写成了订单自动化助手的预设值，CLI 据此误判"有浏览器可用"，强行走了浏览器登录流程 → 才反复 20029 / 登录态 2 小时就失效。
💡 想明白的道理
表面现象是 20029 / 登录态 2 小时就失效，但真因不是 token 过期——是自己账号 MCP 与订单自动化助手 MCP 同时挂载，环境变量被覆盖成后者的预设值，CLI 误判"有浏览器"走了 browser flow。MCP 的登录态本就是"用户在场"设计、不适合无人值守，再叠加多套 MCP / 环境变量打架，坑被放大了好几倍。
🧭 更深一层：身份双轨，Agent 分不清该用谁的凭证
即便把第 4 轮的环境变量冲突修好，这个场景对飞书 MCP 仍是结构性不匹配——它要同时干两件身份相反的事：
• 读：以「你自己」的身份拉多维表格（bitable）——权限、可见范围都绑在你的账号；
• 写：以「订单自动化助手」的身份发通知——动作落在对方侧、要可审计可追溯。

单条 MCP 通道没法按"这次调用该用谁的凭证"精准切换身份上下文，本质要靠 Agent 自己判断。而 Agent 在"这回用齐岳的 token 还是助手的 token"上做选择，是猜的——猜错一次就是越权读不到表、或通知发错身份，且这种错日志里很难一眼看穿。

所以环境变量冲突是"引爆点"，身份双轨才是底层的雷：它从根上解释了为什么 MCP 不适合这种"既要代你读、又要替你发"的无人值守场景。
✅ 最终替代方案
需求导入改成用户从飞书导出 Excel，脚本读本地文件；日志改成本地 JSON + HTML 上传 FDS。每个环节凭证都写死、各走各的——读用你的导出、发用助手的 API，身份不再需要 Agent 临场判断。彻底不依赖 MCP，稳定多了。
🔴 决策 2：为什么放弃飞书卡片交互？
📉 踩坑过程（改了 3 轮，花了 ~4 小时）
第 1 轮： 设计了漂亮的飞书卡片，有「确认」「取消」按钮，觉得用户体验肯定好
第 2 轮： 按钮点了没反应，查了半天才发现 AgentSpace 不支持卡片回调！
第 3 轮： 想绕过去：让用户点完按钮再回对话里说"确认"，那我做卡片干嘛？多此一举
💡 想明白的道理
一开始就想做"漂亮的交互"，但忽略了平台能力边界。卡片回调需要服务端支持，而 AgentSpace 是"对话式"的，没有服务端回调能力。不要为了炫技而炫技，平台不支持的就是不支持。
✅ 最终替代方案
生成 HTML 确认页上传 FDS，用户在浏览器里看，然后在对话里回复"确认"。简单但可靠，虽然不酷，但能用。
🔴 决策 3：为什么先做 skill 版，再做 agno 版？
📉 踩坑过程（凭记忆写字段名，全错了）
第 1 轮： 直接上手写 agno 版 handler，凭记忆写字段映射
第 2 轮： 跑出来 0 条需求，查了半天发现字段名全错：以为是 requireArrivalDate，实际是 deliveryDate
第 3 轮： 一个一个字段对，加了 normalize_items() 做映射，才跑通
💡 想明白的道理
一开始就做复杂架构会浪费更多时间。业务逻辑还没跑通，直接做架构优化是舍本逐末。先把业务逻辑验证对了，再考虑架构调整。
✅ 最终结论
先 skill 版跑通业务逻辑（7 天），再 agno 版做架构优化（1 天）。迁移成本不高，业务逻辑是一样的，核心逻辑直接搬过来就行。
🔴 决策 4：为什么环境检查归 Agent，不归 skill？
📉 踩坑过程（环境检查跑了 6 次）
现象： 每次跑一个 skill，它都先 check_login() 一次，跑 5 个 skill 就检查 5 次，加上 Agent 自己的检查，一共 6 次
为什么： 每个 skill 都觉得自己是独立的，所以都要自己检查一遍，"我不管别人检没检，我自己要检"
结果： 光环境检查就花了 30 秒，用户以为卡住了
⚖️ 两种方案对比
❌ 方案 A：放在 skill 里
做法：每个 skill 启动时自己 check_login()
优点：
• skill 完全独立，自己跑也行
• 不用依赖外部环境
缺点：
• 跑 5 个 skill 就检查 5 次，浪费时间
• 每个 skill 都要写一遍，代码重复
• 改的时候要改 5 个地方，容易漏
• 就是我们现在踩的坑
✅ 方案 B：放在 Agent 里
做法：Agent 启动时统一检查一次，再调 skill
优点：
• 只检查一次，省 30 秒
• 只写一处，好维护
• 逻辑清晰，通用能力下沉
缺点：
• skill 不能单独跑了（脱离 Agent）
• 但我们本来就不单独跑
💡 为什么选 B？
核心判断：skill 不单独用（除了本地调试的情况），所以"skill 独立性"这个优点对我们不重要。

实际使用场景是：Agent Space 启动 → Agent 做环境检查 → Agent 调 skill。skill 永远是被 Agent 调的，不会单独被用户直接调用。

那为什么要让 skill 自己再检查一遍？多此一举。
✅ 最终执行结果
删掉所有 skill 里的 check_login()，环境检查统一到 Agent 层，只跑一次。快了 30 秒。
本地调试的情况：需要手动跑一遍环境检查命令，就当是开发成本了，反正不常用。

🎯 所有坑的共性：Agent 开发的"认知盲区"
👨‍💻 传统开发：先想清楚再动手
  • 先看文档，搞清楚规则再写代码
  • 先定接口契约，再写实现
  • 路径、配置这些固定的东西，一眼就知道
  • 有项目记忆，知道之前做过什么决策
  • 知道"现在调的是哪个系统"
🤖 Agent 开发：边做边想
  • 直接上手写，跑一下看报错
  • 不知道系统边界，开错药（授权搞混）
  • 不知道哪些是固定的，瞎改路径
  • 每次都是新的开始，没有记忆（审查对轰）
  • 凭记忆写字段名，错了好几个
💡 一句话总结：我们花了 60% 的时间，不是在解决业务问题，而是在补"非专业开发者的认知盲区"——授权方式、系统边界、接口设计、基础设施规则，这些东西专业开发一眼就懂，但我们（和 AI）都没有基本框架，所以只能瞎猜，猜错了再改，浪费大量时间。

P0 级问题（反复踩坑，花时间最长）核心问题
P0-1：CLI 授权环境混用，反复报 20029 错误
⚠️ 与「决策 1：放弃飞书 MCP」是两回事：这里是 dev / 生产网关地址 + token 混在同一容器；决策 1 是 双飞书 MCP + 环境变量被订单自动化助手预设值覆盖。两个独立问题，根因不同、解法也不同。
发生了什么：AgentSpace 容器里跑 CLI 永远报不明确的「重定向 URL 错误」（20029），授权链接打不开，改了 4 轮配置都没解决。

🔧 真实根因：dev 环境和生产环境的网关地址、token 混在同一个容器里，CLI 不知道该走哪条，只报"重定向 URL 错误"（20029），完全不提示是环境冲突——这才是一连改 4 轮都没找着的扳机。
踩坑过程：
• 第 1 轮：以为登录态过期 → 重新登录 → 没用
• 第 2 轮：以为 settings.json 不对 → 改 base_url → 越改越乱
• 第 3 轮：以为 CLI 版本不对 → 反复升降级 → 没用
• 第 4 轮：明确环境隔离 → dev 全走 dev 网关，生产全走生产网关，写死地址不混用 → 好了
解法：环境完全隔离——dev环境的配置和授权全部走dev网关，生产环境全部走生产网关，不混用任何一套配置和token；环境检查里直接写死当前要用的网关地址，不允许AI自动识别或修改路径。
P0-2：feishumcp 和 garagehub 授权完全搞混了
发生了什么：为了解决 garagehub CLI 的 20029 错误，AI 跑去调飞书 MCP 的授权流程，让用户点飞书的授权页，结果当然没用，白折腾了好几轮。

两套授权：
• 飞书 MCP 授权：读飞书多维表格，入口是飞书 scope-authorization 页
• GarageHub CLI 授权：调 EP 接口，入口是 garagehub-cli-auth 域名
解法：报错时先看域名/报错码，先判断是哪个系统的授权问题，再对症下药。
🧠 本质思考：都是"授权"，报错信息都长得像，AI 分不清是哪个系统的。本质上是缺乏系统边界感——不知道"我现在调的是哪个系统，这个系统的授权长什么样"。专业开发脑子里有一张"系统清单+每个系统的授权方式"，但 AI 脑子里没有，所以会开错药。
P0-3：AI 自己乱改配置路径，越改越糟
发生了什么：每次授权卡住，AI 就自己改 settings.json 的路径，一会儿改成 /home/xxx，一会儿改成 /root/xxx，改完更不对了。
解法：把配置路径写死在 skill 脚本里，AI 只负责写配置内容，不负责选路径。
🧠 本质思考：AI 不知道真实的文件系统路径，凭感觉猜，猜完改，改完坏，坏了再猜。这是典型的"不知道边界在哪"的问题——AI 不知道哪些东西是固定的（路径、配置位置），哪些东西是可以改的（配置内容）。专业开发一眼就知道"路径是写死的，别瞎改"，但 AI 不知道。
P0-4：公共逻辑重复，改一处漏一处
发生了什么：改了 demand-query，漏了 demand-order 和 daily-report，前后漏了 3 次。
根因：4 个调 CLI 的 skill 各抄了一份 check_login、upload_to_fds，重复代码至少 300 行。
解法：Agno 版抽了 handlers/base.py + fds_uploader.py，所有 handler 复用。
🧠 本质思考：流程串联和连接，有没有更丝滑的方式？MCP 本质就是把"调用外部能力"标准化：你不用自己写上传 FDS 的代码，直接调 MCP 工具就行。但 MCP 也有问题：封装得太好，反而让人不理解底层逻辑。结论：MCP 方向是对的，但需要"足够薄"——封装调用，但不封装授权和配置。
P0-5：不同审查 Agent 互相矛盾，改了又改
发生了什么：第 1 个审查说要抽公共层，第 2 个说不要，第 3 个说 import 中文是断点，第 4 个又说 import 中文是对的。
解法：做代码审查前，必须先把「之前的决策历史和约束条件」喂给审查 Agent。
🧠 本质思考：每个审查 Agent 都是"失忆"的，不知道之前做过什么决策，所以每次都从头开始评判，结果就是互相矛盾。这是Agent 缺乏上下文连续性的问题。专业开发有"项目记忆"，知道之前为什么这么选，但 Agent 没有，所以每次都是新的开始。
P1 级问题（影响稳定性）稳定性
P1-1：FDS 上传反复失败，换了 3 种方式
发生了什么：URL 虚拟主机风格→路径风格；签名 Galaxy→Galaxy-V2；没设 ACL；ACL 少了 type: GROUP 字段。
解法：URL 用路径风格，签名用 Galaxy-V2，上传后加 ACL 设置。
🧠 本质思考：又是"不知道这个系统的规则"的问题。FDS 有自己的一套规则（URL 风格、签名算法、ACL 格式），但 AI 不知道，只能试，试错了再改，改了再试，来回好几次。和授权问题本质一样：对非业务流程类的基础设施，缺乏基本的认知框架。
P1-2：输出契约不统一，skill 串联失败
发生了什么：demand-query 输出 stats，demand-order 读 summary，字段名对不上。
解法：定死统一输出格式：status / stage / batch_id / summary / details / outputs / message。
🧠 本质思考：这是接口设计的问题。专业开发做系统集成第一件事就是定接口契约，字段名、类型、含义都写清楚。但 Agent 开发是"边做边想"，做了一个 skill 就直接跑，没考虑下一个 skill 怎么接，结果就是接不上。正确姿势：先定契约，再写实现。
P1-3：Agent 自己加工 skill 的 message，输出两条回复
发生了什么：skill 输出 message 字段，Agent 又自己写一段总结，用户看到两条回复。
解法：Agent 设定里明确：只允许原样输出 message 字段，禁止 Agent 自己加工总结。
🧠 本质思考：这是"谁负责输出"的边界问题。skill 说"我已经写好 message 了"，Agent 说"我还要再加工一下"，结果就是输出两份。专业开发里，"展示层"和"业务层"是分开的：业务层返回数据，展示层负责渲染。但 Agent 里这两个层是混在一起的，Agent 既当业务又当展示，结果就重复输出了。
P1-4：Agno 版字段名凭记忆写，全错了
发生了什么：agno 版 query_ready 跑出来 0 条需求。凭记忆写字段映射，以为是 requireArrivalDate，实际是 deliveryDate。
解法：加 normalize_items() 函数，做字段映射。不要凭记忆写字段名。
🧠 本质思考：传统开发和 Agent 开发的差异：
• 传统开发：先看 API 文档 → 写 schema / DTO → 写 mapping → 写单元测试。严谨，但慢。
• Agent 开发：直接上手写 → 跑一下看报错 → 错了再改。快，但不严谨。

我们踩的坑就是 Agent 开发的"不严谨"放大了：凭记忆写字段名，错了好几个，跑了 3 轮才全部改对。正确姿势：Agent 开发也要先调一次真实 API，把返回结构拿下来，再写映射函数。这是从传统开发借过来的好习惯。
平台选择的思考：Agent Space / Agno / 本地 / Mico生态思考
🤔 小白会迷惑的问题
编排完 skill 之后，可选平台有好几个：Agent Space / Agno / 本地 Agent / Mico。每个平台都说自己好，结果就是不知道用哪个，或者每个平台都试一遍，浪费时间。
🧠 本质思考：问题不是"选哪个平台"，而是"怎么让一套代码能跑在所有平台上"。就像手机 App：你不用关心用户用 iOS 还是 Android，只要一套代码能编译到两个平台就行。

Agent 时代也是一样：
• 核心业务逻辑应该是平台无关的
• 平台适配层负责对接不同平台
• 换平台只需要改适配层，不用改业务逻辑

未来方向：把核心业务逻辑抽成一个公共库，不同平台都调这个库。这样不管出什么新平台，只要写个薄适配层就行。

什么场景适合 Agent 化 选型判断
✓ 适合 Agent 化的场景
1. 高频重复操作：规则固定、重复度高
2. 有明确 CLI/API 接口：业务系统已暴露接口
3. 需要人工确认节点：Agent 生成确认页，等待用户回复
4. 多步骤编排：需要按顺序调用多个接口、处理异常
5. 非实时性要求：允许秒级到分钟级的执行延迟
✗ 不适合 Agent 化的场景
1. 强实时性要求：需要毫秒级响应
2. 复杂UI交互：依赖图形界面拖拽
3. 需要回调的交互：如飞书卡片按钮回调
4. 登录态频繁失效的外部系统：如飞书 MCP 的 2 小时 token

我们自己的教训 血泪总结
1. 不要闭门造车：一开始就应该先看同团队已经跑通的 ep-agno 是怎么做的
2. 不要拒绝公共逻辑：「独立自包含」不等于代码复制，公共逻辑必须下沉
3. 不要相信多个 Agent 的审查结果：每个 Agent 都不了解业务背景，很容易改了又改
4. 先跑通再优化：先把业务逻辑验证对了，再做架构优化
5. 不要凭记忆写字段映射：先调一次真实 API 看返回结构
6. 业务术语不要猜：找业务方确认，猜错了改起来很麻烦
