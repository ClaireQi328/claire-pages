⚠️ 一句话结论

这套东西现在能跑，但不能上线。四个脚本可以是绿地主工具栏 MVP，但生产跌幅必须先将 15 条开放缺陷修到 P1 以下——其中最硬的三条是：① 批量导入只有 import-json 一条路，撞 CLI 1000 字符硬限，每批只能塞 2 条；② 两套方案存在端到端死锁（有一个"确认"标记，全流程没有任何写入点）；③ 环境检查失败时仍返回退出码 0，导致"看起来通过"。

二、三套方案：差异与改因

三套不是重复劳动，而是三个不同的产品诉求。但在落地时没有先划边界，导致同一份逻辑被改写三次、又在三处口径上打起架来。

方案定位核心设计为什么这样改
① AgentSpace 版
skill-agentspace		 主打「平台原生」
+ 多维表格账表		 单次进程完成 query→create；状态落 state/ 文件；幂等 ledger 为了把审计留痕做厚——每一步都写多维表格执行日志。代价是引入了最多的新机制（state 文件、账表、幂等键），也引入了最多的新缺陷：快照一度缺 TTL 保护、打包时把运行产物一起打了进去
② dexin 版
skill-dexin		 主打「忠实还原线下规则」 拆成 query-ready（产 JSON）+ auto-order（读 JSON）；分组键 = 预算四元组 业务规则来自已经跑通过的线下版本，可信度最高。所以它是三套中唯一把「同一组只能单一供应商」这条规则写对的。代价是引入文件传递，多了「陈旧文件被误用」的风险
③ 飞书卡片版
skill-feishu		 主打「人在群里拍板」 每个环节发交互式卡片，回跳 AgentSpace；confirmed 标记驱动推进 为了解决「谁批准」的合规问题——下单必须有人明确点头。代价是流程骨架最完整，但下单参数一度停留在旧版
🔑 最值得记住的一条：第一轮审查时，我的结论是「③最旧」。第三轮实机复现后，结论倒了过来——③是唯一端到端跑得通的（它有 confirmed: False 初值和 confirm 子命令），而改得最多的 ① 撞进了「confirm() 方法存在但没注册成子命令」的死锁。
教训：改动量 ≠ 完成度。新增机制在修好一个问题的同时，会引入它自己的问题。

三、踩坑总结

排第一的不是业务逻辑，是环境。这一条占了全部返工量的一半以上，而且它的恶劣之处在于——错误不报错，只是安静地不通过。

坑 ①：环境配置 —— 「线下能跑，上 AgentSpace 就卡」

表现根因解法
dexin 版本机正常，AgentSpace 上卡住不动 AgentSpace 容器里 PATH 与本机不同；which dx-ep 找不到 → 检查的实时性与终端环境强相关 环境变量里显式补 npm 全局 bin 路径；不要依赖交互式 shell 的 PATH
「跳版本」 测试环境记录的实际 CLI 是 1.0.7，而三套 config 锁的版本是 1.0.3-beta.3。env_check 用的是子串匹配 required_version in ver_output，只要不是精确那串就判 failed 版本锁定必须写进安装包（镜像/依赖清单），而不是靠 npm install -g 现场解析
验证总是不通过，但报告显示全绿 根因在这里：env_check.py 结尾写着「失败时不退出码 1，改为 0（因为是引导用户修复，不是程序错误）」sys.exit(0)。测试脚本用退出码判断成败 → 所有检查全是 exit 0 → 12/12 全绿 区分「门禁」与「引导」两种运行：CI/批量校验模式返回非零；交互引导模式才返回 0 并输出修复步骤
本机读取凭证文件时整个进程挂起 读取 ~/.dx-garagehub/credentials.json 会被系统层保护拦截；本机验证过同目录其他文件正常，属环境特性非代码缺陷 但这暴露了真问题：这行读取没有超时保护。异常时应 fail-fast，而不是整个 skill 无限等待
⚠️ 这一条要单独拎出来讲：「失败静默 + 成功口径错误」比「直接崩掉」危险得多。测试报告上那 12 个 ✅，实际只证明了一件事——脚本能启动。它没有一条真正执行了下单（方案①③只跑了 query/preview；方案②的 auto-order 耗时 0.10 秒，备注写着「无输入文件，正确返回错误信息」，也就是失败了被记成成功）。

坑 ②：批量写入撞 CLI 硬限

这是整个方案里唯一一条会 100% 阻塞的问题，而且它不在代码逻辑里，在外部工具的参数限制里。

项实测数据
CLI 限制--records 单次不得超过 1000 字符
单条需求字符数按真实字段构造 = 424～428 字符
推导结果1000 ÷ 428 = 每批最多 2 条
200 行需求约 100 次串行调用，按实测单次 ≈2 分钟估算，最坏 3.3 小时
更糟的一层分批是纯按字符数切，不对齐包号边界 → 同一个包的行被拆到两次调用，每次调用内行号不从 10 起、不连续 → EP 校验「行号必须连续」失败
💡 一个省一半成本的情报：xlsx 通道不是没做过，是 0917 版删掉的。旧版 Skill/需求导入Agent完整包/sample_demand_import.py 里明确写着 dx-ep sapo order import-item --file-path <xlsx>，并且已经在用 openpyxl 填模板。这是回抄，不是从零写。

坑 ③：看不见的"状态"最贵

四轮审查里反复出现的是同一类问题——「上一步的结果，下一步拿不到」。它换了四种外衣：

  1. 0916：状态存在内存变量里，而 Agent 是分步、跨进程调用的 → 下一步拿不到
  2. 0916：batch_id 每次进程重建，用它做过滤条件的环节命中率恒为 0
  3. 0917：加了 state/ 文件，但打包时把运行产物一起打进去了 → 新环境解包即用陈旧数据重复下单
  4. 0917：加了 confirmed 标记，但全链路没有写入点 → 必然走到失败分支
🔑 规律：凡是「跨步骤传递的信息」，都必须有一份唯一的权威载体和一个明确的写入方。现在这套里，同样的事实同时住在三个地方：内存变量、state 文件、多维表格——谁改了哪个副本，没人能保证。

四、能力边界：FDE 与专业开发各自的"盲区"

这一条要说实话，因为它决定了质量问题应该由谁担责、用什么方式补。

🧑‍💼 FDE 同学的真实优势

  • 知道「同一预算四元组必须在一包里」这种只有业务才懂的约束——这是文档里查不到的
  • 知道哪条规则是硬校验、哪条其实可以绕过
  • 知道异常单据长什么样，能一眼看出「这批数据不对」
  • 能定义「什么叫做对了」

🧑‍💻 需要开发补位的部分

  • 分页 / 幂等 / 重试 / 超时 / dry-run —— 这五项属于「工程素养」，不属于「业务知识」
  • 并发安全 —— 多人同时触发同一个 skill 时的冲突处理
  • 错误处理与退出码语义 —— 什么叫成功、什么叫失败、谁来感知
  • 字段类型契约 —— 外部系统返回值的类型是不可信的
它们的共同特点：做错的时候系统不报错，只是安静地少做 / 多做 / 重复做。
所以它们不可能靠「跑一遍看看」发现，只能靠代码审查，或者——线上出事。
工程概念不懂会发生什么本项目的实际表现
分页超过单页上限的数据静默丢弃config 里定义了 max_pages: 20，但代码只调用一次，从不翻页 → 需求多于 100 条时漏单
幂等重复操作产生重复业务单据导入后不回写状态字段 → 同一批需求会被反复导入
dry-run调试即生产三套默认配置一度全部是真实下单，而 12 份文档里 dry-run 提及次数为 0
成功判定把失败当成功用正则抓 32 位十六进制当订单号 → 失败响应里的 requestId 会被当成订单号，判成功，并写入幂等账本导致该组永久跳过
退出码语义门禁失效env-check 失败仍 exit 0 → 12/12 全绿
超时 / fail-fast进程挂死读凭证文件无超时保护，卡住而非快速失败
字段类型契约运行时崩溃多维表格公式字段返回 {"type":2,"value":[60]}，归一化没处理 → float(dict) 抛 TypeError
✅ 建议的分工：FDE 负责定义业务契约（哪些字段、什么约束、什么叫对）；专业开发负责把契约翻译成安全的工程实现（分页怎么写、失败怎么判、重复怎么办）；AI 负责中间的快速产出 + 自查。
三者不能互相替。现在这套方案的缺陷分布，恰好印证了这一：业务规则类缺陷 ~0，工程机制类缺陷 15。

五、依赖 AI 写代码：真话

✅ 确实拿到的好处

  • 速度：三天四版本、20,029 行。同样的范围交给传统开发流程，光需求澄清就要一周
  • 可追溯性：每一行都有权利要求解释「为什么这么写」，这点连资深同事都做不到——它让非程序员第一次能真正看懂地读代码实现
  • 低成本试错：三套并行方案如果靠人力做，成本不可想象
  • 知识固化：26 条隐性规则被逼着写成显式文档/SCHEMA

❌ 必须承认的代价

  • 「看起来很完整」是最危险的产物。AI 会输出结构完备、注释漂亮、还能通过 --help 的代码，但内部接线可能是错的
  • Py 对齐问题严重：同一份 bitable_logger.py 被复制到 13 个包里，任何一处修改都需要 13 次同步——而这 13 份已经出现 365 行 vs 375 行两个版本
  • 内部细节前期查不出来：AI 写完后自己检查自己的代码，会沿着写时的思路自证正确，跳不出盲区
  • 专业度差距真实存在：15 个开放缺陷里，13 个属于专科开发凭直觉就能避开的类别
🔑 最核心的一条结论：AI 产出代码的边际成本低，但验证成本很高。写出来的成本近乎 0，而"证明它对"的成本没有降。
所以正确的姿势不是「少让 AI 写」，而是「把验证环节制度化」——引入另一个与写码方不同上下文的模型/人来对抗性审查。

四轮红蓝军：发现什么，怎么解的

轮次对抗形式发现的关键问题解决/暴露方式
R1
0916		 独立模型静态审读 7 个 P0：人工选的供应商根本没被使用（形参声明了，函数体一次没引用）；跨命令状态不落地；batch_id 命中率恒 0 「形参未引用」这种，靠读业务逻辑发现——对着"用户选了 A 却下了 B"这一现象反推
R2
0917 上午		 横向对比三套 + 真实数据离线复现 不再是纯读代码：用包内真实数据复现分组规则，发现 7 条需求 → 2 组 → 1 组被剔除 → 覆盖率仅 29%，而被剔除的 5 条不报错、不告警、不入库 离线复现是最有效的手法：不动生产，把代码逻辑在真实数据上重跑一遍
R3
16:23 版		 第三方评审复核 + MD5 版本追踪 评审 16 条里 9 条成立、1 条推翻（打包"干净"实为被污染）；新增 6 条，其中最重的是「每批最多 2 条」 MD5 逐文件比对是本轮关键——一次就看出「改动集中在下单链路，导入链路一个字节没动」
R4
16:23 版		 构造等价 state 文件实机复现 两个端到端死锁：confirm() 方法存在但没注册成子命令；confirmed 全链路无写入点。以及正则误判导致失败当成功并永久跳过 只有真的跑一次才能发现。静态读到这里会默认"既然有 confirm 方法，那就是支持 confirm"
📌 四轮下来最有效的方法排序（按性价比）：
  1. 实机/离线复现 —— 用真实数据重跑对方逻辑，一次能揪出整类问题（R2、R4 的致命发现都来自这里）
  2. MD5 版本比对 —— 便宜、无争议，能立刻界定"这次到底改了什么"（R3 靠它推翻了一条误判）
  3. 横向对比同功能多版本 —— 三套打架的地方，往往至少一套是错的（B3/B4 就是这么找出来的）
  4. 纯静态读 —— 只能发现表面问题，性价比最低

六、什么场景适合 Agent 化

这次最大的收获之一：不是所有环节都该做成全自动。下面这张表是我建议的判断框架。

档位判定条件样件订单里的对应环节人机责任划分
A 全自动 规则唯一确定、可幂等、失败可逆、单条金额低、频次高 查询可下单待启动、渲染分组、生成候选包、写执行日志、出日报 Agent 做完直接生效，异常才告警
B 建议+确认 规则明确但不可逆或影响外部；或需要人工背书 实际下单、向供应商发正式凭证、修改已提交单据 Agent 备好一切（含 dry-run 结果），人只在最后一步点头
C 辅助/不应做 涉及商务判断、谈判、份额分配、责任归属；或规则本身在变动 多供应商选择（涉及份额与价格策略）、异常单据的责任判定、预算调整 Agent 提供信息和备选，人做决定
⚠️ 这次踩到的实例：「多供应商时的选择」最初被设计成全自动→失败了（选了不生效）→ 改成整组剔除（组内供应商不唯一就整组不下单）。
但剔除不是解决方案，是回避：真实数据跑下来 7 条需求里 5 条被剔除，覆盖率 29%，而且这 5 条只在 stdout 打一行字——不写日志、不发卡片、不进日报。那这 5 条需求现在归谁处理？这是方案里真正的空洞。

一个可复用的判断清单

在决定某个环节要不要 Agent 化之前，先回答这六个问题。答不上来的部分，就是设计缺口：

#问题答不上来的后果
1做错了能撤销吗？必须上 dry-run + 人工确认，或直接不自动
2重复执行会怎样？必须做幂等键 + 状态回写（本次就是栽在这里）
3失败会被发现吗？必须有可观测面；本次的"失败即 exit 0"就是反例
4数据量超预期怎么办？必须分页；本次是"只调一次，定义了却不用"
5规则有例外吗？例外要有明确的人和路径兜住（本次剔除的 5 条就没人兜）
6谁为此负责？不可逆动作必须有署名。Audit trail 是刚需不是加分项
✅ 一句话建议：把自动化停在会犹豫的地方——凡是你要停下来想一想「这次要不要例外」的判断，就往 B 档或 C 档放。
B 档（推荐主色调）：Agent 负责「收集 + 计算 + 呈现 + 留痕」，人负责「拍板」。这句话背后其实是成本账——让 Agent 少判断一步，维护成本降一个量级。

七、选型思考：Skill / 工作流 / 原生应用

AgentSpace 除了「Skill」还有「工作流编排」这条路线。这一节专门讲清楚什么时候该用哪个。

形态擅长不擅长 / 当前限制适配判断
Skill（Python）
本次采用		 复杂判断、循环、分页、幂等、错误分类、文件处理 不直观，业务同学看不懂也改不了 能力内核——所有和 CLI/表格打交道的脏活必须在这里
工作流编排 可视化顺序、分支审批、人工卡点、状态可视化 当前不支持飞书发送、不支持直接对接 CLI；复杂数据处理吃力 做编排层，不做能力层；且必须靠 Skill 当「工具节点」补上 CLI 与通知
原生应用/页面 高频人机交互、批量勾选、报表 开发成本高；也改不了外部系统 当自动化成熟后再考虑，用来替换临时的多维表格
🔑 建议架构：混合编排——工作流做「编排 + 审批」，Skill 做「原子能力」。
分工界面要划在很薄的地方：工作流只负责「按顺序调这些 skill、在哪个环节等人点头、失败了走哪条分支」；Skill 负责「所有和 CLI / 多维表格 / 飞书的实际交互」。
唯一需要注意的是——别让业务规则同时写在工作流的判断节点和 Skill 的代码里。本次三套 Skill 口径打架已经证明了：同一规则写在两处，时间长了必然不一致。

为什么现在不建议全量迁到工作流

  • 能力缺口：不支持直接对接 CLI —— 而这整套东西 90% 的动作就是调 dx-ep sapo order ... 三个命令。要么等平台支持，要么 Skill 包一层，后者等价于没迁
  • 通知缺口：不支持飞书发送 —— 而「人在群里拍板」本来是方案③的核心价值
  • 复杂度：分组、剔除、幂等 ledger、old state TTL 这些是带状态的逻辑，用可视化节点表达会非常盤肿
  • 迁移时机：建议等能力能够稳妥上线之后再谈迁移。现在迁，等于是把一堆未修的缺陷换个地方再写一遍
📌 决策建议：短期（本月）Skill 为主，把 Wort humana 分结束；中期（下季度）待平台补齐 CLI/飞书能力后，把审批与编排迁到工作流，Skill 退化为纯能力节点。这条路径的成本最低，因为能力层不用重写。

结论与反思

✅ AI 路径真正省下的

  • 把「不知道不知道什么」变成了「知道不知道什么」
  • 隐性规则显性化（26 条）
  • 三套方案并行验证，选型有依据
  • 业务同学能读懂实现，沟通成本骤降

⚠️ 不该再用 AI 硬推的部分

  • 涉及外部工具硬限制的问题（1000 字符）— 需要的是查文档/问平台，不是多写几行
  • 涉及合并多套代码的重构 — AI 容易扩大改动面，改动结果难以归零验证
  • 涉及成功/失败判定的安全逻辑 — 应该由最保守的人写，而不是最会生成的人写
✅ 建议的下一步节奏：不要同时修所有缺陷。先合三为一（#10），再逐条修——因为现在每修一处要在三个 package 里同步三次，效率极低。合完之后 12 项修复的复杂度会降一大截。
