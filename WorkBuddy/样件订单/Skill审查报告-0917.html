二、P0 阻断缺陷（上线前必须修复）

1️⃣ 人工选的供应商，根本没被用到

现象：用户在多维表格里选了供应商 A，系统最终按 供应商原始 字段的第一个供应商 B 下单。
证据：create() 声明了形参 supplier_selections，但函数体内一次都没引用（全文只在被调用处出现）：
query_and_order.py:1364 定义 → :1391-1392 分组只用 order["供应商原始"] → :1404 按 supplier_id|br_no|br_line|buyer 分组 → 全函数无 selections 引用。
影响链路：无论走 select-supplier(:846) 还是 wait-selection(:1650)，传进去的 choices 都被丢弃。
为什么危险：它不报错、不发警告，卡片照样显示"订单创建成功"。

2️⃣ 跨命令的状态不落地，create 只能重新拉全量

现象：Agent 按文档分步调用 query → analyze → 确认 → create，每次都是新进程。_query_result / _analysis_result 是内存变量（query_and_order.py:57-58），跨进程必丢。
后果：create 在无状态时回退到 self.query() 全量重查（:1383-1385）→ 对全部可下单需求下单，包括用户没确认过的、以及一价多供里用户还没选的那一批。人工确认形同虚设。
缺失物：没有批次状态文件、没有 `records_out.json` 之类的中间产物契约，run 单次进程能跑通，分步调用跑不通。

3️⃣ wait-selection 永远读不到上一步写入的记录

证据：batch_id 在每次进程启动时重新生成（:54 ORD{now}），而 _read_supplier_selections_from_bitable 用 工作流ID != self.batch_id → continue 过滤（:1341）。
推论：新进程的 batch_id 与写入时的必然不同 → 命中率恒为 0 → 永远返回"等待供应商选择"。加上 select-supplier 返回的 record_ids 也没持久化，流程在第三步必然死锁。

4️⃣ 多维表格轮询被嵌套在 if missing: 里

证据：query_and_order.py:819-840——轮询块 if record_ids: ... _poll_supplier_selection(...) 缩进在 if missing: 分支内部。
后果：只有「存在需要手工添加的供应商选项」这种异常情况下才会轮询；正常情况直接 return WAIT_SUPPLIER，文档承诺的「≥5 家自动轮询、全部选完自动继续」实际是逻辑取反。且就算轮询成功，return self.create(...)(:846) 仍走到缺陷 1。

5️⃣ 需求导入不回写状态 → 重复导入；且导入是真跑

重复导入：demand_import.py 全文无 update_record（已 grep 确认），导入成功后多维表格「样件导入状态」仍为「待导入」，下次 preview/push 会再导一遍同一批。
风险不对称：create_order_dry_run: true（下单是试运行），但 import.dry_run 键在 config 里不存在，代码默认 False（demand_import.py:860）→ 需求导入是真导入。同一套流程里，一半受保护一半裸奔。

6️⃣ 日报数据恒为 0，却返回 SUCCESS（假绿）

两层错位，任一层单独存在就够致命：
① 结构错位：analyze_logs 读 log.get("stage") 等顶层键（daily_report.py:177-230），但 query_records_by_date 返回的是 {record_id, fields:{...}} 原始记录（bitable_logger.py:305-350）→ 所有字段取不到。
② 取值错位：即便拍平，写入时状态已映射为中文「成功/失败」（bitable_logger.py:128-130, 194），比对的是英文 "success"/"failed"（daily_report.py:193-196）→ 命中 0。
结果：导入数、查询数、订单数全部为 0，但 run() 因无异常返回 status=SUCCESS。

7️⃣ 飞书 app_secret 明文硬编码在三处

demand-import/config.json:6、demand-query-and-order/config.json:6、query_and_order.py:67（兜底配置里又抄了一遍）。
Skill 包是要分发/入库的——打包即泄露。最小修复：config 只留引用，密钥走环境变量；已泄露的这个 secret 需要在飞书后台轮换。

五、修复优先级：最小可上线路径

  1. 引入批次状态文件（解 P0-2/3）：query 成功后把订单明细、batch_id 落盘 state/{batch_id}.json；analyze/select-supplier/create 统一用 --batch-id 读写该文件。这是所有后续修复的地基。
  2. 让选择真正生效（解 P0-1）：create 按 supplier_selections 过滤订单——只处理已选择的零件，且一价多供记录用选中供应商对应的 pr_ids 分组；结构化选项里把 supplier_id 补上（现在恒为空，:1116）。
  3. 修正轮询缩进（解 P0-4）：把轮询块移出 if missing:，并让「缺失选项」只作为发提示卡的条件。
  4. 导入回写 + dry-run 对称（解 P0-5）：push 成功后 update_record 状态为「已导入」并写入 EP 需求编号；config 显式加 import.dry_run，默认 true。
  5. 日报重接（解 P0-6）：analyze_logs 改为读 log["fields"]，并把中英映射统一（推荐：日志表里同时存英文 state 字段，避免再靠 mapping 猜）。
  6. 密钥外置（解 P0-7）：config 只存 ${FEISHU_APP_SECRET}，运行时从环境变量读；轮换已泄露的 secret。
  7. 契约层定版（解 P1-8）：二选一并写进 SCHEMA——要么 details 恒为数组（analyze 用 extra 承载分桶），要么允许 dict 并放宽校验。不要两边都留。
  8. MCP 长连接/批处理（解 P1-12）：改为脚本内常驻 MCP 会话，或一次调用批量写多条记录。
