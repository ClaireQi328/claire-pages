合同 AI 审查 Skill 设计方案
contract-clause-review v0.9 · 审什么 + 怎么做

在既有的「字段核对（field-check）」之外，新增一个面向文件本体与条款实质的审查能力。本文回答两个问题：能审什么、怎么落地。

参考：EP-20260903-合同管理-PRD 参考：合同线上化 · AI 机会点与 CLI 开发清单 参考：UAT 第一轮 2026-10-14 参考：合同模版&签署&归档优化-首次共创结论
结论先行

已有的 field-check 管「数字对不对」，新 skill 管「文件本身对不对、条款亏不亏」。两者不是替代关系，是同一条智能检查链路上的两段。

① 审查范围分四层：L0 文件与签章 → L1 要素一致性 → L2 条款完备与偏离 → L3 跨单据业务一致性。L2 是新增增量，L0/L1 是既有能力的补强。

② 落地靠三条硬约束：规则先行、LLM 只做语义、结论必须带原文锚点——否则误报会把采购员逼回人工。

③ 最大阻塞不在 skill 本身，而在数据：contract info detail 缺金额、含税/未税、生效日、关联原合同五个字段，缺了就会让金额类审查项全部标 unparseable。

00定位：与现有能力的分工

先说清楚不重叠。现有链路是 12 条「智能检查」阻断项 + 7 项「字段核对」非阻断项，新 skill 补的是两者之间的空档。

能力审查对象判定方式阻断性回答的问题
智能检查（现有）
12 条		 表单字段本身 确定性必填 / 联动校验（币种、金额、平台、供应商行、模板同步） 阻断 「该填的填了吗」
field-check（现有）

图 3 · 链路：CLI 取数 → 解析切分 → 规则引擎 + LLM 判官 → 契约聚合 → 页面触达

2.1 六个工程决策（决定成败的不是模型，是这六条）

决策做法为什么
① 规则优先 金额、日期、主体名、编号、税率验算、签章有无——全部走确定性规则，不进模型 可解释、零幻觉、可单测；模型只花在「语义判断」上，token 与误报同时降一个量级
② 先结构化再语义 PDF/Word → 版面解析 → 按标题编号切条款块 → 每块带 page / para / 原文 → 逐块判定 整篇长文塞上下文会让模型「挑着看」；切块后每条结论都能落到页，用户才敢信
③ diff 优先于生成 非标件 = 上传件 vs 模板基线段落级 diff，只把「变更块」送模型判偏离方向，未变更块默认合规 把「从零判断这份合同有没有问题」降级为「这几个改动有没有问题」，准确率和成本同时改善
④ 规则包配置化 Rule Pack 按「协议类型 × 审查维度」写 YAML，法务维护内容不改代码（见 2.2） 协议类型会持续新增（现枚举仅「售后配件供货保障协议」），硬编码必然腐化
⑤ 无锚点不出结论 每条 item 必须带 locator（页码+段落）与 evidence（原文片段）；缺失则降级为 unparseable 这是防幻觉的唯一硬门禁，也直接决定采购员是否愿意勾选确认
⑥ 不阻断、可勾销 沿用现有交互：items[].checked 记录确认，不拦提交；仅红线条款可配置为「需勾选后才能发起」 与 PRD「检查类能力仅提示、不阻断」一致；一旦阻断，误报就从「噪音」变成「阻塞业务」

2.5 四条判定样例（看的不是模型多强，是能否落地）

场景原文判定路径结论
账期超阈值 「甲方应在收到发票后 120 日内付款」 规则：正则抽天数 → 比对 warn_above: 90 warn 账期 120 天，超模板上限 90 天
缺失必备条款 全文无「廉洁」「反商业贿赂」字样 规则：关键词 → 无命中 → LLM 二次确认是否以其他表述存在 block 缺廉洁条款，模板为必备
模板条款被降级 模板「乙方承担全部质量损失」→ 本件「乙方承担直接损失」 diff 命中变更块 → LLM 判偏离方向 warn 赔偿范围由全部降为直接损失（downgrade）
跨单据金额不符 合同 1,286 万；定点单 1,298 万 规则：双源取数 → 偏差 0.9% < 容差 → 通过；若 >10% 则 warn ok 在容差内（示例展示「不误报」同样重要）

03触发与交互

沿用已就绪的原型交互（☑️/☐ 勾选、仅提示不阻断），只是把分区从两段扩到三段。

① 上传签署版后自动触发
异步跑，前端轮询/回调；结果挂在明细行「审查结果」角标。非标件主入口。
② 智能检查按钮
与 12 条必填校验合并展示：①必填（阻断）②字段核对 ③条款审查（后两段不阻断）。
③ 详情页浮动「AI 审查」
已流转中的合同补审；支持对单个明细单独发起，避免整单重跑。
④ 发起审批前必跑
红线条款可配置为「需勾选确认后方可发起」，其余仅提示，与现有 PRD 一致。
⑤ 批量巡检（P2）
定时扫存量合同，产出风险台账：漏章、金额不符、过期未续、非标未审。
⑥ AI 助手问答（P2）
3 个查询 CLI 包成 MCP Server，「我哪些合同还没归档」直接问。

04分期与验收

阶段范围前置依赖验收口径
P0 L0 完整性/签章 + L1 要素一致性（把现有 7 项重构为规则化并补金额、期限、原合同）+ 报告与批注版 + 弹窗三分区跑通 contract info detail 补 5 个缺失字段；附件下载链路 30 份真实合同跑通，字段类误报 ≤10%，单份耗时 ≤60s
P1 L2 必备条款缺失 + 模板基线 diff + 关键条款风险；先做 1–2 个协议类型的 rule pack 法务提供模板基线 + 必备条款清单并签认；50 份标注集 条款缺失召回 ≥85%，风险项误报 ≤25%，采购员勾销率可解释
P2 红线条款 + L3 跨单据（定点/报价/预算）+ 批量巡检风险台账 + MCP 对话入口 dx-ep contract 三命令上线；nomi/rfq/supplier 字段口径对齐 台账覆盖在途合同 100%；跨单据差异发现 ≥5 起/月

评估集做法：从 UAT 与历史归档里各取 20–30 份，覆盖标准件 / 非标件 / 扫描件 / 漏章 / 金额不符五类，逐条标注「应报/不应报」，每次改 prompt 或规则都跑回归。没有这套集子，模型调优就是盲调。

风险表现对策

5.3 需要你拍的四件事

  1. 边界：新 skill 是「只做 L0–L2 的自研规则+LLM」，还是「L2 直接接第三方审查引擎（如腾讯电子签/幂律）」？后者上线快、法务背书强，但条款口径与小米模板库对不齐。
  2. 与 field-check 的关系：合并成一个 skill 两个 checkType（维护成本低），还是保持独立两个 skill（迭代快、互不影响）？我倾向先独立，契约共用。
  3. 红线是否阻断：现在是「全部不阻断」。红线条款要不要升级为「必须勾选确认才能发起审批」？
  4. 本期协议类型范围：先只做「售后配件供货保障协议」一个 pack 打通闭环，还是同时铺价格协议/技术协议？
